# docs41 后端数据一致性设计评审

结论：方向通过，**暂不能作为完整 P1–P3 开发冻结基线**。可拆分，但下列四个阻断需先补精确合同。只读审文档与已核正式调用链，未改代码、未跑测试。

## 阻断与所需修订

### LF-B1：预约持久性与外层事务回滚合同冲突

§3 一方面要求墓碑 COMMIT 后才有副作用、首次预约后即使操作失败仍永久保留；另一方面要求已有外层事务用 tx-bound guard。若同一 tx 内新插 scope 后业务失败回滚，该 scope 不会永久存在，tx-bound API 也不能在外层提交前返回“已提交 receipt”。这是可实现性缺口，不能通过另取连接偷偷提交解决。

需明确两种路径：独立多阶段入口先在独立 writer 事务提交预约，再执行原业务；已有受信外层 tx 只能返回 prepared 事实，外层提交后才发布提交结果，回滚时允许新预约随同业务回滚（没有可见业务副作用）。如仍要求失败也留墓碑，必须在外层 tx 开始前完成预约，列明调用改造；禁止嵌套 checkout。多范围先校全范围再写预约，pilot/unknown 拒绝时不得留下部分新预约；业务失败后已独立提交的预约不是业务回滚失败。

### LF-B2：COMMIT unknown 的 operation key 尚无可查询事实模型

§5 承诺通过稳定 operation key 查询未知提交，但没有 key 的归属、保存表、fingerprint、唯一约束、返回结果或查询授权合同。永久 scope 仅能证明范围已属于 legacy，不能证明某次排课/通知/结算成功，不能作为通用业务 receipt。相同 key 不同输入也没有定义。

最小修订：限定 Reserve 的未知结果查询为当前 scope 事实重读，且只授权后续新业务，不推断先前业务已完成；原业务沿各自现有幂等键/提交事实处理。若要通用 operation receipt，须另列 schema/事务/重放设计，不能在本片一句话引入整套协调器。未知或未取得 writer 时不可发成功。

### LF-B3：P1 范围不足以作为可核查的 writer 全覆盖清单

当前只有模块类别，没有方法、调用者、scope来源、缓存/通知先行位置及外层事务所有权映射。正式 SaveLesson/GORM Save、CreateLesson/MAX+1、DeleteStudentBook、Settle 已完成缓存、AlreadyPlanned/ReserveCards 等各有不同语义，不能仅按“接Service门”证明底层无绕过。

需附有限接口表：每个实际可变方法→scope如何可信推导→是否已有外层tx→首次副作用→guard位置→错误传播/回滚。包括 MemRepo 配对合同，不能SQLite拒绝而内存适配静默放行；只读无scope任务不应硬造范围。新ID需区分事务内临时ID供同tx引用与提交后对外发布，避免禁止任何回填导致计划链无法工作。

全局 config 必须沿现已实现的有效配置协调器：只影响最终有效梯度实际变化的学生及其相关书范围，显式override、不改变有效值的配置设置、无卡范围如何检查均沿原合同明确。管理员权限允许配置写，但不授予绕过pilot scope的权力；不得回到“更新所有学生/所有卡”的旧缺陷。

### LF-B4：P3 删除/退休跨进程语义仍未冻结

§4 明确把 settled 重放屏障留到实施前另定，因此 P3 目前确实不可实施。仅本进程 Room 退休不能阻止另一 App 的迟到结算或重建写入；scope 永久 legacy 也不会拒绝这些旧任务。必须给出跨进程删除 generation/fence 或明确可验证的排空部署约束，定义删除重试与重新启用的区别、任务持有的代际何时失效。

精确四类 runtime 按同事务 owned LessonID 清理正确，但还需决定 settled/agent_result 幂等事实的持久归属墓碑、保留策略、历史缺失/孤儿处理与任务引用。禁止大范围前缀删未知key。历史孤儿继续允许未迁移legacy启动、显式迁移blocked、v2严格，不能用迁移blocked否认旧取消操作的合法性。

## 非阻断的文档收敛项

- §1“pilot schema 未就绪就拒绝”与未迁移旧库允许首次写表述易冲突：应明确**完整未迁移结构是合法legacy状态**，partial/invalid/unknown才拒绝，bridge并非v2残表。
- §7 同列scheduler≥80和≥90，最终必须统一scheduler≥90，避免实现者选较低门。
- `student_scope_hash` 缺生成规则；固定ID或受控摘要二选一，若hash需明确稳定性、盐/版本及跨日志关联，不能把可枚举ID哈希当匿名化保证。
- §2所有副作用前获取writer不能被解读为每heartbeat/完成课读请求都写。P2应按只读检查与可变恢复分流，并在DB调用后重新核Room身份；DB失败不得返回可写许可。
- 保持schema校验热路径有界：仅受信pool/已提交schema证明缓存，scope每次实际索引读；SAVEPOINT回滚、TxDone、DDL cookie复用不可缓存成功数据许可。

## 可执行拆片建议

1. **P1a 私有guard和仓储合同**：先补LF-B1/B2与方法表，仍关闭pilot/迁移；实现prepare/commit区分、内存/SQLite一致语义、ID/owner保存边界。独立接口测试不能宣称全部App已保护。
2. **P1b 服务入口接线**：按有限清单逐项将预约放在缓存/通知/任务效果之前；工具外层事务复用guard；跨scope整拒，普通另一book不受影响。该片保持可发布legacy兼容，但不开放任何pilot工厂。
3. **P2 课堂读写分流**：真实完成事实确定纯读分支，SQLite计数覆盖Enter/Join/ticket/report零DML；可变恢复先预约再发布Room。既有phase或finished标签单独不足以豁免。
4. **P3 独立冻结删除协议后实现**：先闭合LF-B4，再做退休/fence/精确删除/重放墓碑/失败重试。未完成前明确不能开放迁移或pilot创建。

P1/P2可在pilot继续不可达的前提下独立验收，不必为P3未定而停止所有工作；但每片需有明确不支持边界，不能把部分门当成“已实现不可绕过的持久隔离”。当前Go全绿与跨批次131用例是旧实现基线，以上新接线行为必须新增逻辑与真实多用户E2E，不能复用现有通过数作新特性证明。
