# Security Review: `lesson.start` Persistence Kernel SDD

Review target: `docs/41-试点课堂Start持久迁移内核SDD.md`, reviewed independently against `docs/33` and `docs/36`. This review is limited to principal authorization, test-harness isolation, command replay/commit-unknown handling, and data exposure. It is a design-text review only: no code was changed and no tests or runtime checks were performed.

## Decision

**Not approved for implementation yet.** The design narrows the feature appropriately, makes Start effects transactional, keeps ordinary product routes absent, and forbids effects before confirmed commit. The remaining issues are chiefly about who is allowed to invoke or read the command, how the test-only boundary is enforced, and what a missing receipt means after an ambiguous commit.

## Findings

1. **P1 — Principal authority and receipt-read authorization need a concrete contract.** Section 3 says an external adapter authenticates the principal and validates lesson owner/scope/task permission, while also correctly saying that an opaque Go type does not itself authorize. But `commitPilotStart` and `lookupPilotStartReceipt` do not specify how the store receives verifiable authority, and the proposed lookup takes only `owner` and `commandID`. A caller-supplied owner ID is not authentication. Freeze the principal claims (actor ID/role, trusted task and scope, lesson owner, current account status, expiry/revocation semantics) and how they are derived from verified middleware or an internal process capability. Internal `lesson.start` must reject student/HTTP/WS JSON requests regardless of claimed role. Revalidate current authorization and ownership before both new commits and receipt replay/lookups; do not reveal whether another owner’s command exists. Keep classroom `auth_generation` distinct from Agent/task authorization and state exactly which generation is checked.

2. **P1 — The test harness boundary is described but not mechanically guaranteed.** Section 5 bars registration in production App/router/Agent registry and says the default production binary has no route, which is good. However, “test-only build/config” leaves open whether a runtime flag could expose fixture-principal Start in a production binary. Specify a separate test-only build target (or avoid HTTP entirely and use Playwright route mocking plus Go integration tests); ensure fixture principal construction and routes are absent from the production artifact, not merely disabled by default. If an HTTP harness is retained, require a fresh temporary database outside configured production paths, loopback-only binding on an ephemeral port, no production credentials, and immediate failure if isolation cannot be established. E2E must assert the production artifact has no Start/receipt route and cannot activate fixture auth via environment/config.

3. **P1 — `not_found` is not defined as proof of rollback after commit uncertainty.** The design says a COMMIT error means unknown, then “only query” the original receipt; it permits a same-ID retry after deterministic rollback. It does not state what the caller does when the receipt lookup returns `not_found` while the original transaction/request may still be executing, or when the lookup itself is unavailable. Explicitly define `pending/unknown` as the safe result; absence alone must not authorize a new command ID, a second plan, a Room/effect, or a user-visible claim of rollback. Any retry must use the same command ID and fingerprint and re-enter the writer transaction, where the durable receipt/state CAS and uniqueness constraint serialize it. Receipt lookup must authenticate the current caller as described above. Add bounded query behavior and an explicit recovery path for persistent unknown outcomes.

4. **P2 — Command fingerprint/replay binding needs to cover the authorization epoch and exact transition.** The proposed fingerprint covers owner, lesson, creation fingerprint, plan version, and normalized candidate, while expected checkpoint version and auth generation are checked separately. The replay path must say whether these checks occur before returning an existing receipt. Bind `lesson.start` kind and expected checkpoint/auth generation into the command fingerprint (or specify an equivalent replay rule), and require current authorization on every replay. Otherwise a stale command could be replayed with altered concurrency claims and still receive a success receipt. Enforce a unique `(lesson_id, command_id)` key and compare canonical fingerprint in the same writer transaction; reject same ID/different payload without leaking the stored payload.

5. **P2 — Log and persisted payload redaction needs field-level allowlists.** The log schema forbids transcripts, tokens, SQL and raw model responses, but `owner_scope_hash` is an unkeyed hash of likely enumerable student IDs. Use a keyed, access-controlled HMAC (with rotation/retention policy), or omit the stable identifier. Also define exact allowed fields and size limits for `tool audit summary`, `StartReceipt`, transition audit and outbox payloads. They should contain only the minimum approved effect and idempotency data; exclude prompts, raw Teacher/model responses, student-authored text, credentials and arbitrary tool arguments. Fingerprints must not become a dictionary oracle for low-entropy content. E2E/log assertions should inspect serialized rows and emitted logs, not only API responses.

## Required next step

Revise the SDD to resolve the three P1 findings before implementation, then obtain a fresh cross-domain review. The later P2 items should be frozen in the same revision because they affect replay and audit storage contracts. No finding here is a claim about current runtime behavior or test results; this review does not establish that the kernel is implemented, that the harness is isolated in practice, or that a classroom is ready.
