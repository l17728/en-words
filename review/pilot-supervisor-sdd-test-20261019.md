# Pilot 隔离运行监督器 SDD：测试与验收评审

- **结论：阻断（设计可继续修订；实现门未通过）**
- **范围：**只读评审 `docs/42-Pilot隔离运行监督器SDD.md`，重点核对失败矩阵、进程/崩溃语义、平台门、E2E、覆盖率和可观测性。未执行测试，未修改设计或代码。
- **P1：**无。

文档清楚划定了 test-only 边界，覆盖了重要威胁和 POSIX/Windows 必须实机运行的要求；也明确说明监督器单测不能替代后续 loopback/Playwright 或课堂 E2E。当前阻断点是验收条款仍以“覆盖某类故障”为主，缺少可复现的注入点、逐项状态 oracle 和平台测试证据格式。若直接实现，各人可能声称覆盖了同一条要求，却测试了不同的失败时序。

## 发现

1. **P2（阻断实现门）：崩溃边界没有逐事件 oracle。** §5 只概括“创建在每个文件 create/write/Sync/父目录 Sync 前后崩溃”，§4 对恢复规则有描述，但没有将实际 syscall 顺序逐一映射到：注入位置、进程强杀方式、磁盘状态、重启后 catalog 状态/代数、允许访问的文件，以及是否可返回成功。请将 create case、目录 Sync、key/sidecar/DB 写入、身份核验、`provisioning→ready` append/Sync 各拆一行；分别规定“操作返回错误”和子进程被强杀两类场景。特别说明完整 frame 已写但 Sync 返回不确定时，不可把已观察到的字节当作持久化成功。

2. **P2（阻断实现门）：失败矩阵没有覆盖所有具有副作用的阶段及精确断言。** §5 列出多种 create/write/Sync/清理失败，但未逐项列出锁获取、读/seek/stat、exclusive-create 碰撞、权限/身份复核、目录枚举、每个成员删除、父目录 Sync、最终 tombstone append/Sync 的失败预期。建议建立矩阵列：操作/注入 seam、调用返回类别、当前 Supervisor 是否 poison、catalog 是否可能已推进、case 是否保持不可打开、重启处理、DB/receipt/Planner/Registry 调用计数。0 副作用断言要按每个失败阶段和每个拒绝入口落到具体测试，而不是只做类别汇总。

3. **P2：跨进程验收少了明确的调度和观测 oracle。** §4、§5 要求并发启动及过期快照复核，但没有规定所有竞争测试都用具名 IPC barrier 强制到达哪个线性化点、如何制造持锁进程崩溃、如何验证第二个进程重读最新 catalog、以及如何检查中间读取绝不暴露半帧。请禁止用 sleep/概率循环作为同步手段，并断言唯一赢家、唯一状态转移、连续唯一 generation、失败方副作用计数为零、锁释放后恢复结果一致；每个 barrier/子进程都应有硬超时和可归档诊断。

4. **P2：Windows/Linux 平台门虽正确提出，但证据要求不够具体。** §5 正确指出交叉编译不能替代实际执行，不过未定义 CI 版本/文件系统/权限身份、平台特有用例报告内容及归档位置。请分别要求 Linux 和 Windows runner 输出实际执行的测试清单、OS/文件系统信息、关键 ACL/mode/file-ID/reparse/lock/directory-Sync 断言及原始日志；任何被跳过/不支持的能力都必须作为 fail-closed 失败，而不是被标记通过。Linux 的 `openat2` 可用与不可用分支也应分别验收，明确 fallback 的预期。

5. **P2：E2E 关联边界清楚，但责任和门槛仍容易被漏掉。** §5 将 Playwright/loopback 放到后续同步实施，这个拆分合理；但没有一个可追踪的用例 ID 映射能证明本监督器接受后，HTTP/SQLite 和浏览器层确实继承同一隔离不变量。建议在独立后续 SDD 中定义跨文档用例映射：本地双用户/跨源拒绝、丢响应后幂等恢复、重启、并发清理、用户数据隔离及零副作用，并明确 supervisor 单测通过不能解锁真实课堂试点。

6. **P2：覆盖率与可观测性门缺少逐项产物。** §5 给出 supervisor ≥80%、目录/生命周期状态决策 ≥90%，但未指定按包/文件还是函数计量、平台文件是否分别计算、生成覆盖率文件和排除 generated/test-only glue 的规则。§4 的结构化事件字段合理，但验收没有规定成功/失败日志成对关系、trace 跨进程传递、敏感字段负向扫描或在并发故障中如何关联 barrier 与操作。建议固定报告命令、覆盖率归档、事件 schema 校验和 secret/path/学生文本负向断言，并将 race/vet/lint/build 与平台集成结果作为互不替代的门。

## 已充分覆盖的部分

- §2 威胁边界和 fail-closed 原则具体，包含 symlink/hardlink/reparse、身份变化、锁与 Sync 不确定性。
- §4/§5 已明确结构化日志字段、禁止敏感字段、核心覆盖率门及 Linux/Windows 实际运行要求。
- 文档明确后续 E2E 与真实课堂验收不属于本监督器单测，避免把 test-only 内核误报成产品/课堂验收通过。
- 建议文档修订后先让测试与安全域复审矩阵，再开始实现；实现阶段每一项失败路径应有可复现的 Go 单测/跨进程集成，并在 loopback/E2E SDD 中有对应用户旅程用例。
