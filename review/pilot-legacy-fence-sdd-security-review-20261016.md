# Security Review: Closed-Pilot Legacy Classroom Fence SDD

Review target: `docs/41-试点关闭态旧课堂保护接线SDD.md`, read with `docs/36-全双工课堂统一提交接线设计.md` §§15–18 and current store/API boundaries. This is a design-only review. No code was changed and no tests or runtime checks were performed. The SDD itself labels the work as a draft awaiting review.

## Decision

**Not approved for implementation yet.** The fail-closed intent is sound, and keeping pilot creation/execution unreachable is the right boundary. However, several security-critical contracts remain open or are only described as process-local actions. These gaps affect authorization, cross-process serialization, and deletion safety; they must be resolved in the SDD before implementation. This verdict does not claim that current product paths are secure or that any behavior has been tested.

## Blockers

1. **Writer proof and transaction-bound guard are not specified tightly enough (P1).** Section 9 explicitly leaves open how the outer transaction proves that it acquired SQLite's writer. A deferred `Begin`, a read-only check, or a guard cached before a savepoint rollback is not proof. Freeze the exact writer-acquisition SQL and transaction owner, and define a tx-bound capability that cannot escape, survive rollback/commit, or be reused on another pool. Every guard must re-read current mode under that writer; an acquisition, cancellation, or commit-uncertain error must not authorize effects. Align this contract with docs/36 §§15.3, 16 and 17, including existing outer transactions.

2. **The pre-v2 bridge/migration race contract is implicit (P1).** Docs/36 §17 requires an unmigrated legacy reservation to persist a strict `runtime_records` bridge under the same writer used by migration and pilot creation, and requires migration to import and retain that bridge. SDD §4/§5 describes scope reservations and schema validation but does not state this no-v2 behavior, the bridge format, malformed-bridge handling, or adoption ordering. Without that contract, a legacy operation may pass while another process migrates and creates a pilot scope. Explicitly specify: writer serialization on the shared table; re-read marker/schema after obtaining the writer; insert/validate the bridge before returning a legacy reservation; migration imports every bridge atomically; any malformed/unknown bridge fails closed; no bridge/cache-only success is publishable before COMMIT.

3. **Scope fencing is not authentication; authorization is underspecified (P1).** The target scope is often derived from the student, book, lesson, task, or a global configuration operation. The SDD says to preserve existing authorization, but does not freeze a caller-to-principal matrix for direct Go calls, Agent tools, REST/WS, background workers, multi-scope feedback/overdue work, and global ladder changes. A `ReserveLegacyScopes` success receipt must never act as identity or permission. Specify, per operation, who may request it, how the authenticated/current principal is bound to the requested student/book, and whether system workers use a separately trusted principal. For global config that triggers `TruncateLadderSteps`, define the complete affected scope set and atomic deny behavior; administrator permission to edit a global setting must not silently grant authority over all student teaching data. If any affected scope is pilot/unknown or cannot be enumerated, reject before changing config, cards, cache, or notices.

4. **DeleteBook retirement is only a local-sounding fence and can race another process (P1).** P3 says to retire Room/worker/task, then delete runtime rows and lessons. It does not define a durable cross-process retirement generation/claim checked by every late callback, nor a writer-order contract for Enter/Join, worker claims, deletion, and callbacks. A local Room/task cancellation cannot stop another App process from committing a late snapshot/report/settlement after deletion, recreating the data that was purged. Define a persistent retirement/tombstone or equivalent DB fence, with compare-and-set generation/token checks in every writer, and define which process owns/renews/releases it. Deletion must serialize with new entries and in-flight effects, fail closed on unknown owners/orphans, and remain retired after a partial failure until a safe retry. Do not implement destructive cleanup until the settled/replay tombstone and retention/reconciliation contract is frozen, as the SDD already recognizes.

5. **Old binary coexistence is identified but has no enforceable release gate (P1 for pilot activation).** Section 8 correctly states that an old binary may not understand the persistent tombstone, but “independent security check” is not an executable deployment condition. Specify how every writer is version-gated or drained before any migration/pilot activation (for example, stop-and-verify all old processes and block old binaries from reopening the DB); record what evidence unlocks the gate. If this cannot be enforced, the deployment policy must keep migration and pilot unavailable. This does not block a strictly closed pilot implementation by itself, but it blocks any later pilot opening.

## Follow-up hardening

- Section 6 proposes `student_scope_hash` plus raw `book_id`. A plain hash of a small, guessable student-ID domain is reversible by enumeration. Either keep identifiers in access-controlled audit storage with a documented retention policy or use a keyed, rotating HMAC and avoid unnecessary raw scope IDs in general logs.
- Specify how `COMMIT`-unknown is resolved before callers proceed: reread the durable scope/bridge on a fresh writer transaction and return success only when the exact intended legacy fact is observed. Otherwise return a stable unknown/retryable result; never treat a receipt constructed before commit as authorization.
- Preserve the explicit distinction in docs/36 between a read-only finished-classroom re-entry and any recovery that changes state. The tests proposed in §7 should count all SQLite DML and assert no runtime writes on the read-only path; the document correctly notes that the “finished” label is insufficient.

## Review status

Five P1 findings remain. Revise the SDD and request another cross-domain review before implementation. No product-security or runtime acceptance is inferred from this document review.
