# Security Review 3: Sidecar Recovery Disposition

Read-only review of the revised `docs/41-试点课堂Start持久迁移内核SDD.md` §108 and current `server/internal/store/pilot_start_sidecar.go`, focused on the prior capacity/quarantine crash finding and the tool-result recovery rule. No files were changed and no tests were run.

## Decision

**The prior SDD disposition is sufficient and internally coherent, but implementation remains blocked on supervisor integration.** §108 now requires a durable `open/recovery-required` catalog record before any sidecar append or DB write, and a durable terminal/recovery disposition before the case can be treated as clean. If a later quarantine write fails and the process crashes, startup sees the earlier durable unresolved marker and must prohibit fresh commands; it cannot infer health from the old sidecar. This removes the prior zero-byte-quarantine-write ambiguity, provided implementations enforce the ordering exactly.

The current event validator also now rejects `terminal_failed` with `commit_unknown` or `rollback_proven`, and its transition table excludes the phases where `tool_started` has no durable `tool_result`. This conforms to §108's `pending_unknown` rule at source-review level; it has not been executed here.

## Disposition and remaining implementation blockers

- **Capacity/quarantine restart policy — closed in SDD.** [§108, line 114](/D:/en-words/docs/41-试点课堂Start持久迁移内核SDD.md:114) requires `open/recovery-required` to be synced before sidecar/DB mutation and a durable disposition before clean status. A crash before quarantine persistence therefore still leaves an unresolved catalog entry. Startup is required to validate catalog state before opening DB/sidecar and to disallow fresh commands for unresolved cases. The fix is stronger than relying on an in-memory degraded flag or on a second quarantine write succeeding.
- **Catalog error handling — coherent with the prior zero-byte/uncertain-write model.** If catalog quarantine itself fails, the supervisor globally fails closed and retains the lifecycle lock while alive. On restart, the preexisting open/recovery-required marker remains the fail-closed basis. A partially written/corrupt catalog still follows the global integrity-failure rule. This depends on the initial open marker being committed before *any* sidecar append or DB write, including initialization paths.
- **`tool_started` recovery — closed in design and current source.** [§108, line 116](/D:/en-words/docs/41-试点课堂Start持久迁移内核SDD.md:116) states no durable result means `pending_unknown`. `nextPilotStartPhase` does not permit `terminal_failed` from phases 3 or 5, which represent say/show_word started without a result ([pilot_start_sidecar.go:366-377,392-396](/D:/en-words/server/internal/store/pilot_start_sidecar.go:366)). `validatePilotStartEvent` now rejects terminal failure carrying `commit_unknown` or `rollback_proven` ([pilot_start_sidecar.go:340-342](/D:/en-words/server/internal/store/pilot_start_sidecar.go:340)).
- **Supervisor/catalog implementation — still blocking.** The reviewed server tree has no catalog supervisor/coordinator implementation that performs durable open/recovery-required and terminal transitions, enforces startup checks before DB/sidecar access, or performs whole-case cleanup. §108 itself identifies coordinator restart/quarantine and Playwright integration as unimplemented ([line 116](/D:/en-words/docs/41-试点课堂Start持久迁移内核SDD.md:116)). Until this exists, the SDD policy cannot be claimed as enforced.
- **Verified file open and creation authorization — still blocking integration gates.** The helper still accepts path/key and performs `Lstat` followed by a separate pathname open ([pilot_start_sidecar.go:90-115](/D:/en-words/server/internal/store/pilot_start_sidecar.go:90)); it does not consume the verified handle or itself establish the file identity/link checks required by §3. Creation is still caller-gated by convention rather than an opaque verified-new-case capability ([pilot_start_sidecar.go:80-88](/D:/en-words/server/internal/store/pilot_start_sidecar.go:80)). The supervisor must guarantee verified case identity and only call create for a catalog-proven new case; recovery must never fall back to create.
- **Windows ACL and directory durability — still blocking integration gates.** Windows mode checking is permissive and parent Sync is a no-op in the helper ([pilot_start_sidecar.go:136-155](/D:/en-words/server/internal/store/pilot_start_sidecar.go:136)). §108:114 explicitly makes effective DACL verification and parent-directory durability supervisor responsibilities. No such supervisor is present in the reviewed implementation.

## Required implementation evidence

Before implementation approval, demonstrate by source and integration acceptance that every new case durably records `open/recovery-required` before DB/sidecar creation or writes; every recovery/start path checks catalog state before open; success/failure/unknown dispositions are durable and correctly scoped; catalog write/Sync failure plus process restart cannot admit a fresh command; and unresolved cases can only take authorized receipt-first recovery or whole-case cleanup. Complete verified-handle, new-case creation, Windows DACL, and Windows directory durability gates. This review does not ask for or claim those runtime checks have passed.

## Limits

No tests, supervisor code, catalog failure injection, restart, path-race, ACL inspection, Windows durability check, or runtime operation was performed. This is a read-only design/source review.
