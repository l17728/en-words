# Pilot RunRoot Stage A Implementation Delta

## Status and precedence

This delta resolves the Stage A blockers in docs/50–53. It is a design proposal until architecture, backend, security, test, and product reviewers approve the exact file hash. It does not enable the product route or a classroom pilot. For the clauses below it takes precedence over earlier stage ordering and ambiguous response/receipt wording; all other docs/43–53 contracts remain normative.

## Stage boundary and trusted startup

**Storage implementation gate:** the current `server/internal/pilotcontrol/sqlite.go` uses the stock path-based SQLite VFS and is an isolated authorizer/schema experiment only. It does not satisfy docs/43 §2.1's pinned-handle VFS contract, even with the same-connection schema revalidation added here. Do not wire it into A0 or publish Pilot readiness. Implement the separately reviewed [docs/55 pinned VFS SDD](55-pilot-control-pinned-sqlite-vfs-sdd.md) first; schema/authorizer tests are necessary but not evidence of filesystem identity safety.

The A0 operations database has the same local trust boundary as the launcher journal: it and its `-wal`/`-shm` sidecars must live under a directory writable only by the dedicated Reaper service identity (and deployment administrator). The database must be a regular, non-symlink file. Startup validates the schema on every newly opened protected SQLite connection before enabling the trigger capability; the deployment must prevent untrusted principals from replacing or writing the database path for the process lifetime. An environment that cannot prove this ownership/permission boundary is not A0-ready and must keep Pilot disabled.

Stage A is split into A0, A1, and A2; none exposes the product API.

- **A0 — resident identity authority.** Install and start the singleton `PilotControlReaper` under its dedicated service identity. Initialize and validate the exact v3 schema in docs/51–53, exclusive writer lock, protected operations database, wrapped identity keyring, alias table, authorization-fence table, journal-anchor row, and read-only launcher key configuration. A0 provides `ResolvePrincipal`, `CheckCurrentAuthorization`, idempotent `PublishAuthorizationFence`, `AdvanceLauncherJournalAnchor`, `ConsumeBootstrap`, `CommitLifecycleBoundary`, `ConsumeRecoveryControl`, and read-only `LoadRecoveryTarget`. `PublishAuthorizationFence` accepts only the authenticated web authorization authority. `ResolvePrincipal`, `CheckCurrentAuthorization`, `AdvanceLauncherJournalAnchor`, `ConsumeBootstrap`, and `CommitLifecycleBoundary` use the launcher identity on their respective pinned channels; startup controls are restricted to the exact generation/nonce/process tuple. `ConsumeRecoveryControl` and `LoadRecoveryTarget` accept only the separately registered recovery-only Reaper identity bound to the fresh control generation and exact old target; the launcher may initiate/register that session but cannot impersonate its RPC caller. No method can create business operations, allocations, leases, RunRoots, finish/close operations, or terminal business results before Stage B. Recovery reads only the exact consumed target; any target requiring business finalization remains quarantined and lease-held. All eight methods execute through the same serialized v3 writer and capability authorizer. Schema/key/alias/anchor integrity errors stop service startup. The API and launcher fail closed when A0 is unavailable.
- **A1 — persistent logger readiness.** Start Logger as a pinned child of the trusted launcher and accept only its authenticated `LOGGER_READY`. A1 ends there: the **per-run Reaper child** does not yet exist, the A0 resident `PilotControlReaper` remains live as the serialized v3 ledger authority, and no `LOGGER_REGISTER` is sent in this stage. A0/A1 use native processes and actual protected stores; mock acknowledgements cannot pass either gate.
- **A2 — launcher lifecycle and channel registration.** Implement the protected journal, fixed owner-only admission IPC, pidfd/cgroup lifecycle, startup protocol, and failure fencing in docs/47–48. It spawns the Reaper and held Gateway only after A1 readiness, performs BOOTSTRAP via A0, then sends LOGGER_REGISTER and requires durable `REGISTER_ACK` plus authenticated `LOGGER_CHANNEL_READY` before Gateway REGISTER. For each journal event the launcher invokes `AdvanceLauncherJournalAnchor` over its authenticated control identity before ack/side effect. This first Stage A slice has no retirement/finalization RPC: it starts at most one disabled test generation per disposable ledger. A stop, crash, or uncertain post-BOOTSTRAP result must reap and contain all children, persist a journal quarantine record when possible, stop admission, and reject replacement generations. It must not invent lifecycle/containment/terminal evidence, call Stage B close methods, or claim automatic recovery. Reuse requires the separately reviewed Stage B retirement/recovery contract. The launcher may call only its five authorized A0 methods and documented logger/generation lifecycle controls. It must reject run allocation, `CreateRunRoot`, finish outbox, close finalization, and every business operation as `pilot_not_enabled`; unauthorized method/caller pairs and unknown methods return generic `rpc_rejected`. Each later stage adds an explicitly versioned RPC allowlist.

Ordering is mandatory: singleton lock → validate journal and resident A0 readiness → authenticate current admission and resolve/create principal → check current fence → perform journal lookup or idempotency replay → start/accept generation. Status and close follow the same authorization-before-journal rule. The resident v3 writer is provisioned and healthy before any launcher/API request; Stage B adds run transactions to that same writer and schema, and must not create a second ledger or writer. `AdvanceLauncherJournalAnchor` is a separately authenticated launcher-control RPC exposed only to the singleton launcher; it is not callable by the web/API process or per-run Reaper. It may only CAS the one pre-provisioned anchor row from `(sequence,hash)` to `(sequence+1,new_hash)` and must commit before the journal event is acknowledged or any bound side effect occurs.

## Launcher journal storage and recovery contract

The launcher journal is a dedicated owner-only append-only file, not the catalog journal. Its parent directory is provisioned mode 0700 beneath an administrator-owned, non-writable directory; the journal and singleton lock are mode 0600, owned by the launcher UID, opened with no-follow semantics, and verified as regular files on the configured filesystem. One process holds the exclusive OS lock for the full lifetime. No API, Reaper, Gateway, or Worker identity can read or write it. The v3 ledger contains exactly one `pilot_launcher_journal_anchor` row: singleton ID 1, random immutable 16-byte `journal_id`, external `restore_generation`, `last_sequence`, `last_record_hash`, and `updated_at`. It is created at sequence zero during A0 provisioning. The idempotency `namespace_epoch` is exactly the lowercase 32-character hex encoding of this row's 16-byte `journal_id`; it is not a separate mutable value. A root-owned deployment control plane provides a fresh signed boot marker containing version, host identity, current restore generation, journal ID, and namespace epoch (which must equal the journal ID encoding), bound to a one-time boot challenge. The marker is verified against a pinned control-plane key; its generation advances in storage outside the host/VM snapshot domain on every platform restore and cannot be rolled back by the host. A0 requires an exact match with the ledger value; stale or replayed markers, signature/host/challenge mismatch, unavailable control plane, or unverified restore status fail closed. Hosts unable to guarantee this external monotonic restore signal are unsupported. A detected database or host snapshot restore disables the pilot service; offline recovery preserves the old ledger read-only for audit, proves all old cgroups and process identities retired, quarantines all old RunRoots, initializes a new empty pilot ledger and journal with a rotated marker/namespace epoch, and imports no old run rows. The pilot route remains disabled until the operator signs an audit confirming old processes are gone and old roots are quarantined. This deliberately sacrifices historical pilot status after a full snapshot restore; old keys fail by epoch and old live resources are never re-admitted. The row is updated only through the launcher's journal-anchor capability, by exact old-sequence/hash CAS to sequence+1 and the new record hash. The literal DDL trigger rejects ID/generation changes, deletion, nonconsecutive advance, unchanged hash, and decreasing timestamp. The table and capability are included in the reviewed v3 DDL manifest before A0 implementation.

Each record is canonical CBOR payload inside a binary frame: magic `EWPJ`, format version `1` (u16 big-endian), payload length (u32 big-endian, 1..1 MiB), sequence (u64 big-endian, starting at 1), previous-record SHA-256 (32 bytes; zero for the first record), payload, CRC32C (u32 big-endian over header and payload), and record SHA-256 (32 bytes over header, payload, and CRC). A record payload has a closed typed schema and event name; unknown versions, fields, or event types quarantine the journal. Every append writes the complete frame with a write-all loop and calls `fdatasync` before acknowledging the operation or allowing its next external side effect. The record hash chain detects reordering, omission, and torn/corrupt interior data; filesystem ownership and permissions provide the write trust boundary.

For every journal event, append and `fdatasync` the frame first, then CAS-advance the independent v3 ledger anchor in a committed writer transaction, and only then acknowledge the event or perform its next external side effect. On first file creation, also `fsync` the journal parent directory before advancing the ledger anchor or performing any side effect. On startup compare the signed external restore generation, journal ID and namespace epoch with the ledger anchor before reading journal events. A mismatch, stale marker, signature failure, or unavailable verifier is a hard admission fence. Then compare the verified journal tail with the sequence/hash anchor. A tail behind the anchor, or same sequence with another hash, is rollback/corruption and quarantines admission. A journal exactly one verified record ahead is the sole permitted crash window (append durable, anchor transaction not committed); validate that record and CAS the anchor forward before replay or side effects. More than one record ahead is impossible under the append/anchor/ack serialization and quarantines. A short final header/frame or incomplete final payload is truncated only to the last verified frame and synced; that boundary must equal the anchor or be exactly the one-record-ahead crash window. This detects replacement with an older complete prefix, including queued/canceled idempotency tombstones that have no business-ledger row. A paired database+journal snapshot retains the old persisted restore generation and is detected because the external generation advances outside that snapshot. On restore, preserve the old ledger read-only, prove old cgroups/processes retired, quarantine old roots, create a fresh empty pilot ledger and journal bound to the new marker, and import no old run rows. If any old process/root cannot be safely accounted for, keep the service disabled for offline operator action. There is no automatic restore/reseed path.

The scan is bounded to 64 MiB and 1,000,000 records. A complete frame with bad CRC/hash, invalid CBOR/schema, sequence gap, bad link, interior corruption, or an impossible anchor relation quarantines the journal and blocks admission; never skip a record or infer missing state. Exceeding either scan bound blocks admission for explicit offline repair. Snapshot/compaction is out of scope for this stage; reaching the bound therefore fails closed.

The same ordered journal records bind admission namespace epoch + admission key hash + payload digest, close namespace epoch + close-key hash + close payload digest, request/epoch/generation/nonce, and each resource's intent/created/active/retiring/removed/quarantined transition. After explicit learner intent, the authenticated API asks the trusted launcher authority to mint a random opaque `intent_handle` using the exact token, AES-256-GCM AAD, and fixed-order canonical-CBOR plaintext schema in docs/50 API and durable idempotency contract; docs/50 is normative for field widths, purpose, timestamp units, expiry, and canonical unpadded base64url. The per-key counter reservation is serialized across concurrent requests, durably fsynced before encryption, and never reused after crash; rollback/corruption disables issuance, with key rotation required before 2^24 uses or counter wrap. The browser persists and reuses the returned handle but cannot choose, decode, or supply an epoch; handle issuance creates no run or other business side effect. The server validates the handle and rejects a stale epoch before journal lookup with `idempotency_epoch_expired`, after authentication and authorization checks. It never silently remints an old handle. After disaster recovery, old handles (including handles whose operations completed or were canceled) cannot replay; clients must display the recovery notice and request a new handle only after a deliberate new Start action. A handle is never logged or stored raw in server-side durable records. Handle binding is durably appended before spawn or replay response; close binding is durably appended before UNREGISTER or teardown. Resource intent is synced before create/bind/spawn; verified resource identity is synced before passing its descriptor or spawning into it. Received ACKs are synced before the next irreversible step. Recovery derives state only by replaying this single sequence; it reconciles against the resident ledger and exact OS identities and quarantines disagreement. A journal record never overrides a Reaper commit receipt.

## Corrected persistent outcomes and close saga

For `CreateRunRoot` EEXIST, the OS errno maps to ledger `response_code=exists`. The allocation/run outcome is `indeterminate`, the lease remains held, and no RunRoot state row, cleanup-disposition row, target open/query/delete, or success projection is written. The API reports recovery-required. This replaces docs/50's incompatible `verified_policy_mismatch`/`cleanup=indeterminate` wording; the literal persisted state is exactly the v3 schema in docs/51–53.

Containment/cleanup ordering follows docs/51: receive authenticated `UNREGISTER_ACK`; independently prove the exact generation's cgroup and process containment empty; the original live Reaper safely cleans or retains a created RunRoot and commits its cleanup disposition; then it atomically persists immutable containment evidence and the permitted lifecycle/run-state transition; finally it performs the applicable terminal transaction. If the original Reaper exits before cleanup disposition and evidence are both committed, replacement recovery cannot clean or manufacture either proof and must keep the lease held in `recovery_required`. If both proofs exist, recovery may run only the matching finalization/read-only already-terminal response. Cleanup cannot be treated as containment proof. Before implementation, docs/50's corresponding RunTermination row must be synchronized to this ordering; this delta is the controlling contract in the interim.

For a no-RunRoot close, required pre-finalization proof is the exact pinned-anchor absence witness and authenticated containment evidence. `cleanup_state=not_required`; there is no RunRoot cleanup-disposition row. `FinalizeNoRootAbort` creates and commits the typed close receipt atomically with close completion and lifecycle terminal. For prepared cancellation, the existing typed cancellation receipt and no-send proof rules remain in force; the pinned-anchor absence witness and containment evidence are required, then `FinalizePreparedCancellation` creates the typed close receipt and atomically writes the terminal tombstone, completes close, and releases the exact lease. These branches are distinct and neither may synthesize a missing cancellation/absence/containment proof.

## Acceptance order

Before any implementation, review and accept this delta and the updated docs/51–53 DDL artifacts against the exact hashes. Freeze the literal DDL manifest only after architecture, backend, security, and test-design approval, then execute the bound 36-case schema-fault suite with the pinned CGO SQLite driver and meet its coverage gate.

Before declaring A0/A2 ready, execute product-manifest cases A0-01, A2-01, A2-02a, and A2-02b against the exhaustive method/caller matrix in docs/51. Only a method's authorized caller may reach the disabled-stage gate and receive `pilot_not_enabled`; unauthorized method/caller pairs and unknown methods receive the same generic `rpc_rejected`, with no method, target-existence, or internal-error detail. Emit the safe `control_auth_rejected` event for authorization failures. Across all RPC denials, ledger rows, journal bytes, generation and lease state, process spawn count, RunRoot inventory, and dispatch count remain unchanged. The A2-02 variants prove startup-only shutdown/restart fencing: graceful-stop child reaping is performed by the original launcher through retained pidfds; the launcher appends and `fdatasync`s the quarantine journal frame, then A0 commits the matching anchor. After hard crash, systemd KillMode=control-group and PID 1 terminate/reap descendants; replacement must prove the prior cgroup empty, never wait on old nonchildren, and append/sync quarantine before asking A0 to advance the anchor. Any uncertain step blocks restart. Neither variant promotes the ledger to terminal or admits a replacement generation before separately reviewed Stage B retirement/recovery exists.

The production PilotControl gate is separate and mandatory: review docs/55 plus its executable callback manifest, generate and review the four runtime goldens from the pinned SQLite 3.45.1 source ID, implement the private pinned-handle VFS, then pass callback, crash/reopen, race, coverage, and native Linux filesystem acceptance. The current path-based `pilotcontrol/sqlite.go` code remains an isolated prototype and cannot open the authoritative ledger, satisfy A0, or publish readiness. Missing goldens, stale source IDs, unexecuted callbacks, or unavailable native runners are `BLOCKED`, not pass.

Only after those schema and VFS gates may A0 begin. Implement and accept A0, A1, and A2 sequentially as independently reviewed slices with real SQLite/filesystem/OS behavior and crash injection; update the product manifest only when a case has executable passing evidence. Stage B can start only after native Linux A2 acceptance. Product route/UI remains disabled until later reviewed stages and native gates pass. Linux amd64/arm64 privileged, ext4/XFS, race, cgroup/pidfd, full package coverage, Playwright, and supervised classroom gates retain the requirements in docs/50; cross-compilation or mocks are supplementary and cannot substitute. Disaster recovery must test rejection of old completed and canceled keys, plus the approved explicit-new-intent flow.
