# First-Audio PREFLIGHT Preparation Phase SDD

Date: 2026-10-29
Status: implementation accepted for the startup/PREFLIGHT slice; Linux and Windows CGO protocol CI passed (run 40839202122); broader matrix remains open.

## Problem

The guarded-app owner must call real `NewApp` while in `STARTUP_PROBE`. The pool may have only one physical connection at that point. The current lifecycle requires three distinct connection-bound probe receipts when publishing `PREFLIGHT`, but identities for the other two connections exist only after they are opened and pinned. Opening them before `NewApp` violates the startup boundary; publishing final `PREFLIGHT` before their identities exist cannot satisfy its immutable receipt contract.

## Proposed transition

Add a test-only lifecycle phase `PREFLIGHT_PREPARE` between startup verification and final PREFLIGHT. The monotonic versions for this owner are `DRIVER_PROBE v0 → STARTUP_PROBE v1 → PREFLIGHT_PREPARE v2 → PREFLIGHT v3`; later journey versions remain monotonic. `NewApp` runs and its transaction/autocommit plus baseline snapshot are verified in STARTUP_PROBE before this transition. After those checks, the owner records a controller-owned, one-use startup verification receipt bound to run, lesson, generation, context version, and equal baseline/readback digests. A caller-supplied boolean is not sufficient proof.

The guarded owner must take `STARTUP v1 → PREFLIGHT_PREPARE v2 → PREFLIGHT v3`; it cannot use the direct legacy transition. Enforce this with controller construction policy: legacy protocol fixtures use the default policy, while the guarded owner constructs its controller with `requirePreflightPrepare=true`; the publisher rejects direct STARTUP→PREFLIGHT for that controller even when evidence is complete. Before entering PREPARE, drain all STARTUP leases. The publisher accepts only the exact next phase/version/generation and an active exclusive transition lease. Skipped, duplicate, backward, foreign-generation, and wrong-phase candidates are rejected without changing the published context; failed identity/evidence checks terminalize the guarded owner.

`PREFLIGHT_PREPARE` is a closed, exclusive phase. It authorizes no application SQL, cleanup SQL, UDF invocation, transaction, or user admission. Its intended activity is opening/pinning connections and recording their unique registry identities. SQLite authorizer denials remain terminal. At registration, each ConnectHook captures phase/version as identity provenance only; it is not a permanent authorization binding. Later authorizer and UDF decisions load the current immutable context and validate the active connection-bound challenge. The original GORM dialector connection is expected to be first registered under `DRIVER_PROBE v0` (it owns the dialector receipt); each additional raw connection must first register under `PREFLIGHT_PREPARE v2`. Any other phase/version is rejected. go-sqlite3 initialization occurs before the ConnectHook installs the authorizer; tests must lock this ordering and assert no authorizer SQL/UDF/transaction/write event occurs while opening extra connections in PREPARE. If an event is observed, the phase contract must be revised before implementation, not silently allowlisted.

After the owner has three distinct live connections, it creates immutable connection-bound challenges and publishes final PREFLIGHT with exactly three unique physical receipts in ISSUED-but-unarmed state and matching bindings/contracts. At publication time, while all three pins remain held, revalidate exact set equality among expected IDs, raw pointers, and live registry registrations under the registry's live-set lock; hold that same lock through the context swap and receipt admission arm. No callback or connection user may run in the interval between context publication and arming all receipts. Reject missing, duplicate, extra, replaced, or stale identities. Receipts remain unusable before publication; only after the PREFLIGHT context publishes may the publisher arm callback admission. Receipts are still incomplete at that point: only the subsequent PREFLIGHT probe may advance them to readback-complete. The lifecycle publisher accepts only a monotonic `PREFLIGHT_PREPARE → PREFLIGHT` transition with the complete matching issued-receipt set.

## Invariants and tests

Tests must prove NewApp precedes pool expansion; the dialector identity is registered only in DRIVER_PROBE and the other two in PREPARE; no authorizer SQL/UDF/transaction event occurs while opening extra connections; and SQL/UDF/write attempts in PREPARE terminalize. Negative cases assert: skip/repeat/backward phase, wrong generation, missing transition lease, strict-owner direct-transition rejection, fewer/more/reused identities, non-PREPARE extra connection, pre-publication wrong-phase/generation candidate rejection, and incomplete/foreign/replaced receipt sets all fail without publishing PREFLIGHT or arming a receipt. Legacy-policy fixtures prove the existing direct transition still works. Separately, mutate the caller's context spec after publication and assert the published immutable context is unchanged. Pins stay held across challenge construction/publication and are then used for the probes. The atomic registry lock covers exact set validation, context publication, and receipt arming. Success ends in PREFLIGHT with three readback-complete receipts and unchanged snapshot. Every failed/open-denied path releases or physically retires connections without SQL cleanup. Failure cleanup follows docs/91; uncertain physical retirement is reported for parent reap and is not accepted as clean.
