# Pilot Run Root Allocation SDD

**Status: design and test matrix reviewed across architecture, backend, security, and testing. Partial implementation exists behind `pilot_e2e`: deterministic evidence digests, Linux anchor preflight, fail-closed filesystem effects, SQLite ledger primitives, strict SOCK_SEQPACKET client, and bounded durable host-logger queue with nonce/digest-correlated ACKs, peer credentials, rate limits, JSONL index rebuild, deduplication, bounded writer/Sync lifecycle, store caps, and poison/restart handling. The host-logger queue slice passed native Linux ext4 and XFS normal/race tests (334 each) and tagged vet on 2026-10-20; default server normal/race suites passed 1,521 runs each (9 explicit skips), full vet passed, and Python discovery passed 23/23. Exact hashes and logs are in `.test-artifacts/pilot-linux-final-current-20261020/linux-acceptance-final-summary.json`. These results do not cover trusted launcher/listener handoff, RunRoot caller/outbox orchestration, atomic run-terminal/lease release, all manifest rows, or product integration. This is a Linux-only pilot infrastructure slice named by docs/44 ?11; it remains behind `pilot_e2e` and does not connect the product app, classroom, model, or real-user data.

## 1. Goal and limits

The PilotHostReaper allocates one empty, identity-pinned run-root below the trusted `pilot-runs/` anchor. It creates no catalog, catalog lock, case directories, logs directory, or other child entry. docs/44 allows these known entries to be absent. `catalog.log` remains absent until a later authorized Supervisor operation can write and Sync a complete first `provisioning` frame under docs/42 §16.

This implementation supports native Linux ext4/XFS only. It supersedes docs/44 outer-anchor owner/mode wording and docs/42 root-creation responsibility as explicitly recorded in those documents; docs/44 epoch-root/member policy and docs/42 case/catalog responsibility remain in force. Windows fails closed with `verified_configuration_missing` and remains a separate reviewed phase requiring a SYSTEM creator, fixed Worker SID ACL, directory durability contract, and trusted launcher. This phase does not alter docs/44's read-only root policy and is preparatory; it does not claim a usable case lifecycle.

### Current repository readiness gap

The current `authenticatedIPCPeer` carries a socket, PID, principal, liveness parent, and a process-local generation. The Linux adapter opens and retains a pidfd, but it opens that FD from a PID supplied to the adapter; it does not receive a pidfd from a trusted launcher or verify the six-field process identity tuple. A pilot-only `SOCK_SEQPACKET` logger client/store and correlated ACK validator now exist, including expected `SO_PEERCRED` matching and durable JSONL replay indexing. The bounded multi-run queue and durable writer are implemented and native ext4/XFS verified; trusted launcher identity source, listener registration, and FD handoff remain unimplemented and unwired. These are missing trusted inputs, not caller-provided fields: `CreateRunRoot` must not accept identity from IPC or synthesize it from PID/UID. Bind the launcher identity handoff, logger channel, ledger, and filesystem primitives before implementing the end-to-end method.

## 2. Typed request, authenticated authority, and durable intent

The only entry point is `(*PilotHostReaper).CreateRunRoot(ctx, peer AuthenticatedGatewayPeer, req RunRootCreateRequest)`. `run_epoch` is exactly 32 lowercase hexadecimal ASCII characters (`[0-9a-f]{32}`), representing the canonical UUID bytes without separators; reject empty values, `.`, `..`, slashes, backslashes, NUL, non-ASCII, alternate encodings, and every other length before ledger or filesystem access. It is therefore one basename component, never a path. `req` contains only this canonical `run_epoch`, bounded `request_id`, authenticated `session_key_hash`, and `layout_version=1`; it never accepts a path, caller-declared `principal_ref`, UID/GID, owner generation, gateway generation, permissions, or member list. Reaper resolves `principal_ref` and role from its own bound authenticated-session map, as docs/43 requires. `AuthenticatedGatewayPeer` is an opaque accepted IPC peer plus the Gateway bootstrap and OS-verified process identity. Reaper requires the live peer PID/UID and pinned process identity to match that bootstrap and checks its `gateway_generation`; caller request fields cannot override it.

The Reaper has a provisioned worker UID/GID pair from protected host configuration, bound to the run lease and worker bootstrap. On the isolated native test host, the trusted launcher creates a private mount namespace with private propagation, pivots into a minimal tmpfs namespace root, bind-mounts only the dedicated pilot-control and pilot-runs filesystems, and detaches the old root. It exposes no `/proc`, `/sys`, `/dev`, host home, application data, or arbitrary host path. The launcher closes every inherited FD except the typed control socket, pinned control/run-root FDs, and a connected host-logger `SOCK_SEQPACKET` FD, verifies the FD inventory, and drops `CAP_SYS_ADMIN` before Reaper starts. Reaper holds only `CAP_CHOWN`, `CAP_DAC_OVERRIDE`, and `CAP_DAC_READ_SEARCH` within this namespace; Gateway and worker hold none. Seccomp narrows syscall classes but is not treated as a validator for pointer-based path strings or `open_how` contents. The security claim is limited to mount-namespace visibility and fixed FD boundaries: even a compromised Reaper can affect only the exposed pilot data and disposable namespace root in this test host. This is not a production privilege model. Reaper creates the directory with mode `0700` before `fchown(fd, configuredWorkerUID, configuredWorkerGID)`, so it needs no chmod privilege after ownership transfer. The worker later runs under that exact UID/GID. IDs cannot come from the request. POSIX root is owned by worker UID and fixed service GID, with no access/default ACL. The anchor must have no default ACL; otherwise fail before create. The Reaper control ledger remains in a separate root inaccessible to the worker. The trusted host launcher is the only component allowed to inspect host /proc before namespace pivot. It launches the configured Gateway itself using clone3 with CLONE_PIDFD (or an equivalent atomic spawn API that returns a pidfd), records starttime, PID-namespace device/inode, cgroup mount/inode, UID, PID, and Gateway generation while the process is pinned, and retains that pidfd as the durable bootstrap identity. It rejects inherited Gateway listener sockets: only the exact launched process may own/connect the authenticated endpoint, and the listener is closed in every child before exec. For each accepted IPC connection the launcher reads SO_PEERCRED, requires its PID/UID to match the pinned bootstrap, checks the retained pidfd is live, and rereads starttime/namespace/cgroup identity through host procfs; any mismatch, missing proc entry, or cgroup drift rejects the peer. It passes a fixed versioned identity record plus a duplicate of the already-pinned bootstrap pidfd to Reaper over a private SOCK_SEQPACKET channel using SCM_RIGHTS. It never opens a fresh pidfd from the peer-supplied PID, so PID exit/reuse cannot substitute a new process. The channel peer is checked against the provisioned launcher UID/process identity at bootstrap. Reaper validates the record schema, SO_PEERCRED PID/UID on the launcher channel, pidfd presence/liveness by poll, and equality with the durable Gateway bootstrap/generation; the tuple is authoritative because Reaper intentionally has no procfs view. The pidfd remains pinned through dispatch and is rechecked immediately before the create CAS/syscall. Exit, malformed/missing FD, inconsistent/stale identity, inherited endpoint, or launcher-channel failure is fail-closed before ledger dispatch.

After committing the durable prepared reservation, Reaper emits critical event run_root_dispatch_intent and waits for logger ACK before the prepared→executing CAS. If this ACK fails, the operation remains prepared and can resume once under the same key after logger recovery. Immediately after the CAS and before mkdirat, Reaper emits critical event run_root_dispatch_committed and waits for ACK. Failure here is after the irreversible executing CAS: mark operation/allocation/run indeterminate, fence the epoch, retain lease, perform no mkdirat, and prohibit same-epoch retry/reopen/new epoch. Only after the second ACK may mkdirat begin. No other blocking logger ACK is inserted between this second ACK and mkdirat. After the filesystem outcome is durably finalized, the same terminal transaction stores the `bootstrap.finish` event in a durable outbox; its later ACK confirms log delivery but does not change the immutable ledger state. No successful root capability is returned until that outbox event is ACKed.

Before filesystem effects, Reaper recomputes the versioned fixed payload digest for `[run_epoch, layout_version]`, atomically records a docs/43 operation `(run_epoch, request_id, principal_ref, gateway_generation, process_identity, operation_kind=run_root_create, schema_version=1, digest)`, and CASes `prepared -> executing` to mint `owner_generation`. The owner generation is minted only by the Reaper and is distinct from the later worker `worker_generation`. This operation uses no `ScopeCreate`; that scope remains exclusively for case creation. The active Gateway generation/process tuple and run lease must still match immediately before the create syscall. A duplicate `(run_epoch, request_id)` with identical immutable bindings returns a durable terminal cached result. If its owner is actively executing, an identical duplicate joins/waits on that owner under a bounded deadline; it never dispatches a second syscall or CAS. If the owner is dead or its state cannot be established, return `ipc_result_indeterminate` and retain the run lease. A prepared operation with no dispatch may be resumed by exactly one owner-generation CAS. A changed principal, gateway generation/process identity, or digest returns `ipc_request_conflict` without an OS call. A stale peer generation is rejected before ledger dispatch.

## 3. Linux create and durable outcomes

Check the pinned anchor with `fstat`, `statx(AT_EMPTY_PATH)` and `fstatfs`: accept only ext4 (`EXT4_SUPER_MAGIC`) or XFS (`XFS_SUPER_MAGIC`), require device and mount identity, ownership by the configured Reaper service UID/GID, mode `0710`, no worker write/list permission, and absence of POSIX access/default ACL xattrs. The worker may traverse this anchor by its fixed service group but cannot create, enumerate, rename, or delete sibling roots. Verify these facts from the pinned FD and fail closed on mismatch. The child run-root is worker-owned, fixed worker GID, mode `0700`, and has no access/default ACL. Then call `mkdirat(anchorFD, epoch, 0700)` with exclusive-create semantics. No request-controlled path is accepted and links are never followed. Open the new child relative to the same anchor using `openat2` with `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV`; inspect only the returned FD. Set `fchmod(fd, 0700)` while Reaper still owns the new object, then `fchown(fd, configuredWorkerUID, configuredWorkerGID)`, and re-read all identity/policy fields from that FD. Recheck that the anchor name still binds the pinned identity. No path-based ownership or permission repair is allowed.

Durability order: `mkdirat`; open/pin; ownership/mode set and verified; `fsync` the new directory FD; `fsync` the anchor FD; recheck parent binding; durably commit the typed run-root-created receipt and terminal ledger state. Reaper retains the verified root FD while the run is active. After Reaper restart, it reopens by the pinned anchor and epoch only for a durably completed run lease, then verifies the same identity/policy receipt before worker use; an executing/indeterminate run is never opened for worker use. Reopen failure or identity mismatch fences the run and returns `ipc_result_indeterminate`.

Use only existing docs/43 terminal states; do not add a `failed` state. For `mkdirat` returning `EEXIST`, do not open or inspect the existing target. Record the atomic collision result with pinned anchor identity, mark the operation `abandoned`, and return `verified_policy_mismatch`; the request key cannot be redispatched. At the run level, fence this epoch and retain its lease in `indeterminate` cleanup state: the colliding object has unknown identity, so operation-level no-effect means only that this syscall created no object, not that the epoch is absent or cleanup-complete. No worker may start and no new epoch may be admitted for this principal/session until a separately reviewed quarantine/inventory operation resolves the collision. For every other returned errno, check the epoch name relative to the same pinned anchor with a no-follow absence query. Only exact `ENOENT` proves absence; if any object is present, a link condition exists, or the query fails/returns another error, mark `indeterminate` and return `ipc_result_indeterminate`. With the single Reaper lease excluding concurrent creators, exact absence permits `run-root-create-effect-absent-v1` and terminal `abandoned`; the run lease remains held until the docs/43 run-terminal transaction durably records the epoch fence, no-worker/empty-containment proof, cleanup_state=not_required, and run terminal abandoned together with operation/allocation terminal state. For EEXIST the run lease remains fenced as specified above. Before the first durable operation or filesystem mutation, precondition checks use this stable error mapping (all cases leave the ledger and filesystem unchanged):

| Precondition result | Returned code | Required oracle |
|---|---|---|
| Recognized filesystem is not ext4 or XFS | verified_policy_mismatch | no prepared operation, lease, or filesystem syscall |
| Pinned anchor device or mount identity differs from trusted configuration | verified_path_invalid | no prepared operation, lease, or filesystem syscall |
| Access/default ACL is present | verified_policy_mismatch | no prepared operation, lease, or filesystem syscall |
| ACL, mount, or filesystem capability query fails or returns an unclassifiable result | verified_io_failed | no prepared operation, lease, or filesystem syscall |

Post-mkdir verification has a separate outcome contract. If the newly created root device, mount, ownership, mode, ACL, or pinned identity differs from the expected anchor/receipt, the root already exists: persist no success receipt, mark operation/allocation/run indeterminate, fence the epoch, retain its lease, return ipc_result_indeterminate, and prohibit reopen, retry, worker start, or new epoch admission. Never treat this as a precondition failure or attempt path-based repair.

| Post-mkdir result | Returned code | Required oracle |
|---|---|---|
| Created root identity/device/mount/policy mismatch or validation/Sync failure | ipc_result_indeterminate | root exists; no completed receipt; epoch fenced; lease held; no reopen/retry/worker/new epoch |

The errno table above is exhaustive and normative. `EIO`, interrupted/unknown syscall status, or errno not in its deterministic allowlist remains indeterminate even if a later query sees absence. If `mkdirat` succeeds, any later create/validate/chown/Sync error leaves a side effect: fence the epoch, mark `indeterminate`, and return `ipc_result_indeterminate`; never retry or reopen it. If close state is unknown, retain the handle, poison/restart Reaper, and return `restart_required`. Cancellation before durable `prepared` returns `operation_canceled` with no ledger or filesystem effect. Cancellation after `prepared` but before the `executing` CAS leaves the durable prepared record and run lease intact, returns `operation_canceled`, and permits exactly one owner-generation resume on same-key retry; no filesystem effect has occurred. Cancellation after that CAS follows the explicit indeterminate rule below; cancellation after a successful mkdir returns `io_uncertain`. Do not unlink or repair partial roots here; later run-level quarantine is separate.

A live cancellation observed after the durable `prepared -> executing` CAS but before calling `mkdirat` is treated exactly like a crash at that point: persist/cached result `ipc_result_indeterminate`, operation and run lease remain fenced, and no no-effect receipt is fabricated because no syscall errno exists. Cancellation before `prepared` returns `operation_canceled` with no ledger or filesystem effect. After `prepared` but before `executing`, retain the prepared record and lease; same-key retry may resume it exactly once. Once the syscall is entered, cancellation follows its observed syscall outcome; after successful mkdir it is `io_uncertain` and fenced. Replaying the same key returns the cached durable result.

Deterministic `mkdirat` errno policy (all rows except `EEXIST` require a no-follow absence witness from the pinned anchor before a terminal no-effect receipt; otherwise use `indeterminate`, retain the lease, return `ipc_result_indeterminate`):

| errno | No-effect receipt | Operation state | Run lease | Returned code |
|---|---|---|---|---|
| `EACCES`, `EPERM`, `EROFS` | `run-root-create-effect-absent-v1` | `abandoned` | Hold until durable run-terminal transaction | `verified_io_failed` |
| `ENOSPC`, `EDQUOT`, `EMLINK`, `ENOMEM` | same | `abandoned` | Hold until durable run-terminal transaction | `verified_io_failed` |
| `ENOENT`, `ENOTDIR`, `ELOOP`, `EXDEV`, `ENAMETOOLONG` | same | `abandoned` | Hold until durable run-terminal transaction | `verified_path_invalid` |
| `EINVAL` | same | `abandoned` | Hold until durable run-terminal transaction | `verified_policy_mismatch` |
| `EEXIST` | `run-root-create-collision-v1`; never query target | `abandoned` | Keep fenced/held; reject new epoch | `verified_policy_mismatch` |
| `EIO`, `EINTR`, `EFAULT`, or any unlisted errno | none | `indeterminate` | Keep fenced/held | `ipc_result_indeterminate` |

This table is exhaustive for the supported Linux `mkdirat` outcome contract. A deterministic errno with an absence witness proves only that this request created no entry; it does not clear an earlier unrelated run-level quarantine. `EEXIST` never proves absence.

The docs/43 §8 amendment defines `run_root_create/v1`, the three typed evidence sources, and the unique permanent epoch tombstone, using the existing `OperationEvidenceReceipt` rather than a parallel receipt. Its exact source schemas are: operation key `(run_epoch, request_id)` plus a permanent unique `run_epoch_allocations` primary key independent of request ID; required `business_operation_id` is the 16 raw bytes decoded from `run_epoch`, and immutable bindings `(session_key_hash, principal_ref resolved by Reaper, gateway_generation, gateway_process_identity, owner_generation, schema_version, payload_digest)`. Completed source identity is `[anchor_dev, anchor_ino, anchor_mount_id, root_dev, root_ino, root_mount_id]`; payload is `[run_epoch, request_id, gateway_generation, gateway_process_identity, worker_uid, worker_gid, mode=0700, access_acl_absent, default_acl_absent, anchor_uid, anchor_gid, anchor_mode=0710, anchor_access_acl_absent, anchor_default_acl_absent, child_fsync=true, anchor_fsync=true]`. Collision source identity is the pinned anchor tuple and payload is `[run_epoch, request_id, gateway_generation, gateway_process_identity, syscall=mkdirat, errno=EEXIST, target_opened=false]`; the existing target is never opened or queried. The no-effect source identity binds the anchor tuple plus `absent_witness=["absent",anchor_platform_identity,epoch_basename_digest,"ENOENT"]`; payload is `[run_epoch, request_id, gateway_generation, gateway_process_identity, syscall=mkdirat, errno_class, absence_verified=true]`. `gateway_process_identity` is exactly Linux `[pid,starttime_ticks,pidns_dev,pidns_ino,cgroup_mount_id,cgroup_inode]`; worker UID/GID come from protected Reaper config bound into the run lease. Source identity, payload, and evidence digests use the docs/43 domain-separated deterministic-CBOR formulas; use fixed positive/negative vectors in docs/43 §8.1 before code. EEXIST yields `abandoned` with the no-effect collision receipt and cached `verified_policy_mismatch`; deterministic errno mappings and lease release follow the exhaustive table above; ambiguous outcomes are `indeterminate` and return `ipc_result_indeterminate`. Missing, duplicate, inconsistent, or unreadable evidence cannot reach a terminal result.

### Filesystem trust boundary

The identity recheck immediately before mkdirat narrows but cannot eliminate the race between checking the parent/name binding and the syscall. This filesystem-effect layer trusts the Reaper code and does not claim safety against a compromised Reaper; its capabilities and pinned FDs can affect the exposed pilot data. It does require that concurrent Gateway and Worker processes cannot rename or replace the anchor or its parent. The external launcher/host control plane must enforce that peer boundary through namespace ownership and credentials, and native adversarial rename tests must verify it. A compromised Reaper remains within the pilot-data impact boundary described above, but violates this allocator's trusted-code assumption; a stronger defense against that threat needs a separate privilege design.

## 4. Logs

Events are sent through a connected `SOCK_SEQPACKET` channel to a trusted host logger outside the Reaper namespace; the logger validates the fixed event schema and appends to the protected host log. Before use, the client requires the connected socket peer kernel `SO_PEERCRED` PID/UID/GID to equal the expected identity supplied by trusted launcher configuration; it fails closed on mismatch, and the expected identity must never come from Gateway IPC. Timeout and cancellation remain distinguishable to the caller, while any ambiguous exchange poisons the channel and cannot be retried on that FD. Reaper holds no FD or path to the underlying log and cannot truncate prior events. Use exactly docs/42 §9's strict JSON schema, its existing `pilot_host_reaper` module, `bootstrap.start`/`bootstrap.finish` event names, enum values, and required null/zero fields. bootstrap.start/bootstrap.finish remain the operation start/terminal pair. The allowlisted run_root_dispatch_intent and run_root_dispatch_committed values are intermediate events under the same operation_id, not replacements or extra operation pairs; logger ACK must echo the exact trace_id, process_id, operation_id, and event tuple. The pair shares the durable operation's opaque `operation_id`, which is the correlation key to its ledger record; do not add fields or log raw epoch, path, UID/GID, process command line, request secret, grant bytes, OS error text, or HMAC material. Reason codes use only the docs/42/docs/44 allowlists: for example `ipc_request_conflict`, `ipc_result_indeterminate`, `operation_canceled`, `io_uncertain`, `restart_required`, or `verified_io_failed`. No new reason string is introduced by this phase.

The transport wraps, but does not alter, the docs/42 event schema. Each outbound UTF-8 JSON envelope is one `SOCK_SEQPACKET` record with exactly these fields in this order: `version` (integer `1`), `delivery_nonce` (fresh 32-character lowercase hex CSPRNG value per send), `event_sha256` (64-character lowercase hex SHA-256 of the canonical UTF-8 JSON bytes of `event`), and `event` (one object conforming exactly to the docs/42 schema). The ACK is one UTF-8 JSON object in one record, with exactly these fields in this order: `version` (integer `1`), `trace_id`, `process_id`, `operation_id` (each exact 32-character lowercase hex copied from the event), `event` (exact event enum copied from the event), `delivery_nonce`, `event_sha256` (copied from the envelope), and `status` (`accepted|rejected`). No length prefix, trailing bytes, duplicate/unknown field, alternate JSON encoding, ancillary data, or second ACK is accepted. One sender call emits one envelope and reads exactly one ACK; both records are capped at 16 KiB. ACK matching is single-flight on the channel and compares the full tuple, nonce, and event digest. `delivery_nonce` is the exact 16-byte outbox ACK correlation (32 lowercase hex on the wire) persisted by `AcknowledgeOutbox`; there is no second correlation field. A retry uses a fresh nonce only after the previous socket attempt is retired at EOF and its handler is drained, and only while the same original Reaper process identity and Logger registration remain live. The transport accepts only the ACK for its current attempt; a delayed ACK from a retired channel is discarded and cannot acknowledge a later attempt. Any mismatch, repeated/stale nonce, rejected status, truncation, malformed record, or channel error fails the call. The receiver reads with `recvmsg`, checks both `MSG_TRUNC` and `MSG_CTRUNC`, parses every received control message, closes every installed `SCM_RIGHTS` FD before rejecting the record, and rejects all ancillary data. The sender uses a monotonic 2,000 ms deadline and checks context cancellation while polling. It does not retry, pipeline, or reconnect an ambiguous critical event; the caller applies the pre/post-side-effect outcome mapping in §2. Socket ownership and peer authentication are established by the trusted launcher before the connected FD is handed to Reaper; this transport does not authenticate a pathname or accept a caller-supplied socket address.

For the prepared `run_root_dispatch_intent`, the ledger durably stores the canonical event bytes, trace ID, originating process ID, and event digest before the first send. A transport timeout or socket loss ends that call without CAS. One application-level resume may resend the exact persisted bytes with a new delivery nonce only after the prior channel handler is retired and while the same original Reaper identity and Logger registration remain valid; it is not concurrent or in-flight retry and is not a new event. If Logger restart invalidates registration or the Reaper is reaped, a replacement recovery-only Reaper cannot replay this event or dispatch the filesystem effect; preserve the held reservation for separately reviewed offline recovery. The host logger deduplicates only the events explicitly guaranteed unique and replayable by this SDD: `run_root_dispatch_intent` and `bootstrap.finish`, keyed by `(operation_id,event)`. An identical canonical event digest returns `accepted` with the current nonce and does not append another JSONL line; a different digest for that key returns `rejected`. Other events, including repeatable `barrier`, are appended per delivery and are not automatically deduplicated. This lets the surviving original Reaper resume a prepared operation using the persisted original event identity while preserving docs/42's meaning of `process_id` as the process that first emitted the event. The logger's durable JSONL is the idempotency index: on startup it strictly scans complete canonical records and rebuilds the key/digest map; a torn record, duplicate key for a deduplicated event, or conflicting digest fails logger startup closed. It appends one canonical line and syncs it before acknowledging, so a crash after append but before ACK is recovered by scanning and cannot duplicate the line. Host logger Write/Sync now runs through the bounded writer and has passed logger-side ext4/XFS acceptance. The unimplemented deadline and recovery gate is end-to-end across trusted launcher, listener, and the CreateRunRoot caller/outbox path; no product-level two-second guarantee is claimed. If Reaper receives a finish ACK but crashes before durably marking the outbox row acknowledged, a recovery-only or replacement Reaper cannot deliver the event under a new process identity. Preserve the committed finish row and lease as recovery-required until a separately reviewed delivery-recovery protocol is approved; Logger deduplication alone does not authorize a new sender. `run_root_dispatch_committed` is never replayed: any uncertain ACK after its CAS fences the run and prohibits mkdirat.

The terminal `bootstrap.finish` payload and its outbox row are committed atomically with the operation/allocation/run-terminal receipt and states in the docs/43 terminal transaction. The product control ledger refines logical unsent/acknowledged delivery into `ready|send_authorized|acknowledged|suppressed` as specified in docs/51; delivery state cannot change or roll back the ledger terminal state or run lease. Reaper sends the exact stored finish bytes with a fresh delivery nonce and marks the outbox acknowledged only after the matching logger ACK. If sending or ACK fails, Reaper returns `verified_io_failed`, exposes no root handle/capability, and leaves the terminal ledger and lease exactly as committed; the same still-live original Reaper may resume exact-byte delivery once on a fresh channel only if its original Logger registration remains valid and the preceding handler reached EOF. A reaped Reaper or Logger restart invalidates that authority; recovery-only Reaper cannot deliver, and the result remains recovery-required pending a separately reviewed delivery-recovery protocol. Logger idempotency ensures append-before-ACK recovery adds no duplicate line. This is the sole post-terminal critical-log exception to §5's indeterminate rule; pre-terminal dispatch ACKs remain transition gates. If the terminal transaction itself fails, no finish outbox event is sent.

The current store slice accepts only a launcher-preopened regular log FD opened `O_RDWR|O_APPEND|O_CLOEXEC`, owned by its effective UID/GID, exact mode `0600`, and exclusively `flock`ed. Startup reads each canonical JSONL record with a strict 16 KiB bounded line reader and fails closed on torn, oversized, noncanonical, duplicate, or conflicting dedup records. The trusted launcher registers each live run with an opaque context ID, its kernel PID/UID/GID, and the matching opaque event `process_id`; the store binds one token bucket to that registration and rejects mismatched event process IDs. Registration is single-use while live: duplicate IDs and concurrent packet handlers are rejected, release fails while a handler is active, and a handler holds the exact registration object until return. This prevents release/re-register from rebinding an old handler to a new run. The trusted launcher still must close the endpoint before releasing it. At most 16 live registrations are allowed; a completed run releases capacity for the next registration. The rebuilt idempotency index is capped at 65,536 keys, which is a hard pilot lifetime ceiling (at most 32,768 runs if each consumes one dispatch-intent and one finish key). New keys beyond the ceiling receive a rejected ACK without append or map growth; no automatic truncation is allowed. An explicit audited log/index rotation policy is required before admitting more than the pilot ceiling. The bounded global writer queue and ACK waiter limits are implemented and ext4/XFS verified; listener accept/registration orchestration and trusted launcher handoff remain absent.

## 5. Tests and acceptance

The reviewed acceptance matrix in `review/pilot-run-root-bootstrap-manifest.json` is hash-bound to this SDD and the docs/42-44 contracts; keep its stable parent/leaf IDs synchronized with implementation and evidence. Fake ledger/native tests cover typed peer and generation binding, PID identity change, request/principal/generation conflict, CAS loss before create, duplicate request, EEXIST, EACCES, ENOSPC, unsupported filesystem, default ACL, mount/device mismatch, UID/GID/mode drift, anchor binding drift, errno table row per class, pre-prepare cancel, post-prepare/pre-CAS cancel, post-CAS/pre-syscall cancel, post-create cancel, child/parent fsync failures, close-unknown, cached terminal response, and zero worker spawn/catalog/HTTP success before durable completion. Invalid epoch values (including empty, dot entries, separators, NUL, uppercase hex, Unicode, and wrong length) must cause zero ledger mutation and zero syscalls. Permission tests prove the worker can traverse the anchor to its own known epoch but cannot list or mutate anchor siblings; Reaper rejects an anchor with wrong owner, mode, or ACL.

Native Linux tests run on dedicated ext4 and XFS. A helper Reaper process pauses at named barriers after `prepared`, after `executing`, after `mkdirat`, after `fchmod/fchown`, after child `fsync`, after anchor `fsync`, immediately before the atomic terminal transaction, and immediately after that transaction but before `bootstrap.finish` ACK. For crash barriers, the parent kills/reaps the original Reaper and starts only the recovery-only session authorized by docs/47. After `prepared`, prove zero filesystem effect, but keep the reservation and lease held: recovery-only code cannot claim or continue business work. Same-process reconnect/retry is a separate case and requires the original Reaper and Logger registration to remain live. A hard kill after durable `executing` but before entry to `mkdirat` has one oracle: operation and run lease remain `indeterminate`/fenced, no absence receipt is fabricated, and same-epoch retry, reopen, worker spawn, or new epoch admission is forbidden until separately reviewed quarantine.
