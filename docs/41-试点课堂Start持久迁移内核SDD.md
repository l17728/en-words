# 试点课堂 `lesson.start` 持久迁移内核 SDD

状态：设计门已通过，可实施隔离 test-only slice；实现和验收尚未完成。本文是 `docs/33` 原子提交合同与 `docs/36` created-only schema 的窄实现切片。它不交付可用课堂，也不开放任何普通产品入口。

## 1. 问题与目标

现有试点 store 只严格支持 `created` 基线；created audit 会拒绝非空 transition receipt、active command、outbox、completion job 等后继事实。直接“写第一条状态”或放宽 audit 会使已存创建事实与运行态协议脱节。

本片仅验证一条可信 `created → lesson.start` 迁移。`started` 是领域术语；现有 v2 数据库仍写 `lifecycle=active`，不改 DDL 枚举。Teacher 规划在事务外形成不可变候选；一个固定 SQLite writer 事务核验身份、授权、版本和命令指纹，并原子提交 active checkpoint、tx-bound 工具审计、transition receipt 与有序 outbox。只有确认 COMMIT 成功后，调用方才能发布成功；outbox 本片不消费，因此不会发声。

## 2. 明确不做

- 不接默认 `App`、旧 `Hub/Room`、Scheduler、普通 HTTP/WS/工具路由、后台 Timer 或产品 UI；不改默认 startupModels 或自动迁移。
- 不发送 TTS、调用模型/网络、采音或执行 outbox；不创建答题机会/claim，不处理回答、暂停、结束或结算。
- 不开 pilot 创建或迁移接口；仅使用独立临时 SQLite 和仅测试可达的 harness。独立文件/数据库本身不构成授权或生产隔离证明。
- 不修改教学规则。首启候选只来自现有 Teacher 决策表和工具 schema；Agent 不得提供任意工具名、SQL、Room 状态或任意 machine JSON。

## 3. 身份、候选与事务合同

本片仅test-only adapter可调用，使用独立SQLite中临时生成的用户A/B及凭证；该fixture为全新账号、无任何历史lesson，仅创建一条lesson reservation，所以其`lesson_ordinal=1`是服务端可验证的首课事实。存储事务再次断言该owner/student恰有当前这一条pilot reservation且无先前完成/活动pilot lesson；不接受客户端“首课”字段，也不声称查询了隔离DB外的真实历史。middleware先验证人类actor为该lesson owner对应的active student，再由服务端生成受信teacher task capability（role=`teacher_agent`、trigger=`classroom_event`、绑定lesson及expiry）；二者是不同身份。客户端提交的student_id/role/task_id不作授权事实。Store从持久identity表`store.User.Nickname`读取昵称，验证principal/owner/status后规范化并冻结在私有`VerifiedPilotStartActor`中；API不能构造或JSON解码此类型。新命令及尚未提交bundle的重试须重核规范昵称；昵称变化使旧bundle失效并要求新command_id。Receipt replay先核当前登录、owner及active账号，再按lesson+command查回执；命中时不检查task expiry或当前昵称，返回原receipt以保证重启恢复。新命令提交仍须核task capability未过期、账号状态、owner及pilot reservation。测试adapter、fixture账号及路由不得编入默认server产物。非首课一律`not_supported`拒绝，不退化成T-02；真实产品task principal与历史课程查询另属后续设计。

创建课已冻结的words/config/revisions/content fingerprint是权威输入。Start不因管理员后来修改live配置或词条而stale，也不得重新读取它们来重造候选；候选必须使用checkpoint中的原冻结事实。当前账号被停用、owner/mode/schema损坏、lesson退休、checkpoint/generation冲突才拒绝。`Machine.Start` 的业务后置状态固定为phase=`show_word`、lifecycle=`active`、StartedAt=`start_command.created_at_ms`，并只附加 `ActShowWord`；它不代表已播放、已生成答题机会或执行完整 `teacherLifecycle`。

规划分两段且不调用模型/网络：Store完成授权预检后构造只读PlanningContext，并从持久冻结facts、规范昵称、lesson/command和expected版本计算planning_fingerprint；它不含Agent待生成的say，但覆盖所有Planner输入。随后sidecar先持久记录attempt_started，再调用Agent确定性T-01渲染与Teacher决策；Agent结果、冻结show_word组成最终canonical command fingerprint。必须先同步plan_ready HMAC绑定最终计划，然后按tool_started→Registry调用→tool_result同步的顺序执行每个本地工具；不读取/修改活动Room。ordinal为受信server事实，不扩展当前agent.TeacherInput公共类型：adapter先验证ordinal=1，再调用TeacherInput{Event=lesson_started,TotalWords=frozenWordCount,StudentName=normalizedNickname}；其它ordinal不得进入T-01。Agent新增TeacherAgent.RenderLessonStartT01(in TeacherInput) (LessonStartUtterance,error)，要求Event=lesson_started、TotalWords>0、StudentName已规范化，结果含Category,Text,TemplateID,Source。方法内部调用Bank.RenderExactID("OP-1", vars)；该Bank API只做固定ID/category验证、占位符替换与安全校验，不运行随机口语化/称呼变体；adapter禁止直接访问Bank或自行拼话术。模板缺失/渲染失败走方法内固定fallback“我是叮当老师，{name}，我们开始学单词。”并标记Source=fallback。已提交receipt replay不检查昵称；新command和未提交bundle重试重核规范昵称。OP-1/fallback均须含叮当老师自我介绍及昵称，最终文本1–60 rune，否则失败。Golden：昵称小明、词数50时category=open,text=我是叮当老师！小明，今天我们搞定 50 个新单词，准备好了吗？；不能声称上次成绩或能力。第二项为Machine.Start产出的ActShowWord经TeacherAgent.PlanEffects映射为classroom.show_word调用。命令与show_word outbox携带该lesson冻结的第一词ID、词面和有序中文释义数组；Registry工具参数仅传固定index=0，审计Args只保存bytes与固定映射元数据，冻结词内容由active checkpoint/receipt/outbox关联验证且不写入审计Args；释义非空且每项trim后非空，保存/展示顺序保持原样，提交前按冻结词ID、词面、释义逐字节验证，绝不live lookup。两个工具均需Registry验证并生成结果；未知工具/effect、额外payload、重复/乱序和越界均拒绝。决策表与工具schema必须在执行前校验，不能信任模型输出。

### Bundle 与失败尝试的恢复补充（优先于§3概括性重试描述）

Coordinator顺序以“执行时序勘误”为唯一合同：per-lesson single-flight、只读owner/receipt/CAS预检、sidecar intent sync、事务外Planner/Registry、bundle cache、writer内二次核验与提交。Registry只运行纯、本地、有界handler，禁止网络/模型；所有工具执行、sidecar写入和Sync均在writer事务外。可证实rollback后的重试必须同进程、同command/task并复用相同bundle digest、decision/task ID、Registry audit及budget；single-flight防并发重复。case级缓存最多32项，满时fail closed且不得驱逐pending/unknown项。

sidecar case目录与SQLite由测试监督器创建并跨harness子进程重启复用。威胁模型限定为单一可信本机监督器OS账号，排除该账号、管理员、内核或宿主机被攻陷；其他主体均不得读取或写入case/DB/WAL/SHM/sidecar/key。监督器首先以OpenVerified校验并打开owner-only case catalog本身；catalog ACL/owner/file-ID/格式/Sync任一异常时全局fail closed，不创建或打开任何case。catalog首次创建必须在受保护父目录中以CREATE_NEW/O_EXCL创建、Flush+Sync文件并Sync父目录；之后只允许通过已验证handle追加记录并Sync，不原子替换、不截断、不改名，故同一catalog的file ID在其生命周期内稳定。预期身份锚点是本次监督器进程持有的已验证catalog handle及其file ID；重启时通过受保护父目录ACL/owner、固定路径、单链接/非reparse属性及新打开handle的file ID建立新进程锚点。外部主体无法在该威胁模型内替换该目录项；同账号攻击不在保证范围。全局catalog锁是跨进程OS排他锁，使用已验证catalog handle对应的文件锁原语；持锁期间重新读取并校验当前记录链、分配max_generation+1、完整追加一条frame并Flush+Sync，最后释放锁。所有catalog读取快照及写入均持该锁，避免读取半条记录。per-case生命周期锁与全局锁的顺序固定为先case锁、后catalog锁；任何持有catalog锁的代码禁止等待/获取case锁；catalog锁只覆盖记录链读取、generation分配、单条追加与Sync，不覆盖Planner、DB事务、文件删除或网络/模型操作。每条append记录均为有界长度、严格schema、单调generation及完整帧标记；记录追加并Sync成功后才可确认状态迁移。启动时完整读取并验证记录链，任意格式/序号/截断/Sync不确定错误均全局fail closed，不回退到旧状态、不丢弃隔离事实。创建、启动Coordinator、任何receipt处理（包括命中）及每次DB/sidecar/key open之前，都先在catalog查验该随机case ID状态并用OpenVerified原子安全打开case目录与目标文件，校验canonical路径、owner、ACL/mode、reparse/link与file ### Case 打开与清理的双阶段授权

case open/receipt/restart 必须采用两阶段 catalog 授权，避免旧快照与 cleanup 竞争：①在全局 catalog 锁内读取并校验记录链、对目标 case 做乐观状态检查，随后释放锁；②取得该 case 的 OS 生命周期锁；③重新取得全局 catalog 锁，重读完整最新记录链并再次验证 case 状态，释放 catalog 锁；④仅当第二次检查仍允许访问时，才执行 OpenVerified 并打开 DB/sidecar/key。case OS 生命周期锁必须从步骤②持续持有到本次操作全部完成、SQLite连接及DB/sidecar/key句柄全部关闭；不得仅在授权或OpenVerified后释放。cleanup也持同一锁贯穿quarantine记录及Sync、所有文件/目录删除、父目录Sync和永久tombstone记录及Sync；失败则依照已持久状态fail closed后释放。任何路径在case锁释放后都不得继续使用旧状态快照。cleanup、Start、receipt查询、进程重启恢复统一遵守此序列；case锁持有期间写catalog也必须用同一全局锁。不同case的业务工作可并行，只有catalog短临界区串行。catalog锁不得包围Planner、Registry、SQLite事务或文件删除；catalog锁持有者不得等待case锁。

## 4. 状态、codec 与审计边界

生命周期分派拆为全库完整性与逐课校验，不能把旧created-only的全库空表假设套到混合课堂。每个现有读写facade均先运行`auditPilotDatabaseIntegrityTx`，保留旧`auditPilotDataTx`中的legacy bridge/runtime兼容性验证、未迁移记录拒绝、schema与逐表`PRAGMA foreign_key_check`；仅将其全库created-only后继表空检查替换为全库结构完整性验证。随后对每条reservation调用`auditPilotLifecycleTx(tx, lessonID)`：created走lesson-scoped的`auditPilotCreatedLessonTx`与creation replay verifier，仅要求本lesson后继receipt/claim/command/outbox/job为空；active走`auditPilotActiveLessonTx`验证本课codec/receipt/audit/outbox。全库层仍检查未知/重复/孤儿事实，不能因A active而拒绝B created。每个active receipt必须通过`audit_logs.TraceID=receipt.decision_id`精确关联两条唯一say/show_word audit；每条pilot audit Args必须含普通工具永不生成的保留键`pilot_marker="pilot-audit-map/v1"`；全库凡含该marker均必须且只能匹配一条receipt，孤儿可被识别；固定marker+effect_index必须匹配对应outbox的`decision_id+effect_index`，outbox lesson/student/checkpoint version必须与同一receipt一致；say payload.text逐字节等于active `room_facts.teacher_text`；receipt独立校验lesson/command/decision/kind/version及outbox_count，show_word payload的word_id/word/ordered meanings逐项等于同一checkpoint `frozen_words[0]`，effect kind/index与receipt固定序列一致。拒绝跨课、跨学生、孤儿、重复、额外或缺失行；非pilot普通审计不受此分类影响。该分派必须覆盖`inspectPilotSchema`、`migratePilotSchema`、创建nonce replay、Start提交/receipt读取、创建审计及所有Pilot facade读写，旧全created数据库保持严格语义，同时允许A active+B created及双学生并发。Start只能从created到active；DDL仍使用schema v2，不加列。若实现需要加字段则另起schema版本设计。

新增严格active codec；`started`仅为领域/event术语，不写数据库lifecycle。active时恰有一条`kind=lesson.start` receipt（lesson+command唯一、decision唯一、from_version=1,to_version=2,logical_revision=0），`result_json`严格为`{"result":"queued","audit_trace_id":"<decision_id>","outbox_count":2}`；public StartReceipt只返回固定result及command ID，不返回request_fingerprint/候选内容摘要。工具审计用现有`audit_logs`列同事务写入；test DB初始化与生产相同DDL；恰两行，Tool为say/show_word各一，TS/DurationMs/OK/Result必须与task-local Registry原始成功AuditEntry一致（TS为工具调用时间、OK=true、Result=`ok`、Risk=`low`、ActorType=`agent`、ActorID=taskID、ActorRole=`teacher_agent`、TraceID=decisionID）。Registry原始Args必须为`{"bytes":N}`；持久化前按固定`pilot-audit-map/v1`映射为Args精确对象：say `{"bytes":N,"schema_version":1,"scope":"teacher_agent","pilot_marker":"pilot-audit-map/v1","effect_index":0}`、show_word 同结构`effect_index`:1。N是工具schema参数字节数，未知/额外字段拒绝。该映射版本、scope、保留pilot_marker与effect序号因此有持久审计证据；普通工具Registry禁止生成此marker，全库据此识别孤儿pilot audit，不改既有audit_logs DDL。事务插入前必须断言该TraceID记录数为0，插入后恰两行且工具各一，否则回滚。独立verifier根据映射版和receipt逐向验证两条audit及两条outbox均一一对应，也检查audit/outbox没有孤儿receipt；不声称DB层唯一约束。outbox恰有2行、effect_index=0..1连续、`kind`严格为`say`与`show_word`。say payload是固定typed DTO `{"type":"say","category":"open","text":"<rendered text>"}`；show_word payload是`{"type":"show_word","word_id":<id>,"word":"<word>","meanings":[<frozen ordered strings>]}`。它们是Registry返回结果的类型化归一，不是Registry输入参数；status=`pending`、attempt_count=0、claim/lease全NULL、`next_attempt_at=start_time_ms`、`created_at=start_time_ms`。answer_claims、active_commands、completion_jobs保持为空；额外/缺失/孤儿/重复/篡改均fail closed。verifier同时将say payload.text逐字节对比active room_facts.teacher_text；并从receipt字段、checkpoint.started_at、冻结word及room_facts.teacher_text重建§3 canonical command fingerprint，逐字节校验receipt.request_fingerprint；receipt另独立验证同一lesson/command/decision/kind/version及outbox_count，将show_word逐字段对比冻结words[0]。不可变创建事实与生命周期审计分开校验；创建nonce重放/恢复共同使用生命周期分派。

失败工具尝试审计与成功生命周期审计分账：sidecar仅保存固定role/trigger/scope/risk、工具名allowlist、result_class、HMAC及时间；task/trace仅密钥HMAC关联，不存明文Actor、TraceID、task ID、原始Args或课堂内容。字段由Store验证的capability和Registry AuditEntry派生，错误字段fail closed。成功时才将Registry task-local auditor内存审计映射至DB audit并与receipt/outbox同事务提交；失败不写audit_logs。bundle完整但事务rollback时工具尝试仍在sidecar，DB生命周期行全部回滚。

Outbox 只记录计划效果及稳定序号/幂等键，不在本片派发。恢复只读回执和 checkpoint，不自动重播媒体或执行工具。未来 consumer 必须另有独立设计，核对授权 generation、效果 ACK/取消和重放 fencing。

## 5. 可审查执行边界

## 108. 2026-10-17 sidecar recovery and capacity amendment

The JSONL sidecar has a 1 MiB total limit and an 8 KiB per-event limit. Append must check the existing file length before writing; an append that would exceed the replay limit fails closed without writing and marks the current coordinator degraded. This in-memory flag is not restart-persistent and is not sufficient authorization state. The catalog must durably record a case as open/recovery-required before any sidecar append or database write. A case may be considered clean only after its terminal/recovery disposition has itself been durably cataloged. Before releasing the per-case lifecycle lock after a capacity/integrity failure, the supervisor must durably mark the case quarantined; if that write or sync fails, the supervisor must fail closed globally and retain the lock while alive. If the process crashes before quarantine persists, startup must treat every durable open/recovery-required catalog entry as unresolved and prohibit fresh commands; it must not infer health from an otherwise-valid old sidecar or recreate a missing chain. Startup consults and validates catalog state before opening any case database or sidecar. An unresolved/quarantined case may only use the separately authorized receipt-first recovery or whole-case cleanup path; it must never accept a fresh command, truncate, rotate, or silently start a new chain. Recovery opens an existing sidecar only: a missing or zero-length file is an integrity failure. Only first-time initialization of a supervisor-verified new case may create the sidecar with exclusive-create semantics. POSIX creation syncs the parent directory. Windows parent-directory durability and ACL verification remain mandatory supervisor integration gates; the test helper does not claim to implement them.

`tool_started` without a durable `tool_result` is an unresolved external effect and must recover as `pending_unknown`; it cannot be converted to `terminal_failed` or `not_committed`. Likewise, `commit_unknown` and `rollback_proven` are event/result classes reserved to their matching transitions and cannot be carried by `terminal_failed`. Terminal failure is legal only after the applicable side effect is known, with a deterministic non-success result. These transition rules are covered by the isolated kernel tests; coordinator-level restart/quarantine behavior and the Playwright pilot harness remain unimplemented integration gates.

## 109. 2026-10-19 catalog journal wire format and state machine

This section freezes the catalog format before supervisor implementation. It does not claim that a catalog or supervisor exists in the repository. The catalog is an authorization journal, not a secret store or an HMAC-authenticated source of truth; its integrity boundary is the verified owner-only handle, OS ACL/mode, and trusted-supervisor threat model in §42. CRC detects torn/corrupt frames only and is not an authenticity check.

### 109.1 Record and frame

The catalog is one append-only regular file with a fixed identity for its lifetime. A file is either absent and created exclusively by first-time supervisor initialization, or already present and fully validated; an empty existing file is invalid. Each record payload is canonical UTF-8 JSON (ASCII-only values, no BOM, no whitespace/newline, fixed field order, no duplicate/unknown keys, no nulls): `{"schema_version":1,"generation":N,"case_id":"<32 lowercase hex>","state":"<enum>"}`. `generation` is a positive base-10 integer with no sign or leading zero; the JSON encoder emits the four fields in the shown order and no optional escaping is needed because every string is constrained to ASCII. The allowlist is exact. Do not persist paths, usernames, lesson/student IDs, command IDs, fingerprints, keys, tokens, free-form errors, or caller-provided values. Generation starts at 1 and increments by exactly one across the entire catalog, including records for different cases; integer overflow is a global integrity failure. Case IDs are 16 bytes from the OS CSPRNG, lower-case hex, and never reused, including after deletion.

Each frame is binary and big-endian: 4-byte magic `DWC1`; uint32 payload length; payload (1–256 bytes); uint32 CRC-32C/Castagnoli of the payload; repeated uint32 payload length; 4-byte trailer `1CWD`. There is no padding. A catalog is valid only if it is an exact concatenation of complete frames, each payload decodes and re-encodes byte-for-byte canonically, lengths agree, CRC matches, generations are contiguous, and each case follows §109.2. Maximum catalog size is 16 MiB and maximum frame count is 65,536; exceeding either is a global integrity failure. Compaction/replacement is not defined; a future bounded-retention format requires a new reviewed protocol and cannot silently discard tombstones.

Every supervisor startup first acquires a persistent OS `catalog.bootstrap.lock` under the protected supervisor root through an OpenVerified handle. The lock root/file has owner-only ACL/mode and stable identity; it is created exclusively if absent, is never unlinked/replaced, and startup contenders wait on its cross-process lock. While holding it, startup verifies or initializes the catalog; no other startup may inspect the catalog during first-frame creation. For an existing catalog, hold the global catalog lock continuously across full-chain replay, catalog file-ID/identity validation, file Sync, and parent-directory Sync. On a missing catalog, scan the fixed case root and per-case lock root for any case artifacts before allowing explicit first-run initialization; the expected permanent bootstrap lock is excluded. Any residual case directory/member/per-case lock with a missing catalog is global integrity failure. Release the catalog lock, then the bootstrap lock, before acquiring any case lock. Normal case operations never acquire the bootstrap lock. Thus there is no lock cycle: bootstrap may wait for catalog, but neither bootstrap nor catalog holders wait for a case lock.

Normal append protocol under the verified-handle global OS lock: seek/read/validate the entire current chain; derive the next state from its latest per-case state; append exactly one complete frame; Flush+Sync the file; then acknowledge. A successful file Sync is the transition's durability linearization point. Initial catalog bootstrap is the sole exception to ordinary append: while holding the bootstrap lock, `CREATE_NEW` creates the catalog and writes its first complete `provisioning` frame for the first random case ID before syncing the file and then the parent directory. The case directory/DB/sidecar/key and stable case lock are created only after this first frame and parent directory are durable. This avoids a valid-but-empty catalog state; an existing empty catalog is corruption. Any short write, write error, Sync error, invalid old chain, or uncertain durability poisons the supervisor instance globally. It must not retry the append, truncate, or answer success. On restart, a complete valid frame is authoritative whether or not its prior HTTP response reached a caller; callers converge by reading catalog state. There is no durable "acknowledged" bit and the protocol makes no attempt to infer response delivery. A partial final frame is corruption and fails closed. A later explicit repair tool, if ever designed, must preserve the original file as evidence and is outside this protocol.

### 109.2 States and legal transitions

`provisioning` is appended before any case directory, DB, sidecar, or key is created. Once all initial files and permissions are verified and durable, append `ready`; only `ready` permits the first start attempt. Before the first sidecar append or any DB write for a start, append `open_recovery_required`. `open_recovery_required` denies fresh commands after restart and remains unresolved until a durable disposition is recorded. Allowed transitions are:

| Current state | Next state | Meaning |
| --- | --- | --- |
| absent | `provisioning` | Reserve a never-used random case ID. |
| `provisioning` | `ready` | Initial empty case is fully created and verified. |
| `provisioning` | `quarantined` | Provisioning failed or its outcome is uncertain. |
| `ready` | `cleanup_quarantined` | Authorized cleanup removes a case that has not started. |
| `ready` | `open_recovery_required` | Start is admitted; recovery obligation begins before side effects. |
| `open_recovery_required` | `committed` | Receipt and all required DB facts were independently verified durable. |
| `open_recovery_required` | `terminal_failed` | A deterministic non-success outcome is proven and no effect is unresolved. |
| `open_recovery_required` | `quarantined` | Integrity, capacity, or durability failure; no fresh command. |
| `open_recovery_required` | `cleanup_quarantined` | Authorized cleanup has durably claimed the case lock. |
| `committed` / `terminal_failed` / `quarantined` | `cleanup_quarantined` | Cleanup starts under the lifecycle lock. |
| `cleanup_quarantined` | `deleted` | All case files are removed and the parent directory is synced. |

All other transitions are invalid, including repeated `ready`, reopening any disposition, moving from `quarantined` to `committed`, and any transition from `deleted`. A `provisioning` case that cannot be verified first transitions to `quarantined`; it cannot skip directly to cleanup. Cleanup from `ready` is allowed only under the lifecycle lock and after proving there is no start attempt or sidecar/DB lesson write. `committed` authorizes receipt-first reads only; it does not authorize another command. `terminal_failed` authorizes only the explicitly designed status/recovery path, not retrying side effects. `quarantined` permits only receipt-first recovery or cleanup as separately specified. `cleanup_quarantined` denies all opens. A cleanup failure leaves this state durable and the case unavailable. IDs in `deleted` remain permanent tombstones.

The supervisor must perform the existing two-phase authorization around every case open: optimistic catalog check, acquire case lifecycle lock, re-read/revalidate catalog under global lock, then OpenVerified. On every startup, while holding the bootstrap lock and global catalog lock across full replay, identity validation, catalog file Sync, and parent-directory Sync, validate all existing state before authorizing any case; failure remains globally closed. First-frame bootstrap reserves `provisioning`; a provisioning-recovery operation may acquire/create the stable case lock and inspect only the exact fixed initial-member allowlist. Concurrent recovery processes must converge on the same atomically created stable lock identity before inspecting members. If all initial members and permissions are complete and durable, provisioning recovery appends `ready`; otherwise it appends `quarantined` and permits cleanup only. It never starts a lesson or invokes Planner/Registry. For an existing `ready` case, the `ready → open_recovery_required` append is performed while holding the case lock and must Sync before sidecar/DB effects. On a known successful commit or known terminal failure, append the matching disposition before releasing the case lock. If this final append fails or has uncertain durability, retain/poison the in-process supervisor and treat the case as unresolved on restart. Recovery may append a disposition only after independently checking the existing DB receipt and sidecar; it cannot infer success from an in-memory flag.

### 109.3 Case scope and cleanup restart

For this isolated harness, one catalog case is one private fixture database and exactly one target `lesson.start` operation. The fixture may contain synthetic users A and B so the browser can verify that B cannot read or mutate A's receipt; only the designated target student has the single lesson reservation described in §3. A case in `committed`, `terminal_failed`, or `quarantined` never accepts another Start command. An explicit retry after a proven terminal failure creates a new isolated case, database, reservation, and fresh IDs; it does not reuse the failed case or repeat its side effects. Different lesson Start operations may run concurrently only in different case IDs. Same-case HTTP operations serialize under that case's lifecycle lock. Sidecar append-mutex concurrency is tested directly at the test-only kernel boundary and does not imply concurrent Starts in one case. These rules supersede earlier broad wording in §§32, 40, 95–97 that could be read as permitting multiple lesson Starts in one case.

The lifecycle-lock object is supervisor-owned beneath a separate protected lock root, keyed by the random case ID, and is not stored inside the removable case directory. The root and each lock object must pass owner-only ACL/mode, link/reparse, and file-identity checks; open the persistent lock through a verified handle and never unlink or recreate it while any process may be waiting. Keep the same lock identity across process restarts and cleanup. This lets cleanup reacquire the same cross-process lock after a crash even if part or all of the case directory has already been removed. `cleanup_quarantined` remains non-openable for every ordinary request. Only the supervisor's cleanup-resume operation may acquire the stable case lock in this state; it verifies and removes only the fixed case members, syncs the parent directory, then appends `deleted`. If the case directory is already absent after a crash, cleanup-resume verifies absence and appends the tombstone. It never opens SQLite, sidecar, or key, never resumes Start/recovery, and never releases the case ID. Any verification, removal, or sync error leaves the catalog state at `cleanup_quarantined` and denies ordinary access.

### 109.4 Acceptance additions

Unit and child-process tests must lock golden frame bytes and CRC-32C, canonical JSON rejection cases, contiguous global generations across interleaved cases, every allowed and forbidden transition, file-size/frame-count limits, and complete-frame crash boundaries. Inject short write, partial frame, file Sync failure, and first-create parent Sync failure; assert no success response and no case DB/sidecar/key open after uncertainty. Restart at every frame boundary: accept a complete valid chain as authoritative state and reject any partial frame globally. Tests must not assert whether a complete frame's earlier response was delivered; they instead query state and converge idempotently. Two processes appending different case IDs must produce one contiguous generation chain. Case-scope tests prove one Start per case, deny a second command in `committed`/`terminal_failed`/`quarantined`, allow retry only by a fresh case with fresh storage and IDs, and run two different lesson cases concurrently. Cleanup-resume tests crash after `cleanup_quarantined` at each removal boundary, then reacquire the external stable case-ID lock, remove remaining fixed members without opening DB/sidecar/key, sync the parent and append `deleted`; also cover an already-absent case directory. A normal request in `cleanup_quarantined` must always be rejected. Windows and POSIX verified-handle/ACL/mode, file identity, and parent-directory durability remain separate mandatory platform acceptance gates. The isolated kernel's existing sidecar tests do not satisfy catalog or supervisor acceptance.

Deterministic crash/fault oracle (run each row in a child process and restart from the same protected root):

| Injection point / disk outcome | Restart result | New case/DB/sidecar/key opens |
| --- | --- | --- |
| Before exclusive catalog create; no case-level lock or case-directory artifacts | Explicit first-run initialization may create the catalog. The permanent bootstrap lock is not a case artifact. | 0 before initialization. |
| Crash after exclusive catalog create but before its first complete frame | Empty/partial existing catalog is global `catalog_integrity_error`; preserve evidence. If the catalog entry itself is absent and no case artifacts exist, only explicit first-run initialization may proceed. | 0 |
| Crash after complete initial `provisioning` frame bytes but before/during file or parent Sync | If the complete frame and entry survive, recover `provisioning` and perform provisioning-only verification; if absent with no case artifacts, explicit first-run initialization; any partial/invalid bytes fail globally. | 0 until catalog recovery succeeds; then fixed provisioning members only. |
| Crash after any strict prefix of a frame, including magic, either length, payload, CRC, or trailer | Global `catalog_integrity_error`; no truncate or retry. | 0 |
| Crash after complete frame bytes but before/during file Sync; complete CRC-valid frame remains | Rebuild from the complete valid chain; use the resulting state, never infer response delivery. If partial/invalid bytes remain, global integrity error. | Only if recovered state permits it; `open_recovery_required` and later states deny fresh Start. |
| Crash after successful file Sync and before HTTP response | Same state as the complete-frame row; caller reads state and converges. | State-gated only. |
| First catalog create: parent Sync failed | Poison current supervisor. On restart, if the complete initial frame remains, startup re-Syncs catalog and parent before provisioning recovery; if absent with no case-level artifacts, explicit first-run initialization; if empty/partial/invalid or case artifacts exist without a catalog, global integrity error. | 0 until catalog validation succeeds. |
| Failure acquiring lock, seek/read/replay, or catalog file identity verification | Current process globally poisoned; no append/ack. Restart independently validates whole file. | 0 |
| Cleanup crash after each member removal / directory removal, while catalog is `cleanup_quarantined` | Cleanup-only resume under stable case-ID lock; missing fixed members count as removed, anomalous links/identity mismatch fail closed; tombstone only after parent Sync. | No DB/sidecar/key opens. |

Write-fault subtests distinguish zero-byte write (old state remains authoritative; no side effect may have started), partial write (restart global integrity failure), full frame plus Sync error (current process poisoned; restart follows the complete-valid-frame oracle), and parent Sync error during initial creation (no case directory/DB/sidecar/key may be created until a complete initial frame and parent entry are durable). Every failure asserts no success response, no in-process append retry, exact poison scope, returned typed error, and expected open counters. Catalog-level illegal transitions and invalid input are rejected without changing bytes or generation; detected on-disk chain/identity errors poison globally. Boundary vectors separately test the framing parser's declared payload-length range 1–256 (payloads of 1 and 256 reach strict-record validation; 0 and 257 fail framing), and the strict JSON record validator's smallest valid golden record plus malformed lengths. The 16 MiB catalog byte limit is an early file-size guard; fixed schema and 65,536-frame limit may make an exactly-full valid journal unreachable, so test the guard with a stat/read seam and verify a valid journal just below the cap. Accept frame count 65,536 but reject another append, and reject generation overflow before writing.

Multi-process tests use named barriers, never sleeps: both writers signal ready before the parent releases them toward the catalog lock; a reader signals it is waiting while a writer is paused after lock acquisition and must observe only the pre- or post-append chain after release. Additional barriers kill a writer while it owns the lock after zero/partial/full frame writes; the parent waits for process exit before starting recovery. Assert contiguous unique global generations, valid per-case state chains, bounded completion, and OS lock release on process death on Windows and POSIX.

Same-case Start contention test launches two child supervisors against one `ready` case. A first named barrier is released only after both processes independently record that their optimistic catalog snapshot said `ready`; a second barrier then releases both toward the stable case-ID lock. Exactly one may append and sync `open_recovery_required`; the loser must acquire the lock, re-read/revalidate the latest catalog state, and return `already_started`/`case_not_ready` before opening DB/sidecar/key or invoking Planner/Registry. Assert one transition, one winner, zero loser side effects, and bounded completion. Provisioning tests race two recovery processes at stable lock creation and assert both observe the same verified file identity; when both verify complete initial members, exactly one `provisioning → ready` frame/generation is appended and the other observes `ready` without a duplicate transition. Also reject an absent catalog when case directories/lock artifacts remain, and reject extra/unlisted/reparse initial members. Test provisioning when the complete `provisioning` frame and directory Sync succeed but the child response is lost: the supervisor's private case handle resolves the same durable case without allocating another ID. Golden frame/CRC and case-ID test vectors use fixed IDs/keys only in test code; production case IDs always come from OS CSPRNG and no golden identifier is accepted by runtime interfaces.

已实现的切片包括：DWC1 帧与 CRC-32C 校验、严格规范 JSON、跨案例单调 generation、状态转移校验、文件/帧上限、启动重放、文件及父目录 Sync、失败时 supervisor 共享 poison、同进程 operation gate，以及 POSIX flock / Windows LockFileEx 适配。`TryLock` 对同进程与跨进程竞争都应立即返回未获取；其回归测试分别覆盖本地竞争与子进程 IPC 屏障。故障测试还覆盖短写、Sync/读取失败、解锁窗口 poison、非法帧和子进程退出上限。

实施复核期间发现并修正两类测试/实现缺口：共享 operation gate 加入后，旧屏障测试等待顺序会死锁，现改为在解锁返回窗口检查 poison，并在后续请求断言 fail-closed；安全复核发现 `TryLock` 本地 gate 使用阻塞 Lock，现改用 `Mutex.TryLock`，并增加有界回归。复核结论和全量 tagged store 测试、Windows 编译结果以 `review/` 中 2026-10-19 记录为准。

## 112. Pilot Supervisor Driver 与密钥边界勘误（2026-10-19）

本节是实现前的设计勘误，优先并废止 §42 中关于“`PRAGMA database_list` 后比较 SQLite 实际 OS file ID”及“将完整 case HMAC key 交给子进程”的旧要求，也废止 §100 中“通过继承句柄/匿名管道将 HMAC key 交付子进程”的旧要求。该权威勘误仅适用于 `docs/42-Pilot隔离运行监督器SDD.md` 描述的 `pilot_e2e` 合成数据监督器；若旧句与本节冲突，以本节为准，不改变 catalog 状态机、receipt 语义或生产安全要求。

仓库当前锁定的 `glebarez/sqlite`/modernc 接口可由 `PRAGMA database_list` 返回 canonical path，但不能提供连接实际 SQLite VFS handle 的 OS file ID。因此该试点只校验 PRAGMA path，并依赖 owner-only 私有父目录、已验证目录句柄/身份、其他 OS 账号不可写及排除同账号攻击的测试威胁模型；不得声称 driver handle binding。若真实部署或更强威胁模型要求抵抗同账号目录竞态，则此试点方案不获准启用，须另行评审可证明 VFS handle identity 的 driver/VFS。

case HMAC key 由可信 Supervisor 保留在本进程内，不进入浏览器或子进程。现有同进程 store 组件可以经内部 capability 使用受限签名操作；若后续拆分签名服务，必须另行规定并评审 IPC 的身份/权限/请求约束，不能直接复制完整 key。HMAC 只保证受信 Supervisor 边界内的 sidecar 一致性，不抵抗 Supervisor/其 OS 账号被攻陷。上述限制均未由当前 catalog 内核实现或测试证明；仍须按 docs/42 的安全、跨进程、平台和 E2E 门验收。
