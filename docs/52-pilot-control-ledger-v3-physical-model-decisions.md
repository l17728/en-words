# Pilot Control Ledger V3 Physical Model Decisions

## Status

Proposal for review before literal v3 DDL. It resolves storage choices required by [docs/51](51-pilot-control-ledger-v3-sdd.md), [docs/50](50-pilot-runroot-product-orchestration-sdd.md), and the identity-resolution amendment in [docs/43](43-Pilot授权幂等与父进程身份绑定SDD.md). This is not implementation approval. The alias registry and all control data stay in protected `operations.sqlite`; the wrapped HMAC keyring is a separate Reaper-protected file/OS credential-store object, and launcher-only browser idempotency bindings stay in its protected journal. Stage A adds a singleton `pilot_launcher_journal_anchor` with the externally signed restore generation; the launcher advances its sequence/hash only after each journal frame is durable and before acknowledging or acting on that event.

## Pilot schema precedence

For the Pilot RunRoot integration, permanent business-key uniqueness includes tenant: `(tenant_id,principal_ref,business_operation_id)`. This supersedes docs/43's generic principal-only uniqueness where the older wording conflicts. The protected launcher journal alone maps browser idempotency keys to immutable operation/epoch bindings; the resident ledger does not duplicate the browser-key hash. Exact resolution and physical column decisions are completed by docs/53 and the reviewed literal DDL manifest.

## Identity resolver storage and lock order

`PilotControlReaper` is the one resident process that opens `operations.sqlite` and owns its OS single-writer lock. It provides principal resolution and all ledger mutation methods over authenticated typed IPC. Per-run Reaper children never open SQLite. The resolver's alias insert is its own committed transaction. User-initiated business RPCs validate current signed admission and resolved principal before opening their transaction; startup, live-run, and recovery control RPCs use the caller classes and exact target bindings in docs/51's authorization table and do not depend on a learner session. The launcher resolves identity before acquiring its journal mutex. No caller may wait for resolver IPC while holding the SQLite writer, launcher journal mutex, or a run-root lock. The resident service serializes ledger RPCs on one controlled writer path.

The fixed admission resolver wire contract is in the docs/43 §2.1 amendment: canonical-CBOR request with fresh 16-byte nonce, signed admission bytes, and 32-byte admission digest; signed canonical-CBOR response binds the same nonce/digest and returns only tenant, principal/session hashes, role, and expiry no more than five seconds later. Only the configured launcher may call this resolver. Each call has a 500 ms deadline; timeout or invalid signature fails closed before journal lookup/spawn. Per-run Reapers use a separate typed ledger-RPC endpoint and must prove the registered process identity plus exact generation/run binding on every packet; service UID alone grants no authority. The resolver checks every retained HMAC key version. The alias table contains no raw immutable ID and cannot be written by launcher or per-run Reaper directly.

## Authorization-fence ordering

The signed admission claims include account `authz_revision`, `authz_snapshot_digest`, and per-session `session_revision`; role and fixture ID remain explicit signed claims. The resident ledger stores the current account state/snapshot, active or revoked session state, and per-fixture grant. `PublishAuthorizationFence` accepts only canonical signed updates from the configured web authorization authority, resolves the stable principal inside the resident service, and applies monotonic revisions idempotently. A restrictive role downgrade, fixture removal, account disable, or session revocation is not reported effective by the auth authority until the fence transaction commits. If publication fails, pilot access is denied and the update remains pending; grants are enabled only after both systems agree.

`PublishAuthorizationFence` accepts one canonical signed update with kind `account_snapshot` or `session_transition`, envelope version `1`, a fresh 16-byte `request_id`, and one typed payload: complete account snapshot `(tenant_id, immutable_user_id, next_authz_revision, role, account_state, sorted fixture grants)` or one session transition `(tenant_id, immutable_user_id, session_key_hash, next_session_revision, active|revoked, expiry)`. The canonical-CBOR envelope is the fixed array `["en-words-pilot-authz-update-v1",1,request_id,kind,payload]`; payload is the fixed positional array in the field order above, fixture entries are `[fixture_id,allowed]` sorted by UTF-8 bytes, and duplicate fixture IDs reject. Signature is Ed25519 over the exact envelope bytes using a dedicated pinned authorization-authority public key separate from admission signing. `update_digest = SHA256(ASCII("en-words-pilot-authz-update-digest-v1\0") || envelope_bytes)`; the signature is not part of the digest. No alternate map form, noncanonical CBOR, trailing bytes, or unknown version/kind is accepted. The resident checks envelope canonicality and bounds, verifies the signature, derives/resolves `principal_ref`, and only then opens the writer transaction and looks up `request_id`. An existing request ID returns its receipt only when the verified envelope digest and resolved tenant/principal/target/revision all match; otherwise it rejects as request-ID conflict. A new request ID must have a strictly increasing target revision; lower/equal revisions reject without writes. The transaction commits the state change and exactly one immutable receipt atomically. Session revocation is irreversible; a replacement session gets a new hash. Fixture grant changes advance the account revision and snapshot digest. Restrictive updates must reach the resident ledger before the auth authority reports success; permission grants remain unavailable until both sides are current. If either side is uncertain, Pilot endpoints fail closed.

The authorization objects have closed physical keys: account state PK `(tenant_id,principal_ref)`; session fence PK `(tenant_id,principal_ref,session_key_hash)` with FK to account state; fixture grant PK `(tenant_id,principal_ref,fixture_id)` with FK to account state; update receipt PK `request_id` (16-byte BLOB), plus unique `(tenant_id,principal_ref,target_kind,target_key,revision)`. `authz_revision` is scoped to an account; `session_revision` is scoped to one session hash, so equal numeric revisions across these domains are valid. Each fixture row's `grant_revision` equals the latest published account revision. Account updates are complete snapshots: every previously granted fixture omitted from the new set is retained as `allowed=0`, never deleted. All grant rows and the single account receipt are committed atomically; no fixture-target receipt is emitted. The snapshot digest is SHA-256 over domain `en-words-pilot-authz-snapshot-v1\0` plus canonical CBOR `[tenant_id,principal_ref,authz_revision,role,account_state,[[fixture_id,allowed],...]]`, with fixture IDs bytewise sorted and duplicates rejected. Session update digest uses domain `en-words-pilot-session-fence-v1\0` plus canonical CBOR `[tenant_id,principal_ref,session_key_hash,session_revision,session_state,expires_at]`. Receipts store `target_kind=account|session`, `target_key=zeroblob(32)` for account or exact session hash for session, target-scoped revision, update digest, and commit time; account revision 1 and session revision 1 do not collide. The request ID is the idempotency key for exactly one signed update and therefore resolves to exactly one receipt. Parser negative tests construct raw CBOR fixtures for noncanonical integer/array encoding, trailing bytes, unknown version/kind, and duplicate fixture IDs; each must reject before database access, with a valid test signature over raw bytes where envelope framing permits. Signed semantic vectors use a deterministic test-only Ed25519 seed and canonical envelope bytes: (a) mutate only request_id while retaining the signature => signature failure before DB access; (b) replay identical signed bytes => same receipt bytes, no revision/write; (c) same request_id with a separately valid signature over changed payload => request-ID conflict, no write; (d) new request_id with an already-used revision => stale-revision rejection, no write; (e) account snapshot changing multiple grants => one account receipt and all grant/tombstone rows in the same commit, or none. The hash-bound test artifact records public key, envelope hex, signature hex, update digest, expected outcome, and before/after row digests; it contains no private key. Signed vectors cover the exact request replay/conflict/revision cases and complete account snapshot; parser-only signed malformed vectors separately cover noncanonical encodings, trailing bytes, unknown version/kind, and duplicate fixture IDs.

`PrepareWithHandoff` compares every admission revision and explicit role/fixture/session predicate to current fence rows inside the same `BEGIN IMMEDIATE` that creates/replays the business operation. Therefore, writer order defines the race: a fence commit first rejects the stale admission with no effect; a Prepare commit first means the request was durably prepared before the revocation became effective. `CheckCurrentAuthorization` performs the same comparison before status replay, close-key/result lookup, or journal disclosure; uncertain, missing, or stale fence state denies. API middleware is only an early filter. Session and authorization identifiers are hashed; raw IDs and credential material are never stored or logged.

Principal HMAC key versions and alias mappings are never retired while any associated account, alias, or business-operation tombstone can exist. Because the current product ledger keeps tombstones permanently, retain every key version indefinitely; routine rotation changes only key wrapping. Destruction is permitted only after a separately reviewed, verifiable proof that all aliases and tombstones using that version have been permanently removed.

## Binding, constraints, and review oracles

### SQLite authorizer driver contract

The v3 ledger is an isolated `database/sql` store and must use a driver that exposes SQLite's per-connection authorizer. The existing application GORM driver (`glebarez/go-sqlite`) is not suitable for this boundary. The design candidate is a separately registered `github.com/mattn/go-sqlite3` driver, pinned during implementation, with [`SQLiteDriver.ConnectHook`](https://github.com/mattn/go-sqlite3/blob/master/sqlite3.go) installing [`SQLiteConn.RegisterAuthorizer`](https://github.com/mattn/go-sqlite3/blob/master/sqlite3.go) before a physical connection enters the pool. This does not change the application GORM database. The ledger package owns its pool, the authorizer registry, and all raw `Conn.Raw` access; RPC and feature packages see typed methods only. Within each typed transaction, the package leases one `*sql.Conn`, sets an unexported per-connection capability immediately before preparing/executing fixed SQL, and clears it with `defer` before releasing the connection. It does not use `*sql.Stmt` or a cross-capability prepared-statement cache. Initialization uses a distinct one-shot authorizer mode for the atomic DDL+seed transaction, then permanently switches each connection to runtime policy. Any connection-hook failure prevents pool admission. This choice requires a CGO-enabled build toolchain; CI and the Linux reference host must build with CGO and run multi-connection denial probes. Driver compatibility, Windows distribution, Go race build, and the one-million-row performance gate remain blocking implementation acceptance; the Python harness validates SQL rules only, never this driver contract.

The Go driver acceptance suite is separate from the Python authorizer harness and is a prerequisite to ledger implementation. It must pin at least eight `*sql.Conn` values simultaneously to prove eight distinct physical connections installed the hook, reject DML/DDL/TEMP/ATTACH/DETACH/mutating PRAGMA on each, and prove trigger-originated counter writes are the sole trigger exception. A deterministic test hook must fail both the first connection and a later pool expansion; either failure must close that connection and prevent store/service readiness. Typed capability tests must cover success, returned error, and panic, then reuse the same physical connection and a second connection to prove capability clearing and no cross-call leakage. Failures must leave the transaction rolled back and must not publish an unprotected connection. Log only the connection class and failure stage.

- **Identifiers and encodings:** tenant ID is canonical authenticated opaque bytes (1–256 bytes, BLOB); `principal_ref` is 32-byte HMAC-SHA256 BLOB; `session_key_hash`, payload/evidence/ACK digests are 32-byte BLOBs. Their lowercase-hex forms exist only at documented wire/display boundaries. Operation/business/outbox IDs and epochs are 16-byte BLOBs; launch nonce remains lowercase hex TEXT exactly as docs/47; timestamps are signed Unix nanoseconds in INTEGER with range checks. Text columns contain only fixed ASCII enums or bounded validated UTF-8 canonical CBOR/JSON bytes stored as BLOB.
- **Operation insertion order:** validate signed admission and resolve the stable principal before opening the transaction; then take `BEGIN IMMEDIATE`, compare the current authorization fence, and only then resolve/replay the exact business key. Exact replay returns immediately and bypasses capacity limits. For a new business key, read global/tenant/principal counters and policy; reject quota before any write. Still under the writer reservation, require the lease singleton to be empty and lifecycle branch available, insert allocation (the sole cross-table trigger updates counters/threshold events), then operation, then CAS the lease owner tuple (its allocation and operation FK parents now exist), bind lifecycle and insert outbox. Every step is one transaction and any failure rolls back. The operation-to-allocation and operation-to-lifecycle FKs are immediate because parents exist first. For close/no-root insert operation after lifecycle, then update close tuple/state. No reciprocal FK is used. The only cross-table trigger is the named allocation-insert counter/threshold trigger from docs/53; it updates three pre-seeded counter rows and inserts immutable threshold events atomically. Before commit, run bounded method-local assertions against the exact IDs and full tuples being written; mismatch rolls back. `INV-01..11` are whole-ledger startup/offline reconciliation oracles and must never run in the hot transaction path. Local triggers reject invalid state/null combinations and immutable-row replacement.
- **Connection enforcement:** before any transaction or SQL dispatch, every newly opened physical connection sets and reads back both `PRAGMA foreign_keys=ON` and `PRAGMA recursive_triggers=ON`. A pooled connection that fails either check is closed and never admitted; validate every connection, not only the pool opener. This is required because foreign-key enforcement is connection-local and SQLite ignores attempts to change it inside a transaction.
- **Permanent row protection:** immutable tables reject UPDATE/DELETE. Since SQLite `REPLACE` may bypass delete triggers when `recursive_triggers=OFF`, permanent-key tables also have `BEFORE INSERT` triggers that abort on any key collision. Tests exercise REPLACE with and without child references, UPSERT `DO UPDATE` and `DO NOTHING`, and direct SQL state tampering. `INSERT OR IGNORE` is prohibited in ledger methods.
- **Capacity limits:** production pilot defaults are global 1,000,000, per tenant 100,000, and per principal 1,000 permanent allocation tombstones. These are nested independent ceilings; each principal allocation counts toward tenant and global. The exact three limits are stored in immutable `pilot_capacity_policy` and must match the configured values on open; the database is rejected without writes on mismatch. Existing-key replay, status, close, cleanup, and lease release remain available at 100%; only new business keys reject. The allocation trigger writes one immutable `pilot_capacity_alert_events` row when each global/tenant/principal scope first crosses 80% and 90%; these protected durable rows are the audit record and cannot be lost or duplicated by crash/retry. This slice exposes no admin health endpoint; product/API access to these tenant/principal-scoped events is out of scope and requires a separately reviewed privacy contract. Never delete tombstones or alert rows. Limits are immutable for a database schema instance; changing them requires reviewed offline capacity migration. Tests may set lower limits only when initializing a fresh test database; CAP fixtures use global=7, tenant=5, principal=3 and independently exercise each ceiling. Threshold event count is the first crossing count `ceil(limit*percent/100)`; for limit=3, both 80% and 90% events are inserted in the same allocation transaction at count 3, each once.
- **Capacity workload bound:** benchmark global, tenant, and principal counter reads against 1,000,000 allocation rows in the serialized writer transaction; record elapsed time, SQLite query plan, rows visited, trigger updates, and lock-held duration. Acceptance is p95 <=50 ms on the documented reference host; otherwise redesign and review before code.
- **ACK correlation:** correlation is a cryptographically random 16-byte value created by the original Reaper for each send; exact ACK requires process identity, correlation, event digest, and outbox ID to match. The ACK transaction persists correlation and digest together. Reuse, cross-outbox replay, late ACK after deadline, and changed correlation are rejected without mutation.
- **Principal alias recovery:** resolve a signed `(tenant_id,immutable_user_id)` by computing candidate HMACs with every retained principal key version and looking up the protected alias table. Existing aliases always return their original canonical principal. If no alias exists, check those candidate refs against permanent operation tombstones before creating a new alias with the active write version; a tombstone without its alias is corruption and fails closed. Missing key versions/keyring integrity fail closed globally. Never fall back to a web-generated principal or silently create a new namespace for an identity with prior tombstones.
- **Principal alias versions:** aliases are stored only in `operations.sqlite`, never a second sidecar. `identity_digest` is the version-specific candidate HMAC; `principal_ref` is the canonical HMAC first assigned and `canonical_key_version` records its origin. Resolve by trying every retained key version. New accounts insert only one alias row under the current write version. Wrapping-key rotation does not change any HMAC bytes or alias. The transaction inserts the alias only after checking candidate tombstones; any candidate with an existing business tombstone and no alias is corruption.
- **Alias test range:** IDRES-04 iterates all retained versions, binds an old-version alias to an existing business tombstone, checks that a new account uses the active version, and verifies the old account still resolves to its original principal after a new session and wrapping-key rotation. IDRES-05 also tests missing any required key version for a new unknown identity (global fail-closed), corrupt alias digest/principal/version fields, and an existing tombstone with a missing alias.

|---|---|---|

| Authenticated identity binding | Signer binds opaque server-authenticated tenant/user identity; Reaper derives canonical HMAC alias before lookup | Forged tenant/principal and admission/RPC mismatch reject before lookup/write/effect; changed opaque bytes fail signature; noncanonical lowercase-hex display/wire forms are rejected before decode; cross-tenant same user remains isolated; known tombstone with missing alias/key fails `ipc_registry_corrupt`; cross-principal lookup is indistinguishable not-found; new session with same stable principal retains business-key identity |
