# First-Audio Matrix Test-Binary Control Protocol SDD

## Status and scope

This is an implementation delta for `docs/70-classroom-first-audio-latency-sdd.md` §7a and §7h. It specifies only the parent-runner ↔ dedicated Go test-binary control channel. It adds no production route, CLI command, database reset endpoint, or product behavior. Implementation starts only after architecture, backend, and security review of this document.

## Process boundary

The browser runner builds the harness with `go test -c`, launches that binary directly, and owns its lifetime. While the protocol is active, each accepted command has one JSON response on stdout; diagnostics go to stderr. The runner supplies a fresh per-process capability from `crypto/rand` with at least 32 random bytes, encoded as base64url, over a sanitized child environment allowlist (private `HOME`/temp paths, required runtime locale/path variables, run ID, DB path, capability, and the non-secret gate `EN_WORDS_FIRST_AUDIO_MATRIX_HARNESS=1` only); it must not inherit API keys or other secrets. The capability is never echoed, logged, persisted, or included in artifacts. The harness opens only a newly created database under a unique private `.test-artifacts` run directory. Both root and DB parent are canonicalized and checked for containment; the directory is owner-only, the DB uses exclusive create/no-follow semantics, and pre-existing DB, WAL/SHM/journal sidecars, symlink/reparse-point escape, missing run ID, or production port/database settings are rejected. A valid `bind` request bootstraps exactly one fixed synthetic fixture into the empty DB using a temporary setup pool whose ConnectHook registers only the test UDF required by fixed trigger DDL. Install those fixed triggers after fixture creation and before closing the setup pool; do not enable the immutable authorizer on this setup pool. Then open a fresh matrix pool with a per-physical-connection ConnectHook that registers the UDF and installs the immutable authorizer before any application statement is prepared. Pin every physical connection up to the configured maximum, verify UDF/authorizer behavior on each, and release them only after all pass. Only then instantiate the application and start the API listener on `127.0.0.1:0`. Startup verifies the actual listener address is loopback before serving; metadata returns that verified origin. No external pre-populated DB or unguarded production listener is accepted. The runner builds with `go test -c` and launches the dedicated binary using `-test.run=^TestFirstAudioMatrixControlHarness$`; the test entrypoint requires `EN_WORDS_FIRST_AUDIO_MATRIX_HARNESS=1` and otherwise skips. Protocol bytes alone use stdout; Go test diagnostics and stderr are separate. After a successful shutdown response, the Go test runner may emit its final `PASS` trailer; the parent accepts that trailer only after shutdown and routes it to stderr, then uses the process exit code as the result. Any other non-JSON stdout before shutdown is a protocol failure.

## JSONL contract

Each request is one UTF-8 JSON object, at most 64 KiB, with exactly `request_id`, `capability`, `command`, and `args`. `request_id` and `reset_id` use only `[A-Za-z0-9_-]`, 1–64 ASCII bytes. Reject duplicate JSON keys, unknown fields, invalid UTF-8, malformed objects, invalid capability, and invalid IDs. Request IDs are unique except that a byte-for-byte identical `reset` request may replay its recorded response after that reset has completed. Independently, a repeated `reset_id` with a new request ID and identical normalized `{lesson_id}` payload returns the same recorded result; changed payload is rejected. After validating JSON shape, capability, command, and ID syntax, resolve exact request-ID and reset-ID replays before checking current lifecycle or lesson ID; this ensures retries after a successful reset return the original result even though the current lesson has changed. Replays never re-execute reset or increment generation/count. Other duplicate request IDs are run-fatal. Commands are exactly:

- `bind`: once per process; args are exactly `{"fixture":"first_audio_v1"}`. Create the fixed synthetic student, book, words and scheduled lesson; do not accept caller-supplied IDs, paths, names, or content. Return their generated IDs only after the guarded application pool and loopback API are ready.
- `metadata`: empty args; return only loopback API origin (null before bind), bound synthetic IDs/current lesson ID, generation, lifecycle state, monotonic `successful_reset_count`, and source/build identity needed to bind browser evidence.
- `reset`: args contain a bounded `reset_id` and current `lesson_id`. On success, increment `successful_reset_count` once and return the recreated `lesson_id` and new generation so the runner can open the next journey. Exact request/reset replays return the stored result without incrementing the count. Any failed, timed-out, uncertain, or baseline-drift outcome is terminal and cannot create another generation.
- `shutdown`: empty args; close server, pools, and child cleanly. EOF before successful shutdown is a failed run.

## Lifecycle and failure handling

The command state machine is `UNBOUND → BOUND → RESETTING → BOUND`, with any failed/uncertain reset entering `TERMINAL_FAILED`; `UNBOUND`, `BOUND`, and `TERMINAL_FAILED` may enter `SHUTDOWN`. `BOUND` retains a monotonic `successful_reset_count`, initially zero after bind; each distinct successful reset increments it once, and replay never increments it. `UNBOUND` accepts bind/metadata/shutdown; `BOUND` accepts metadata/reset/shutdown; `RESETTING` accepts no command until its reset result; `TERMINAL_FAILED` accepts metadata, one shutdown, and only an exact replay of a recorded reset result (never re-execution). A semantic command rejection leaves the state unchanged; a rejected bind may be retried with the valid fixed fixture. Parser/transport violations (malformed or oversized JSON, invalid UTF-8, duplicate keys, unknown fields, invalid capability/IDs, or forbidden duplicate request ID) are protocol-fatal: no response, close resources, exit nonzero. Bind setup/guard/listener failure is terminal and cleans up. During reset, a known error returns `failed`; commit/cleanup uncertainty returns `outcome_uncertain`; both immediately close the API server and DB pools, preserve only sanitized in-memory status for metadata/replay, and prohibit another generation. A successful shutdown responds `ok`, closes resources, and exits 0. A shutdown command received in `TERMINAL_FAILED` takes precedence over the reset-count gate: it responds `failed` with the recorded terminal code, closes resources, and exits nonzero. The runner sends successful shutdown only after the two browser journeys pass; otherwise it kills/reaps the child and marks the run failed. Only shutdown from `UNBOUND` or nonfailed `BOUND` with `successful_reset_count=0` responds `failed/shutdown_incomplete`; this same request transitions directly to `SHUTDOWN`, closes resources, and exits nonzero without waiting for a second shutdown. The parent independently checks the exact cold/warm sample counts before treating the matrix as complete. EOF before shutdown closes the server/pools and fails the test process. On protocol failure or deadline, the parent kills the child process tree, waits/reaps it, then records exit status; no artifact cleanup or next sample starts while the child is alive. The harness independently bounds reset drain/cleanup by §7b and closes resources on its own terminal errors.

Every response echoes `request_id` and is at most 64 KiB. The exact fields are `request_id`, `status`, `data`, and `error`. `status` is one of `ok`, `rejected`, `failed`, or `outcome_uncertain`; `ok` has an object `data` and null `error`, other statuses have null `data` and `error:{code}`. There is no `retryable` field; a corrected semantic request must use a new request ID. Error mapping is fixed: `invalid_state`, `command_unsupported`, `fixture_unavailable` (unknown fixed fixture), `lesson_mismatch`, and `reset_id_payload_conflict` return `rejected` and leave the current state unchanged; `shutdown_failed` is reserved for cleanup failure during an otherwise successful shutdown; `bind_setup_failed` and `reset_failed` return `failed`, enter `TERMINAL_FAILED`, clean up, and exit nonzero after the subsequent shutdown command; `reset_outcome_uncertain` returns `outcome_uncertain` with the same terminal cleanup. `shutdown_incomplete` applies only to a shutdown from `UNBOUND` or nonfailed `BOUND` with zero successful resets; it returns `failed`, cleans up, transitions directly to `SHUTDOWN`, and exits nonzero in response to that same shutdown request. From `TERMINAL_FAILED`, shutdown instead returns the recorded terminal code. If cleanup fails during an otherwise successful shutdown, return `failed/shutdown_failed`, transition directly to `SHUTDOWN`, and exit nonzero on that request. A request-shape/ID/capability violation is fatal without response, not a semantic rejection. No free-form message, SQL, path, or payload is returned. Deadlines remain those in §7h: bind/metadata 5s, reset 35s, shutdown 5s. Missing/late replies or child exit terminates the run; the parent records the child exit code separately.

## Verification and acceptance

Parser tests cover limits, invalid UTF-8, duplicate keys/IDs, unknown fields, wrong capability, schema errors, exact reset idempotency (including retries after lesson replacement with both same and new request IDs), terminal failure, stdout/stderr separation, each deadline, and child exit. Process tests prove the production binary has no harness symbol/route and the harness rejects a pre-existing DB and resolved-path escape. On protocol failure/deadline, terminate the full child process tree (Windows Job Object or equivalent), wait/reap the process, and verify no child remains before recording artifacts or beginning another run. Browser containment is supported only on Windows and Linux: Windows uses a Job Object; Linux's private Node preload keeps Chromium in the runner-owned process group and synchronously appends each detached shell-based web-server PGID plus the process start time to a private manifest before returning from `spawn`. The parent validates bounded, newline-terminated records against `/proc`, admits each identity once, retires exited groups, and merges active manifest groups with `/proc` descendants. On timeout it first requests graceful group termination briefly, allowing a synchronous spawn registration to finish before force-kill cleanup. `/proc` enumeration/stat failures or manifest read/parse/identity failures are fatal; monitor errors propagate after cleanup attempts, and cleanup fails closed if a live group remains. Other POSIX platforms are rejected before the Go child starts. The dedicated Playwright entry point and parent orchestration are now present in `web/e2e/first-audio-matrix.spec.ts`, `web/playwright.first-audio-matrix.config.ts`, and `review/first_audio_matrix_control.py`; it launches a first-entry journey, records synthetic first-frame and speech-start times, confirms the browser WebSocket closes, waits for the browser process tree to exit, resets the same controller, then launches the second journey. The runner command is `python review/first_audio_matrix_control.py --run-id <unique-id> --go <go.exe> --node <node.exe>`; it must remain unused until the isolated backend is implemented and reviewed. This wiring is not matrix acceptance: the guarded SQLite backend, reset-fence race cases, canonical snapshots, and implementation review remain open. Measurements use mock browser speech and do not represent acoustic onset. Until those gates and the actual two-journey run pass, matrix status is `NOT RUN`.
