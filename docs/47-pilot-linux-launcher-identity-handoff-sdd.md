# Pilot Linux Trusted Launcher Identity Handoff SDD

**Status:** Approved for the first isolated Linux implementation slice. Native privileged Linux acceptance, durable production ledger integration, product orchestration, and browser/E2E integration remain gated; this is not authorization to start a classroom pilot. It replaces PID-number-derived authority and leaves product orchestration and browser/E2E integration out of scope.

## 1. Goal, trust boundary, and prerequisites

The host launcher is the sole process-identity authority. It is installed from an administrator-owned immutable configuration and runs as a dedicated provisioned service UID. Each Gateway generation owns exactly one active `run_epoch`/lease; a new run epoch requires a new Gateway generation. Gateway, Worker, Reaper request fields, procfs text, and numeric PIDs received over IPC are untrusted. The launcher itself is trusted; compromise of its executable, root account, or host kernel is outside this slice. Reaper receives one private inherited `AF_UNIX/SOCK_SEQPACKET|SOCK_CLOEXEC` control socketpair endpoint created before Reaper is spawned. The kernel supplies peer credentials; Reaper requires the provisioned launcher UID/GID and `SO_PEERCRED.pid == getppid()`. This inherited capability plus protected launcher configuration is the complete launcher trust root; no launcher pidfd is transferred and there is no second/bootstrap pidfd frame. A launcher or Reaper restart invalidates the channel and requires a new one-shot bootstrap with a higher control generation. Ordinary Gateway starts use `BOOTSTRAP`; recovery of an old run uses the restricted `RECOVERY_BOOTSTRAP` in section 4 and never allocates a new business/Gateway generation until reconciliation succeeds. No pathname lookup, environment variable, or caller-supplied PID can establish trust.

The launcher and Reaper are direct parent/child; the launcher is also the direct parent of Gateway. This Linux topology supersedes the older docs/43 Reaper-parent-of-Gateway model; Gateway remains the direct parent of its lesson worker. A root-owned systemd service manager delegates one exclusive cgroup v2 subtree (`Delegate=yes`) to the dedicated launcher UID. The launcher creates separate Reaper and Gateway leaves inside that subtree; each leaf and `cgroup.kill` is writable only by launcher, while Reaper/Gateway have no cgroupfs mount, cgroup FD, or write permission. Gateway has an empty capability set; Reaper has only the narrowly scoped mount-namespace capabilities already specified by docs/45 and explicitly lacks `CAP_KILL` and `CAP_SYS_ADMIN` after setup; both set `no_new_privs`. The launcher starts each with `clone3(CLONE_PIDFD|CLONE_INTO_CGROUP)`, retaining a pidfd and placing it into its leaf before first instruction. Reaper's control-channel `SO_PEERCRED` must identify the direct parent launcher (`pid == getppid()`) and provisioned launcher UID/GID. Gateway workers inherit Gateway's generation/run leaf through normal fork/exec; Reaper is not their parent or placement broker. The launcher is sole normal reaper for Reaper and Gateway: once each pidfd is readable it calls `waitid(P_PIDFD)` and journals exit before releasing handles. Numeric-PID waits are forbidden. After a 2-second graceful Reaper deadline, launcher writes `1` to only the Reaper leaf's `cgroup.kill`, waits another 2 seconds for pidfd exit and `populated 0`, then calls `waitid(P_PIDFD)`; failure quarantines and blocks new generations. A dedicated systemd service unit with `Delegate=yes` and `KillMode=control-group` owns launcher and all delegated descendants; if launcher dies, systemd kills the full service cgroup before restart, and PID 1 reaps orphans. Recovery verifies old leaves empty before replacement and never waitids old nonchildren. Before exec it sets Gateway real/effective/saved/filesystem UID/GID to configured service IDs, which Gateway cannot change. Thus attested UID, accepted Gateway socket `SO_PEERCRED` UID, and packet `SCM_CREDENTIALS` UID agree. The launcher's seccomp policy denies namespace-changing `setns`, `unshare`, `clone` flags and `clone3` for Gateway/Reaper; runtime startup/thread creation must pass smoke tests or the combination is unsupported. Required kernel baseline is Linux 5.14; unsupported hosts fail before endpoint registration.

## 2. Durable generation and one-shot registration

Before any Gateway spawn, the launcher obtains an exclusive `flock(LOCK_EX|LOCK_NB)` on a launcher-owned mode-0600 singleton lock file under the launcher state directory and holds it for its entire lifetime. Failure to acquire it means another launcher owns the host and startup stops. Under that lock, the launcher maintains a launcher-owned mode-0600 fsynced journal in a mode-0700 launcher state directory, beneath a root-owned non-writable parent. Each control-generation record contains `generation`, `mode=normal|recovery`, its fresh transport nonce, lifecycle state, and resource records `reaper_cgroup={name,parent_dev,parent_inode,dev,inode,state}`, `gateway_cgroup={name,parent_dev,parent_inode,dev,inode,state}`, and `endpoint={basename,parent_dev,parent_inode,dev,inode,state}`. A normal record also binds one `run_epoch`; a recovery record binds `target_generation,target_launch_nonce,target_run_epoch` and sets Gateway/endpoint resource states to `absent` by construction. Each resource state independently advances `absent|intent|created|active|retiring|removed|quarantined`; the generation lifecycle is `allocated|spawned|bootstrapped|registered|terminating|unregistered|terminal_committed|recovering|recovery_terminal|retired|quarantined`. Before creating any individual cgroup leaf or binding the socket, it durably records that resource's exact unique name, parent directory device/inode, and `intent`; after creation it records the leaf's own device/inode before spawning into it or passing its FD. Reaper and Gateway leaves are never represented by one shared cgroup identity/state. Generation is nonzero uint64 and is allocated durably before any resource creation/spawn; nonce is fresh and bound to that generation. Corrupt state, rollback against the durable Reaper ledger, overflow, or any durability error is fail-closed; gaps are allowed. Reaper durably consumes each control generation at either `BOOTSTRAP` or `RECOVERY_BOOTSTRAP` and rejects any generation not greater than its last accepted value. A normal transport nonce is consumed once by BOOTSTRAP; its only continuation messages are REGISTER, UNREGISTER, and (after successful unregister) CONTAINMENT_EMPTY. A recovery transport nonce is consumed once by RECOVERY_BOOTSTRAP and authorizes only recovery of its exact target tuple; it never authorizes Gateway work. Duplicate BOOTSTRAP and duplicate continuation requests are always rejected; an ACK timeout is never resolved by replaying a request, and instead closes the channel and follows the uncertain-outcome teardown path. A new Gateway/business generation is never allocated until recovery has retired prior host resources and reconciled the Reaper ledger. A higher control generation may be allocated solely for the restricted recovery session in section 4; it cannot start a Gateway or accept business operations.

Recovery starts under the singleton lock, before creating Reaper or Gateway. The launcher scans only the two fixed launcher-delegated cgroup parents and the launcher-owned endpoint directory, whose parent device/inode identities are fixed in protected configuration. It recovers `reaper_cgroup` and `gateway_cgroup` independently using each resource's journal state and recorded parent/leaf identity; it never infers one leaf identity from the other. For a journaled inode it mutates only after exact device/inode/type/owner checks. For each narrow `intent` crash window where creation succeeded before leaf-inode journaling, it may recover only that resource's exact unique name in its launcher-exclusive delegated parent, and only if expected type/owner match; otherwise it writes that resource `quarantined`, preserves it, and blocks all new generations. Cgroup recovery issues `cgroup.kill`, waits for `populated 0`, then removes that leaf; socket cleanup checks `fstatat(..., AT_SYMLINK_NOFOLLOW)` relative to the pinned directory FD before `unlinkat`. This covers crashes independently after Reaper leaf intent/create, Gateway leaf intent/create/spawn (including before BOOTSTRAP), endpoint intent/bind, BOOTSTRAP commit, REGISTER install, and UNREGISTER. Most recover to `retired`; ambiguous/replaced resources reach explicit `quarantined`, with test oracle: no new generation/spawn, no guessed deletion, and an operator-visible bounded failure. The launcher and Reaper durable stores are reconciled by consuming/skipping any generation accepted by either store; disagreement never rolls either counter backward.

Each normal or recovery control generation gets a fresh cryptographically random 128-bit transport nonce, consumed durably exactly once by its bootstrap frame. A normal BOOTSTRAP nonce authorizes the one-shot REGISTER, UNREGISTER, then (only after successful unregister) CONTAINMENT_EMPTY sequence. A RECOVERY_BOOTSTRAP nonce authorizes only its exact target old-run tuple. The control channel never retries any bootstrap on a new connection; a retry after uncertain outcome requires a later control generation and fresh nonce. `RECOVERY_BOOTSTRAP` additionally requires `target_generation,target_launch_nonce,target_run_epoch` to match one existing ledger binding exactly; it cannot nominate a principal or derive a target from request data. Reaper records each consumed `(generation, nonce)`; duplicate bootstrap, stale generation, or mismatched continuation is rejected. If persistence is unavailable, restart is required.

## 3. Identity record and pidfd validation

The BOOTSTRAP identity fields are embedded directly in the control packet schema in §4; there is no separately encoded/nested identity object. The ordered identity fields are `generation`, `launch_nonce` (32 lowercase hex digits), `pid`, `uid`, `start_time_ticks`, `pidns_device`, `pidns_inode`, `cgroup_mount_id`, `cgroup_device`, `cgroup_inode`. Numeric fields are unsigned canonical decimal integers; generation and `target_generation` are 1..MaxUint64; `launch_nonce` and `target_launch_nonce` are exactly 32 lowercase hex digits; `target_run_epoch` is exactly 32 lowercase hex digits; pid fits Linux positive pid range; uid is nonzero, fits Linux uid range, and must equal the provisioned non-root service UID; remaining identifiers fit uint64. Unknown, missing, duplicated, reordered, noncanonical, signed, fractional, or out-of-range values are rejected. No paths, argv, environment, secrets, raw procfs contents, or identity values are logged. §4 is the sole wire encoding and packet size limit.

The launcher sends exactly one `SCM_RIGHTS` duplicate of the already pinned Gateway pidfd with the record. Reaper uses `recvmsg(MSG_CMSG_CLOEXEC)`, requires one record and exactly one rights descriptor with no other ancillary data, and rejects `MSG_TRUNC`, `MSG_CTRUNC`, EOF, short data, or extra packets. Every received FD is closed exactly once on every rejection path. It never calls `pidfd_open` on a record PID.

Only the trusted launcher reads host procfs. It obtains the PID from `fdinfo` for its own retained pidfd, verifies pidfd liveness with `poll`, reads `stat`, `status`, `ns/pid`, and `cgroup` through an opened `/proc/<pid>` directory FD, then repeats fdinfo and poll. Exit, disappearance, parse ambiguity, or identity drift rejects the snapshot. It sends that snapshot plus the pidfd through the inherited authenticated channel. Reaper intentionally has no procfs view (docs/45); it trusts the provisioned launcher and inherited channel, validates the control-channel `SO_PEERCRED` only against the provisioned launcher UID/GID and direct-parent PID, treats Gateway PID/UID as launcher-attested record values bound to the transferred pidfd, polls that pidfd, and pins it through dispatch. On every separately accepted Gateway connection, it compares that connection's `SO_PEERCRED` and per-message `SCM_CREDENTIALS` to the BOOTSTRAP record. Because a live pidfd itself cannot be retargeted to a reused PID and Gateway cannot change cgroup/namespace membership under the enforced policy, this binds the procfs snapshot without granting Reaper procfs access or signal permissions. A malformed/unpollable descriptor or dead pidfd is rejected. Reaper does not call `pidfd_open` and does not inspect `/proc/self/fdinfo`.

## 4. Listener, peer authentication, and teardown

All control records are individual SOCK_SEQPACKET packets, canonical UTF-8 JSON with the exact ordered keys below, at most 768 bytes, no duplicate/unknown keys, and one packet per transaction. Every request and ACK includes `version:1`, `type`, `generation`, and `launch_nonce`; requests/ACKs are correlated by that tuple. ACKs use a bounded `result` enum and no free-form text: ordinary ACKs use `ok|rejected|restart_required`, while RECOVERY_BOOTSTRAP_ACK uses `already_terminal|finalized|recovery_proof_missing|recovery_not_ready|rejected|restart_required`. The Gateway identity values in BOOTSTRAP are launcher-attested data bound to the attached pidfd; they are not compared to control-channel `SO_PEERCRED`. Control-channel credentials authenticate the launcher. Later accepted Gateway-message credentials are compared to the BOOTSTRAP identity.

| Type | Exact ordered payload keys | FDs | State transition |
| --- | --- | ---: | --- |
| `BOOTSTRAP` | `version,type,generation,launch_nonce,run_epoch,pid,uid,start_time_ticks,pidns_device,pidns_inode,cgroup_mount_id,cgroup_device,cgroup_inode` | 1 Gateway pidfd | `absent -> accepted`; persist generation/nonce/run binding before ACK |
| `BOOTSTRAP_ACK` | `version,type,generation,launch_nonce,result` | 0 | `accepted` only when `result=ok`; any error retires tuple |
| `REGISTER` | `version,type,generation,launch_nonce,endpoint_parent_device,endpoint_parent_inode,endpoint_device,endpoint_inode` | 1 listener FD | `accepted -> registered`; exact tuple only |
| `REGISTER_ACK` | `version,type,generation,launch_nonce,result` | 0 | `registered` only when `result=ok` |
| `UNREGISTER` | `version,type,generation,launch_nonce` | 0 | `registered -> retiring`; stop accept and close Reaper listener before ACK |
| `UNREGISTER_ACK` | `version,type,generation,launch_nonce,result` | 0 | Reaper `registered -> unregistered`; lease remains held and control channel remains open |
| `CONTAINMENT_EMPTY` | `version,type,generation,launch_nonce,run_epoch,gateway_pid,gateway_start_time_ticks,gateway_cgroup_mount_id,gateway_cgroup_device,gateway_cgroup_inode,endpoint_parent_device,endpoint_parent_inode,endpoint_device,endpoint_inode,endpoint_removed,leader_reaped,populated` | 0 | Launcher attests the bound process/cgroup tuple plus `leader_reaped=true,populated=false`; Reaper durably inserts `RunContainmentEvidence`, then commits the matching `FinalizeRunTerminal` or prepared-cancel `FinalizePreparedCancellation` transaction |
| `CONTAINMENT_EMPTY_ACK` | `version,type,generation,launch_nonce,run_epoch,result` | 0 | `terminal_committed` only on `ok`; Reaper exits after ACK |
| `RECOVERY_BOOTSTRAP` | `version,type,generation,launch_nonce,target_generation,target_launch_nonce,target_run_epoch` | 0 | create a recovery-only session; no Gateway, listener, lease, or business dispatch is created |
| `RECOVERY_BOOTSTRAP_ACK` | `version,type,generation,launch_nonce,result` | 0 | `already_terminal|finalized|recovery_proof_missing|recovery_not_ready|rejected|restart_required`; Reaper exits after ACK |

For ordinary ACKs, `result` is exactly `ok|rejected|restart_required`; RECOVERY_BOOTSTRAP_ACK uses only its table-defined recovery result enum. Before a request's durable commit point, rejection closes all received FDs, leaves durable state unchanged, sends `rejected` if the tuple is parseable, then closes the control channel. After durable commit, any failure sends `restart_required` if possible, closes locally owned/received FDs, closes the channel, and exits Reaper. EOF/malformed packet/rejection before terminal commit makes Reaper stop accepts, close all local descriptors, persist the safe state (`unregistered` if listener was active; otherwise accepted generation remains fenced), retain the lease, and exit. For a valid `UNREGISTER`, Reaper stops accepts, closes its listener duplicate, persists `unregistered` while retaining the control channel and run lease, then sends ACK and waits for `CONTAINMENT_EMPTY`. If the launcher receives `UNREGISTER_ACK`, it unlinks the endpoint, kills the Gateway cgroup, waits for pidfd exit plus `populated 0`, calls `waitid(P_PIDFD)`, and sends `CONTAINMENT_EMPTY`. Reaper binds this to the sole active `run_epoch`, generation/nonce, process tuple, and cgroup identity; it first persists the typed run-containment evidence defined below, then it commits the matching docs/43 terminal transaction: `FinalizeRunTerminal` for a created root or the narrowly scoped `FinalizePreparedCancellation` for the prepared/no-dispatch case in docs/43 §8.4. The latter requires its cancellation receipt, abandoned operation/allocation, absent root run_state, and cleanup_state=not_required; both paths require exact containment evidence and held lease before release. It sends `CONTAINMENT_EMPTY_ACK` only after durable commit, then exits. If the `UNREGISTER_ACK` deadline expires or the channel closes, the launcher MUST NOT replay `UNREGISTER` or send `CONTAINMENT_EMPTY` on that channel. It still removes the endpoint and contains/reaps Gateway; the run remains terminating with its lease held and generation quarantined. Once the old Reaper is reaped, launcher may start a control-only Reaper under a newly allocated higher control generation and fresh transport nonce using `RECOVERY_BOOTSTRAP`; this session has no Gateway pidfd, listener, or operation-dispatch capability. Reaper returns `recovery_proof_missing` and makes no target run/operation/lease-ledger change if `RunContainmentEvidence` is absent (the authenticated recovery control generation and nonce are still durably consumed); the run remains `terminating` and its lease held; this recovery result does not mutate the pre-existing `cleanup_state` (which may be `pending` or `indeterminate` depending on the last durable Reaper transition), and separately reviewed offline administrator reconciliation is required; that procedure is outside this SDD. If `CONTAINMENT_EMPTY_ACK` is lost, launcher reaps the old Reaper and starts the same restricted recovery session: an already terminal row returns `already_terminal`; a durable evidence row with `run_state=containment_empty` and without terminal state permits only `FinalizeRunTerminal`, while the exact prepared-cancel receipt plus absent root run_state and `run_terminal_state=none` permits only `FinalizePreparedCancellation`; either returns `finalized`; inject and assert a crash immediately after the atomic evidence-row/state commit, with the lease still held. The session never synthesizes evidence, repeats business effects, or guesses whether a transaction committed. Recovery bootstrap itself is one-shot per control generation/nonce. A later higher recovery generation may automatically query the same target only when the prior recovery outcome is genuinely uncertain (for example, ACK loss or transport failure after request commit) and the previous recovery Reaper has been reaped. A known `recovery_proof_missing` or `recovery_not_ready` result forbids automatic re-query; a later query is allowed only after separately recorded offline administrator reconciliation. A known target `rejected` result likewise requires offline repair of the target binding/configuration first. Launcher always waits on retained pidfds and performs `waitid(P_PIDFD)` for its children before removing their cgroup leaves. A new Gateway/business generation is permitted only after the Reaper ledger proves the old run terminal, endpoint removed, Gateway/Reaper leaves empty and removed, and launcher/Reaper stores are reconciled. Recovery-only control generations are allowed before this point but cannot start a Gateway or serve a listener; quarantined/indeterminate runs without evidence block that principal until separately reviewed offline reconciliation. Request replays are rejected; any FD is closed exactly once on rejection. Launcher owns the endpoint pathname and listener FD; Reaper owns its duplicate. All descriptors are close-on-exec.

For the inherited control socket, `SO_PEERCRED` is the credential snapshot associated with socketpair creation, so both endpoints validate that snapshot against the launcher identity provisioned before spawn. Per-packet `SCM_CREDENTIALS` identify the process that sent each record: Reaper requires the launcher's provisioned PID/UID/GID for BOOTSTRAP and continuation requests; the launcher requires the spawned Reaper's retained child PID plus provisioned Reaper UID/GID for ACKs. The launcher must keep these two expected credential tuples distinct; checking ACK packet credentials against socketpair `SO_PEERCRED` would reject the specified parent/child topology. A parseable BOOTSTRAP tuple with a dead or non-pidfd descriptor receives a correlated `rejected` ACK without consuming the durable generation; malformed/unparseable frames remain silent and close the channel. After receiving an ACK, the launcher rejects any queued additional record while treating peer EOF after the single ACK as channel closure, not as a second ACK.

A recovery-only session is legal only after the previous Reaper process has been collected by its parent via pidfd `waitid`, or after systemd has completed `KillMode=control-group` cleanup and the restarted launcher has verified all old delegated leaves empty. Launcher durably allocates a new monotonically higher control generation and fresh 128-bit transport nonce, records the exact target tuple `(target_generation,target_launch_nonce,target_run_epoch)`, then spawns Reaper in a fresh Reaper-only cgroup leaf using the inherited authenticated control socketpair. `RECOVERY_BOOTSTRAP` carries no FDs. Reaper durably consumes the new control tuple and opens only the existing control ledger; it creates no Gateway context, endpoint, listener, run lease, or business-operation capability. It validates the target tuple against the ledger. If target run is already terminal, it returns `already_terminal`; if exactly one matching immutable `RunContainmentEvidence` row exists, it performs only the matching idempotent final transaction: `FinalizeRunTerminal` requires run state `containment_empty`, required operation receipts, and cleanup `complete|retained`; `FinalizePreparedCancellation` instead requires the exact cancellation receipt, abandoned operation/allocation, absent root run state, `run_terminal_state=none`, and cleanup `not_required`. It returns `finalized` only after the matching transaction commits; if evidence is absent, it returns `recovery_proof_missing`; if evidence exists but run state, operation state, required receipt, or cleanup predicate fails, it returns `recovery_not_ready`; if authenticated target binding conflicts or mismatches, it returns `rejected`. A well-formed authenticated request consumes its higher control generation for all these results; stale/equal/lower control generations return `rejected` without consumption. `recovery_proof_missing` and `recovery_not_ready` change no target run/lease state, retain quarantine, and prohibit automatic retry: offline administrator reconciliation is required first. After that reconciliation has repaired the ledger, a later higher control generation may query the same target; it never manufactures containment evidence. `rejected` also leaves target state unchanged; retry is permitted only after offline repair of the target binding/configuration and uses a higher control generation. `restart_required` consumes the control tuple and permits a higher-generation query only after the previous Reaper is reaped. The ACK is sent only after any terminal transaction is durable. If the ACK is lost, after that Reaper is reaped a later strictly higher recovery generation may query the same target idempotently. The launcher must receive `already_terminal` or `finalized`, collect the recovery Reaper, verify its cgroup empty, remove it, and reconcile both journals before allocating a Gateway/business generation. No regular BOOTSTRAP for a new Gateway can bypass this gate.

`BOOTSTRAP` records the Gateway cgroup identity as the exact tuple `[cgroup_mount_id,cgroup_device,cgroup_inode]`, obtained by the launcher from the pinned cgroup directory FD using `statx` mount ID plus `fstat` device/inode. `CONTAINMENT_EMPTY` carries `[gateway_cgroup_mount_id,gateway_cgroup_device,gateway_cgroup_inode]`; Reaper compares all three fields exactly with the persisted BOOTSTRAP tuple and the run/generation binding. Launcher obtains the empty observation from that same pinned cgroup FD and confirms the same tuple immediately before and after observing `cgroup.events populated 0`. Reaper does not read cgroupfs or infer device-to-mount mappings.

`REGISTER` binds the pinned endpoint directory identity `[endpoint_parent_device,endpoint_parent_inode]` and socket identity `[endpoint_device,endpoint_inode]`. The launcher requires the parent tuple to equal the protected endpoint-directory configuration and its durable journal; Reaper persists the REGISTER tuple with the listener FD. In `CONTAINMENT_EMPTY`, all four endpoint identity fields must exactly equal that REGISTER tuple. `endpoint_removed=true` is a trusted launcher attestation that, after unlink, `fstatat(dirfd, basename, AT_SYMLINK_NOFOLLOW)` returned `ENOENT` while the pinned parent FD still matched the registered parent tuple. The Reaper cannot observe the launcher's private directory directly and trusts only this authenticated launcher assertion. It rejects `endpoint_removed=false`, any tuple mismatch, or an empty assertion before Gateway containment/waitid is complete.

The terminal evidence object is a distinct immutable control-ledger row named `RunContainmentEvidence`, not an `OperationEvidenceReceipt` and not a new business operation. Its exact v1 fields are `[run_epoch,gateway_generation,launch_nonce,gateway_process_identity,gateway_cgroup_identity,endpoint_identity,endpoint_removed,leader_reaped,populated,evidence_version]`; `gateway_process_identity` is `[pid,start_time_ticks,pidns_device,pidns_inode]`, `gateway_cgroup_identity` is `[mount_id,device,inode]`, and `endpoint_identity` is `[parent_device,parent_inode,socket_device,socket_inode]`. Valid values require `endpoint_removed=true`, `leader_reaped=true`, `populated=false`, Gateway identities equal the persisted BOOTSTRAP binding; endpoint identity equals the REGISTER tuple and launcher journal, whose parent device/inode must equal protected endpoint-directory configuration, and exactly one row per `(run_epoch,gateway_generation)`. `evidence_digest` is `SHA256(ASCII("en-words-run-containment-evidence-v1\0") || deterministic_CBOR(fields))`. Reaper inserts this row durably and idempotently before the final run-terminal transaction; a duplicate is accepted only when every field and digest are identical. The final transaction reads and verifies this already committed row, confirms operation receipts and cleanup predicates, then atomically writes terminal run state, binds the evidence digest, and releases the lease. The evidence-row transaction atomically changes `run_state=terminating` to `containment_empty` while leaving the lease held; a crash between that row/state commit and terminal transaction is recovered by revalidating the row and rerunning only the final transaction; evidence is never appended twice. Tests mutate each process/cgroup/endpoint field independently, including mount ID, and crash at both durable commit boundaries.

If Reaper exits before `RunContainmentEvidence` is committed, a new Reaper cannot reconstruct launcher-held pidfd wait evidence or reuse the consumed generation nonce. It MUST leave the run `terminating`, retain the lease, mark the generation quarantined, and refuse new runs for that principal. Only a separately reviewed offline administrator reconciliation procedure may clear this state; it is outside this SDD and must not be simulated by automatic retry or operator confirmation in the product UI. This permanent-hold oracle is an intentional availability tradeoff for missing proof.

The private state directory is provisioned mode `0700`, owned by the dedicated launcher UID, below a root-owned non-writable parent; the lock and journal are launcher-owned mode `0600` with no ACLs. The endpoint directory is mode `0710`, owned by the launcher UID and grouped to the Gateway service group, with no ACLs. Its root-owned parent is provisioned mode `0711` (traverse only for the launcher/Gateway identities) and is non-writable by them. Gateway can traverse the endpoint directory but cannot create, replace, or unlink names; the trusted launcher owner can bind and unlink. Launcher holds its directory FD opened with `O_DIRECTORY|O_NOFOLLOW`; it binds via `/proc/self/fd/<dirfd>/<basename>` while host procfs is available, creates a launcher-owned socket node, then sets the node to mode `0620` and the configured Gateway group. Before bind it requires the exact basename absent using `fstatat(..., AT_SYMLINK_NOFOLLOW)`; afterward it records device/inode in the journal. At cleanup it verifies socket type, owner, mode, device, and inode relative to the pinned dirfd before unlink. Any mismatch quarantines and blocks startup. This prevents Gateway pre-creation or replacement and avoids path-based cleanup races.

Reaper accepts on the registered listener and enables `SO_PASSCRED` on the accepted socket before reading its first request. The application protocol is one bounded SOCK_SEQPACKET record per operation, with no ancillary FDs permitted. Each `recvmsg` must return exactly one `SCM_CREDENTIALS`; its PID must equal the Gateway bootstrap PID and its UID is the kernel-reported real UID (Linux `ucred.uid`), required equal to the attested UID. `MSG_TRUNC`, `MSG_CTRUNC`, zero/multiple credentials, any `SCM_RIGHTS`, any other ancillary record, or malformed packet closes the connection before dispatch. This prevents a child process from reusing a connected socket FD and inheriting the original `SO_PEERCRED`. Reaper also checks the accepted Gateway connection's `SO_PEERCRED` at accept and polls the pinned pidfd before and after authentication and immediately before dispatch. The extended process identity tuple is snapshotted by the trusted launcher; Gateway cannot change namespace/cgroup membership under the enforced policy and start time is immutable. Any failed check closes the peer and does not dispatch a request. On a valid `UNREGISTER`, Reaper stops accepts, closes its listener duplicate, durably records `unregistered`, sends `UNREGISTER_ACK/v1`, and keeps the authenticated control channel and run lease open for the terminal containment handoff. The launcher removes the endpoint, kills the Gateway leaf, waits for Gateway pidfd exit and `populated 0`, calls `waitid(P_PIDFD)`, then sends `CONTAINMENT_EMPTY`. Reaper verifies the bound generation, nonce, run epoch, Gateway identity, and full cgroup tuple; it persists the distinct immutable docs/43 `RunContainmentEvidence` row, then the final run-terminal transaction verifies that row and operation receipts and atomically commits terminal state plus lease release. It sends `CONTAINMENT_EMPTY_ACK` and exits only after that commit. The launcher then collects Reaper through its pidfd and removes its leaf. Channel loss before terminal commit fences the run and retains the lease; for UNREGISTER_ACK timeout/EOF, launcher still contains and reaps Gateway but MUST NOT send CONTAINMENT_EMPTY over the closed/invalidated channel. A control-only Reaper launched via `RECOVERY_BOOTSTRAP` can finalize only an already committed containment-evidence row; if absent, it returns `recovery_proof_missing` and the generation remains held for separately reviewed offline administrator reconciliation. Uncertain CONTAINMENT_EMPTY_ACK outcomes quarantine until durable-ledger reconciliation. Reaper is one-shot and does not serve a next generation.

Retirement order is fixed: Reaper stops accepts, closes its listener, persists `unregistered` while retaining its control channel and lease, and sends `UNREGISTER_ACK`; launcher validates and unlinks the endpoint by dirfd/inode, writes `cgroup.kill=1` to the Gateway leaf, waits for Gateway pidfd exit and `cgroup.events populated 0`, then collects Gateway with `waitid(P_PIDFD)`. Launcher sends `CONTAINMENT_EMPTY`; Reaper validates the attested tuple, durably inserts `RunContainmentEvidence`, then the final docs/43 run-terminal transaction verifies the evidence row and operation receipts and atomically commits terminal state plus lease release. Reaper sends `CONTAINMENT_EMPTY_ACK` and exits only after that commit. Launcher collects Reaper with `waitid(P_PIDFD)`, confirms its leaf empty (or uses its protected `cgroup.kill` and waits), removes both cgroup leaves, closes remaining pidfds/namespace/cgroup handles, and commits journal state `retired`. Exit identity and status are journaled before releasing handles. Timeout, waitid error, nonempty cgroup, control-channel loss, or uncertain terminal ACK is restart-required: retain/quarantine the lease and context, report bounded failure, and never claim the child tree was reaped. A replacement generation cannot start until containment, terminal ledger, and journal are reconciled. Launcher crash recovery follows the systemd service-manager cleanup path; Reaper is not the Gateway parent and never waits/reaps it.

## 5. Failure behavior, logs, and test cases

Every transition logs `trace_id`, bounded `stage`, `event`, `reason`, elapsed time, accepted/closed FD counts, generation state (`absent|accepted|retired`), and whether dispatch/registration occurred. Logs exclude PID/UID, nonce, namespace/cgroup identifiers, paths, argv, environment, raw IPC, and descriptor numbers. Cleanup errors are preserved as restart-required, not overwritten by the original error.

Acceptance tests cover exact byte vectors and numeric limits for every request/ACK; include per-field mismatch negatives for the REGISTER and CONTAINMENT_EMPTY endpoint tuples and assert `endpoint_removed=false` or a non-ENOENT post-unlink observation rejects terminal evidence; unknown/duplicate keys, noncanonical records, invalid ordering, oversized packets, malformed/truncated/extra ancillary FDs, wrong launcher credentials, dead/unpollable pidfds, and launcher-side procfs exit/PID reuse with a deterministic barrier after each `stat`, `status`, `ns/pid`, and `cgroup` read plus the final `fdinfo`/poll immediately before BOOTSTRAP and dispatch. At every barrier inject exit and PID reuse; assert no stale identity is accepted, no operation dispatch occurs, no BOOTSTRAP generation is consumed unless its durable commit was reached, all untransferred FDs close, and any already accepted run lease stays held. For every frame, assert expected prior state, commit point, resulting state, FD owner, ACK result, and allowed next action. Any rejected request/closed control channel must make Reaper stop accepts, close all owned descriptors, exit, and be observed exited through the launcher-held pidfd before cleanup or a new generation. BOOTSTRAP failure before durable consume leaves Reaper ledger unchanged; failure after consume permanently skips that generation. REGISTER failure before install closes received FD, marks Reaper terminal, exits, and launcher retires the generation; after install but before ACK it closes listener, records `unregistered`, exits, and is reaped before cleanup continues. UNREGISTER_ACK timeout/EOF leaves Reaper with no listener and invalidates the control channel: launcher completes Gateway containment and pidfd wait, MUST NOT send CONTAINMENT_EMPTY on that channel, then reaps old Reaper and launches only a recovery-only session. With no containment-evidence row, parameterize pre-existing `cleanup_state=pending` and `cleanup_state=indeterminate`; assert `recovery_proof_missing`, byte-for-byte unchanged target run/cleanup/lease state, consumed recovery control generation+nonce, and permanent operator quarantine pending separately reviewed offline reconciliation. Separately, after a received UNREGISTER_ACK, inject crashes/channel loss before and after containment-evidence row commit and before final terminal transaction, and before/after CONTAINMENT_EMPTY_ACK: before evidence commit the lease remains held and no automatic recovery is allowed; the evidence-row transaction must atomically persist `run_state=containment_empty` with the immutable evidence row while keeping the lease held; after that commit recovery verifies the exact row and state and retries only the final transaction; after terminal commit recovery-only Reaper returns `already_terminal`; for evidence-row-only state it executes only the final transaction and returns `finalized`; neither path duplicates evidence or lease release. For RECOVERY_BOOTSTRAP test no-evidence, evidence-row-only, terminal-already-committed, and prepared-cancellation evidence-row-only targets; the last must expose no Gateway/listener/dispatch capability and may call only FinalizePreparedCancellation after rechecking its immutable receipt, suppressed-or-acknowledged intent, absent root run_state, and held lease. Assert recovery sessions have no Gateway/listener/lease allocation, no operation dispatch, no duplicate evidence/lease update, and correct `recovery_proof_missing|recovery_not_ready|finalized|already_terminal` result. Inject a post-commit failure after RECOVERY_BOOTSTRAP control-generation/nonce persistence but before target-ledger evaluation/ACK; require `restart_required` when sendable, Reaper exit, unchanged target run/operation/evidence/lease state, consumed generation+nonce, and rejection of replay on that generation. ## 6. Implementation boundary

This SDD authorizes implementation only after all four design domains pass and the test reviewer confirms each failure case has a deterministic fixture/oracle. The first code slice may implement the launcher-to-Reaper handoff, restricted recovery bootstrap, and tests behind the existing Linux pilot build tags. It must not expose a production API, claim a classroom-ready RunRoot, or enable real-user audio. Product wiring, browser E2E, multi-student classroom load, model/network recovery, and human voice-quality acceptance remain separately gated.

# Pilot resident-ledger Reaper caller registration amendment (2026-10-21)

For the docs/50–52 resident `PilotControlReaper` architecture, a live per-run Reaper is a distinct process from the Gateway recorded in `BOOTSTRAP`. The launcher remains the sole process-identity authority. After spawning the per-run Reaper and before allowing any ledger operation, it registers the Reaper's own `(pid,start_time_ticks,pidns_device,pidns_inode,uid,cgroup_mount_id,cgroup_device,cgroup_inode)` identity with the resident control service over a launcher-only authenticated endpoint. That registration binds the Reaper tuple to the consumed `(generation,launch_nonce,run_epoch)` and separately copies the Gateway process/cgroup tuple from the immutable BOOTSTRAP handoff as the operation target. It does not alter the BOOTSTRAP wire schema or transfer a pidfd.

For each live-Reaper ledger packet, the resident service checks kernel `SCM_CREDENTIALS` PID/UID and derives the sender's current start-time, PID namespace and cgroup tuple from the live process; all fields must equal the launcher registration. It independently checks the requested target tuple against the immutable BOOTSTRAP handoff. Gateway credentials, matching service UID, a replaced PID, or a Reaper registered to another generation cannot authorize the call. The original Reaper registration remains valid only through its permitted lifecycle and is revoked after the launcher collects that exact child by pidfd and durably records retirement. Lost registration or uncertain process identity fails closed and quarantines the generation; restart does not silently transfer the old capability to a replacement Reaper. Recovery-only Reaper is registered under a new higher control generation and receives only the recovery methods and exact target tuple allowed by docs/47.
