# Pilot RunRoot Product Orchestration SDD

## Status and scope

This SDD defines the missing product-to-launcher-to-Reaper/logger path using docs/41–49 as normative contracts. It is a proposal; architecture, backend, security, test, and product/E2E reviewers must approve this exact version before orchestration implementation. The route and binaries remain opt-in (`pilot_e2e`) with synthetic fixtures only. This slice ends at verified RunRoot readiness plus safe process teardown; it does not claim lesson completion or production classroom authorization. A shared multi-student classroom and full docs/41 lesson completion require a separate reviewed product SDD because docs/41 currently binds one student owner to one lesson.

## Current gap and boundaries

Existing pilot code includes lesson-start rendering/sidecar, BOOTSTRAP and recovery wire transports, RunRoot filesystem primitives, `RunRootLedger`, durable logger queue/store/client/service, and peer/recovery helpers. There is no trusted host launcher executable/journal, no integrated `PilotHostReaper.CreateRunRoot`, no atomic RunRoot finish outbox or docs/43 containment-finalization store, no API coordinator or browser route, and no end-to-end lifecycle. `RunRootLedger` currently proves handoff and contains partial allocation primitives; it is not the docs/43 control ledger and cannot authorize classroom success or release a lease.

The browser never supplies path, principal, session hash, PID/UID/GID, epoch, generation, nonce, process identity, logger endpoint, evidence, or capability. The application authenticates the learner and fixture. The dedicated admission signer receives `tenant_id` and immutable `immutable_user_id` only from authenticated server context (never HTTP/body), and derives `session_key_hash` from the current server session. It does not derive or claim `principal_ref`. It signs fixed-order canonical CBOR bytes, not JSON: `ASCII("en-words-pilot-admission-v1\\0") || CBOR([version=1,key_id,issuer="en-words-web",audience="pilot-launcher",tenant_id,immutable_user_id,session_key_hash,authz_revision_u64,authz_snapshot_digest_32,session_revision_u64,role="student",fixture_id,idempotency_key_hash,payload_digest,issued_at_unix_seconds,expires_at_unix_seconds])` with Ed25519; the frame is canonical CBOR `[claims_bytes,signature_64_bytes]`. Intent-handle minting uses a distinct signed claim: `ASCII("en-words-pilot-intent-mint-v1\\0") || CBOR([version=1,key_id,issuer="en-words-web",audience="pilot-launcher",tenant_id,immutable_user_id,session_key_hash,authz_revision_u64,authz_snapshot_digest_32,session_revision_u64,role="student",fixture_id,request_nonce_16,payload_digest,issued_at_unix_seconds,expires_at_unix_seconds])` signed with the same web-only Ed25519 admission key; its frame is `[claims_bytes,signature_64_bytes]`. The web service generates the fresh 16-byte nonce; it is correlation data, not a one-time token. The launcher verifies exact canonical bytes, signature, issuer/audience, freshness and closed field schema before sending the authenticated claim to the resident resolver, which validates current authorization and resolves principal. Replaying an otherwise valid mint claim may issue another unused handle but has no journal, run, lease, generation, spawn, or root effect; one browser activation is single-flight and only the returned handle can be submitted to run start. Invalid, expired, wrong-audience, or forged claims are rejected. This mint claim contains no idempotency handle or epoch. The launcher accepts it only for principal resolution, current-fence validation, and AEAD handle encryption; it cannot enter journal lookup or business admission. The subsequent run-start admission uses the ordinary schema above and hashes the opaque handle. `tenant_id` and `immutable_user_id` are bounded canonical opaque bytes from the authentication service, and never names or client assertions. The resident `PilotControlReaper` runs under the dedicated control-service identity before the launcher/API admission route is enabled; it owns the protected versioned HMAC keyring and principal alias table per docs/43 §2.1 amendment. Its `ResolvePrincipal` endpoint accepts only the configured launcher identity. It validates the signed admission/current authorization and is the sole principal resolver; no HMAC key or alias secret is shared with web or launcher. The launcher calls it before journal lookup, key replay, queueing, or spawn, including status and close requests for old runs. The resolver atomically returns/creates the canonical principal under all-version alias lookup; the launcher verifies a resolver-signed response bound to a fresh request nonce and the admission digest. It discards the raw immutable ID and persists only tenant/principal/session hashes. Per-run Reaper does not call the admission resolver; it uses a separate typed ledger-RPC endpoint whose caller identity is registered by the launcher and checked against its exact generation/run binding. Missing resolver, key material, or alias integrity, or a tombstone with missing alias, fails closed before journal lookup/spawn (`pilot_unavailable` for unavailable service; `ipc_registry_corrupt` for identity corruption). It never mints a second namespace. Authorization freshness is a durable control-ledger fence, not the admission TTL. The signed claims include the current monotonic `authz_revision`, `authz_snapshot_digest` (covering role and fixture grants), and `session_revision`. The authenticated web authorization authority publishes every restrictive role/fixture/session change to the resident `PilotControlReaper` with an idempotent signed `PublishAuthorizationFence` before reporting that change effective; the resident commit is the revocation linearization point. Grant increases become usable only after both authority and fence are current. The fence stores only tenant/principal/session hashes, revisions, allowlisted role/state, fixture ID and snapshot digest. `PrepareWithHandoff` compares admission revisions/digest to the fence inside the same `BEGIN IMMEDIATE` transaction that commits the operation, so prepare-before-revocation or revocation-before-prepare has a single writer-ordered outcome. Status replay and close retry call `CheckCurrentAuthorization` before any launcher-journal lookup; unavailable/stale fence fails closed. Initial HTTP middleware is preliminary only. The launcher journal receives only the resolver-issued principal pseudonym. `key_id` is 1–32 lowercase ASCII `[a-z0-9-]`; hashes are exactly 32 raw bytes; timestamps are unsigned 64-bit seconds; lifetime is 60 seconds and accepted clock skew is at most 30 seconds. Reject noncanonical CBOR, wrong field count/order/type/length, unknown key ID, bad signature, wrong audience/issuer/role/tenant/fixture, future/expired claims, or unknown fields before state changes. Provision current/next public keys read-only to launcher and resolver; the admission private key is readable only by the web service and the resolver response signing key only by the resolver. Rotation keeps at most current+next; revocation fences new admission and every not-yet-prepared request at the resident-ledger commit point, while a committed operation remains governed by its persisted receipt. The API reaches launcher over a fixed owner-only Unix `SOCK_SEQPACKET` endpoint; launcher checks socket identity, `SO_PEERCRED`, and one matching `SCM_CREDENTIALS` per packet against the configured web-service UID/GID. This does not alter BOOTSTRAP's fixed wire schema. Raw session tokens, immutable IDs and names never enter logs; session tokens and names never cross this boundary.

The resolver is a host control service, not a per-run child. It must be healthy before the pilot route or launcher accepts requests; its stop/restart cannot silently reset alias/key state. Concurrent first use of the same authenticated account is serialized by the protected ledger and returns one canonical principal. Same-account reauthentication and wrapping-key rotation preserve the original alias. Resolver timeout, signature mismatch, unavailable HMAC version, alias/tombstone mismatch, or damaged resolver database never falls back to creating a fresh principal.

`PilotControlReaper` is the resident singleton that owns the protected VFS connection, OS single-writer lock, alias table, and every control-ledger transaction; `PilotIdentityResolver` is its pre-launch command. Per-run Reaper children never open `operations.sqlite`; they submit typed ledger RPCs to this single writer using their registered process identity and exact generation/run binding. The launcher resolves an admission before acquiring its own journal mutex, and the resident service completes identity RPC before starting any business transaction. The resolver frame, Ed25519 response binding, launcher-only peer identity, and 500 ms fail-closed deadline are fixed by the docs/43 §2.1 amendment. No ledger transaction may call or wait on resolver IPC, eliminating a resolver↔writer lock cycle.

## API and durable idempotency contract

Expose only in pilot builds:

- `POST /api/v1/pilot/intents` with body `{ "fixture_id": "..." }` is called only after the learner explicitly selects Start. After authentication, authorization, and principal resolution, the trusted launcher authority returns a random opaque `intent_handle` bound to the current `namespace_epoch`, tenant, stable principal, fixture, and key purpose. The handle is an AEAD-encrypted opaque token whose authenticated plaintext binds its claims; the browser cannot inspect, choose, edit, or supply an epoch or principal, and no claim is exposed as a separate field; the handle is not authority without a fresh authenticated admission. Issuance has no run, lease, generation, spawn, or journal business effect, so losing the response may leave an unused handle but cannot start work.
- The `/pilot` Start handler takes a synchronous single-flight lock before its first `await`, disables the control while handle issuance/start is pending, and permits at most one handle request and one run-start request for one activation. Rapid/double clicks in that pending interval are ignored. Retries after the handle is persisted reuse that same value; they never mint another handle. If intent issuance fails before a handle is returned, the UI reports that no run started and unlocks for a new explicit activation. Other tabs or later explicit activations are distinct user intents.
- Before sending `POST /api/v1/pilot/runs` with body `{ "fixture_id": "..." }`, the browser persists the returned opaque handle and sends it as `Idempotency-Key`; it reuses that exact handle for retries, refresh, and reauthentication. The launcher validates handle authenticity, current epoch, fixture binding, and current authorization; stale epochs fail before journal lookup. For a current epoch it hashes the opaque token and checks for an existing owner-scoped binding; existing identical bindings remain usable after first-bind expiry, while an unbound token must still be unexpired before the journal bind is written. Handle issuance is not silent reminting: after `idempotency_epoch_expired`, the UI requires a new explicit Start action and obtains a new handle; it never auto-retries the expired operation. Identity and role come only from authenticated server context.
- `GET /api/v1/pilot/runs/by-key` with the same key; it is scoped to the stable authenticated principal (with current tenant/role authorization), and remains queryable after reauthentication. Raw request IDs or epochs never authorize lookup.
- `POST /api/v1/pilot/runs/by-key/close` with the run's original `Idempotency-Key` plus a distinct random `Close-Idempotency-Key`; only the owning currently authorized principal may request closure. The launcher journal is the durable close-key fact source: before teardown it fsyncs `(principal_ref,run_epoch,close_key_hash,close_payload_digest,close_operation_id,state)`; retry with the same tuple returns the recorded result, while any conflicting tuple is rejected. The launcher creates a random close operation ID with the first durable close-key journal write; clients never supply this field. Identical retries return the same close result; changed close payload conflicts. Queued-before-spawn runs are durably canceled without launching children and report `canceled`; there is no generation or lease. During `starting` before BOOTSTRAP commit, the launcher may cancel, reap all children, and report `canceled` only after durable proof that no ledger handoff/lease or business effect exists. After BOOTSTRAP commit but before Gateway REGISTER_ACK, close uses the startup failure containment/reap path and MUST NOT send UNREGISTER; it reports `recovery_required` and holds the lease if any outcome is uncertain. A `registered` run with no RunRoot operation may send one UNREGISTER and close without a `bootstrap.finish` row only when the ledger proves no RunRoot operation was prepared and the root is absent; `ready` runs require all RunRoot finish rows ACKed before final lease release. If CreateRunRoot is prepared, `BeginRunTermination` first atomically commits the close and freezes Claim, then the original Reaper must cancel the exact prepared/no-dispatch operation and acknowledge its durable cancellation before UNREGISTER. Missing proof or ACK yields `recovery_required` with the lease held and no UNREGISTER. If CreateRunRoot is executing, closure waits for its durable terminal outcome; uncertainty remains `recovery_required` with lease held. `closing` replays the same close result without resending it; `closed` returns the stored terminal result; unknown state returns `recovery_required` without side effects. GET never starts cleanup. Close returns `202 closing`, then `closed` only after finish-event ACK, durable cleanup disposition, containment finalization, and lease release. A pending finish does not prevent containment teardown, but prevents finalization: return `recovery_required`, hold the lease, and block another generation until offline reconciliation. An EEXIST collision receipt may deliver a typed failure finish, but its indeterminate allocation/run terminal is never finalized or cleaned automatically; close can prove Gateway containment empty while preserving the lease and `recovery_required` until offline reconciliation. A no-RunRoot registered abort has no finish event or RunRoot cleanup-disposition row; it requires the exact pinned-anchor absence witness and containment evidence, then the finalizer creates the typed close receipt atomically with terminal state.

The trusted launcher authority issues each opaque intent handle as `ih1.<key_id>.<base64url-no-padding(nonce_12 || ciphertext_and_tag)>`; decoding must re-encode to the identical unpadded base64url text or reject: AES-256-GCM uses a 96-bit nonce formed from a per-key random 32-bit prefix and a monotonically increasing 64-bit counter. A per-key process mutex covers keyring read, counter reservation, durable fsync, and encryption across all concurrent launcher requests; each counter value is reserved once, persisted before use, and never rolled back after a crash. Rotate before 2^24 handles or counter wrap, whichever comes first. The keyring counter and key material live outside the VM snapshot domain; missing/corrupt state or any uncertain rollback disables handle issuance. AAD `ASCII("en-words-pilot-intent-handle-v1\0") || ASCII(key_id)`. The exact canonical-CBOR plaintext is the fixed-order array `[version_u8=1, namespace_epoch_bytes_16, tenant_id_bytes_1_to_128, principal_ref_bytes_32, fixture_id_utf8_1_to_128, purpose="pilot-run-start", handle_id_bytes_16, issued_at_unix_seconds_u64, first_bind_expires_at_unix_seconds_u64]`. Epoch bytes are the raw 16-byte journal ID; the external API renders its lowercase hex form only where the existing protocol requires it. Reject any alternate array length/order/type/width, noncanonical CBOR, unknown purpose, invalid UTF-8, zero/all-zero required IDs, or expiry not exactly issue time + 86,400 seconds. The AEAD key is launcher-only and separate from the resolver HMAC/signing keys; the browser sees only opaque ciphertext. Handles expire 24 hours after issuance for first binding only. Keep previous AEAD keys decrypt-only in the external, non-snapshotted launcher keyring for as long as any handle under them may be presented, including after their namespace epoch is retired; do not discard a key merely because restore advanced. Missing keys or a counter/high-watermark mismatch disables issuance and admission rather than weakening verification. Validation order is: authenticate and resolve current principal; decrypt and validate the exact token; compare its embedded epoch to the externally current epoch (stale returns `idempotency_epoch_expired` before journal access); enforce current tenant/role/fixture fence; then perform an owner-scoped hash lookup. If an identical handle is already durably bound with the same payload, allow status/retry/close after the 24-hour first-bind window, subject to fresh authorization. If no binding exists, an expired handle returns `intent_handle_expired` without writes, spawn or root access; a changed payload conflicts. GET and close only operate on an existing binding. Malformed, unauthenticated, wrong-purpose, wrong-principal, wrong-fixture, and stale-epoch handles cannot disclose a journal result. The epoch is exactly the lowercase 32-character hex encoding of the ledger journal ID. A fresh signed boot marker from the deployment control plane binds that ID and its externally stored restore generation to a one-time challenge; the generation advances on each platform restore. Stale epochs return `idempotency_epoch_expired` after authentication/current authorization and before journal lookup. This principal-scoped handle is admission idempotency only. The internal docs/43 `run_root_create/v1` business_operation_id remains exactly the 16 raw bytes decoded from the newly allocated run_epoch, as required by docs/45; launcher durably maps the handle hash and payload digest to that epoch/request before any retry can create another run. Before any idempotency lookup the server validates the current authenticated tenant, role, and stable principal; no RPC can self-assert identity. The idempotency namespace is `(tenant_id, stable principal_ref, namespace_epoch, idempotency_key_hash)`; `session_key_hash` is recorded as the original admission evidence but is not part of the business-operation key. Thus the same principal may recover/query the same operation after reauthentication with a new session, subject to current role/tenant authorization; another principal's attempt to use an identical handle is rejected with the same generic not-found response and no side effect; independent operation requires that principal to obtain a handle in their own authenticated context. A changed payload under the same principal/handle conflicts before side effects. Cross-principal lookup returns the same generic not-found result whether or not another operation exists. Before spawn, the singleton-locked launcher journal binds the namespace/handle hash to payload digest, docs/45 epoch-derived business operation ID, `request_id`, `run_epoch`, generation, original session hash, and lifecycle state, then fsyncs. Same principal/handle/digest/epoch returns the existing operation without another spawn. After disaster restore, the old handle fails epoch validation; only a new explicit Start action can request another handle. The server never silently remints for an existing operation. Crash recovery reconciles this mapping against the docs/43 control ledger; missing/mismatched mapping quarantines instead of allocating another epoch. Launcher status is authoritative for spawn lifecycle; Reaper's docs/43 operation/allocation/run-terminal/outbox state is authoritative for business status. Stale launcher projections cannot say `ready` or `closed`; when Reaper state cannot be verified, return `recovery_required`.

HTTP results use exactly these public states: `queued`, `starting`, `ready`, `closing`, `canceled`, `rejected`, `recovery_required`, `closed` (RunRoot startup/teardown only; this is not lesson completion). An accepted asynchronous start or close returns `202` and opaque request correlation; status polling uses only the authenticated idempotency key. Errors use stable codes, including `idempotency_conflict`, `intent_handle_expired`, `invalid_intent_handle`, `idempotency_epoch_expired`, `pilot_unavailable`, `fixture_not_allowed`, `operation_canceled`, `restart_required`, and `ipc_result_indeterminate`. `restart_required` and `ipc_result_indeterminate` map to `recovery_required`, never to a new attempt. `ready` is returned only after the RunRoot receipt, required `bootstrap.finish` delivery acknowledgement, and active lease are verified. `closed` requires terminal ledger commit, containment evidence, required event ACKs or the exact prepared-cancellation suppression proof, and lease release; it does not mean a lesson finished.

## Trusted lifecycle and exact ordering

The single allowed order follows docs/47 and docs/48: (1) acquire launcher singleton lock and fsync a new generation/nonce/request binding; (2) start Logger and authenticate exact `LOGGER_READY(ok)` against its pinned child; (3) spawn Reaper and a held Gateway, each with clone3-created pidfd and target cgroup placement before first instruction; neither may serve business work; (4) send BOOTSTRAP to Reaper with the already-pinned Gateway pidfd and wait for commit-bound ACK; (5) send LOGGER_REGISTER with the pinned Reaper pidfd and wait for durable ACK; (6) Reaper connects and authenticates Logger, waits for `LOGGER_CHANNEL_READY`; (7) Reaper emits `bootstrap.start`, waits for durable ACK; this event is not replayable; (8) launcher sends Gateway REGISTER and waits for ACK; only then may Gateway accept authenticated business requests or spawn a worker. Any failed/uncertain gate closes admission, kills and reaps affected children by pidfd/cgroup, and keeps the lease held.

For the authenticated student's start request, Reaper binds the signed admission to its session map and requires the complete BOOTSTRAP handoff tuple to match docs/47: generation, launch nonce, run epoch, PID, UID, start-time ticks, pidns device/inode, and cgroup mount ID/device/inode. `Prepare` must atomically verify this exact consumed handoff and insert the docs/43 allocation/operation/reservation; a standalone consume followed by an unbound prepare is forbidden. Before implementing this integration, define the control-ledger schema as version 3: an empty database may initialize the exact v3 schema, the reviewed v2 fixture is rejected, and there is no implicit migration. V3 includes the immutable BOOTSTRAP/recovery generation+nonce domain, docs/43 operation/allocation/receipt/containment tables, and the outbox below. Schema object inventory and DDL are hash-bound and must be reviewed with docs/43–49.

## RunRoot, outbox, and recovery semantics

The Reaper transaction is deliberately split at durable boundaries; SQLite, Logger, filesystem, and launcher journal are never described as one cross-system transaction. The global kill/reap rule below applies to startup gates (LOGGER_READY through Gateway REGISTER_ACK) only. After that point, the phase matrix controls; in particular, a pending finish outbox does not cause terminal state to be rewritten or lease released.

| Boundary | Durable action | Failure/retry rule |
| --- | --- | --- |
| Before `prepared` | Validate admission/handoff; no filesystem effect | Stable rejection; same idempotency binding may retry. |
| `prepared` | Insert allocation/operation and exact `run_root_dispatch_intent` bytes/outbox delivery identity | Intent ACK loss leaves `prepared`; same request may resume once with the exact stored event and a fresh delivery nonce. |
| `executing` CAS | Persist owner generation and `run_root_dispatch_committed` identity before syscall | Missing/uncertain ACK fences epoch, retains lease, and prohibits mkdir/reopen/business retry. |
| Filesystem effect | Create via pinned handles; verify owner/mode/ACL/device/mount; fsync child and anchor | Deterministic errno plus exact absence witness may terminal-abandon only via docs/43 final transaction. EEXIST records operation=`abandoned`, `response_code=exists`, allocation/run=`indeterminate`, lease=held; it creates no root-state or cleanup-disposition row and never opens/queries/deletes the collided target. The API projects recovery-required. Post-create error, crash, or unknown result is indeterminate and held. |
| Terminal commit | One docs/43 transaction writes receipt, operation/allocation/run state and `bootstrap.finish` outbox row | Commit uncertainty requires process restart and ledger inspection; never infer from logger output. |
| Finish delivery | Send exact stored event; mark only its outbox delivery acknowledged after matching durable ACK | ACK loss preserves the committed terminal state and lease exactly; replay only exact deduplicated `bootstrap.finish`; expose no capability/ready until acknowledged. |
| Run termination | Launcher sends UNREGISTER only after any prepared/no-dispatch cancellation ACK; Reaper drains and acknowledges; launcher removes endpoint, kills Gateway cgroup, proves empty and waitid-reaps by pidfd; on authenticated CONTAINMENT_EMPTY, the original live Reaper safely cleans or retains a created RunRoot and commits cleanup disposition, then persists immutable containment evidence and finalizes. A prepared-cancel run has no root, uses the pinned-anchor absence witness and `cleanup_state=not_required`; the dedicated finalizer writes the typed close receipt atomically. | Only the final transaction releases lease. A new Reaper is spawned only after old children are reaped. `RECOVERY_BOOTSTRAP` consumes a strictly higher shared control generation. Exact old target + missing evidence returns `recovery_proof_missing` without target mutation; exact committed cleanup and containment evidence permit only the matching reviewed finalization/read-only already-terminal response; mismatched target rejects. Replacement recovery never performs cleanup or fabricates evidence. It cannot create Gateway, worker, new epoch, or business operation. |

Recovery actor is the launcher under its singleton lock plus a fresh higher-generation recovery-only Reaper over the authenticated private channel. The recovery-only actor cannot create or infer containment evidence, and cannot deliver a pending `bootstrap.finish`: current docs/47-48 authorize neither action. A missing-evidence target returns `recovery_proof_missing` without target mutation. A separate protocol SDD and review are required before any recovery-only outbox delivery can be implemented. Normal Gateway/business retry on the old epoch is forbidden. Before any original Reaper sends any outbox event, it must durably commit `AuthorizeOutboxSend`; retries may send only the exact stored bytes after that commit. Cancellation and send authorization share the ledger writer, so a late sender cannot send a suppressed intent. A prepared operation with a durable `run_root_dispatch_intent` may resume only while the original Reaper remains live and has a valid Logger registration/channel; if the row is `ready`, it first commits send authorization, and if already `send_authorized`, it may redeliver only the exact stored intent bytes with a fresh delivery nonce. If logger restart invalidates registration and requires Reaper reap, the old generation cannot resume business dispatch. An already committed outcome-bound `bootstrap.finish` may still be authorized and delivered by the original live Reaper while lifecycle is `terminating`, `unregistered`, or `containment_empty`; this exception only reports the stored terminal business result and cannot start new work. It remains available after Gateway UNREGISTER while the original Reaper identity and Logger registration remain valid (a fresh data channel is allowed only after EOF/drain), and finalization waits for its ACK. If the original Logger registration expires or the Reaper exits, the result remains recovery-required with the lease held; recovery-only Reaper cannot deliver it under a replacement identity. On restart, any operation durably in `executing` without a terminal receipt becomes `indeterminate`; the epoch lease stays held and no filesystem retry is allowed because the syscall may have happened. Recovery reads only durable state and may finalize only the exact docs/43/47 containment path; it never rewrites an uncertain business result as success or no-effect. After `executing`, an unacknowledged dispatch-committed event never permits mkdir. On restart, this state is fenced as `indeterminate` with lease held; only offline reconciliation may resolve it, and recovery cannot infer whether the syscall occurred. After terminal commit, a pending `bootstrap.finish` remains pending and the run remains `recovery_required` until a separately reviewed recovery-delivery protocol exists; the current Recovery Bootstrap path cannot replay it. If containment evidence is absent, consume the recovery generation, return `recovery_proof_missing`, and preserve the hold for offline reconciliation.

V3 `run_root_event_outbox` has a strict allowlisted schema: immutable `outbox_id`, `operation_id` FK, event name, original `process_id`, canonical event bytes, event digest, and creation time; plus delivery state (`ready|send_authorized|acknowledged|suppressed`), nullable acknowledged digest/correlation, and nullable suppression receipt digest. Unique `(operation_id,event_name)` is enforced for the two documented deduplicated events only: `run_root_dispatch_intent` and `bootstrap.finish`. `run_root_dispatch_committed` is never replayed. Insert `bootstrap.finish` in the same SQLite transaction as the terminal receipt/state. Before Logger writes, the original Reaper commits `ready→send_authorized`; only then may an exact ACK commit `send_authorized→acknowledged`. Prepared cancellation may instead commit `ready→suppressed` with its immutable receipt. An already acknowledged intent remains acknowledged. Each send carries a fresh Logger `delivery_nonce`; the successful ACK persists that exact nonce as the sole correlation alongside the matching digest. No second nonce field exists. Retries are single-flight after EOF/drain under the same live Reaper identity and active Logger registration; stale ACKs from retired channels are ignored. ACK is accepted only when original process identity, outbox/event tuple, correlation, and digest match; any other transition fails and fences the store. Delivery receipt mutation cannot change operation result or lease. Unknown tables/columns/DDL fail startup. Exact DDL, FK/unique constraints, all writer transaction predicates, recovery interfaces, v2 rejection, and fault matrix are a required separate v3 ledger SDD and remain a blocking design dependency for implementation stage B.

## UI, lesson, and diagnostics

This slice exposes one run per authenticated student; it does not model shared classroom membership. E2E uses two synthetic student sessions and an administrator context for role-denial checks; the fixture is pre-provisioned by the isolated test harness: both students submit start requests concurrently, but the single-generation launcher serializes them: exactly 2 idempotency namespaces, generations, epochs, RunRoots, and ready results are produced sequentially, with at most one active run at a time. Each student closes their own run through the close operation before the next queued generation is admitted. Replaying either student's key creates no additional launch/root; replaying a close key does not repeat UNREGISTER. Cross-student status lookup returns generic not-found; this slice exposes no join operation.
