## 1. 目标与边界

在 `pilot_e2e` 构建标签下，隔离测试网关父进程承载HTTP入口、session/CSRF认证和owner映射；专属 Pilot Worker 子进程承载应用handler、Supervisor、catalog及所有case文件/锁句柄。网关只通过受ACL保护的本机IPC转发已授权的typed请求；浏览器不直连worker。父进程死亡会终止并废弃整个run；worker单独重启时父进程的owner map/session和run签名密钥保持。case ID仅为签名授权信封内的不透明catalog selector，不是权限凭据或路径输入，详见§3。

本文冻结完整test-only pilot harness的进程/授权边界，以便设计评审能覆盖真实重启与浏览器调用路径；当前首个实现增量仅包含可信本机Supervisor、签名grant IPC adapter和隔离文件生命周期，不接入产品App/Room、模型、音频或课堂Coordinator。Gateway loopback HTTP、产品Coordinator接线和Playwright浏览器旅程仍是后续独立实施/验收门；不得绕过或复制本SDD的授权路径。默认server与`go list ./...`不得包含这些pilot专用实现。

## 2. 威胁模型与安全不变量

监督器进程及其 OS 账号可信；浏览器输入、子进程消息、已有磁盘内容、目录项和并发启动均按不可信处理。排除同一可信账号、管理员、内核、宿主机或文件系统被攻陷。case 仅含合成学生数据。若文件系统不支持所需锁、身份或耐久语义，启动失败，不允许降级。

1. 每个run的supervisor根为OS固定私有数据根下的`pilot-runs/<32hex-run_epoch>/`。Gateway用OS CSPRNG生成128-bit run_epoch；anchor的`pilot-runs/`只允许`<32hex-run_epoch>/`直接子目录。Supervisor从已验证anchor handle相对操作run目录；`mode=new`以CREATE_NEW创建，已存在即fail closed；`mode=resume`仅允许同一Gateway确认旧worker PID已退出后打开并验证原目录。公开构造器只接受严格格式run_epoch与枚举mode、不接受路径。新Gateway run必须使用未存在的新epoch目录，abandoned目录永不重新打开。POSIX 从已验证的 trusted anchor directory handle 开始逐级 pin 根路径每个祖先，验证 owner/mode/身份并拒绝 symlink；Windows 同样逐级 pin parent handle。不能把尚未验证的绝对路径作为后续访问根。测试可用仅包内构造器传临时父目录并走同一验证流程。case ID 为 OS CSPRNG 产生的 16-byte/128-bit 随机值，编码成 `docs/41` §109.1 冻结的 32 位小写 hex；永不复用，它不是授权凭据。
2. POSIX 根/目录使用 owner-only 权限（目录 `0700`、文件 `0600`、umask `077`），验证 owner、mode、单链接、设备及 `(dev,ino)`。拒绝 symlink、硬链接、挂载点/设备跨越和目录交换。Linux 可用时必须使用 `openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV)`；fallback 对父目录 FD 与已打开子目录 FD 分别调用 `statx(fd, "", AT_EMPTY_PATH|AT_SYMLINK_NOFOLLOW, STATX_MNT_ID)`，证明两者 mount ID 一致，再以 `openat(O_NOFOLLOW|O_CLOEXEC)` 打开并在使用前对返回的同一 FD 再次 `fstat/statx(AT_EMPTY_PATH)`。若打开后的 handle mount ID 与打开前验证的父目录不同则拒绝。`st_dev` 单独不足以拒绝同设备 bind mount。内核或文件系统不提供已打开 handle 的 mount ID 或等价可验证能力时 fail closed；不得只对路径做 statx 后再按字符串路径操作。
3. Windows 固定 root 的每级祖先以 parent-handle-relative 方式打开并 pin identity；拒绝 reparse、owner/DACL 放宽及祖先句柄身份变化。目标 root 以受保护 DACL 原子创建，禁用继承，仅监督器 SID、SYSTEM 及明确需要的受限子进程 SID 获得所需访问；每次打开均使用 reparse-point-safe flags 并检查 reparse tag、owner、DACL、volume serial/file index。需阻止替换的文件句柄不共享 DELETE/RENAME；cleanup 在同一经核验的 DELETE handle 上使用 handle-based disposition。不能验证 DACL 或身份时 fail closed。实现不得把 `FileMode` 当作 DACL 证据。
4. supervisor 持有已验证根、catalog 和锁句柄；`CaseHandle` 保存不导出的路径/文件句柄/身份。所有用于校验或授权的 catalog 读取必须持 global catalog lock。打开流程先持 catalog lock 读 advisory 状态并释放；再锁 case；最后重新取得 catalog lock 重读并裁决，释放后才 `OpenVerified`。第一读不得无锁解析 journal、报告损坏或授权。持 catalog lock 的代码不得等待 case lock。cleanup 也遵守 case lock → catalog lock 顺序。
5. catalog 首次创建用 `CREATE_NEW/O_EXCL`，文件 `Sync` 后同步父目录；只经已验证 handle append，不能截断、替换或原子改名。初始 catalog 预留 case 为 `provisioning` 后，才创建 case 数据。所有操作有界；任何损坏、身份变化、锁/Sync 不确定、共享 health poison 均停止该 supervisor，不回退状态或继续访问其他 case。
6. 数据库只允许已存在主文件以 `mode=rw` 打开，禁止连接字符串触发创建、迁移或自动重试。打开后首条 SQL 是 `PRAGMA database_list`，只比较 SQLite 返回的 canonical path；该 PRAGMA 不返回 OS file ID，也不证明实际 SQLite handle 与预验证文件句柄相同。当前 `glebarez/sqlite` 无法提供该证明，因此本阶段明确依赖可信私有目录、其他 OS 账号不可写并排除同账号攻击，不声称 handle binding。此为 `docs/41` §112 对其§42旧文件身份措辞的明确勘误。若未来威胁模型扩大到同账号竞态，须先引入经评审的 VFS/driver 实际 handle identity 能力，否则 fail closed。路径不匹配立即关闭且零应用 SQL/receipt/Coordinator 操作。
7. case HMAC key 留在可信 Supervisor 内，不得交给不可信子进程；这是 `docs/41` §112 的明确勘误。未来若子进程需要 sidecar 签名，只能请求字段严格 allowlist 的窄化 MAC 操作；Supervisor 校验状态、序号与内容后代签，子进程永不取得 key。case MAC key 与日志 pseudonym key 独立生成、用途域分离；后者仅 Supervisor 可读，位于受保护目录（POSIX `0600`/Windows 专属 DACL）。轮换只在新 root epoch 发生，日志携带 epoch 标识但不含 key。`trace_id` 由监督器使用 CSPRNG 生成固定长度 UUIDv4/hex，不接受调用方字符串；`module/event/reason` 来自编译期枚举，外部错误只能映射固定错误类。日志仅记录 trace id、module/event、case ID 的 keyed short hash、状态前后、耗时与固定错误类别，不记录路径、原始 ID、学生信息、key、token 或输入。

## 3. 生命周期与接口

状态只通过 `pilotCatalogJournal.Transition` 推进，状态图以 `docs/41` §109 为唯一来源。监督器公开内部 API 为：

- `OpenPilotSupervisor(ctx, runEpoch, mode PilotRunMode) (*Supervisor, error)`：验证/创建本run root、初始化日志及控制锁；若 catalog 已存在则全量重放，若不存在则保持 absent，不分配case ID、不写 catalog。首次 catalog 与首个 case 只由已验签、已校验 digest 的 `CreateCase` grant 触发，避免无 principal/request_id 的构造器副作用。返回对象持有 root/bootstrap及可用时的catalog handles。任一异常不返回可用对象。
- 授权边界与进程协议：loopback Gateway只暴露test-only `POST /__pilot/v1/cases`用于创建case，路由固定签发`create` scope，不接受客户端指定scope；其余case能力使用明确的test-only typed路由。长期存活的Gateway父进程是唯一HTTP入口及认证权威，先验证服务端session/cookie、CSRF与role，再取得不可由请求字段覆盖的`HarnessPrincipal`。所有创建HTTP请求必须且只能带一个`Idempotency-Key`，格式严格为ASCII `[A-Za-z0-9._~-]{16,128}`；缺失、重复、空白包裹或非法值返回`invalid_idempotency_key`，不得分配request_id或发送IPC。Gateway维护本次run的`caseID→principal` owner映射、`(session_key_hash,idempotency_key_hash)→(request_id,digest,scope)`及`request_id→(scope,digest,selector)` create幂等映射；request_id由Gateway随机生成并按已认证session作用域内的HTTP key复用。只存key的带密钥摘要；同key不同payload或scope返回`request_conflict`。两项映射必须在同一父进程临界区绑定且均成功后才向浏览器返回。映射失败或父进程在绑定前崩溃，该run整体作废，worker由Job Object/PDEATHSIG终止，root标记abandoned、永不复用、不能跨run重开。Gateway每次run以CSPRNG生成128-bit随机run_epoch，并生成Ed25519密钥对；私钥仅驻留Gateway内存，启动worker时通过受保护继承句柄提供公钥。Gateway在会话/owner/scope校验后，将固定字段canonical编码成两种严格schema之一：create grant省略case_id，case grant必含case_id；字段为`version,run_epoch,worker_generation,request_id,principal_ref,scope,expires_at_ms,request_digest[,case_id]`；`request_digest`是对应固定typed operation canonical payload的SHA-256，worker必须在副作用前重算比对以阻止grant/body错配。Ed25519签名与canonical grant bytes封装为`SignedHarnessGrant{grant_bytes,signature[64]}`，经Windows ACL named pipe或POSIX owner-only Unix socket发送；grant有效期最多60秒；worker用本机UTC时钟验证`now < expires_at_ms <= now+60s`，并只接受已认证IPC peer、有效签名/epoch/current bootstrap worker_generation/固定schema及未过期scope；旧generation grant拒绝。所有effect-bearing请求还须由docs/43 Gateway registry按(run_epoch,worker_generation,request_id,principal_ref,scope,digest)原子claim；相同完成请求返回缓存结果，冲突拒绝，dispatch后不确定则indeterminate且禁止重派；拒绝HTTP/body/CLI直接构造的grant。worker验签后才在Supervisor进程内构造不可序列化、私有字段的`AuthorizedCase`，所有受保护成员读取前再验证run epoch、principal/scope和case selector。`create` grant不含case_id；Gateway以`(run_epoch,request_id)`为唯一create幂等键，绑定canonical payload digest。相同键/相同digest的已完成HTTP重试返回同一selector；相同键的并发重试只等待同一in-flight操作，不重复发IPC；相同键配不同digest/scope返回`request_conflict`且不调用worker。worker进程内也对相同键/digest缓存同一结果、对冲突拒绝。若worker在create结果未知时崩溃/超时，Gateway不得重发该grant，必须杀死并reap worker、将整个run/root标记abandoned并拒绝该run全部后续请求；新worker/新run使用全新root和epoch。只有完整收到selector并原子写入owner及幂等映射后才可返回成功。未知case/非owner/无权限管理员使用同一`case_not_found`状态/响应体且不得发送到worker；owner摘要constant-time比较。worker崩溃/Close unknown时Gateway有界杀死并确认旧PID退出，以相同run public key/epoch和`mode=resume`启动新worker，owner map与session保持；新worker对同一root全量replay。Gateway退出或run key丢失则拒绝恢复旧root，worker终止并将该run隔离为abandoned。
- `(*Supervisor).CreateCase(ctx, grant *VerifiedHarnessGrant) (*ReadyCase, error)`：仅由worker IPC adapter提供验签后的grant。若catalog absent，先由此请求执行§7首建；否则按后续case流程。首次 `provisioning` frame 必须先于 stable case lock，后续 case 则先创建并锁住永久 case-lock entry，再按 case→catalog 写 `provisioning`。完成固定成员创建/Sync/身份核验后才写 `ready`。uncertain 不返回 ready；worker恢复时可按§8内部replay catalog可见ID，但若Gateway尚未收到并绑定selector，则创建结果按§3 Gateway授权与创建结果协议视为unknown并废弃run/root，不得重试、重绑或返回恢复出的selector。case ID永不复用。Gateway仅在成功后建立owner映射并返回用户可见selector。
- `(*Supervisor).OpenReadyCase(ctx, authorized *AuthorizedCase) (*ReadyCase, error)`：仅 `ready` 且 scope 为 `start` 可得到允许 Start 的最小能力句柄；任何其他状态在 DB open 前拒绝。`OpenReceiptCase`、`RecoverCase`、`ResumeCleanup` 使用同一进程内capability类型并各自要求§8对应scope；capability绝不跨IPC，Gateway通过每请求签名grant委托操作；不提供接受裸`caseID`的泛化`OpenCase`。
- `(*CaseHandle).Close(ctx)`：排空本 case 在途操作，依序关闭 DB、sidecar、key、case-dir handles，只有全部关闭成功才释放 stable case lock；绝不关闭 Supervisor 共享资源。等待ctx在任何底层Close之前超时返回`close_pending`；任一底层Close调用返回错误均为`unknown`，返回`restart_required`并要求child有界退出、harness确认PID退出后才可重启。
- `(*Supervisor).CleanupCase(ctx, authorized *AuthorizedCase)`：要求case owner principal授权的 `cleanup` scope；管理员角色本身不授予跨principal清理权限，须满足docs/43 owner相等校验；持 case lock，持久写并 Sync `cleanup_quarantined` 后才删除；关闭连接，成组删除 SQLite 主/WAL/SHM/journal、sidecar、key、case 目录并 Sync 父目录，最后写并 Sync `deleted` tombstone。任一步失败保留隔离状态，不允许重开或复用 ID。
- `(*Supervisor).Close(ctx)`：进入 closing 后拒绝新操作，排空并关闭全部 CaseHandle，再关闭 catalog/global/bootstrap locks 及 root handle。等待 context 超时时不做 cleanup；保留句柄，返回可重试 `close_pending`。若底层 close state 为 `unknown`，标记 `restart_required`、拒绝全部新操作并请求专属 pilot child 非零退出；外部 harness 必须在有界时间内终止并确认该 PID 已退出，再启动新 child。不得在同一进程内构造替代 Supervisor 或允许其它 case 继续。

稳定错误码分层枚举为：基础Supervisor=`case_not_found`, `case_not_ready`, `case_integrity_error`, `supervisor_poisoned`, `lock_timeout`, `operation_canceled`, `io_uncertain`, `recovery_integrity_error`, `cleanup_pending`, `close_pending`, `restart_required`, `request_conflict`, `invalid_idempotency_key`；OS-authenticated IPC wire/peer层仅使用六类=`ipc_bootstrap_invalid`, `ipc_peer_rejected`, `ipc_listener_failed`, `ipc_cancelled`, `ipc_timeout`, `ipc_parent_gone`；docs/43定义的Gateway/HostReaper控制面另使用=`ipc_registry_corrupt`, `ipc_request_conflict`, `ipc_operation_abandoned`, `ipc_result_indeterminate`, `ipc_registry_full`, `ipc_launcher_failed`。控制面代码只由Gateway/Reaper边界返回，绝不能伪装成worker IPC peer/wire错误；HTTP映射须由Gateway固定表生成，不透出底层错误文本。POSIX/Windows底层错误只写受限诊断日志，不向HTTP/调用者透出路径、ACL、SID或文件细节；未知内部故障映射 `case_integrity_error`，提交/Sync未知映射 `io_uncertain`，receipt无法裁决映射 `recovery_integrity_error`。OS-authenticated IPC阶段仍只使用上述六类peer/wire错误，按§15.2稳定映射；其余适用错误规则不变。仅底层Close尚未调用前的in-flight context超时映射`close_pending`；Close调用后的任意错误或非法结果组合均映射`restart_required`，不允许同进程重试或接收新工作。所有锁等待、文件 I/O、Sync 和关闭必须可观测，锁/Sync 的 uncertain outcome 不得转换为可重试成功。

## 4. 并发、恢复与日志

不同 case 可并行；同 case 的 Start/open/cleanup 由独占 OS lock 串行。catalog 全局锁仅覆盖记录链读取、generation 分配、单 frame append/Sync。跨进程竞争时赢家在锁内重读最新 catalog，输家不得使用旧快照执行 DB/sidecar/key open。锁 owner 崩溃由 OS 释放；下一 Supervisor 必须先全量重放并校验记录和目录身份；完整状态的逐状态恢复和权限见§8。不得把 `open_recovery_required` 当作 `ready`，也不得在恢复中调用 Planner/Registry。

日志为UTF-8 JSONL；每行严格schema并拒绝重复/未知字段。必填字段为`trace_id`(32位小写hex)、`process_id`(每次进程启动随机128-bit hex)、`operation_id`(同一操作start/terminal共享的随机128-bit hex)、`module,event,case_hash,state_before,state_after,lock_wait_ms,io_ms,outcome,reason`；barrier事件另含枚举`barrier_name`。配对键为(trace_id,process_id,operation_id)，父子操作共享trace_id但各有process_id。时长为非负整数毫秒，outcome/reason/module/event均受固定枚举约束；每个无崩溃操作恰有一个start和一个terminal，崩溃允许start无terminal。每次bootstrap、case create/open/close/quarantine/delete、catalog replay、身份拒绝、OS lock/Sync失败均有一条结构化事件。禁止记录完整路径、case ID、principal、HMAC key、token、DB DSN或音频/文本内容。失败日志和保留文件是测试证据，不是授权来源。 Run-root bootstrap extends the compile-time event allowlist with exactly run_root_dispatch_intent and run_root_dispatch_committed, under module pilot_host_reaper; these are intermediate transition events and do not replace the operation start/terminal pair. The logger ACK echoes the exact (trace_id, process_id, operation_id, event) tuple and a bounded accepted/rejected status; mismatched or duplicate ACKs are rejected. run_root_dispatch_intent is emitted while durable state is prepared and must be ACKed before the executing CAS; run_root_dispatch_committed is emitted after the CAS and must be ACKed before mkdirat. The standard strict schema and privacy rules still apply, and no arbitrary new event or field is accepted.

## 5. 验收用例与平台门

单元/集成用例必须覆盖：随机 ID 冲突与格式边界；catalog 首建/重放/截断/坏 CRC/损坏尾；创建在每个文件 create/write/Sync/父目录 Sync 前后崩溃；provisioning 恢复；不同进程同 case create/open/cleanup 竞争；过期快照在第二次 catalog 复核时拒绝；旧 handle 被替换、owner/mode/DACL 放宽、hardlink/symlink/junction/reparse、跨设备目录、预存在 DB/WAL/key、文件 ID 变化；DB `mode=rw` 与首条 `PRAGMA database_list`；清理失败、部分删除、tombstone 写/Sync 失败；worker在ready durable后、IPC selector响应前崩溃。授权用例覆盖伪造/跨run/过期/错scope/错payload capability、A/B跨用户打开与管理员cleanup权限，并断言拒绝发生在任何成员open前、返回同一`case_not_found`且DB/sidecar/key/receipt/Planner/Registry计数为零。时间golden与故障用例注入墙钟跳变、tool_started Sync延迟、handler耗时和tool_result Sync延迟；断言Registry原始AuditEntry.TS等于permit TS、DurationMs只含单调handler耗时、逻辑tool_result.event_time_ms=TS+DurationMs，所有延迟不改变审计对应关系。仅测试构造器可注入Clock。每个进程/屏障等待设硬超时，timeout保留为失败。另固定marker/schema恢复负例：缺行、重复行、重复key约束破坏、非法UTF-8/BOM、重复/额外JSON key、非canonical空白/转义、错误version/migration ID、DDL/digest偏差；`open_recovery_required`须durably quarantine，`committed`须保持原状态、返回`recovery_integrity_error`且不返回receipt或写catalog/sidecar。R-*事实错绑/缺失/重复也分别锁定两种状态行为；断言schema/recovery/application SQL分类计数精确且Planner/Registry=0。

## 7. Bootstrap、建 case 与锁协议修订

本节优先于§2–§4中概括性锁叙述，并与 `docs/41` §109.1–§109.3 完全一致。

**首次授权 CreateCase 与 catalog bootstrap。** `OpenPilotSupervisor`只建立/验证空run root、控制锁、case/case-lock目录及§9.2日志，不分配case ID。首个create grant先完成IPC peer、签名、epoch、scope、digest及Idempotency-Key对应request绑定验证，再进入bootstrap；无有效grant不得创建catalog或case。取得bootstrap lock后核对固定inventory；catalog absent时以CREATE_NEW创建并同步文件，取得其handle上的global lock，生成case ID并追加完整首帧`provisioning`，Sync catalog及root后释放catalog lock。随后先释放bootstrap lock，再创建/取得首个stable case lock并完成固定成员provisioning。frame→stable-lock窗口仍是唯一允许有catalog ID但无lock状态；recovery只允许从完整首帧推导同ID并获取原lock，不分配替代ID。若任一步使create结果对Gateway未知，按§3 Gateway授权与创建结果协议废弃整个run/root；catalog缺失或空文件只允许由Gateway确认从未dispatch过create的同run新worker继续，否则fail closed。已完成有效catalog首建后，所有并发create均走后续case流程。

**已有 catalog 启动。** `mode=resume`仅在同一Gateway确认旧worker已reap后使用。取得bootstrap lock及catalog handle上的global lock；连续全量重放、验证catalog file identity、Sync文件和父目录。启动阶段不取得任何case lock；释放catalog，再释放bootstrap，才可调用逐case provisioning/recovery。bootstrap持锁不等待case lock，避免环锁。空的已存在catalog、坏帧、未知文件或身份不符均global fail closed；不得reset/截断。catalog absent仅当Gateway可证明该run从未dispatch过create grant时允许resume，否则废弃run。

**后续新 case。** 首建完成后，生成未曝光的16-byte ID；在永久、受保护、不可删除的`case-locks/`根下CREATE_NEW `<32hex>.lock`，验证并Sync lock文件和lock-root后取得此stable OS lock；然后取得catalog lock、重读完整catalog，确认ID从未出现，追加并Sync `provisioning`，释放catalog lock。只有此后才创建case目录、DB、sidecar、key，并逐项Sync/验证，最后在同一case lock下以case→catalog顺序追加`ready`。若进程在catalog reservation前崩溃，留下的合法孤儿lock是已消耗的随机ID：永不删除/复用，只允许它是合规的32hex lock文件且无同名case directory；计入`maxCases=65536`配额。孤儿含糊、权限错误或伴随case dir则global fail closed。catalog absent的inventory规则按本节前述首次创建授权流程裁决。

锁对象唯一且永久：root 内 `catalog.bootstrap.lock` 只序列化 bootstrap，CREATE_NEW/O_EXCL 后 Sync 文件与 root，永不删除；已验证 `catalog.log` 文件句柄本身是唯一 global catalog lock 对象，不另建同义锁文件。catalog 不存在时 bootstrap lock 串行 CREATE_NEW，再锁定这个新 handle 并 Sync 后才允许 contender 读取。启动时按 catalog state 双向核对 case-lock inventory：每个已 reservation 的 ID 必须有同 ID stable lock；唯一例外是首次已授权CreateCase写出的首个provisioning ID，在case-lock CREATE_NEW前崩溃时允许无锁；只可由同一有效create grant的内部恢复按§7创建原lock，外部结果未知时Gateway仍须按§3 Gateway授权与创建结果协议废弃run且不得返回selector。`ready/open_recovery_required/committed/terminal_failed` 必须有case directory；`provisioning` 可无目录或有目录并按§8裁决；`quarantined/cleanup_quarantined` 可有或无case directory，但仅cleanup/recovery权限；`deleted` 不得有case directory且必须保留stable lock。无 reservation 的合法锁只能是无同名 case directory 的 orphan；孤儿计入永久ID配额。任何应有锁缺失、重复ID、unknown entry、state不允许的目录或identity drift均 global fail closed。编译期精确allowlist：root仅`catalog.bootstrap.lock`,`catalog.log`,`case-locks/`,`cases/`,`logs/`；`case-locks/`仅`<32hex>.lock`；`cases/`仅`<32hex>/`；case目录仅`db.sqlite`,`db.sqlite-wal`,`db.sqlite-shm`,`db.sqlite-journal`,`attempts.jsonl`,`case.key`；`logs/`仅`events.jsonl`,`log.pseudonym.key`。所有层按目录只准对应子集，未知项 fail closed，禁止glob/前缀删除。`case-locks/` 位于可删除 case directory 之外。case lock 文件一经 CREATE_NEW 永不 unlink/recreate，即使 `deleted` tombstone 已 durable；其身份必须跨 supervisor/child 重启一致。cleanup resume 按同一 ID 在该目录 OpenVerified 原 lock identity，再取得同一锁对象。root、catalog、bootstrap locks 均为 Supervisor 持有的共享句柄，CaseHandle 不关闭它们。

## 8. Catalog 状态能力与重启恢复矩阵

每次操作在任何 DB/sidecar/key open 前按“持 catalog lock 读取 advisory 快照并释放→取得 stable case lock→重新取得 catalog lock并重读/复核→释放 catalog lock→OpenVerified 允许成员”执行。两次读取均在锁内；advisory 快照不能授权或判损坏。`provisioning` 是唯一例外：它由创建/启动 recovery 在 case lock 下检查固定成员；不调用课堂 Coordinator。状态和最小能力如下：

| catalog 状态 | 可用能力 | 重启/恢复规则 | 禁止行为 |
|---|---|---|---|
| absent | 仅经有效 create grant 新建 | 首个case由§7首建协议分配ID；worker重启仅在Gateway证明create从未dispatch时可继续absent run，否则整个run废弃 | 不得打开 case 数据或无授权bootstrap |
| provisioning | ProvisioningRecoveryHandle | 验证精确固定成员、owner/ACL、身份与 Sync；全部完整则追加 `ready`；缺失/多余/损坏则追加 `quarantined`。若 I/O/Sync 结果不确定，保持当前进程 poisoned，重启全量复核 | Start、Planner、Registry、普通 DB 查询 |
| ready | ReadyCase | 状态不变，可在 case lock 下执行一次 Start 准备并 durable append `open_recovery_required` 后才做 DB/sidecar 写 | 同 case 第二次 Start、绕过 reservation |
| open_recovery_required | RecoveryCase，仅 receipt-first/sidecar 核验 | 先校验授权及所有固定成员元数据；独立检查 receipt、audit、outbox、frozen facts 与 sidecar。完整receipt/facts可追加`committed`；仅当receipt与所有后继事实均不存在且R-NO-ORPHANS通过时，本test-only supervisor返回`pending_unknown`并拒绝新工作；部分或矛盾事实追加`quarantined`。只有仍存活的原操作已证明确定性失败、无效果且写入完整terminal失败记录时，才能直接追加`terminal_failed`；recovery不得根据sidecar单独作此转换。Sync未知保持poisoned，重启重做只读核验 | Planner/Registry重放、创建新命令、仅凭无receipt假设`not_committed` |
| committed | ReceiptCase，只读读取并核验原 receipt | 每次重启/读取都重新核验 owner、DB identity、receipt 完整事实。仅当sidecar从attempt_started至say和show_word两条已Sync `tool_result`事件（含）之前的每一行均完整、canonical且HMAC链有效，而损坏严格局限于该完整前缀之后的末尾suffix时，DB receipt仍完整且DB/目录权限有效才可只读返回原receipt并派生`sidecar_degraded`；发生在该前缀内的缺行、短读、CRC/JSON/HMAC错误或身份异常一律`recovery_integrity_error`且不返回receipt，禁止降级；catalog保持`committed`原状态、不写catalog/sidecar，后续仍拒绝Start且每次读取重新校验。两类路径都永不接受新命令 | 写 DB/sidecar、Planner、Registry、重置 degradation |
| terminal_failed | StatusCase（catalog-only）或 CleanupCase | catalog state 是 durable terminal outcome；按明确 status API报告 not_committed；随后只可 cleanup | 打开 DB/sidecar/key、重试副作用 |
| quarantined | CleanupCase only | 保留证据，等待显式 cleanup；不自动从 quarantine 恢复 | DB、receipt、sidecar、key、Planner、Registry 全部不得打开/调用 |
| cleanup_quarantined | CleanupResumeHandle only | 复用 stable case lock，按固定成员清单移除剩余文件；不访问 DB 内容。若 case directory 存在，验证为空后以 pinned parent handle 删除并 Sync parent；若其不存在（允许的“删除+Sync已成功、deleted frame未写”崩溃点），在 pinned case-root/父目录复核 absence 并 Sync parent；两条路径均成功后追加 `deleted` | 所有普通 open/recovery/receipt/Start |
| deleted | Tombstone only | 永久拒绝，case ID 与 stable lock identity 永不复用 | 任意成员创建/open/Start |

Provisioning文件创建顺序及允许打开集合：case directory→CREATE_NEW复制已校验的嵌入`pilot-case-v2.sqlite`模板→CREATE_NEW empty sidecar→CREATE_NEW 32-byte key；模板逐字节hash必须等于fixture digest，每项文件Sync再Sync case directory，全部权限/identity复核通过后append `ready`。恢复只核固定名单和元数据；`provisioning`下不打开SQLite，仅以同identity、完整模板SHA及固定长度确认原子复制完成后，必须对已验证的DB文件句柄Sync，再对已验证case目录Sync；两次Sync及随后目录复核均成功前不得追加`ready`，任一失败/不确定结果全局poison并返回`io_uncertain`。其它恢复状态最多一个`mode=ro`连接，并严格执行§9的schema验签SQL与§9.1只读业务事实SQL；无migration/写SQL/业务执行SQL/Planner/Registry。sidecar须为空且合法，key长度/权限正确。空、缺失、额外或损坏成员一律quarantine；唯一可重试的模板复制是catalog仍为provisioning且DB目录项尚不存在的CREATE_NEW之前。

`OpenReadyCase` 只接受 `start` scope 并返回 ReadyCase；`OpenReceiptCase` 只支持 `committed`、要求 `receipt_read` scope，经授权返回只读 receipt，并允许派生 sidecar_degraded；所有 case-scoped API 都先验证当前 run 的不可伪造 `AuthorizedCase` 和case归属，普通用户scope还必须匹配owner principal；case selector不能替代principal认证或成为路径输入；`RecoverCase` 只支持 `provisioning`/`open_recovery_required` 并要求 `recovery` scope；`ResumeCleanup` 只支持 `cleanup_quarantined` 并要求case-scopedcase owner授权的`cleanup` scope；管理员角色不绕过owner检查；`terminal_failed` 只提供 catalog-only status 与 cleanup；`quarantined/deleted` 没有数据 handle。每个 typed handle 接口不暴露其它 capability。拒绝状态的测试必须断言 DB/sidecar/key open计数为0。

## 9. 内部接口、超时、资源及 SQLite 接线

文件层在平台 adapter 后仅暴露内部窄接口：`verifiedRoot`（`Identity, OpenDir, CreatePrivateDir, ReadNames, Sync, Close`）、`verifiedDir`（`Identity, OpenExisting, CreateExclusive, CreateDir, RemoveFile, RemoveDir, ReadNames, Sync`）、`verifiedFile`（有限大小 `Read/Write/Seek/Stat, Identity, Sync, Close`）、`osFileLock`（`TryLock, Unlock`）。传入名称必须属于编译期目录精确 allowlist：root控制项`catalog.bootstrap.lock`,`catalog.log`；case-lock根下`<caseID>.lock`；case根下`<caseID>/`；case目录成员`db.sqlite`,`db.sqlite-wal`,`db.sqlite-shm`,`db.sqlite-journal`,`attempts.jsonl`,`case.key`；日志目录成员`events.jsonl`,`log.pseudonym.key`。未知项 fail closed，禁止glob/前缀删除，不接受外部相对路径。接口返回 owner/mode-or-DACL/link/reparse/device/file-ID能力快照；业务包不通过`filepath.Join`重开成员。唯一字符串绝对路径只用于root初始化和SQLite driver URI。

支持矩阵：Linux amd64/arm64 本地 ext4/XFS；openat2 必须含 `RESOLVE_NO_XDEV`，fallback 必须逐级使用 `statx` mount ID，无法辨别 mount 拓扑即拒绝，不能只比 `st_dev`。Linux CI 必测 native 与强制 fallback 两支；`/proc`、NFS/SMB/FUSE、未知 fs type、没有目录 Sync/跨进程 flock 的环境拒绝。Windows amd64 NTFS；每级路径相对已验证父目录句柄打开，用 reparse-safe `CreateFile` 并核对 reparse tag/DACL/owner/VolumeSerial+FileIndex。cleanup 先关闭 DB/sidecar/key 句柄，再以 DELETE 权限打开固定成员、复核同一 handle 的身份并用 handle-based disposition 删除；不按字符串路径删除。阻止替换的常驻句柄不共享 DELETE，稳定 case-lock 永不删除，受保护父目录 DACL 阻止验证到删除间替换。ReFS/FAT/network share/未知文件系统拒绝。macOS/BSD 当前不支持；未经同等 review 不可编译成“可运行”。

锁获取通过非阻塞 `TryLock` 循环和 `context` 检查，不调用无界阻塞 `LockFileEx/LOCK_EX`。bootstrap/catalog/case 各有 5 秒默认等待上限，可由仅测试构造器缩短，不可由请求放大；轮询间隔 5→10→20→40ms capped，测试通过 IPC barrier 不用 sleep 调度。尚未拿锁时`context.Canceled`映射`operation_canceled`，`context.DeadlineExceeded`或内部5秒cap映射`lock_timeout`；两者均保证catalog state不变且零成员open。取得锁后，输入校验、读取和 OS syscall不可保证被 context 打断；一旦开始持久写，忽略请求取消并完成 write+Sync，或以 `io_uncertain` poison，绝不把 context cancellation当回滚证明。OS `Sync`、close等若被内核挂起只能由 runner watchdog终止进程，API不虚报硬实时期限。Unlock失败时 shared supervisor poison，case保持不可用；Sync/write未知后不在同进程重试。

Supervisor拥有root/bootstrap/catalog/global locks及health/handle registry；CaseHandle拥有case lock、case-dir、DB、sidecar/key与inflight计数。每次操作先取Supervisor operation lease，再取case lease；Close转换状态、拒绝新lease、等待inflight归零，再依序关闭 case DB→sidecar/key→case-dir→case lock。Supervisor.Close先关闭全部CaseHandle，再关闭 global/catalog/bootstrap/root。重复成功Close是幂等；任何底层Close/Unlock调用返回错误即为`unknown`，不得重试任何OS Close/Unlock，设置`restart_required`、请求专属pilot child退出，外部harness必须在有界时间内终止并确认PID退出，然后才可启动新进程；同进程不允许创建替代Supervisor。不得双重Close共享句柄。close等待使用ctx，超时发生在调用任何底层Close之前，返回`close_pending`且不cleanup、不释放仍被使用的句柄。

生产 close adapter 返回 `{state: closed|unknown, err}` 并绑定唯一 handle generation；唯一有效组合为 `{closed,nil}` 与 `{unknown,non-nil}`，其它组合一律按 unknown 处理。`closed` 可推进关闭序列；任何 OS/driver Close 或 Unlock 错误均为 unknown，永不再次调用关闭/解锁，不推断原 handle 仍可用。`os.File.Close` 与 `database/sql.DB.Close` 错误必须按 unknown 处理。测试 fake 只有在明确提供“关闭系统调用未执行且原 handle 仍有效”的可证明事实时才可注入 `still_open`，该状态不属于生产实现合同。unknown 时 Supervisor poison、标记 `restart_required` 并请求专属 pilot child 退出；外部 harness 有界终止并确认 PID 退出，OS 随后回收锁与句柄后才可启动新进程。不得同进程创建替代 Supervisor。任一关闭失败即停止后续 close/unlock 并保持 case lock；Supervisor.Close 同理保持仍拥有的共享锁。等待 in-flight 的 context 超时发生在任何底层 Close 之前，返回 `close_pending`；只有这种未调用 Close 的情形允许同一 owner 稍后继续等待关闭。

SQLite 使用仓库锁定的 `github.com/glebarez/sqlite`/modernc driver。`pilot_e2e`构建嵌入只读空库模板`pilot-case-v2.sqlite`及其schema manifest；包含当前store基础schema、`pilotV2Objects`、索引/触发器和唯一V2 marker，不包含任何用户/课程/运行数据。离线生成器按仓库锁定的`startupModels`、trigger/index定义及`pilot_schema.go`构建，模板SHA与canonical schema digest必须作为固定golden随实现提交。运行时provisioning只通过verified file handle以CREATE_NEW复制模板字节并Sync，不执行SQLite写SQL、GORM迁移或AutoMigrate。普通DB仅以`mode=rw`打开已存在文件；URI由内部verified case directory构造，POSIX `file:/absolute/path/db.sqlite?mode=rw`，Windows `file:///C:/absolute/path/db.sqlite?mode=rw`，query escape用`url.Values`，路径含`%?#`需golden。禁用mode=rwc/cache=shared/automatic retry/Ping，GORM DisableAutomaticPing，pool max open/idle=1。每个新连接第一条SQL必须为`PRAGMA database_list`；连接替换/重连必须重新验证canonical path。

只读recovery SQL白名单（统一计入`db_schema_validation_sql`，不计`db_application_sql`）：`PRAGMA database_list`、`PRAGMA integrity_check`、`PRAGMA user_version`；`SELECT type,name,tbl_name,sql FROM sqlite_master WHERE type IN ('table','index','trigger','view')`；`PRAGMA query_only=ON`；`SELECT value FROM runtime_records WHERE key='pilot/schema/version'`与`SELECT COUNT(*) FROM runtime_records WHERE key='pilot/schema/version'`；对`pilotV2Objects`中每张表逐项执行`PRAGMA table_info`、`PRAGMA index_list`、`PRAGMA foreign_key_list`、`PRAGMA foreign_key_check`，对manifest中每个index执行`PRAGMA index_xinfo`；`SELECT id,schema_version FROM classroom_mode_metadata`。该清单只穷尽schema验签类别；receipt/业务事实读取仅按§9.1的`db_recovery_data_sql`清单授权，不得使用其它SQL。`PRAGMA user_version`必须严格等于2；marker行数必须严格为1，value必须是无BOM UTF-8且逐字节等于`{"schema_version":2,"migration_id":"classroom-pilot-v2-initial"}`；拒绝缺行、重复行、空值、非法UTF-8、BOM、重复/额外JSON key、非canonical空白/转义、错误类型/版本/migration ID。已验证schema中的`runtime_records.key`为主键；重复key同时要求行数/唯一约束审计通过。固定marker字节与generator/code golden一致。schema manifest包含全部`startupModels`基础对象和`pilotV2Objects`对象，按(kind,name,table)排序；sqlite_master每行的kind/name/table/canonical SQL以4字节长度前缀+UTF-8编码，拼接后SHA-256，与嵌入manifest digest逐字节比较；SQL规范化复用`pilotSQLTokens`。任何额外/缺失对象、DDL、marker或digest不匹配时，`open_recovery_required`须在case lock持有期间durably quarantine；`committed`须保持catalog原状态，返回`recovery_integrity_error`且不返回receipt、不写catalog/sidecar。quarantine journal写失败则global poison。模板provisioning recovery不打开SQLite；其它recovery最多一个ro连接。`PRAGMA database_list`只返回canonical path，不返回OS file ID，也不证明driver handle binding；本阶段依赖可信owner-only私有目录、其他OS账号不可写且排除同账号攻击。

### 9.1 receipt-first 恢复数据 SQL 白名单

恢复数据查询与schema验签是两个独立许可类别：`db_schema_validation_sql`只计§9 schema/marker查询；`db_recovery_data_sql`只计本节下列固定只读查询；`db_application_sql`计所有普通业务查询/写入。仅`open_recovery_required`与`committed`可运行恢复数据查询，且必须先通过签名grant、case owner授权、目录/文件identity和canonical DB path验证。确定执行顺序为：按§9语句清单顺序完成schema/marker验签；首个失败立即停止后续schema SQL及所有sidecar/data查询。全部通过后验证case key和sidecar HMAC事件链；tool-event前缀首个失败立即停止R-*。sidecar有效（或仅末尾suffix损坏）后按R-LESSON、R-RESERVATION/SCOPE、R-CHECKPOINT、R-TRANSITION、R-AUDIT、R-OUTBOX、R-NO-ORPHANS顺序执行；首个事实不匹配立即停止后续R-*。每条语句均独立计数，计数必须等于该分支执行到的最后一条语句。sidecar在`tool_started`/`tool_result`完整有效前缀内损坏时不执行R-*；仅完整有效前缀后的末尾suffix损坏会继续执行全部R-*后才可degraded。连接URI为`mode=ro`；第一条SQL必须为`PRAGMA database_list`并通过canonical-path比较，紧接着执行`PRAGMA query_only=ON`，之后才准运行任何其它恢复查询。只有固定编译期语句ID与绑定参数可调用，不接受SQL文本/表名/列名来自外部。`ready`不执行receipt恢复查询；其它状态不得打开DB。

每个固定语句使用显式列投影（严禁`SELECT *`）、绑定参数、固定排序；与`docs/41` §3的命令/receipt合同及§4的codec/audit合同逐字段比对。当前fixture恰有一个目标lesson、一个pilot reservation、一个checkpoint、一个`lesson.start` decision。列投影与唯一成功值如下：

- **R-LESSON**：在case专属DB（模板为空且每case最多创建一个目标lesson）执行固定发现查询`SELECT id,student_id,book_id,status,open_at,batch_word_ids FROM lessons ORDER BY id LIMIT 2`，必须恰1行；0行或2行视为事实缺失/多余并停止。此行的`id`成为本次恢复的内部lesson key，后续R-*只能使用此已读行及绑定case的DB结果，不要求Gateway保存或从HTTP提供lesson_id。owner/student、book、计划时间、冻结word ID顺序由reservation、checkpoint及创建事实相互核验，status=`scheduled`且lesson行其余创建字段不变；`open_at`与checkpoint/创建计划毫秒值相等。
- **R-RESERVATION / R-SCOPE**：`classroom_mode_reservations(lesson_id,student_id,book_id,mode,schema_version,reserved_at,first_entered_at,creation_nonce,creation_version,creation_fingerprint)`按lesson_id恰1行；`classroom_scope_reservations(student_id,book_id,mode,schema_version,reserved_at)`按student_id+book_id恰1行。reservation期望mode=`pilot`、schema_version=2、reserved_at等于创建时间、first_entered_at=NULL、creation_nonce等于创建计划nonce、creation_version=1、creation_fingerprint等于创建计划canonical hash；scope期望mode=`pilot`、schema_version=2、reserved_at等于reservation.reserved_at。
- **R-CHECKPOINT**：`classroom_pilot_states(lesson_id,student_id,book_id,schema_version,mode,lifecycle,checkpoint_version,logical_input_revision,question_key,phase,auth_generation,connection_epoch,retired,active_command_id,state_json,room_facts_json,frozen_words_json,frozen_config_json,config_snapshot_schema_version,config_revisions_json,config_fingerprint,content_fingerprint,creation_plan_json,created_at,updated_at)`按lesson_id恰1行。created或active codec按docs/41 §4严格解码；active时checkpoint_version=2、lifecycle=`active`、phase=`show_word`、logical_input_revision=0、question_key/active_command_id/connection_epoch为NULL、auth_generation=0、retired=false；JSON必填/禁额外字段/禁重复key/null，canonical fingerprints及冻结facts逐字节核验。
- **R-TRANSITION**：固定查询按已发现的lesson_id读取`classroom_transition_receipts(lesson_id,command_id,student_id,request_fingerprint,kind,from_version,to_version,logical_input_revision,decision_id,result_json,committed_at)`最多2行，active成功profile必须恰1行、无receipt profile必须0行；不以sidecar或HTTP值作SQL command_id参数。成功profile唯一行的`command_id`必须用case key按docs/41 §3定义的`pilot-attempt-key/v1`域分离公式重算`command_key_hmac`，与已完整校验sidecar首个attempt事件逐字节相等；再验证command_hmac/plan_hmac、request fingerprint、decision_id及全部关联记录。kind=`lesson.start`、from/to=1/2、revision=0、student与reservation一致，`result_json`严格为`{"result":"queued","audit_trace_id":"<decision_id>","outbox_count":2}`，fingerprint按docs/41 §3 canonical算法重算相等。多行、错lesson或HMAC不符均integrity failure并停止；不尝试从HMAC反推command ID。
- **R-AUDIT**：`audit_logs(ID,TS,ActorType,ActorID,ActorRole,Tool,Risk,OK,Result,Args,DurationMs,TraceID)`按ID升序且TraceID=decision_id恰2行（active成功profile）；say/show_word各1行且ID顺序匹配effect_index。ActorType=`agent`、ActorRole=`teacher_agent`、Tool精确为`say`/`show_word`、Risk=`low`、OK=true、Result=`ok`；对DB中的ActorID/TraceID用Supervisor保留的key按docs/41 §112指定域分离算法计算HMAC，分别与同attempt的sidecar task_hmac/trace_hmac逐字节比较，原始值不写日志。时间使用单一Registry timing contract：attempt开始时锚定`wall_ms`与单调时钟；每个工具调用在构造`tool_started`前从单调时钟采样`start_mono`，其`event_time_ms=wall_ms+(start_mono-attempt_mono)`，并将该TS作为不可变字段放入Supervisor签发的`PilotToolPermit`。Registry不再独立读取墙钟，原始AuditEntry.TS直接取permit的TS；Registry仅围绕工具handler用单调时钟测量`DurationMs`， sidecar `tool_result.event_time_ms=TS+DurationMs`，该值是逻辑完成时间而非写盘墙钟。`tool_started`必须先Sync再调用Registry；其Sync耗时不计入DurationMs，handler返回后的`tool_result` Sync耗时也不计入。AuditEntry.DurationMs与sidecar时间差因此逐毫秒相等且非负，满足docs/41 §3/§4冻结的原始AuditEntry一致性合同。单调时钟来源固定为进程内不可替换的`Clock`接口，测试注入仅测试构造器可用。事件链须HMAC有效、attempt_id/tool/index绑定无歧义。Args只允许以下两个精确canonical对象：say `{"bytes":N,"schema_version":1,"scope":"teacher_agent","pilot_marker":"pilot-audit-map/v1","effect_index":0}`；show_word同对象但`effect_index`=1；N等于Registry schema参数JSON字节长度。无receipt profile要求全库`pilot_marker`审计行数为0。
- **R-OUTBOX**：`classroom_effect_outbox(decision_id,effect_index,lesson_id,student_id,schema_version,checkpoint_version,kind,payload_json,delivery_status,attempt_count,next_attempt_at,claim_token,claim_until,output_auth_generation,segment_id,lease_id,created_at)`按decision_id/effect_index排序恰2行（active成功profile）；index=0/1对应say/show_word，均schema_version=2、checkpoint_version=2、delivery_status=`pending`、attempt_count=0、claim/lease/output-generation为NULL、created_at和next_attempt_at均等于start_time_ms。`payload_json`为精确canonical DTO：index0 `{"type":"say","category":"open","text":"<room_facts.teacher_text>"}`；index1 `{"type":"show_word","word_id":<frozen_words[0].id>,"word":"<frozen_words[0].word>","meanings":<frozen_words[0].meanings>}`。无receipt profile要求该case outbox行为0行。
- **R-NO-ORPHANS**：活动成功profile要求本fixture全库恰1条lesson、1条pilot reservation、1条pilot scope、1条checkpoint、1条transition receipt、2条且仅2条pilot marker audit、2条outbox；`classroom_answer_claims`、`classroom_active_commands`、`classroom_completion_jobs`均为0。无receipt profile要求lesson/reservation/scope/checkpoint仍各1条、checkpoint仍为created，transition receipt=0、pilot marker audit=0、outbox=0，claims/active_commands/completion_jobs=0。所有profile均拒绝未关联/重复/跨lesson/student/额外pilot marker/缺行。

`open_recovery_required`只有两种合法裁决：所有上述active事实完整匹配且sidecar链有效时durably append `committed`并只返回原receipt；若transition receipt、active checkpoint、pilot audit、outbox均不存在且R-NO-ORPHANS无额外行，返回`pending_unknown`并拒绝新工作；本恢复路径不从sidecar单独升级为`terminal_failed`，绝不重放。此test-only harness将docs/41 §3的一般`not_committed`恢复语义收窄为`pending_unknown`；不向调用者声称not_committed，也不改变后续产品实现必须遵守的docs/41合同。terminal_failed仅能由原存活操作在可证明无副作用后写入，不能由本恢复路径产生。事实部分存在、互相矛盾或sidecar不支持时追加`quarantined`；无法durable quarantine则global poison。`committed`正常路径仅在上述全套DB事实完整匹配且完整sidecar链有效时返回逐字段相同receipt。例外仅为损坏严格位于完整有效的attempt_started→两条tool_started/tool_result记录之后的sidecar末尾suffix：仍必须完成R-LESSON/RESERVATION/SCOPE/CHECKPOINT/TRANSITION/AUDIT/OUTBOX/NO-ORPHANS全部DB-only核验；R-AUDIT中的ActorID/TraceID HMAC、TS和DurationMs必须仍可用有效的sidecar tool events验证，不能跳过。此时返回原receipt并派生`sidecar_degraded`，只允许读取/清理，不准任何新命令；对`committed`状态，sidecar有效前缀内任一损坏或无法读出上述事件均保持catalog为`committed`、返回`recovery_integrity_error`且不返回receipt，不写catalog/sidecar；不允许违反docs/41 §109迁移到`quarantined`。对`open_recovery_required`状态，同类完整性失败可按合法`open_recovery_required→quarantined`迁移隔离。

R-*查询参数只允许来自已认证case授权绑定、固定编译期常量及此前已完整校验的R-*结果；lesson_id由R-LESSON单行发现，command_id由R-TRANSITION唯一DB行提供并必须通过sidecar HMAC反核。任何查询参数均不接受HTTP/body/CLI直接传入，也不从HMAC倒推。每条查询的预期行数固定为上列基数，单字段长度受docs/41 §3/§4对应codec上限约束，单行≤1 MiB、整次恢复结果≤4 MiB、总返回行数≤16；超限即integrity failure。R-*每个固定语句ID、行数、字节数均独立计数并进入FI/E2E诊断证据；缺行、重复/额外字段、非canonical JSON、错绑或完整读取失败：`open_recovery_required`须durably quarantine，`committed`保持原状态并返回integrity error/no receipt/no catalog-sidecar write；quarantine journal不确定则global poison。恢复查询只读，不改DB/sidecar，不创建命令，不读live词库/用户/Room，不调用Coordinator/Planner/Registry，不产生课堂副作用。
### 9.2 监督日志文件生命周期与失败语义

bootstrap 在已验证 root 下先于首次catalog创建初始化固定 `logs/` 目录、`log.pseudonym.key` 与`events.jsonl`；仅当catalog及所有case-lock/case目录均不存在且root符合空bootstrap inventory时，重启可幂等续建缺失日志成员；catalog或case artifact任一存在时日志缺失即global fail closed。目录/文件均用 CREATE_NEW，按平台专属权限设置、Sync文件和父目录并重新验证identity；只有三者均有效才可发布Supervisor并记录首个bootstrap事件。两把key均留在Supervisor内存，child无读取权限；case hash只能经受限MAC接口生成。事件只追加单行canonical JSON，每行写完Sync；禁止截断、修补或轮换。单个root epoch使用一把pseudonym key，不跨epoch复用；root销毁时在全部case清理后一起销毁。日志容量上限严格为67,108,864 bytes（64 MiB）。在任何业务副作用前，日志互斥锁内按当前文件长度为本操作原子预留operation_started与唯一terminal事件所需的完整编码字节，另预留8,192 bytes安全余量；当 `current_length + outstanding_reservations + new_reservation + 8192 == 67108864` 时允许该预留，只有 `>` 才拒绝。预留成功后先追加并Sync operation_started，再执行副作用，最后消费terminal预留并追加/Sync终态；终态事件编码不得超过其预留。若当前日志+既有预留已无空间容纳拒绝前所需预留，则副作用不得开始，Supervisor全局poison并返回`io_uncertain`，不尝试写拒绝事件；任何日志write/Sync不确定同样poison，绝不覆盖/截断/轮换旧事件。单行上限4,096 bytes。

每项业务操作必须先持久写 operation_started；写入/Sync失败则不执行副作用并全局poison。副作用完成后终态日志写入失败时，catalog/DB仍是状态权威，但本进程全局poison并返回io_uncertain；重启先按权威状态恢复，不能重放副作用。启动发现日志缺失、权限/identity不符、行不完整/非法或超限时，先按FI-LOG-01a判定是否仍处于catalog及case artifact均不存在的空bootstrap inventory：仅该状态可按精确allowlist续建或整体重置logs subtree；一旦catalog/case artifact存在，或Supervisor已发布后再发现上述异常，必须fail closed，绝不重建/截断。结构字段和事件枚举按§4，敏感字段禁止清单按§11。
## 10. 故障矩阵、崩溃 oracle 与并发 schedule

所有注入有两个独立变体：A) syscall返回错误（包括完整frame write后Sync报错）及short write；B) 子进程在具名barrier命中后被parent TerminateProcess/SIGKILL。每case用独立root；barrier经named IPC、禁止sleep；所有wait有硬时限并保留child stdout/stderr、OS/fs、catalog SHA、member identity、`db_template_bytes`、`db_open_rw`、`db_open_ro_recovery`、`db_schema_validation_sql`、`db_recovery_data_sql`、`db_application_sql`及receipt/Planner/Registry计数。`db_template_bytes`仅在完整模板复制时等于固定模板size；普通操作连接记`db_open_rw`（首条database_list也计）；允许的schema查询逐条记`db_schema_validation_sql`，receipt-first固定恢复查询逐条记`db_recovery_data_sql`。状态拒绝、第二次Start、pre-open identity失败时所有DB连接计数=0；路径不匹配时`db_open_rw=1`,`db_schema_validation_sql=1`,`db_recovery_data_sql=0`,`db_application_sql=0`。只读恢复statement清单及分类计数见§9；应用SQL任何恢复阶段均为0。catalog Sync error即使完整frame可见也结果未知，fresh process仅按完整合法replay恢复，当前调用永不回成功。

| 注入阶段 | 返回错误的当前进程结果 | 强杀后/重启 oracle | 允许打开/副作用 |
|---|---|---|---|
| 私有root / bootstrap lock Create/ACL/Sync失败 | 不返回Supervisor；身份/权限不确定poison。无case成员 | root存在则重新verify；不合格全局停。仅固定空root可bootstrap | 零DB/Planner/Registry |
| bootstrap锁竞争/超时 | `lock_timeout`，不poison，不看catalog中间态 | 重启重试取得同一永久锁 | 零case open |

## 15. 下一切片设计：OS-authenticated IPC peer

本节仅设计真实本机IPC监听/接受时的peer认证，不授权任何case文件或课堂副作用。该切片必须替换 `authenticatedIPCPeer{verified bool}`，让 `VerifyGrant` 只接收平台adapter签发的不可伪造、连接绑定的私有证明；OS API失败、连接身份不符、配置缺失或平台能力不可用时统一拒绝。证明绑定单一已认证连接及一次Grant验证，不能从HTTP/body/CLI字段构造或跨连接复用。

**Linux设计。** 仅在`pilot_e2e && linux`编译。监听器创建owner-only Unix domain socket；启动前验证父目录为可信私有目录，socket路径不存在时以受控umask创建，设置`0600`并复核owner、mode及socket inode。接受后从该`*net.UnixConn`的`SyscallConn.Control`取得FD，以`getsockopt(SOL_SOCKET, SO_PEERCRED)`获取内核返回的PID/UID/GID；必须匹配worker启动时由可信bootstrap handle固化的Gateway PID及UID，并核验连接仍指向已验证listener。任何fallback到地址字符串、`RemoteAddr`、可由请求者声明的PID/UID都禁止。仅在Unix listener创建/权限复核成功后开始Accept；listener close与context取消均有界退出，socket identity变化则fail closed。

**Windows设计。** 仅在`pilot_e2e && windows`编译。命名管道必须在创建时使用受保护DACL、关闭ACL继承、授权严格allowlist的Gateway SID及SYSTEM，并设置拒绝远程客户端的pipe mode；不能使用默认DACL或事后字符串路径检查。连接后调用`GetNamedPipeClientProcessId`，打开该进程token并由OS读取TokenUser SID，要求与受保护bootstrap提供的预期Gateway SID及预期PID同时匹配；reparse/无效handle/token查询失败一律拒绝。受保护DACL必须从实际Security Descriptor复读验证，`FileMode`或pipe名称不能作为身份凭据。管道实例、等待、取消、close与child process终止均须有界；不能关闭或替换连接handle后复用peer proof。

**共享API与测试。** 平台函数只接受实际已连接的OS socket/pipe handle及可信bootstrap身份对象，返回非导出的`authenticatedIPCPeer`；peer证明保留进程ID、OS principal与底层连接的不可变身份，不公开setter。`VerifyGrant`验证peer proof仍属于当前连接之后才验签。测试必须使用真实OS IPC、真实父子进程及错误身份子进程，覆盖有效peer、不同UID/SID、相同principal但非预期PID、断开/替换/关闭handle、权限放宽、查询API失败、listener取消和超时；每项断言错误类别稳定且Supervisor/member-open/业务副作用计数为0。Linux和Windows都必须在原生runner实际执行；交叉编译只作附加检查。此切片不接HTTP、Supervisor、catalog或文件操作，不声称已完成Gateway/worker完整IPC协议。

实施前门：架构与安全域必须独立复审本节的handle/身份来源及Windows DACL/Linux socket创建流程；后端与测试域复审API/进程fixture和取消界限。四域全PASS并记录本节body SHA后才可编码。若测试环境缺少Linux原生runner，Windows实现可独立提交为未完成阶段，但不得声称双平台peer认证已通过。

### 15.1 评审问题关闭与可执行bootstrap合同

前置launcher不是环境变量、CLI参数或worker IPC消息；由可信Gateway创建worker并显式传递bootstrap OS handle。Gateway生成128-bit随机`endpoint_nonce`，与`run_epoch`、32-hex `worker_generation`、Gateway public key、协议版本及父进程身份一起编码进严格canonical schema。bootstrap为单个4-byte big-endian长度前缀帧，payload上限4092 bytes、总帧上限4096 bytes；worker须在5秒内读完，拒绝零长度、超长、截断、重复字段、非canonical编码、帧后额外字节或第二帧。Linux使用`pipe2(O_CLOEXEC)`创建单向bootstrap pipe，仅将只读端映射为FD 3；Windows使用专用匿名pipe，Gateway写完一帧即关闭写端，worker读至EOF并验证恰一帧。Linux以`poll`按单调时钟截止时间读取；Windows匿名pipe不使用overlapped I/O，worker以`PeekNamedPipe`每10ms有界轮询并检查同一5秒截止时间，读完预期帧后继续轮询至写端关闭，确认EOF且无额外字节。身份材料不从argv/env/HTTP/业务帧覆盖。

Windows launcher使用`STARTUPINFOEX/PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，仅继承bootstrap pipe、Gateway `PROCESS_QUERY_LIMITED_INFORMATION|SYNCHRONIZE` process handle及标准句柄；标准句柄不作为身份来源。Linux launcher通过`exec.Cmd.ExtraFiles`只映射FD 3 bootstrap read end、FD 4 Gateway pidfd，所有其它FD设`CLOEXEC`。bootstrap解析后关闭bootstrap及任何不再需要的句柄；Windows父进程process handle与Linux pidfd必须保留到worker退出，以便每次授权派发时复查父进程仍存活。父进程身份句柄缺失、权限过宽/不足或查询失败均禁止启动listener。

Windows worker先从继承的Gateway process handle读取PID、TokenUser SID与process creation time；trusted launcher必须通过`OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION|SYNCHRONIZE)`申请并传递该handle。普通Win32 API不能可靠查询handle原始请求mask，因此由launcher代码审查/测试锁定申请mask；worker运行时验证所需查询成功且process尚存活。命名管道accept后两次读取`GetNamedPipeClientProcessId`，必须均等于该已pin process handle的PID；中间以该进程handle读取token SID与creation time，并核对与bootstrap记录一致，且handle未signaled。禁止仅凭PID重新`OpenProcess`后假设进程相同。Linux Gateway pidfd在parent进程退出后会变为signaled；worker要求`SO_PEERCRED.pid == getppid()`、UID等于可信bootstrap记录且pidfd仍未signaled。每次`VerifyGrant`/dispatch前再次检查pidfd未signaled或Windows process handle未signaled；连接accept时及派发前都复核peer PID仍为固定Gateway PID。另有专用parent-exit watcher持续监视pidfd/process handle；父进程退出时立即取消accept和当前连接并关闭listener。PID/UID检查失败或pidfd能力不存在时关闭连接并拒绝。

peer proof保存实际已接受的conn wrapper引用、不可复用的连接generation、OS principal/PID及closed状态；grant验证与唯一请求dispatch必须在同一wrapper生命周期内执行。连接关闭先原子标记closed，再Close底层handle；proof不能仅存裸FD/HANDLE整数，不能跨连接复用。每连接最多接收一个完整typed frame。平台不能承诺阻止同一权限主体主动复制任意handle；实现合同是：Linux拒绝带`SCM_RIGHTS` ancillary data的帧并关闭连接，Windows不授予`PROCESS_DUP_HANDLE`且不把Gateway handle暴露给IPC客户端；继承句柄采用明确allowlist，socket/pipe listener及accepted connection均CLOEXEC或清除`HANDLE_FLAG_INHERIT`。测试验证这些可执行控制和连接关闭后proof失效，不宣称OS层面绝对禁止复制。worker不能在关闭旧listener前复用generation proof。

**dispatch与关闭竞态。** `VerifyGrant`为一个peer最多登记一次grant；唯一dispatch必须经`VerifiedGrant.dispatch`，不可提供绕过grant状态的peer级派发入口。dispatch以原子状态完成closed、grant单次消费、单次dispatch和父进程存活复核后才调用授权操作，并传入peer context。关闭先原子置closed、取消该context并关闭连接，再等待在途dispatch最多1秒；操作实现必须在开始副作用前检查context，并让可取消等待响应取消。持久化操作遵守本SDD锁/Sync语义：写入开始后不得把取消当作回滚证明，必须完成write+Sync或poison并返回`io_uncertain`。超过1秒说明回调未遵守取消合同，Close返回`ipc_timeout`，外层worker watchdog必须终止并reap专属进程；不得无限等待或继续接收新工作。parent watcher只有在同步资源清理成功（包括listener accept join和peer关闭）后才报告`ipc_parent_gone`，清理失败保留为`ipc_listener_failed`。Linux pidfd的存活检查与Close必须串行，已关闭handle恒为`ipc_parent_gone`。验收用例须证明grant以外的直调不可用、并发重复dispatch至多一次、关闭能取消在途授权操作并有界返回。

Linux每个worker generation使用由bootstrap nonce确定的短basename：`worker-<32hex-generation>-<32hex-nonce>.sock`（小于NAME_MAX），置于已验证私有control directory；worker重启创建新generation路径，不按旧路径盲目unlink。旧socket仅可在旧worker已wait/reap后，以已pin control dirfd执行`fstatat(AT_SYMLINK_NOFOLLOW)`校验对象仍为同owner、mode `0600`的socket且dev/inode等于记录身份，再`unlinkat`；身份不符或查询不确定保留对象并fail closed。Windows endpoint为`\\.\pipe\enwords-<32hex-epoch>-<32hex-generation>-<32hex-nonce>`；新实例名不重用。命名管道DACL必须关闭继承并精确只允许bootstrap中的Gateway SID（`FILE_READ_DATA|FILE_READ_ATTRIBUTES|FILE_WRITE_DATA|SYNCHRONIZE`，mask `0x00100083`）及`SYSTEM`（`FILE_ALL_ACCESS`）；不得有Everyone、Authenticated Users、Administrators或其他allow ACE，也不得有deny ACE覆盖allowlist。Windows客户端`CreateFile`仅请求`FILE_READ_DATA|FILE_WRITE_DATA|SYNCHRONIZE`（不请求GENERIC_READ/WRITE或FILE_WRITE_ATTRIBUTES）；原生连接验收要求DACL有`FILE_READ_ATTRIBUTES`，缺失时`CreateFile`被拒，单独添加`FILE_WRITE_ATTRIBUTES`无效。pipe server设置`nMaxInstances=1`与`FILE_FLAG_FIRST_PIPE_INSTANCE`；创建后从实际Security Descriptor复读并逐ACE核对SID、mask、继承flag与ACE数量；远程拒绝flag须在`CreateNamedPipe`参数生效。

失败注入细分`FI-IPC-PEER-BOOT`（继承bootstrap缺失/错误/截断/版本错/epoch错/句柄权限错）、`FI-IPC-PEER-LISTENER`（bind/create、DACL/chmod、identity复读、listen/connect/accept、取消/close）、`FI-IPC-PEER-AUTH`（SO_PEERCRED/ProcessId/Token SID/creation time/pidfd查询失败、UID/SID/PID/creation不符、parent退出与PID复用）、`FI-IPC-PEER-HANDLE`（inheritance、FD/HANDLE duplicate/transfer尝试、连接关闭/复用、第二frame）和`FI-IPC-PEER-RESTART`（worker kill/reap、fresh generation、旧socket cleanup身份不符）。每一项分别断言稳定错误类别、proof未生成或失效、grant验签/消费次数为0、Supervisor/member-open/业务副作用为0，且清理未删除身份未知的对象。Reviewers需逐项判断bootstrap句柄传递在Windows/Linux原生runner可实现，并确认权限配置与失败路径满足本威胁模型。

Filesystem ACL/mount, byte-corruption, syscall and hard-kill assertions remain Go/process tests; each E2E row verifies only the matching user-visible outcome. Before pilot enablement every row must link an exact Playwright test title, FI IDs and run artifact.

## 16. 2026-10-20 评审问题收敛契约

本节优先于本文早期草案中冲突的描述；实现和测试必须按本节及docs/43执行。职责按副作用类型唯一划分：Gateway是HTTP认证及session/idempotency权威；PilotHostReaper唯一拥有跨run control ledger、run lease、worker containment与run终止回收；worker内Supervisor是唯一拥有本run catalog、stable case lock、case目录和case成员生命周期的执行者。Reaper不得创建、改写或删除case catalog/member；可在pin handles上只读核验提交证据。Reaper仅在Gateway和worker均已fence、containment empty且所有handles关闭后，按run-level策略隔离或清除整个abandoned root。Gateway只签发typed授权并派发；不得直接操作文件、catalog或DB。普通case create/open/cleanup的唯一执行路径为Gateway request registry→Reaper durable intent/claim→签名IPC→Supervisor→Reaper提交receipt/terminal；任意阶段不确定均禁止盲目重派。该执行归属覆盖docs/43 §2中`CreatePinnedCaseRoot`和`ExecutePinnedCleanup`措辞：这些名字代表Supervisor的受限typed操作，不是Reaper直接文件操作。

签名grant必须包含`worker_generation`，由当前Gateway bootstrap逐请求绑定；Supervisor仅接受与本进程bootstrap generation相等的grant。`owner_generation`是docs/43 ledger内的并发claim fencing token，与worker_generation分属不同命名空间，禁止互相替代。Gateway request registry在IPC dispatch前持久记录request_id、principal_ref、scope、digest、worker_generation和dispatch状态；同键同digest的completed只返回同一规范响应，in-flight只等待同一owner，冲突拒绝。若记录证明尚未dispatch，可安全恢复派发；dispatch已开始而结果不确定时只能进入indeterminate/abandoned，不得在同一run或新worker重派。所有有副作用scope及receipt read均走此规则。

Cleanup严格owner-only：case创建时绑定的principal必须与cleanup请求principal逐字节相等；管理员role不产生隐式delegation。跨principal cleanup当前不支持，统一返回`case_not_found`且不得发送IPC或打开成员。docs/43 §2 cleanup anchor绑定和本文§5、§8、§10、§13相关测试均按此负向规则执行。

首个catalog的完整`provisioning`首帧Sync成功并完成root目录Sync，才是catalog durable commit point。CREATE_NEW后出现的空文件、短帧、坏帧或身份不确定均不是可恢复catalog；只要创建请求已dispatch，崩溃后必须abandon整个epoch，不允许自动补帧、重建或恢复selector。只有Gateway registry的durable证据证明请求未dispatch，才可由原授权请求重试；新run使用新epoch及新root。后续catalog恢复只接受完整校验的首帧链。

C2 schedule固定为：opener读完advisory snapshot后、取得case lock前暂停；cleanup先取得同一lock、写并Sync quarantine/tombstone后释放；opener随后取得lock、重新读取catalog并拒绝，断言DB-open=0。C3维持反向顺序（opener先取得lock并进入DB屏障，cleanup等待），两者不得合并或靠sleep安排。

§13每个FI稳定ID的fault applicability必须记录于`review/pilot-supervisor-fault-manifest.json`：变体为`syscall_error`、`short_write`、`post_write_sync_error`、`named_barrier_kill`；不适用项必须提供原因，适用项须映射到唯一稳定子测试名。manifest绑定本节最终SHA及docs/44 SHA；发现器缺项、重复、额外或无理由N/A均失败。覆盖率profile分别从`server/`运行`go test -tags pilot_e2e -coverprofile=<artifact> ./internal/pilotsupervisor`与`go test -tags pilot_e2e -coverprofile=<artifact> ./internal/store`，分包计算门槛；pilotsupervisor≥80%，实际状态恢复和cleanup决策生产包≥90%，不把两个包合并成一个不可归因profile。

| 操作 | 唯一副作用执行者 / 锁 | intent、receipt、terminal owner | 拒绝与恢复边界 |
|---|---|---|---|
| run root、run lease、worker spawn/terminate | PilotHostReaper；run lease及OS containment | Reaper写control ledger与run终止证据 | 旧generation未fence或containment非empty时不启动新worker、不释放lease |
| case catalog、stable case lock、case root及固定成员创建 | worker内Supervisor；bootstrap→case→catalog锁顺序 | Gateway/Reaper先持久化operation intent；Supervisor写catalog与成员；Reaper提交receipt/terminal | dispatch后不确定即indeterminate/abandoned；不得由Reaper或Gateway补写catalog/成员 |
| lesson业务事务与receipt读取 | worker内Supervisor/store；case lock及DB事务 | ledger由Reaper持有，业务marker/receipt由case DB持有 | marker与ledger不一致时隐藏结果、禁止重判/重做，等待Reaper按证据裁决 |
| case级cleanup | worker内Supervisor；case lock后catalog lock | Reaper先claim/写intent；Supervisor执行quarantine、固定成员删除及tombstone；Reaper提交receipt/terminal | 仅owner principal；管理员不绕过。失败保留隔离状态，禁止普通open |
| abandoned run root隔离/清理 | PilotHostReaper；必须先fence Gateway/worker并确认containment empty | Reaper写run cleanup evidence及terminal | 不逐项解释或清理活动case；身份不确定时保留隔离root且不释放lease |

锁顺序表的箭头描述分阶段先后，不代表bootstrap、case、catalog三锁嵌套持有。首次case先取bootstrap lock并完成catalog完整首帧/Sync，释放catalog lock再释放bootstrap lock，然后取得stable case lock；后续case取得stable case lock再短暂取得catalog lock。任何路径均不得持catalog lock等待case lock；cleanup/open遵循case→catalog并在打开成员前释放catalog lock。

日志schema的枚举和空值规则固定如下：`module`仅可为`pilot.gateway|pilot.reaper|pilot.supervisor|pilot.fs|pilot.ipc|pilot.store|pilot_host_reaper`；`event`仅可为`bootstrap.start|bootstrap.finish|case.create.start|case.create.finish|case.open.start|case.open.finish|case.close.start|case.close.finish|case.cleanup.start|case.cleanup.finish|catalog.replay.start|catalog.replay.finish|identity.reject|os.lock.error|os.sync.error|barrier|run_root_dispatch_intent|run_root_dispatch_committed`。`outcome`仅可为`ok|error|indeterminate|blocked`；`reason`仅可为`none`、§3稳定错误码或docs/44定义的`verified_*`稳定错误类。成功时reason为`none`，否则必须是非`none`错误码。`case_hash`在global事件为JSON null、case事件为32位小写hex keyed digest；`state_before/state_after`在bootstrap或无case身份事件为null，其余为固定catalog状态字符串；`lock_wait_ms/io_ms`始终为非负整数，未知/不适用写0，不得省略。JSON不允许额外字段、重复字段、浮点数、负时长或非canonical编码。docs/44只读句柄切片当前简化slog事件须在Supervisor接线前映射为该schema；不得把不同schema拼接后宣称满足本节日志门。

Gateway registry只是session/key coalescing cache及可重建projection；PilotHostReaper control ledger是唯一durable dispatch authority。Reaper必须以一个原子API `BeginOperation` 持久提交`prepared`记录，并以CAS提交`prepared→executing`、绑定owner_generation后返回单次owner token；Gateway只有持有该token才可签grant/dispatch。Reaper ledger的`prepared`且无dispatch记录才可安全发起；`executing`必须先通过marker/evidence裁决，无法证明则`indeterminate`，不得因Gateway cache缺失而重派。Gateway启动/重启时从ledger、catalog与case marker重建cache，重建结果不得提高可重试性。

HTTP cache/ledger状态映射固定为：HTTP `pending`对应ledger `prepared`或`executing`；HTTP `completed`仅在ledger `completed` durable后可见；ledger `abandoned`或`indeterminate`映射为不可重试的稳定失败，绝不能变回HTTP `pending`。HTTP cache只合并等待者和缓存规范响应，不授权副作用、不持久化dispatch事实。`owner_generation`用于ledger CAS fencing，`worker_generation`用于签名grant和peer bootstrap，两者均绑定同一操作但不可互换。





















## Run-root creation authority update (docs/45)

For run-root allocation, this update supersedes any earlier statement that `OpenPilotSupervisor` verifies or creates the root. `PilotHostReaper` is the sole creator and durable owner of a run root. `OpenPilotSupervisor` may only open and verify a Reaper-completed root; it must not create, repair, or remove the root. Case/catalog lifecycle remains owned by Supervisor under the existing grant and lock protocol.
