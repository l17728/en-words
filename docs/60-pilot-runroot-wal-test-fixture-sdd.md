# RunRoot Cross-Platform WAL Test Fixture SDD

## Status and scope

This test-only delta addresses a native Linux failure found on 2026-10-22 in the two cgo RunRoot writer-wait regressions defined by [docs/59](59-runroot-deterministic-writer-wait-tests-sdd.md). It does not change production SQLite configuration, ledger behavior, lock policy, timeout, or cancellation semantics. The exact amended document and test hashes must pass architecture, backend, and test-design review before implementation.

## Finding

`TestRunRootLedgerWALTransitionHonorsContextCancellation` and `TestRunRootLedgerConstructorDiscardsConnectionAfterWALInitFailure` originally mixed the `modernc.org/sqlite` holder with the pinned `go-sqlite3` contender and assumed a new database began in DELETE mode. The native Linux run showed the WAL transition could succeed immediately, so the barrier never fired and the constructor case never exercised a `SQLITE_BUSY` path. A platform-dependent default cannot establish the test's lock precondition. The corrected fixtures now use the registered `pilot_busy_test` (`go-sqlite3`) driver for both holder and contender, and explicitly establish and verify DELETE mode. This removes cross-driver lock behavior as an uncontrolled fixture variable.

## Required fixture contract

Both tests must establish the same initial database state explicitly before opening a read transaction:

1. Open the holder with `pilot_busy_test`, execute `PRAGMA journal_mode=DELETE`, scan its returned mode, and require exactly `delete` (case-insensitive). Record this as `initial_mode`.
2. Create and populate the lock-probe table while DELETE mode is active.
3. Start a transaction, read the probe row, query `PRAGMA journal_mode` through that same holder transaction, and require/record `holder_mode=delete` (case-insensitive) while the read transaction remains open.
4. On the contender connection that will perform the WAL transition, independently query `PRAGMA journal_mode` and require `delete` before installing the busy callback or invoking ledger initialization. Record this as `contender_mode`; do not query a separate pool connection and treat it as proof of the contender's state.
5. Only then reach the named busy-handler barrier. Cancellation/commit remains gated on the callback signal; no timing assumption may substitute for the signal.

If either connection reports a different mode or the setup query fails, the test must fail at a named precondition diagnostic and must not claim that the lock callback was reached. The cancellation case still requires `context.Canceled`, final journal mode `delete` (case-insensitive), and zero managed ledger schema objects. Its final log records `initial_mode`, `holder_mode`, `contender_mode`, callback count, gate reached/released, result class, final mode, and `ledger_schema_objects`.

The constructor case's tracked connector must perform the contender mode query on the exact `SQLiteConn` returned to `database/sql` before returning it from `Connect`, and retain that verified mode for diagnostics. If connector setup fails before returning the connection, it must close that raw connection itself. Do **not** install the custom busy callback in `Connect`: the constructor first executes `PRAGMA busy_timeout=50`, which replaces SQLite's current busy handler. Instead, the tracked `QueryContext` must install the callback on that same `SQLiteConn` immediately before forwarding the exact `PRAGMA journal_mode=WAL` statement to the underlying driver. The callback increments a count, sends a nonblocking signal to a buffered `busyEntered` channel, and returns `false`; it must not block the synchronous constructor call. Here `busy_callback_reached` means the native callback actually ran and `busy_callback_returned_false` means it released SQLite to return `SQLITE_BUSY`; there is no held gate or separate release event in this synchronous constructor case. The holder read transaction remains open until initialization returns. After initialization returns, the test must receive the callback signal and assert callback count is positive independently from `walBusy`/SQLite error classification. It also requires a discarded pinned connection, unchanged `delete` mode (case-insensitive), `ledger == nil` plus initialization error, and zero managed ledger schema objects (the three `run_root_*`/`run_epoch_allocations` tables, the bootstrap table, and both immutable-bootstrap triggers). The tracked driver's `closed` signal is emitted only when the underlying SQLite connection closes successfully. Its final log records `initial_mode`, `holder_mode`, `contender_mode`, callback count, `busy_callback_reached`, `busy_callback_returned_false`, `wal_result`, `wal_busy`, final mode, `ledger_schema_objects`, and connection disposal. The separate stale-generation case remains unchanged because it explicitly uses `BEGIN IMMEDIATE` and passed on Linux.

## Regression and evidence

Keep the correction in the existing cgo-only regression family. Run the three focused tests (`stale high-water`, `WAL cancellation`, and `constructor disposal`) on Windows and native Linux, then run the tagged `pilotsupervisor` package and race suite on Linux with `PILOT_FS_TEST_ROOT` pointing to a non-root-owned ext4/XFS fixture. Preserve the trace diagnostics defined above. A browser E2E is not applicable to this fixture-only correction: no product route or user-visible behavior participates, and the required oracle is a native SQLite lock callback.

Implementation evidence (2026-10-22): the tagged `pilotsupervisor` package passes on Linux/ext4 as an unprivileged user with `PILOT_FS_TEST_ROOT`; the same final package passes with `-race`, and `go vet -tags=pilot_e2e ./internal/pilotsupervisor` is clean. Package statement coverage is 80.5% after adding `TestReadPeerBootstrapFrameRequiresExactlyOneCompleteFrame`; this clears the package-level 80% threshold only, not the native platform matrix or all trust-boundary function-level cases. The three focused cgo tests (stale high-water, WAL cancellation, constructor disposal), the new portable frame-reader regression, and the full tagged Windows suite `go test -tags=pilot_e2e -count=1 ./...` pass on Windows/amd64 with LLVM-MinGW; the full default Windows `go test ./...` also passed. ## Package coverage follow-up

The 79.9% Linux coverage result exposed an uncovered bounded framing reader that is shared by the bootstrap protocol but had only decoder-level coverage. The added test exercises the actual `io.Reader` contract rather than duplicating decoder assertions: exactly one valid frame must be followed by EOF; malformed prefixes, short bodies, extra bytes, and 100 consecutive `(0, nil)` no-progress reads are rejected as `ipc_bootstrap_invalid`, while a transient `(0, nil)` followed by EOF and a final read that returns all requested data together with `io.EOF` are accepted. The final Windows/amd64 tagged full-suite run and Linux/ext4 tagged package, race, and vet runs pass. Coverage is recorded as package-level only; the Linux RunRoot trust, launcher, VFS, XFS/arm64, product E2E, and real classroom acceptance requirements in docs/44–55 remain independently open.
