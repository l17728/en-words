# 课堂朗读后等待提示最小设计

状态：2026-10-16架构/前端设计共识已达成，主审已授权并完成实现。专项四例及后续冻结浏览器验收均通过（§7）；其功能验收不关闭真实声学验收，也不解决21.678秒COMMIT长尾或改变原15秒性能断言。范围仅现有legacy课堂成功朗读结束后的等待提示。

## 1. 用户行为与边界

实际浏览器onend/本地Audio ended成功后，现有complete先清字幕，再发送tts_finished。此时在课堂老师区域、字幕下方显示独立 `role=status` 文本“本段播放结束，正在等待老师继续”，不把提示写入朗读字幕，不发声，不遮挡退出/返回入口。提示不出现“已提交”“保存成功”“已回滚”等数据库结论。

不新增教学行为、模型请求、自动重试、轮询或REST回放；等待状态本身没有超时推进/重发定时器。现有一次事件发送路径保持原样（包括当前非答题控制已有的WS不可用时一次REST降级）；本特性不得因等得久而额外调用该路径。断线转既有重连界面，停止显示本提示；课堂动作失败转既有明确错误提示，不能显示成功。

仅成功实际ended建立等待。loading、onstart、播放失败、watchdog、cancel、段间间隔不建立。原来的成功ACK次数与本地音频/字幕清理顺序不变。与答题“正在判分”互斥：答案提交不使用此状态。

## 2. 状态、身份与顺序

最小纯逻辑对象 `PlaybackContinuationWait`，状态只有idle/waiting；不存音频正文/token，不建立持久提交事实。

waiting保存：页面会话generation、lessonId、连接epoch、结束段的turn、建立时已接受的最大seq，以及本地播放generation。会话generation由现有页面生命周期生成，不复制JWT。不保存event_id，因为这里只跟踪本地播放后等待，不关联持久提交回执，也不猜eventCounter。一个新等待替换旧等待时需新generation；旧清理回调必须持有原generation，不能清掉新状态。

在有效实际ended、现有发送调用之前同步建立本地等待ref/state，再执行原tts_finished发送，以免极快后继帧先到导致永久等待。这只表示本段真实结束，不代表后台已收到/提交；不读取void返回猜发送成功，不修改sendEventRef或dispatchClassroom运输合同。建立前核该播放仍是当前页面/连接/播放generation；已经取消、换课、换号或旧context的ended不建立等待。发送ACK时也必须重新核验当前token和TurnContext；跨标签页storage事件已切换账号但React清理尚未运行时，旧onend不得向旧Room发送ACK。WS与现有一次REST降级路径均保持，等待状态不自动重发、不补ACK、不推进教学。若连接生命周期已将课堂标记离线，连接错误/重连状态优先，不显示等待提示；若底层readyState先变为CLOSED而onClose尚未处理，允许在这段短暂竞态中显示等待，REST降级结果到达后清理。后到的onClose/发送错误沿既有连接处理清理本等待。

## 3. 完成判据

只在Classroom.handleFrame现有身份与seq过滤**通过之后**尝试完成等待，且帧epoch必须与等待一致、seq为有限合法数字且严格大于建立时baseline。以下现有教学业务动作代表老师确已继续：

- ui_action.action.type = play_tts、start_repeat、show_word、show_quiz_item、lesson_summary；
- 或实际phase_changed进入与等待时不同的非朗读阶段（repeating、wait_answer、show_word、lesson_end），作为已接收状态机推进事实。

不能用heartbeat_ack、event_processed、同相位state_snapshot、普通反馈reply、仅连接成功或ASR结果清除。snapshot即使展示变化也不冒充本等待事件的完成回执；断线/重连按生命周期清理而非成功。较旧seq/异epoch帧在既有过滤入口被拒，不能假完成。新播放业务帧到达先结束旧等待，再按原路径启动新段；下一段真正ended时产生新等待。

以下是撤销显示而非完成：classroom_error、session_timeout/lesson_paused、disconnect、换号、换课、卸载。它们同步失效当前等待generation；错误/重连提示沿现有UI保留。不要把通用cancelTts直接绑成无条件clear：成功段已经清字幕，后续play_tts取消旧媒体的顺序必须由上述业务帧完成判据控制，避免旧cancel清新等待。

## 4. 为什么不修改Go

当前服务已提供教学ui_action/phase_changed与epoch/turn/seq，且工具成功后才发送业务动作（hub.go:333–365）。显示“等待老师继续”仅表达浏览器的可见等待，不需要新增持久receipt或后端协议。服务端Room锁、事务边界、Teacher决策和重试策略均不变；数据库慢时提示可一直显示，用户仍可退出，不能因此宣称速度门通过。docs36的active_input/committing_unknown/decision.committed属于另一特性，禁止在此伪造。

## 6. 本地等待定位日志（2026-10-16 主审批准增量）

原有 playback_completed 和媒体探针只能证明播放结束，不能单独证明本提示是否建立、被哪条有效进展清理。补两个固定结构事件 `waiting_started`、`waiting_cleared`，由等待 helper 的状态变化 observer 统一发往现有 console 摘要通道；不新增数组、网络请求、持久记录或后端协议。当前专项正在执行时不修改其源码；该轮结束后再实施观测增量，按新源码重验四例，明确属于日志门补齐而非对失败盲重试。

字段只含事件名、本地 generation/session/playback、lesson_id、baseline_seq，以及适用时 accepted_seq 和 reason。它们是本地关联身份，不能命名为后端 trace_id 或持久 receipt。禁止正文、token、完整帧、URL、原始错误内容及音频数据。

只记录真实状态变化：有效 begin 记 started；当前等待被清理记 cleared。清理 reason 限定为 `business_progress`、`transport_error`、`disconnect`、`session_invalidated`、`paused`、`classroom_error`、`lesson_end`、`replaced`。新 begin 替换已有等待时，先为旧代记 cleared/replaced，再记新代 started。空状态清理、旧 ticket 拒绝、heartbeat、重复或无关帧均不产生 clear 日志，避免错误证明旧请求清掉新状态或逐帧刷屏。

Node 用例锁定真实变化顺序、旧 ticket 拒绝无事件、有限字段和隐私边界；四个真实课堂专项收集结构 console，核本地 ended→started、后继业务或运输错误→相应 cleared，不将这些日志当作服务端提交回执。原 SUB02 推进时限与长尾问题状态保持不变。
