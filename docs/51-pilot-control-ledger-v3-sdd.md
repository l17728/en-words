# Pilot Control Ledger V3 SDD

## Status and scope

Design for the durable control plane required by [docs/50](50-pilot-runroot-product-orchestration-sdd.md). This document is a design gate, not implementation approval. It specifies a fresh SQLite v3 schema, handoff-to-operation binding, RunRoot event outbox, and containment finalization. It adds no normal lesson completion, shared-classroom membership, or recovery-only Logger delivery. Those remain separate reviewed designs.

Stage A adds the singleton `pilot_launcher_journal_anchor` specified by docs/54 and listed in docs/53. A0 provisions it before launcher admission. Its only runtime write is `AdvanceLauncherJournalAnchor`, restricted to the authenticated singleton launcher and exact sequence/hash compare-and-swap; the protected ledger transaction commits after the corresponding journal frame is synced and before acknowledgement or external side effect. This method is not a business operation.

The persistent `PilotControlReaper` is the sole owner of the pinned VFS connection, OS single-writer lock, alias table, and ledger transactions. Launcher and per-run Reaper use distinct authenticated typed IPC endpoints; per-run Reaper never opens SQLite. The launcher-only admission resolver validates current user authorization before user-initiated operations. Control-plane operations use caller identity and target-binding rules, not a learner admission. Every identity/peer check completes before a business transaction starts and is never called from inside an open transaction. No code holds a ledger transaction while waiting on another control RPC.

### RPC authorization classes

| RPC class | Authorized caller and checks before transaction |
|---|---|
| User operation (`PrepareWithHandoff`, `LookupByPrincipalOperation`, `BeginRunTermination`) | Launcher service identity plus signed current admission and stable principal. Prepare/close compare authorization fence inside their writer transaction; ledger lookup compares it in the same read snapshot. `CancelQueuedRun` is launcher-journal internal and is not a resident ledger RPC. |
| Authorization fence (`PublishAuthorizationFence`) | Authenticated web authorization authority on its dedicated pinned endpoint, with a signed monotonic revision and exact tenant/account/session target. Restrictive updates must commit here before they are reported effective; same request ID/digest is idempotent and stale revisions reject. |
| Authorization check (`CheckCurrentAuthorization`) | Launcher identity plus signed current admission; compare account revision/snapshot digest, session revision/state, role, and fixture grant against the resident fence. It runs before any journal lookup or status/close response. |
| Startup control (`ConsumeBootstrap`, `CommitLifecycleBoundary`) | Launcher service identity on its pinned control channel; validate exact docs/47 frame, generation/nonce, and process/cgroup tuple. Do not require a learner session or admission. |
| Live run control (`AuthorizeOutboxSend`, `Claim`, `CancelPreparedRunRoot`, `FinishWithOutbox`, `AcknowledgeOutbox`, `CommitUnregister`, `CommitRunCleanupDisposition`, `RecordContainmentEvidence`, normal `FinalizeRunTerminal`, normal `FinalizePreparedCancellation`, `FinalizeNoRootAbort`) | The launcher registers a distinct Reaper child identity with the resident service over the authenticated launcher-control channel, binding Reaper PID/start-time/PID-namespace/UID/cgroup tuple to generation/nonce/epoch and the separate Gateway tuple from the immutable BOOTSTRAP handoff. Each RPC kernel peer credentials and live process tuple must match the registered Reaper identity; its target tuple must match the BOOTSTRAP Gateway tuple. Registration is revoked only after launcher pidfd collection and durable retirement; stale generation, substituted process, or Gateway-as-Reaper identity rejects. ACK is accepted only from the original registered Reaper that owns the pending delivery. |
| Recovery (`ConsumeRecoveryControl`, `LoadRecoveryTarget`, recovery `FinalizeRunTerminal`, recovery `FinalizePreparedCancellation`) | A recovery-only Reaper child registered by the launcher for the fresh higher control generation. Its registration binds its distinct child identity to the new control nonce and exact old target generation/nonce/epoch. `ConsumeRecoveryControl` consumes that new generation; target read/finalization must match its persisted tuple. Finalization may use only already committed evidence; recovery cannot call `RecordContainmentEvidence`, `AcknowledgeOutbox`, `FinalizeNoRootAbort`, deliver events, or resume business work. No learner admission and no target/authority inferred from caller data. |

Before enabling live-run methods, the resident service records the launcher's authenticated Reaper registration and verifies the supplied child identity against the kernel-observed sender tuple on every packet, as specified by the docs/47 resident-ledger amendment. Recovery-only children register separately under their new generation and exact old target tuple; their method allowlist excludes live evidence writes, event acknowledgements, no-root finalization, and event delivery.

Reject a caller or target mismatch before writer reservation and emit a safe `control_auth_rejected` event. The method allowlist above is exhaustive: an unlisted method/caller combination is denied. Peer authentication does not itself authorize every RPC; each method is restricted to its caller class.

## Initialization and schema identity

Before changing journal mode, perform a read-only schema preflight: reject any non-empty schema other than exact v3, including v2, without changing its schema objects, ledger data, metadata, or `user_version`. Initialize every physical SQLite connection before any transaction or SQL dispatch by setting and reading back `PRAGMA foreign_keys=ON` and `PRAGMA recursive_triggers=ON`; reject and close a connection if either is not verified. Validate each pooled connection independently because both settings are connection-local. For a completely empty user schema, set WAL, take `BEGIN IMMEDIATE`, and recheck the schema under the writer reservation before creating the full schema and metadata atomically. Validate exact `user_version`, metadata version, normalized DDL, indexes, triggers, foreign keys, and user-object inventory at every open. Ignore SQLite-owned names only when their literal prefix is `sqlite_`; do not use an unescaped SQL `LIKE` pattern for this check. A concurrent opener must recheck under the writer lock. Reject partial, unknown, or tampered schemas without schema/data mutation; never migrate implicitly. WAL side effects are outside the schema/data non-mutation guarantee. Store uint64 generations as eight-byte big-endian BLOBs; do not store them as SQLite INTEGER or decimal text.

The v3 schema is a closed allowlist containing the existing base ledger objects plus:

- `pilot_control_generations`: immutable control generation BLOB primary key, 32-character lowercase-hex nonce unique, mode (`normal|recovery`), nullable `normal_run_epoch`, nullable target tuple, and creation timestamp. Fields are `generation`, `launch_nonce`, `mode`, `normal_run_epoch`, `target_generation`, `target_launch_nonce`, `target_run_epoch`, `created_at`; `normal` requires `normal_run_epoch` and null target fields, while `recovery` requires null `normal_run_epoch` and all target fields. Add explicit unique parent key `(generation,launch_nonce,normal_run_epoch,mode)` for the handoff FK. One table is the shared monotonic generation/nonce replay domain. Every valid BOOTSTRAP with a unique normal run epoch atomically consumes its control generation/nonce; invalid normal tuple or reused normal epoch commits no control row. Every authenticated, well-formed RECOVERY_BOOTSTRAP above the high-water mark consumes its new control generation/nonce even for target mismatch or `recovery_proof_missing`; stale/equal generations do not. Normal mode binds a fresh globally unique `run_epoch`. Recovery mode binds `(target_generation,target_launch_nonce,target_run_epoch)` of an existing run and may refer to that same old epoch on later, higher recovery generations after the protocol's retry/reconciliation gate.
- `pilot_principal_aliases`: immutable protected alias table in `operations.sqlite` (the separate alias-file wording in docs/43 §2.1 is superseded by its 2026-10-21 identity-resolution amendment). Fields are `tenant_id`, `identity_key_version`, version-specific `identity_digest`, canonical `principal_ref`, `canonical_key_version`, and `created_at`. Primary key `(tenant_id,identity_key_version,identity_digest)`; unique `(tenant_id,principal_ref)`. It never stores `immutable_user_id`. A resident Reaper-identity resolver writes a new-account alias in its own transaction before launcher journal/business operations; crash-left unused aliases are safe. The keyring itself remains a separately protected wrapped-key object.
- `pilot_authorization_state`, `pilot_session_fences`, and `pilot_fixture_grants`: mutable current-state fence objects written only by `PublishAuthorizationFence`. Account/snapshot and fixture grant revisions advance monotonically; session state is one-way `active -> revoked` and expiry only moves earlier. RPCs reject stale/lower revision, changed same-revision bytes, role/session mismatch, absent fixture grant, and unknown state. These are added to the exact schema allowlist and never inferred from HTTP middleware.
- `pilot_authz_update_receipts`: immutable idempotency receipts for signed authorization-fence updates, keyed by 16-byte `request_id` and bound to target kind/key, target-scoped revision, and update digest. Account and session revisions have separate scopes, so the same numeric value may coexist.
- `pilot_prepared_cancel_receipts`: immutable pilot-only `PreparedRunRootCancellationReceipt` rows, keyed by 32-byte receipt digest and unique per 16-byte RunRoot operation ID. Each canonical CBOR receipt binds exact generation, epoch, operation ID/payload digest, close operation ID, `owner_generation=0`, `claim_absent=true`, `filesystem_dispatch_absent=true`, pinned-anchor absence witness, exact dispatch-intent event digest, and `intent_delivery_disposition=acknowledged|never_authorized`. For `acknowledged`, validator joins by the unique `(operation_id,event_name)` row and requires its immutable ACK digest to match `intent_event_digest` plus a non-null 16-byte delivery correlation; the correlation is relational evidence and not encoded in this CBOR receipt. `never_authorized` binds the exact event digest whose `ready` row becomes `suppressed` with this receipt digest in the same transaction. No mutable Logger side-journal digest is required. Its digest domain and field order are fixed by docs/43 §8.4; it is not an `OperationEvidenceReceipt` and cannot satisfy another operation's receipt predicate.
- `pilot_bootstrap_handoffs`: immutable consumed BOOTSTRAP tuple keyed by generation, with exact docs/47 ordered identity fields plus ledger discriminator `control_mode='normal'`: `generation`, `launch_nonce`, `run_epoch`, `pid`, `uid`, `start_time_ticks`, `pidns_device`, `pidns_inode`, `cgroup_mount_id`, `cgroup_device`, `cgroup_inode`, `control_mode`. There is no GID in the docs/47 wire tuple. PID/UID and uint64 fields use docs/47 ranges and encodings. A composite FK `(generation,launch_nonce,run_epoch,control_mode)` references the explicit control parent key (the parent epoch column is named `normal_run_epoch`); unique normal `launch_nonce` and `run_epoch` constraints are permanent tombstones. Insert control, handoff, and initial lifecycle rows in that order in one transaction; ACK follows only after all three commit.
- `pilot_run_lifecycle`: one mutable, compare-and-set row per accepted normal generation, with fields `generation`, `run_epoch`, `lifecycle_state`, nullable `run_root_operation_id`, nullable `close_operation_id`, nullable `close_key_hash`, nullable `close_payload_digest`, `terminal_result`, and `updated_at`. States are `bootstrapped|logger_registered|logger_ready|reaper_ready|registered|active|terminating|unregistered|containment_empty|terminal`. Only the enumerated forward transitions are permitted: `bootstrapped->logger_registered->logger_ready->reaper_ready->registered->active->terminating->unregistered->containment_empty->terminal`; `registered->terminating` also applies to the exact prepared/no-dispatch cancellation branch and ordinary no-root path. Each transition CAS binds the exact generation/epoch and preceding durable ACK/evidence. `terminal` is immutable. `rejected`, `canceled`, and `indeterminate` are not lifecycle values: rejected bootstrap has no lifecycle row, queued cancellation is launcher-journal state, and indeterminate/recovery-required are API projections of underlying durable rows. `terminal_result` is NULL until finalization and then `abandoned|closed_without_root`; it does not duplicate the operation result. This lifecycle table describes host protocol progress; docs/43 `run_state`/`run_terminal_state` remain business containment/result fields and are deliberately separate. On successful RunRoot receipt commit, docs/43 `run_state` becomes `active`, while lifecycle remains `registered` until the finish ACK. The ACK transaction advances lifecycle `registered->active` only if close has not already begun; a concurrent close winning first leaves lifecycle `terminating`, and a later ACK only acknowledges the outbox row.
- The docs/43 operation, allocation, receipt, reservation, run-terminal, and containment-evidence objects, with their exact documented columns and constraints, including immutable `business_operation_id` (the 16 raw bytes decoded from `run_epoch` for docs/45 `run_root_create/v1`), `request_id`, canonical payload digest, owner generation, typed terminal response, and receipt binding. For close/no-root, both operation primary `operation_id` and `business_operation_id` equal the exact launcher-journal `close_operation_id`; this is also the lifecycle/receipt operation ID. The browser idempotency-key-to-epoch mapping is a distinct immutable launcher-journal binding, not this internal business key. Operation/allocation/run uniqueness is scoped to the stable tenant and principal namespace; epochs are globally unique and never reused.
- `run_root_event_outbox`: immutable `outbox_id`, operation FK, allowlisted event name, original process ID, canonical event bytes, SHA-256 digest, and creation time; mutable delivery state (`ready|send_authorized|acknowledged|suppressed`), nullable `acknowledged_digest` (32-byte BLOB), nullable `acknowledged_correlation` (16-byte BLOB containing the raw `delivery_nonce`), and nullable suppression-receipt digest. Ready requires all disposition fields NULL. `AuthorizeOutboxSend` atomically changes `ready→send_authorized` before the original Reaper may call Logger; retries remain `send_authorized` until exact ACK. A cancellation writer may change only a `ready` `run_root_dispatch_intent` to `suppressed`, with all ACK fields NULL and a matching immutable prepared-cancellation receipt. Since sender authorization and suppression share the writer, only one wins; `send_authorized` with missing ACK is uncertain and blocks cancellation. No ACK is fabricated. The Reaper uses the Logger protocol `delivery_nonce` as the exact 16-byte ACK correlation (32 lowercase hex on the wire); there is no separate nonce/correlation field. Each attempt has one outstanding request and a fresh nonce. The matching accepted ACK is committed with its exact event digest and nonce. After timeout, the channel must reach EOF and its handler drain before retry; stale ACKs from retired channels are discarded, and only the current-attempt ACK may commit. An identical durable ACK replay is idempotent; changed nonce/digest rejects. Unique `(operation_id,event_name)` for `run_root_dispatch_intent` and `bootstrap.finish`; no outbox replay row is created for `run_root_dispatch_committed`.

All immutable tables reject UPDATE and DELETE with abort triggers. No `REPLACE` or UPSERT is permitted. Exact normalized DDL, including every docs/43 object, must be recorded as a hash-bound manifest in review evidence before implementation.

## Transaction contracts

Every write method reserves the SQLite writer before reading any decision input. A BUSY/LOCKED, cancellation, or commit ambiguity is an infrastructure-uncertain outcome: fence that ledger instance, send no success ACK, and require process restart plus durable inspection. Normal operations do not retry automatically.

`PublishAuthorizationFence(ctx, signed_update)` verifies the pinned authorization-authority signature, canonical payload, tenant/user alias, monotonic request ID/revision, and complete role/fixture or session state. It atomically applies the new authorization snapshot and immutable update receipt. Exact replay returns its recorded result; stale revision or changed bytes reject. A restrictive auth-store change is not reported effective until this transaction commits; failure is fail-closed. Permission grants are not usable until both auth authority and fence contain the grant. `CheckCurrentAuthorization(ctx, admission)` is a read-only bounded check that compares the signed admission's principal, account revision/snapshot digest, role, fixture grant, session hash/revision, active state, and expiry to the latest committed fence. For launcher-journal status projection, run it before lookup; its successful read snapshot is the authorization linearization point, so a later revocation is ordered after this read and the request may finish from that snapshot. `LookupByPrincipalOperation` checks the fence and reads its result in one snapshot. For close, `BeginRunTermination` rechecks the fence in its writer transaction. Unknown/stale state is denied.

`ConsumeBootstrap` inserts the initial lifecycle row in the same transaction as the control generation and handoff. `CommitLifecycleBoundary(ctx, generation, expected, next, evidence)` performs each startup transition by CAS on the exact row and validates the evidence appropriate to the boundary (logger registration ACK, Logger channel readiness, bootstrap.start ACK, or Gateway REGISTER_ACK). It never accepts a caller-provided PID/UID/epoch; those are loaded from the immutable handoff/journal binding. A duplicate identical boundary returns the durable current state without replaying the side effect; an out-of-order or conflicting boundary fences the generation. After a successful RunRoot receipt and finish-event ACK, one CAS enters `active`. A startup failure before REGISTER_ACK uses launcher containment/reap; it cannot call the normal UNREGISTER transition.

1. `ConsumeBootstrap(ctx, request)` is authorized by launcher control identity, validates the canonical docs/47 fields, reserves the writer, requires `generation > high_water`, a fresh nonce, and a globally unused normal `run_epoch`, then inserts both `pilot_control_generations(mode=normal)` and the complete `pilot_bootstrap_handoffs` row in one transaction. ACK follows only after both rows commit. Any duplicate/stale tuple is rejected without writes; unknown commit outcome fences the instance and requires restart inspection.
2. `ConsumeRecoveryControl(ctx, request)` is authorized only to the launcher-registered recovery-only Reaper for this fresh control generation. It requires a fresh control nonce and generation greater than the shared high-water mark, then inserts a recovery control row containing the full launcher-registered target tuple in the same transaction. It does not insert a handoff or allocate a business epoch. After that commit, `LoadRecoveryTarget` and (only when permitted) `FinalizeRunTerminal` or `FinalizePreparedCancellation` use that exact tuple: valid existing evidence may permit only the matching final transaction; missing proof returns `recovery_proof_missing`; authenticated target mismatch returns `rejected`. These outcomes leave target rows untouched except the allowed final transaction. Recovery may reference the same target epoch again only when docs/47 explicitly permits a higher-generation query (uncertain prior outcome or post-offline-repair); a known missing-proof/not-ready/rejected outcome is not automatically retryable.
3. `PrepareWithHandoff(ctx, admission, handoff, operation)` validates signed admission and stable principal, then in the same `BEGIN IMMEDIATE` transaction compares account authorization revision/snapshot digest, explicit role/fixture grant, and session revision/active state against the current fence before replay lookup or insert. Replays return their stored projection only after this check; changed payload conflicts. For a new key it also checks the exact consumed BOOTSTRAP Gateway tuple and absence of another active generation/lease, requires lifecycle=`registered` with no close fields, then atomically inserts allocation, operation, held reservation, and dispatch-intent bytes/digest. A writer-serialized race with `PublishAuthorizationFence` has one outcome: fence commit first makes stale admission reject, or Prepare commit first makes the operation durably prepared before revocation becomes effective. A race with `BeginRunTermination` either binds the RunRoot operation first or moves lifecycle to `terminating` first; late Prepare rejects without effect. `Claim` is separately authorized only to the registered live Reaper and repeats lifecycle, operation-ID, owner-generation, and empty-close predicates. Caller Reaper and Gateway target identities are distinct.
4. `Claim` is a compare-and-set requiring operation=`prepared`, allocation=`prepared`, exact owner generation, and held reservation; it atomically changes operation/allocation to `executing` and records the immutable dispatch-committed identity before any filesystem syscall. Duplicate claim or owner mismatch fails without another syscall. An unknown commit fences the instance; after restart the operation becomes `indeterminate` with lease held unless the exact durable ledger proves the CAS did not commit. No recovery path retries mkdir after an uncertain executing commit.
5. `FinishWithOutbox` is a CAS requiring operation=`executing`, matching `owner_generation`, allocation=`executing`, and a validated immutable RunRoot receipt. The receipt outcome controls the persisted business result: only `created` changes operation/allocation to completed and `run_terminal_state=active`; a documented deterministic no-effect outcome may become `abandoned` only through the complete docs/45/43 absence-proof terminal transaction; `EEXIST` leaves operation=`abandoned`, allocation and run terminal=`indeterminate`, and lease held; any ambiguous effect remains `indeterminate` and fenced. A validated EEXIST collision receipt may enqueue exactly one typed failure `bootstrap.finish` so the live Gateway can show a terminal failure; it can never signal readiness. Only a durable typed outcome may enqueue this event; an ambiguous/uncommitted effect cannot emit success or finish. For the successful `created` outcome, the receipt, completed operation/allocation, active run-terminal state, and finish outbox row commit atomically. The lease remains held and the public run is not `ready` until the exact finish ACK is recorded. Commit ambiguity fences the store; restart reads durable state and never infers rollback.
6. `AuthorizeOutboxSend` is callable only by the original registered live Reaper. In one `BEGIN IMMEDIATE` transaction it requires the exact event row=`ready` and CASes it to `send_authorized` before any Logger write is permitted. For `run_root_dispatch_intent`, it additionally requires lifecycle not `terminating` and operation=`prepared`; close therefore prevents a late dispatch-intent send. For `bootstrap.finish`, it requires an already committed typed receipt/outbox tuple and lifecycle=`registered|active|terminating|unregistered|containment_empty`. A `created` result requires operation/allocation=`completed` and run terminal=`active`; an EEXIST failure requires the exact collision receipt, operation=`abandoned`, allocation/run terminal=`indeterminate`, and held lease. These predicates permit delivery of an existing result after close wins, including after Gateway containment is proven empty but before finalization. The failure result never authorizes readiness, cleanup, or lease release. This method never authorizes a new business effect and is rejected after lifecycle=`terminal`. It is allowed only through the original Reaper process identity and its still-active Logger registration; a new data channel is allowed only after prior EOF/handler retirement, with a fresh delivery_nonce. Logger restart or Reaper exit invalidates this authority. Replay is idempotent for the same outbox/event digest; any changed event or terminal/suppressed row rejects. Cancellation and intent authorization serialize on the same writer, so a suppressed intent can never race a sender that has permission to emit it. An authorized row without ACK is ambiguous and is not suppressible.
7. `AcknowledgeOutbox(ctx, CorrelatedLoggerAck)` accepts only the exact `send_authorized` row, original process ID, 16-byte `delivery_nonce` generated for the current send attempt, and matching event digest. `CorrelatedLoggerAck` is an internal value created only by the original Reaper's trusted Logger transport after it verifies the complete wire ACK against the single outstanding request on that channel; the ledger RPC is not exposed to Gateway/API callers and accepts no unverified raw ACK. The ledger authenticates the original Reaper process on this method; trusted Reaper code is the current-attempt provenance boundary, and compromised Reaper is outside the threat model. In one writer transaction it changes `send_authorized,NULL,NULL -> acknowledged,digest,correlation`. A `bootstrap.finish` ACK may promote lifecycle `registered->active` only in that same transaction when the bound immutable receipt says `created`, operation and allocation are both `completed`, docs/43 `run_terminal_state=active`, the exact lease remains held, and all close fields are NULL. Any non-created outcome ACK is acknowledgement-only and can never make the lifecycle active or the public run ready; EEXIST remains fenced/indeterminate and a deterministic abandoned result follows its docs/45 terminal projection. If close already changed lifecycle to `terminating`, `unregistered`, or `containment_empty`, the exact ACK from the original live Reaper/current delivery attempt is recorded without promoting or otherwise changing lifecycle or the close operation; this does not permit a replacement Reaper to deliver or fabricate an ACK. The original Reaper identity and Logger registration must remain live; the response must match the current delivery_nonce within the docs/46 ACK deadline while that channel/store remains healthy. A retired channel cannot contribute a late ACK. A timed-out, poisoned, retired, or unregistered Logger channel cannot accept a delayed ACK; then quarantine and keep the lease held. A test harness may delay/release the real Logger response within the deadline but may not impersonate the Reaper or inject its PID/credentials. Finalization may commit only after all required outbox rows are acknowledged, except the single dispatch-intent suppressed by a valid prepared-cancellation receipt. Repeated identical ACK is idempotent; changed identity/correlation/digest or any other transition fails closed. ACK state never releases the lease. A finish ACK loss leaves the committed receipt and unacknowledged (`send_authorized` or `ready`) row intact; docs/45-48 do not authorize delivery under a replacement process identity, so recovery reports `recovery_required` and keeps the lease held.
8. `RecordContainmentEvidence` is callable only by the normal active Reaper after authenticated `CONTAINMENT_EMPTY` on its original docs/47 control channel. One `BEGIN IMMEDIATE` transaction validates the exact target generation/nonce/epoch, full persisted Gateway process and cgroup identity, endpoint tuple/removal, leader-reaped/populated flags, then inserts the immutable `RunContainmentEvidence` row and CASes lifecycle `unregistered->containment_empty` in the same transaction, with exact docs/47 fields `[run_epoch,gateway_generation,launch_nonce,gateway_process_identity,gateway_cgroup_identity,endpoint_identity,endpoint_removed,leader_reaped,populated,evidence_version]`, where the process identity is `[pid,start_time_ticks,pidns_device,pidns_inode]`, cgroup identity `[mount_id,device,inode]`, and endpoint identity `[parent_device,parent_inode,socket_device,socket_inode]`; for a successfully created RunRoot the same transaction CAS-transitions docs/43 `run_state=terminating` to `containment_empty`. For a validated EEXIST collision, no docs/43 root `run_state` row exists; the transaction advances only host lifecycle to `containment_empty`, preserves `run_terminal_state=indeterminate` and the held lease, and makes terminal finalization ineligible pending offline reconciliation. A `no_root_abort` also has no docs/43 run-state row, but follows its distinct no-operation/no-lease finalizer. This is the atomic evidence boundary in docs/47. Recovery-only Reaper has no evidence-write method or capability; it can only read committed evidence.
9. `FinalizeRunTerminal` is the docs/47 finalization transaction, invoked by the normal Reaper after evidence commit or by recovery-only Reaper for an existing evidence row. Its predicates require exact target binding; `run_state=containment_empty`; evidence digest and tuple match; all business operations except the current close-control operation are `completed|abandoned` with required matching receipts; cleanup is already `complete|retained` (it cannot set cleanup complete); all required outbox rows are acknowledged with exact digests; and the exact lease is held. It atomically writes terminal run state, lifecycle `terminal`, binds the evidence digest, and releases that lease. An identical already-terminal retry returns `already_terminal` with no writes. `recovery_proof_missing`, `recovery_not_ready`, tuple mismatch, unknown operation, EEXIST collision, or uncertain effect never releases the lease. Crash after evidence commit leaves `containment_empty` and held lease, so a later permitted recovery may retry only this transaction.
10. `BeginRunTermination(ctx, principal, run, close_key, close_operation_id)` validates signed current admission and close-key binding before close-result lookup, then in one writer transaction rechecks the durable authorization fence and requires lifecycle `registered|active`, a held lease where one exists, and either (a) no pending business operation, or (b) exactly one `run_root_create` operation in `prepared` with no committed Claim/dispatch. It inserts an immutable docs/43 operation with kind `pilot_run_close` or `pilot_no_root_abort`, records its ID and close-key digest in `pilot_run_lifecycle`, and CASes lifecycle state to `terminating`. For a successfully created RunRoot whose receipt is committed, the same transaction CASes docs/43 `run_state=active->terminating`; this includes lifecycle `registered` when `bootstrap.finish` is still pending. For EEXIST, no root `run_state` row exists and the indeterminate run-terminal/allocation remain unchanged while host lifecycle enters `terminating`; later containment evidence cannot make this outcome finalizable. In that pending-finish case UNREGISTER/containment may complete, but the pending outbox row prevents finalization and lease release. For `registered` with no RunRoot operation, docs/43 has no run-state/lease row to update and the distinct `no_root_abort` predicates apply. This writer reservation competes atomically with Prepare, Claim, and finish ACK: Prepare winning binds an operation and prevents the no-root path; close winning first prevents late Prepare; Claim winning first makes close reject as `recovery_required`; close winning first moves lifecycle to `terminating`, so late Claim cannot dispatch; finish ACK winning first promotes lifecycle to `active`; close winning first keeps it `terminating` when the later ACK arrives. Within that same writer transaction the close operation is created in `prepared` and immediately CASed to `executing`, before any teardown effect; this makes the durable close commit its execution authorization. For the exact prepared/no-dispatch branch, close first commits durably and freezes Claim, then the original registered live Reaper calls `CancelPreparedRunRoot`; cancellation requires `state=prepared`, no committed Claim/dispatch/syscall, a durable no-send proof for any pending intent event, and exact no-effect evidence. In one cancellation transaction, operation and allocation become `abandoned`, a `PreparedRunRootCancellationReceipt` commits to its dedicated immutable table, lease remains held, `run_terminal_state` remains `none`, and root `run_state` remains absent. An acknowledged intent remains acknowledged; an intent in `ready` is atomically suppressed with its exact event digest in the cancellation receipt; `send_authorized` without ACK blocks cancellation, while a late AuthorizeOutboxSend after suppression is rejected. After UNREGISTER and containment-empty evidence, `FinalizePreparedCancellation` requires the exact absence witness, the cancellation receipt, abandoned operation/allocation, `cleanup_state=not_required`, and every outbox row acknowledged or this one intent suppressed. It atomically marks the close operation completed, terminalizes lifecycle and `run_terminal_state=abandoned`, and releases the exact lease; it is distinct from `FinalizeNoRootAbort` because allocation/operation tombstones exist. Only after cancellation ACK may the launcher send UNREGISTER. If proof or ACK is unavailable, return `recovery_required`, retain the lease, and send no UNREGISTER. An executing RunRoot operation rejects close as `recovery_required`; the caller waits for a durable terminal result and retries closure. Same-key/same-run replay returns the stored close projection; changed key binding conflicts; GET never calls this method. The launcher first generates a random close operation ID and fsyncs the immutable close-key tuple `(principal_ref,run_epoch,close_key_hash,close_payload_digest,close_operation_id,state=intent)` in its journal; it then calls Reaper to commit the same tuple in the control ledger and updates the launcher record to `ledger_committed` only after the ledger ACK. UNREGISTER is sent only after both durable commits and any required prepared-operation cancellation ACK. If the launcher crashes between these commits, restart compares exact tuples and may finish the missing ledger binding before any effect; mismatch quarantines and holds the lease. If ledger commit ACK is uncertain, restart inspects the ledger; it never resends UNREGISTER until journal and ledger agree. Same-tuple retry is idempotent; conflicting reuse rejects. If the run is `queued` before any spawn, a `CancelQueuedRun` journal transaction tombstones its API key without allocating an epoch or launching children. It requires `state=queued` and `spawn_count=0`; duplicate cancellation returns the same result; once spawn intent exists it cannot claim no-effect. If the run is `starting` before Gateway REGISTER_ACK, the launcher uses startup failure containment/reap and never sends UNREGISTER. Only a `registered|ready` run sends one UNREGISTER. If the begin-close commit is uncertain, no teardown message is sent until restart inspection; the lease remains held.
11. `CommitRunCleanupDisposition(ctx, run, disposition, proof)` applies only to an actually created RunRoot and may run only after the original Reaper has received authenticated `CONTAINMENT_EMPTY`, verified Gateway/worker containment empty and all RunRoot handles closed, and completed safe cleanup or verified safe retention. It records immutable cleanup evidence and CASes `cleanup_state=pending` to `complete|retained`; failure or uncertainty records/retains `indeterminate` with lease held, and no finalization follows. A prepared cancellation has no root to clean and retains `cleanup_state=not_required` under the docs/43 §8.4 absence-witness rule. It cannot run on browser/API supplied evidence. The proof binds exact epoch and root identity and is never logged.
12. `CommitUnregister` is called by the original Reaper after it verifies the exact authenticated UNREGISTER tuple and closes/stops the listener. In one ledger transaction it CASes lifecycle `terminating->unregistered`; docs/43 run state and lease are unchanged. Only after that transaction commits does Reaper send `UNREGISTER_ACK` to the launcher. If that ACK is lost or times out, the launcher MUST NOT replay UNREGISTER or send CONTAINMENT_EMPTY on the uncertain channel; it contains/reaps Gateway, reaps the old Reaper, then starts the docs/47 recovery-only higher-generation session. Without committed containment evidence that session returns `recovery_proof_missing` and leaves target rows and lease unchanged. A read-only ledger projection of `unregistered` is diagnostic only and never authorizes continuing the old protocol. The launcher records a received ACK in its own journal before containment. The close operation gets a deterministic CBOR `pilot-run-close-v1` receipt binding `(run_epoch,close_operation_id,close_key_hash,terminal_result,containment_evidence_digest)`; no-root abort additionally binds the exact pinned-anchor absence witness. The `pilot_run_close` operation becomes `completed` only inside finalization. After the launcher receives `UNREGISTER_ACK`, `RecordContainmentEvidence` atomically advances lifecycle `unregistered->containment_empty` and docs/43 `run_state=terminating->containment_empty` for a root that was created; for the prepared-cancel branch, host lifecycle advances but docs/43 root `run_state` remains absent. `FinalizeRunTerminal` atomically advances both lifecycle `containment_empty->terminal` and docs/43 `run_state=containment_empty->terminal`, updates the terminal binding, and releases the held lease. Preconditions distinguish tables: `run_state=containment_empty`; every business operation except this close operation is `completed|abandoned` with its required receipt; the unique close operation is `executing` with matching ID/key digest; prior cleanup evidence is `complete|retained`; containment evidence matches; and every existing required outbox row is acknowledged. `FinalizeRunTerminal` then atomically changes the close operation to `completed`, commits terminal run state plus lifecycle `terminal`, and releases the exact lease. For a prepared cancellation, `FinalizePreparedCancellation` is the distinct terminal transaction: it requires lifecycle=`containment_empty`, exact immutable handoff and containment evidence, the typed cancellation receipt, operation/allocation=`abandoned`, `run_terminal_state=none`, no root `run_state` row, `cleanup_state=not_required`, exact pinned-anchor absence witness, close operation=`executing`, and all outbox rows acknowledged or the one dispatch-intent row suppressed with the matching no-send proof. It atomically writes `run_terminal_state=abandoned`, completes the close operation, marks lifecycle terminal, and releases the exact lease. This is not `FinalizeNoRootAbort`: its permanent allocation/operation/outbox tombstones are required and retained. For ordinary `no_root_abort`, a separate `FinalizeNoRootAbort` transaction verifies lifecycle=`containment_empty`, exact immutable handoff and containment evidence, a typed close receipt, no RunRoot operation/allocation/reservation/outbox rows for the epoch except the current `pilot_no_root_abort` operation, and an exact pinned-anchor absence witness. By construction it finds no lease to release; it atomically completes the close operation and marks lifecycle terminal with result `closed_without_root`. This path cannot treat a missing or corrupt expected lease as success. A no-root abort and prepared cancellation have no RunRoot finish row requirement. A pending finish or unsuppressed pending intent prevents the applicable finalization and keeps the lease held. Duplicate identical finalization returns the committed result; conflicting close attempts fail without state change.
13. `LookupByPrincipalOperation` receives the immutable business-operation/epoch binding resolved by the protected launcher journal from the browser idempotency key. It checks the current signed authorization fence before lookup, then reads by authenticated tenant + stable principal + resolved business_operation_id; it does not store or query the browser idempotency hash. It never trusts RPC-supplied principal or exposes cross-principal existence. The pilot unique key includes tenant, superseding the generic principal-only key wording in docs/43.

## Recovery and outbox delivery boundary

Recovery consumes a strictly higher shared control generation before inspecting the exact old target. The normal close sequence is launcher close-intent fsync -> `BeginRunTermination` ledger commit -> launcher ledger-committed fsync -> optional prepared-cancellation receipt/ACK -> UNREGISTER/ACK -> launcher containment and CONTAINMENT_EMPTY -> cleanup disposition when a root exists -> containment-evidence/run-state commit -> `FinalizeRunTerminal` or `FinalizePreparedCancellation`; each effect follows its durable predecessor. `recovery_proof_missing` consumes that control nonce/generation but performs no mutation to the target operation, allocation, run, evidence, cleanup state, or lease. Existing committed evidence permits only read-only terminal projection or the matching final transaction where all predicates match. Recovery never waits for or reaps an old process, inserts evidence, delivers/suppresses outbox rows, or resumes normal business work. The normal `RecordContainmentEvidence` call is driven only by the original live Reaper receiving authenticated `CONTAINMENT_EMPTY` as defined by docs/47; that transaction updates host lifecycle and, for an existing root only, docs/43 containment `run_state` as specified above.

The existing docs/47-48 Logger protocol binds events to the current registered process identity. Consequently, a new recovery-only Reaper cannot deliver an old `bootstrap.finish` row using a new registration. This v3 schema intentionally leaves that row pending and keeps status `recovery_required`; it defines no bypass. Any later delivery-only recovery protocol must bind the original process identity and exact event digest, have its own SDD and security/backend/test review, and prove it cannot emit arbitrary events. The dispatch-intent retry remains limited to the original live Reaper and its still-active Logger registration as specified in docs/45-50; a fresh channel is allowed only for the same live Reaper identity after EOF/drain.

## State invariants and fault matrix

- No filesystem effect precedes committed `prepared`; no mkdir follows uncertain `executing`/dispatch commit.
- No terminal business result is inferred from Logger output. Only the ledger receipt decides it.
- No lease release precedes durable exact containment evidence and the final CAS transaction.
- No committed epoch, idempotency binding, control generation, or nonce is reused after commit, crash, or cleanup; stable validation rejections that commit no row do not consume an identifier. Recovery target epochs may be referenced by later higher-generation recovery controls only under docs/47 retry/reconciliation rules.
- Fault tests bind to the stable IDs in docs/50's versioned manifest; every fault has a named barrier and exact pre/post rows/bytes, lease, ACK/result, syscall/event count, and trace oracle, with no sleep-based synchronization. Cases cover pre-commit rollback, commit-then-error, ACK loss, duplicate/out-of-order ACK, stale generation racing across independent connections, invalid/cross-bound handoff, every writer crash boundary, outbox replay, evidence absence/tamper, and evidence-commit/finalize crash window.
