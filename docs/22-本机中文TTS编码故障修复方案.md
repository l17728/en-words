# 22 本机中文TTS编码故障修复方案

日期：2026-10-14。状态：同模型UTF-8隔离对照及独立故障测试通过；已授权完成仅8002应用。原冻结12条TTS自动复测及用户人工试听全部通过，完整浏览器媒体旅程仍单独待验。以下probe人工pending保留为历史时点，不代表本轮12条当前状态。

## 事实与设计边界

产品按UTF-8 JSON向8090提交“猫”，平台返回500，错误包含`Ignore OOV 'è'`、`Failed to convert è to token IDs`。原20秒服务预算未耗尽，词典本身包含“猫”。有效诊断见`review/tts-cat-valid-diagnostic-20261014.json`；此前因测试管道把文本变成问号的探针不能算成功对照。

平台TTS包装层经PowerShell把中文作为Sherpa CLI位置参数传入。系统ANSI代码页为936；“猫”的GBK字节`C3 A8`按UTF-8解码正好是`è`。CLI使用窄字符argv，而分词器期待UTF-8，此边界与失败一致。必须再用同模型、同参数的显式UTF-8输入做修复对照，不能只凭推断宣布关闭。

## 最小修复候选

保留平台现有模型、词典、FST、voice和speed。包装层将文本保存为UTF-8临时文件，由与已安装发行包匹配的小型C API辅助程序读取原始字节，调用同版本Sherpa动态库。命令行只传受控文件路径，不再传中文正文。保持同一HTTP接口、超时、并发限制、取消和临时文件清理。

先在en-words的`.test-tools/`编译和运行隔离探针，输出仅到测试目录；不更改平台文件、系统代码页或模型配置。确认同文本从500变成合法非静音WAV后，形成可评审的平台补丁、构建说明、源文件及DLL版本校验和回退步骤，再处理共享服务的应用和重启。不能猜测不存在的`--text-file`参数，不能以全局`chcp`或系统UTF-8选项代替明确编码合同。

## 验收门

隔离对照至少覆盖“猫”、常用双字词、标点和中英混合输入；成功/失败均保留原文标签及状态。测试UTF-8字节传递、临时文件唯一性、失败清理、取消、超时、并发及不记录正文。平台正式应用后，重跑产品真实MediaRecorder→WAV→ASR、中文TTS播放及完整课堂旅程；独立音质矩阵和人工试听仍分别验收，不因修复编码便提升模型质量分数。

## 隔离对照结果

`review/tts-utf8-isolated-20261014.json`记录同模型、同配置的UTF-8 C API探针：“猫”由原HTTP500改为8.046秒生成7168采样；“苹果”5.735秒、“猫，苹果。”7.062秒，均为合法16kHz单声道PCM16且非静音。CLI帮助核验默认噪声、长度、静音、分句和词典参数保持一致。这支持命令行编码边界为本次故障根因，尚不代替候选HTTP包装层及产品真实链路验收。

“cat是猫。”5.875秒也产生WAV，但原生诊断明确忽略OOV“cat”，属于内容缺失，不能记为混合语言成功。保留中文平台合成、英语本地浏览器voice的能力边界，不因容器合法而宣称英语或音质通过。人工可懂度仍待试听。

实际候选`platform-tts-server.candidate.cjs`与宽字符辅助程序在独立18002服务验证同一“猫”请求：HTTP200、7.000秒、15916字节WAV、16kHz单声道PCM16、7936采样、RMS431.4，见`review/tts-utf8-candidate-http-20261014.json`。独立进程已退出；模型和Sherpa目录只读引用，未改8002/8090。独立包装层测试7/7通过，覆盖UTF-8正文、同步启动失败、进程错误、超时、取消、预取消、不同临时目录和清理；测试直接读取可提交候选源，不依赖ignored临时源。
