# 中文 TTS 常驻模型可行性与 SDD（草案）

## 目的与基线

现有 8002 中文 TTS 每请求调用一次 `tts-utf8-worker.exe`，原生程序每次创建并销毁 Sherpa 模型，导致双学生虽然可以排队完成，N=2 p95 仍为 5.699 秒；N=4 发生 1/40 次排队 429。目标是在不更换中文音色、不改变课堂 `tts_failed` 语义的前提下，将公开短词的 N=4/8 合成 p95 降到 2 秒内、p99 降到 5 秒内。此目标必须经 8090 代理和真实浏览器测量，不能由原生微基准代替。

本机具备 WinLibs MinGW g++ 16.2.0（`D:\en-words-toolchain\winlibs-gcc-16.2.0\toolchain\mingw64\bin\g++.exe`）、Sherpa C API 头/DLL/import lib；现有源码已通过 `-std=c++17 -municode` 临时编译。CPU 为 2 核/4 逻辑线程。仅在 `.test-artifacts/` 编译计时副本，线上 8002/模型未修改：10 次单进程调用总耗时 p50 3.495 秒、p95 6.608 秒；其中模型创建 p50 2.703 秒、p95 3.140 秒，实际合成 p50 0.454 秒、p95 0.891 秒。临时副本在同一模型实例上连续合成 30 次，热合成 p50 0.422 秒、最大 0.625 秒。

并行热探针（每进程加载一次、连续合成 10 次）显示：2 个进程各 1 线程 p95 0.641 秒；4 个进程各 1 线程 p95 0.812 秒。2 个进程各 4 线程 p95 1.062 秒；4 个进程各 4 线程 p95 2.125 秒。该结果支持优先验证 **4 个常驻进程、各 1 个推理线程**；N=8 每进程需要约两段，实际 HTTP p95<2 秒仍未证实，受这台 CPU 和请求长度限制。

## 最小运行架构

保留 8090 管理平台和 8002 Node HTTP 入口。新增原生 worker 的 `--serve` 模式：进程启动时加载固定的现有 Sherpa 模型一次，并预热；之后通过私有 stdin/stdout 二进制帧逐段合成。每个 worker 同时只处理一段。Node 启动最多 4 个 worker，采用 FIFO 把请求分配给空闲进程，最多 8 个未完成请求（4 执行+4 等待），满载返回 429。管理平台的 `tts.maxConcurrent` 先保持已验收的 2，只有独立容量门通过才受控提升至 4、再到 8。不得把调用并行直接加在同一个 Sherpa 模型句柄上；C API 线程安全性尚未证实。

协议固定版本、固定模型 ID；请求帧包含单调 request ID、UTF-8 长度（≤2000 字符/8000 字节）、voice/speed；响应包含相同 ID、状态和 WAV 长度（≤8 MiB）。Node 必须校验帧长度、音频格式和 request ID，禁止路径参数、任意命令或正文日志。stdout 只写协议，stderr 只写不含正文的状态；日志记录 trace、worker ID、队列/合成/首字节耗时、结果。worker 未达到 READY 不进入容量池，`/v1/models` 至少一个健康 worker 时可报告 ready，但应另报 `ready_workers/target_workers`；少于 4 个时容量标为 degraded。对外可接收容量随健康 worker 数收紧（最多每健康槽 2 个含等待请求），不得在仅 1 个槽健康时继续接受 8 路；超额明确 429，课堂维持原段暂停。

等待中取消直接移出队列。执行中取消保留 worker 槽位直到对应响应被完整读出，然后丢弃旧 WAV；不得把结果匹配给下一学生。单段超过 6 秒或协议损坏时杀掉该 worker、确认进程退出、失败当前请求并重建该槽；其他 worker 继续服务。进程重启有界退避，连续失败时停止重试并让入口返回 503，课堂维持原段暂停/文字降级。Node 崩溃时 8090 既有 supervisor 最多重启 3 次，重启后不得重放已取消请求。热 worker 启动和预热应在对外报告 ready 前完成，避免首个学生承担冷启动。

Windows 父进程崩溃边界：每个原生 worker 启动时打开并持有 Node 父进程的 `SYNCHRONIZE` 句柄，独立 watchdog 线程执行 `WaitForSingleObject`；父进程退出时立即结束自身，即使合成线程阻塞。父 PID 仅用于打开句柄，句柄持有可避免 PID 重用误判。每个槽使用仅限本服务、带版本和槽号的命名 mutex 防止 supervisor 重启期间新旧 worker 双驻留；新 Node 应等待旧槽退出，超时明确降级而不得额外启动副本。实现前以“杀 Node → 8090 连续重启 3 次 → 检查每槽最多一个 worker、旧 PID 全部消失、RSS 回到稳态”故障测试证实该机制；若不能保证，改用 Windows `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` 的原生 broker，不上线常驻版。

资源升级门：当前系统约 15.9 GiB RAM、空闲约 4.7 GiB；单个 1 线程常驻模型的隔离探针峰值 RSS 186.4 MiB、峰值提交 180.6 MiB，四槽不能仅按模型文件大小估算。上线前和 2→4→8 每阶记录 worker 总 RSS、系统可用内存、CPU p95、8090/ASR/Picer 健康及 ASR 延迟。持续 10 轮期间空闲内存须 ≥2 GiB、CPU p95 ≤85%，ASR/Picer 既有健康检查全绿且延迟不得超过升级前基线 20%；任一失守即回退前一档。4 个槽是最大原生并发，平台放行 8 时剩余 4 个只排队，不能将 8 误记为 8 模型实例。

## 实施顺序、验收和回滚

测试唯一入口为 `zh-tts-resident-isolated-plan-20261112.md` 的 P01–P07：N=8 至少 100 轮才报告样本 p99；P06 以不同 hash 的 A/B WAV 及双学生浏览器字幕/ACK 证明取消后不串音；P07 先用等价隔离 supervisor 连续重启三次，正式切换前另验 8090 真 supervisor。任何一门缺证据均不能升级生产容量。

先在独立端口实现原生协议和 Node 适配器，冻结协议测试：畸形帧、超长输入/输出、request ID 错配、worker crash/hang、取消后旧结果、重建后容量恢复。再以公开冻结短词和稍长释义跑 N=1/2/4/8 各 10 轮，另测混合 ASR、中文/英文 TTS；记录 HTTP 状态、p50/p95/p99、首字节、CPU/内存、worker 重启与 429/5xx。容量门为 N≤8 非故意取消均 200、p95<2 秒、p99<5 秒、无跨请求音频及计数泄漏。浏览器在 N=2/4/8 独立学生上下文分别测 `play_tts` 到实际 `playing` 的首音 p95<2 秒、p99<5 秒、非故意失败率 0；打断动作到旧音频 `pause` 且字幕清除 p95<300 ms、p99<500 ms，旧段不得再出现。每人还须验证真实 `playing→ended`、字幕、唯一 ACK 与原段故障恢复，不以 HTTP 计时替代浏览器计时。真人音质和噪声试点独立验收。

音色回归使用冻结的旧版/常驻版单字、单词、词组、较长释义 WAV：记录时长偏差与响度差异，校验声道/采样率；同一发音参数下盲听样本须由人确认没有明显音色或发音退化。人工试听未完成时只能宣称协议/性能通过，不能宣称音色一致。

上线前备份当前 8002 脚本/原生 worker/注册表，按 2→4→8 阶梯调整平台容量，每阶失败即退回已通过值。若性能门未达，保留当前单 worker 队列 `tts.maxConcurrent=2` 版本；不能以热微基准声称目标完成。设计须经架构、后端、测试、安全与课堂 UX 评审后才修改生产服务。
