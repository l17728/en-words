# Pinned SQLite Golden Harness Design Delta

## Status and scope

This is a review draft for the pre-VFS evidence phase in `docs/55-pilot-control-pinned-sqlite-vfs-sdd.md`. It authorizes only ABI verification, a test-only transparent callback tracer, deterministic fixture generation, and manifest/test-plan checks. It does not implement, register, or route Pilot Control through a private VFS and does not satisfy any production readiness gate.

## Pinned source identity

The server module pins `github.com/mattn/go-sqlite3 v1.14.22` and replaces it with `server/third_party/go-sqlite3`. Runtime verification through that fork's `Version()` returned SQLite `3.45.1`, number `3045001`, source ID `2024-01-30 16:01:20 e876e51a0ed5c5b3126f52e532044363a014bc594cfefa87ffb5b82257cc467a`, matching docs/55. The file `server/.test-artifacts/pilot-linux-current-20261021/pinned-sqlite-harness/source-hashes.txt` is frozen historical evidence from an earlier snapshot; its docs/55, docs/56 and manifest hashes are stale and must not be presented as current. Current docs/55/docs/58/manifest bindings are recorded in the manifest and loader constants, and should be verified against working-tree SHA-256 values before any new run.

Before every generation and comparison, a tagged test must call `sqlite3.Version()` and require all three values above. A mismatch exits as `NOT RUN` with a diagnostic; no `-update` option may bypass this guard. The runtime check, rather than comments/macros alone, is the source of truth.

## Harness boundary

Use a build-tagged CGo test shim named `pilot_vfs_trace`, registered under a unique non-default name. It wraps the pinned platform VFS and delegates every operation and result unchanged; its only normal-mode effect is recording callback entry/arguments/result in a bounded, synchronized trace buffer. The shim must assert its parent VFS identity and SQLite source ID before registration, unregister/close all handles on cleanup, and never be imported by production code. Test-only fault/barrier controls are restricted to explicit negative tests and may not synthesize successful filesystem or locking operations. The transparent trace can characterize SQLite's real callback requests; it cannot prove the future private VFS meets those requests.

The wrapper copies and preserves the parent VFS's advertised `iVersion` and every method present at that version, wrapping extension hooks so they receive the actual parent VFS object. Registration fails for an unsupported version. Tests assert the advertised version and method-presence surface are preserved. Callback events use `file_handle_id: null` before a successful `xOpen`; only a successful open assigns an integer ID. `xFullPathname` records a sanitized basename output token rather than an absolute temporary path.

Run candidate generation only through `python ../review/run_pilot_vfs_candidate.py --artifact-dir <new-absolute-directory>` from `server/`. The runner creates a fresh 128-bit lowercase-hex `run_id`, passes it to the test process, and wraps the test binary in passive `strace -f -yy` over `openat`, `openat2`, `newfstatat`, `statx`, `fstat`, `fcntl`, and `flock`; missing `strace` is a failed preflight. It requires a process-level lock command with a complete `l_start`/`l_len` range before producing a callback candidate, and retains open/stat calls to support a future descriptor/inode join. This trace is supplemental only: it does not establish a mapping between OS descriptors, inode identities, and callback-assigned `file_handle_id`s. Candidate PASS therefore means callback-candidate generation only; no lock-byte-range golden or per-handle lock conclusion is accepted. Every candidate group references one `process_record.json`. That record contains the exact command, run ID, exit code, and separate immutable stdout, stderr, and raw syscall artifacts, each with SHA-256 and byte length. The artifact directory is forced to mode 0700; the supplied directory leaf must be a real directory, so a symlink leaf is rejected before path resolution. Regular evidence files are forced to mode 0600 through no-follow file descriptors; symlinks, non-regular entries, and multiply-linked files invalidate candidate status. Linux E2E cases inject both an entry symlink and replacement of the entire artifact-directory leaf during the subprocess; neither path may receive post-run writes. The runner writes artifacts exclusively and refuses a nonempty evidence directory. The runner pins the new directory with a no-follow directory FD and uses that FD for post-run reads, enumeration, and writes; it verifies the subprocess-visible path still names the pinned inode before collecting evidence. If that check fails, it emits a failure record only on its own stdout and performs no further writes through the artifact path. Raw syscall logs may contain temporary absolute paths and are restricted evidence; candidate JSON uses only normalized names and stable handle IDs. A candidate is reviewable only when the report, process record, callback traces, syscall trace, and their hashes all agree on the same run ID.

Golden generation is Linux-only on a disposable local filesystem and must record filesystem type, kernel, architecture, Go version, CGO/compiler version, driver revision, SQLite version/number/source ID, harness hash, and scenario seed. Goldens use stable JSON with ordered event arrays and no wall-clock timestamps, PIDs, inode numbers, random bytes, or absolute temp paths. Normalize only documented volatile fields; fail if a new event field or callback appears. The generator requires an explicit persistent artifact-directory path, creates it if absent, and fails closed if the directory already contains entries, so a rerun cannot overwrite reviewed evidence. Candidate comparison is read-only by default. Updating checked-in fixtures requires separate review of the raw trace and normalized diff.

## Exact runtime scenarios

Generate four grouped fixture files from the scenarios below. Every scenario has a stable ID, status/reason, a nonempty `oracle` object (including NOT RUN rows), raw JSONL trace reference/hash when executed, and normalized candidate record; reviewed candidates are grouped by stable scenario ID. The oracle schema is `{ "expected_outcome": string, "observed_outcome": string|null, "execution_status": "CANDIDATE"|"NOT RUN", "reason": string, "details": object, "event_count": integer }`. `event_count` equals the length of that scenario's normalized `events` array, includes partial events for NOT RUN scenarios, and excludes control-protocol messages; it is zero when no callback event occurred. For executed scenarios, observed outcome is a concise measured result and reason is empty; for NOT RUN, expected outcome remains populated, observed outcome is `NOT_OBSERVED`, and reason is nonempty with the unmet precondition. No other execution-status values are allowed. Scenarios generated in one Go test process share one process record with `run_id`, exact command, stdout/stderr immutable artifact references, SHA-256, byte lengths, and exit code. The acceptance report links this record and all candidate groups by `run_id`; stdout and stderr are separate artifacts. Duplicating whole process streams per scenario would obscure rather than improve attribution. A child-process scenario records `child_executions` as an array under that scenario ID, allowing one record per child: `started` boolean, sanitized command template using placeholders only (no PID, executable absolute path, temp path, or environment values), process role, exit code, separate stdout/stderr artifact refs with SHA-256 and byte lengths, allowlisted error summary, protocol terminal outcome, and cleanup status including control descriptor closure, trace persistence, timeout, kill, and reap. A child that was never started has `started=false`, `execution_status="NOT RUN"`, `cleanup_status="NOT_APPLICABLE"`, and null exit, terminal, and output artifact fields; a started child records cleanup booleans and whether timeout/kill/reap occurred. Empty output from a started process has the empty-stream SHA-256 and length zero. Never embed raw output or absolute paths in candidates. The table is the executable contract. Connection IDs are stable within a run and assigned by the test harness; file_handle_id is assigned only after successful xOpen. Failed xOpen events carry null; IDs are neither OS PIDs nor FDs. Every xOpen event records input name, derived object role, caller flags, observed flags, pOutFlags, rc, and file_handle_id. Subsequent I/O/lock events reference that handle. Ambiguous role inference is a failure.

For lock-byte ranges, callback events alone are insufficient. The current passive fcntl/flock sample is process-level and is deliberately not joined to callback `file_handle_id` or inode identity; all per-handle lock-range conclusions and lock-range goldens remain NOT RUN until a separately reviewed, verifiable descriptor-to-handle-to-inode join exists. Host-dependent traces (especially pOutFlags, lock ranges and pager order) stay separate by OS/architecture; do not normalize semantic differences.

## Review and acceptance before harness implementation

Architecture review must verify the shim cannot become a production dependency, delegates every unmodified callback, and does not overstate what default-VFS goldens prove. Test review must verify deterministic barriers, trace normalization, per-scenario isolation, exact manifest mapping, negative outcomes, and cleanup. Only after both reviews record no unresolved blocking findings should the test-only tracer and ABI check be implemented. The four golden generations and manifest schema test must then run on Linux; implementation of the private VFS is a later, separately reviewed stage.

## Current-spec evidence binding (2026-10-22, review required)

### Snapshot and path boundary

A candidate run is valid only for an independently reviewed expected source inventory and the exact source bytes it executed. `review/pilot-vfs-source-snapshot-manifest.json` lists the closed source paths and expected SHA-256 values; its own SHA-256 is supplied as `--source-manifest-sha256` from the authenticated review record and is never auto-regenerated by the runner. The inventory covers docs/55, docs/56, docs/57, docs/58, docs/62; all regular `server/` build/test inputs (excluding only `.git` and `.test-artifacts`); callback and recovery manifests; `review/run_pilot_vfs_candidate.py`; and `review/test_pilot_vfs_candidate_runner.py`. Updating any entry requires a new exact-hash review and externally anchored manifest digest. The runner pins the checkout root and reads inputs through root-relative, allowlisted paths using no-follow directory/file opens. Reject absolute paths, `..`, symlinks, special files, missing/duplicate paths, malformed digests, duplicate case IDs, and paths resolving outside the pinned root. Enumerate paths in bytewise lexical order. Manifest or cross-binding failure occurs before the requested evidence directory is created or a child is launched.

Copy the reviewed source set into a fresh, owner-only, read-only execution snapshot before starting Go; run tests from that snapshot, not the mutable checkout. Hash exact copied bytes and derive ordered `source_bindings` plus a canonical snapshot-tree digest from `{path, size, sha256}` entries. Verify the snapshot tree again after execution and before accepting candidates. The runner's already-loaded Python source hash is captured before preflight; its expected value also appears in the externally reviewed inventory. A changed checkout after the snapshot cannot change the Go inputs. Any copy, verification, or post-run mismatch fails with no candidate/proposal publication. Snapshot and output writes use exclusive creation and no-follow semantics.

The build environment is also a closed input. Set `GOWORK=off`, `GOFLAGS=-mod=readonly`, `GOTOOLCHAIN=local`, `GOENV=off`, `GOPROXY=off`, `CGO_ENABLED=1`, absolute reviewed Go/CC paths, and explicit reviewed `CGO_CFLAGS`/`CGO_LDFLAGS`; remove all other inherited build-affecting variables. Stage module-cache files into the read-only execution snapshot, run `go mod verify` there, and fail if any required module is missing or modified. Capture the resolved module graph and content digests, Go toolchain/compiler/linker binary hashes, build environment values, OS/kernel/architecture, SQLite version/source ID, and filesystem. Never fall back to another workspace, module cache, compiler, or toolchain. A build input that cannot be pinned is a preflight failure.

Before execution, verify manifest cross-bindings: callback-manifest source hashes equal docs/55 and docs/58; callback-manifest and recovery-manifest recovery hashes equal docs/62; manifest byte digests equal their externally reviewed values; and case counts/statuses/IDs satisfy the bound loader contract. Reports contain the external source-manifest digest, ordered `source_bindings`, snapshot-tree digest, module graph/cache and toolchain digests, callback/recovery manifest digests and case counts, run ID, process-record digest, candidate/proposal digests, and `promotion_state="NOT_APPROVED"`.

### Provenance threat model and promotion boundary

The local runner detects accidental stale or mixed snapshots and source changes during a run. It does not cryptographically attest execution against a malicious actor able to rewrite the checkout, snapshot, report, or artifact files with the same local privileges. Reports and SHA-256 fields are integrity checks, not signatures. Golden promotion therefore requires an independently authenticated review record that names the immutable archive SHA-256 and exact source snapshot digest; a self-reported `PASS_CANDIDATE` or a locally edited report is never approval. Where an authenticated runner/review system is unavailable, promotion remains blocked. `PASS_CANDIDATE` and `PASS_GOLDEN` are distinct closed statuses: only the separately reviewed human-promotion procedure may create a `PASS_GOLDEN` approval record, and every consumer rejects unknown fields/statuses, missing bindings, stale bindings, or a candidate report presented as promotion approval. Candidate success does not establish private-VFS or product readiness.

## Evidence-binding security protocol delta (2026-10-22, review required)

This section supersedes any earlier implication that a bare `--source-manifest-sha256` is an authenticated anchor. A digest supplied on a command line is an integrity value only and MUST NOT authorize a run. The canonical UTF-8 RFC 8785 JSON payload schema is `pilot-vfs-run-authorization-v1` with exactly these fields: `schema`, `repository`, `source_manifest_sha256`, `source_snapshot_sha256`, `purpose`, `subject`, `run_nonce`, `issued_at`, `not_before`, `expires_at`, `sequence`, and `key_id`. Its detached envelope is an RFC 8785 JSON object with exactly `payload_b64u` and `signature`, and no duplicate keys. `payload_b64u` decodes to the canonical payload bytes; the parser rejects duplicate payload keys before interpretation, serializes the parsed object with RFC 8785, and requires exact byte-for-byte equality with the decoded bytes. Ed25519 verifies those exact bytes. For every unpadded base64url value, acceptance requires decode, re-encode with the unique unpadded base64url encoder, and byte-for-byte equality to the original ASCII; this rejects alternate pad bits as well as padding. No unknown fields or alternate encodings are accepted. The signed values bind the exact manifest and derived source snapshot digests, purpose `PILOT_VFS_CANDIDATE_ONLY`, repository `l17728/en-words`, authenticated operator subject, fresh 256-bit nonce, UTC RFC 3339 times, and monotonically increasing sequence. The runner pins the trust-root public-key fingerprint out of band and verifies signature, key ID, subject, purpose, repository, expiry, revocation floor, nonce freshness, and every digest before creating the evidence directory or launching a child. A one-use authorization service must atomically consume `(key_id, sequence, run_nonce)` and return a signed consumption receipt; local files cannot establish freshness or prevent rollback. Missing/unavailable verifier, receipt, or trust-root provisioning; invalid signature; unknown key; wrong subject/purpose; expiry; revoked/old sequence; replayed nonce; or any digest mismatch fails closed. A key shipped beside the runner is not a trust root. Test vectors include valid, forged, altered-payload, wrong-key, wrong-subject, wrong-purpose, expired, revoked, replayed, missing, and service-unavailable cases. Human promotion uses a separate schema and purpose and cannot be substituted for candidate-run authorization.

All payload field types and encodings are closed as follows; reject nulls, booleans in numeric slots, floats, leading-zero numbers, Unicode lookalikes, uppercase digests, padded base64url, and unknown fields before signature or policy acceptance:

| Fields | Required JSON type and canonical value |
|---|---|
| `schema`, `repository`, `purpose` | Strings exactly equal to the constants in this section. |
| `source_manifest_sha256`, `source_snapshot_sha256` | 64 lowercase ASCII hex characters, encoding exactly 32 bytes. |
| `subject` | 1–128 ASCII characters matching `[A-Za-z0-9][A-Za-z0-9._:@/-]{0,127}`; must map to an active operator identity in the verifier. |
| `run_nonce` | 43 unpadded base64url ASCII characters decoding to exactly 32 bytes; generated by the verifier for one authorization and never reused. Decode/re-encode must reproduce the identical 43 ASCII characters. |
| `issued_at`, `not_before`, `expires_at` | UTC strings exactly `YYYY-MM-DDTHH:MM:SSZ`; valid Gregorian seconds only, with `issued_at <= not_before < expires_at` and lifetime at most 15 minutes. |
| `sequence` | JSON integer in `[1, 9007199254740991]` (RFC 8785 exact-integer range); strictly increasing per `key_id`. |
| `key_id` | 1–64 ASCII characters matching `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` and resolving to one currently trusted key. |
| envelope `signature` | 86 unpadded base64url ASCII characters decoding to exactly 64 Ed25519 signature bytes; decode/re-encode must reproduce the identical 86 ASCII characters. |

The source snapshot inventory is a closed, sorted file list, not a glob or phrase such as “all regular files.” `entries` is the complete allowlist. `closed_roots` identifies exactly which subtrees must be exhaustively enumerated; singleton files outside those roots are permitted only when individually listed in `entries`. The runner proves that every regular file in each closed root appears exactly once and rejects every unlisted file, symlink, hard link where the filesystem reports multiple links, device, socket, FIFO, or special entry. The only exclusions are `.git/**` and `server/.test-artifacts/**`. The draft `review/pilot-vfs-source-snapshot-manifest.json` is materialized with status `DRAFT_NOT_AUTHORIZED`, explicit file entries, and unresolved native toolchain requirements. The manifest is not self-hashed: its exact digest must be anchored by the signed authorization payload. Any source or manifest change requires a new authorization. An independent reviewer must inspect the concrete list and approve its exact digest; a draft manifest or this design review is not that approval.

Build provenance uses a pinned Linux toolchain bundle and an empty, per-run `GOCACHE` inside the immutable snapshot. No host Go, compiler, linker, module cache, or inherited environment is accepted. The signed inventory binds the bundle digest and each executable/component digest, OS image identity, module-cache tree digest, module graph digest, and build recipe. The runner uses only absolute paths inside the verified bundle/snapshot; sets `GOOS`, `GOARCH`, `CGO_ENABLED`, `GOWORK=off`, `GOFLAGS=-mod=readonly`, `GOTOOLCHAIN=local`, `GOENV=off`, `GOPROXY=off`, `GOCACHE` to the newly empty snapshot-local cache, and a fixed allowlist for `PATH`, `HOME`, `TMPDIR`, `GOPATH`, `GOMODCACHE`, `CC`, `CXX`, `CGO_CFLAGS`, `CGO_CPPFLAGS`, `CGO_CXXFLAGS`, `CGO_LDFLAGS`, `GOEXPERIMENT`, and `GODEBUG`. All unspecified variables are removed. It verifies the staged module tree and graph before and after the run and records their digests. Any unresolved executable, unpinned input, unexpected environment value, cache entry before the build, or post-run mutation is a preflight/run failure. BIND-06 must mutate each allowlisted variable, inject a pre-populated cache and alternate compiler/toolchain/module tree, and verify rejection before child launch or exclusive use of the signed inputs.

### Consumption receipt and promotion authorization protocol

The one-use authorization service verifies the run-authorization signature and all validity/binding fields itself before atomically consuming the key/sequence/nonce tuple. Its canonical RFC 8785 JSON receipt schema is `pilot-vfs-consumption-receipt-v1` with exactly: `schema`, `authorization_payload_sha256`, `key_id`, `sequence`, `run_nonce`, `repository`, `purpose`, `subject`, `source_manifest_sha256`, `source_snapshot_sha256`, `consumed_at`, and `receipt_id`. The detached Ed25519 signature is verified against a separately pinned service key. The runner compares every tuple/binding field to the verified authorization and verifies the receipt signature, service identity, consumption time, and unique receipt ID before any write or process launch. Reject wrong-key, invalid-signature, altered-field, mismatched tuple/digest/subject/purpose, stale or replayed receipt, and duplicate receipt ID. The service's nonce ledger and per-key sequence/revocation floor are durably committed before it signs or returns a receipt; storage must provide monotonic, anti-rollback recovery across process crash, restart, restore and failover. If commit outcome is uncertain or the receipt is lost, retry returns a refusal/consumed result and requires a newly authorized nonce; it never issues a second success receipt. Concurrent submissions of the same authorization have exactly one success and one refusal, and only the successful caller may proceed.

Receipt fields use these exact types: `schema`, `repository`, `purpose`, `subject`, and `key_id` are strings with the same restrictions/constants as the authorization payload; `authorization_payload_sha256`, `source_manifest_sha256`, and `source_snapshot_sha256` are 64 lowercase hex characters; `sequence` is an integer in `[1, 9007199254740991]`; `run_nonce` is the exact 43-character unpadded base64url authorization nonce; `consumed_at` uses the exact UTC second format above; and `receipt_id` is 43 unpadded base64url characters decoding to 32 random bytes. Receipt envelope is exactly `{payload_b64u, signature}` with duplicate keys rejected; decoded receipt payload must be duplicate-free, RFC 8785 canonical and byte-identical after reserialization. Receipt-envelope `signature` is exactly 86 unpadded base64url characters decoding to 64 bytes. Every base64url field must round-trip to its identical original ASCII representation. Any noncanonical type or representation is rejected before matching fields.

**Amendment (2026-10-23):** the project owner removed the two-reviewer requirement. Golden promotion now requires one accountable human reviewer; all artifact binding, cryptographic verification, authorization-role, and separate-promotion-key requirements remain.

Golden approval uses canonical RFC 8785 schema `pilot-vfs-golden-approval-v2` and one detached Ed25519 signature from a promotion trust root distinct from the run-authorization and receipt keys. The payload is a closed JSON object with exactly these required fields and no others: `schema`, `repository`, `purpose`, `archive_sha256`, `source_snapshot_sha256`, `candidate_report_sha256`, `reviewed_diff_sha256`, `review_outcome`, `reviewer_subject`, `reviewer_key_id`, `approved_at`, `expires_at`, and `approval_sequence`. Use exact constants `schema="pilot-vfs-golden-approval-v2"`, `repository="l17728/en-words"`, and `purpose="PILOT_VFS_GOLDEN_PROMOTION"`; each digest is 64 lowercase ASCII hex characters (32 bytes); outcome is exactly `APPROVE`; `reviewer_subject` is exactly `l17728`; key ID matches `[A-Za-z0-9][A-Za-z0-9._-]{0,63}` and resolves to the promotion key registered to that subject; times are UTC `YYYY-MM-DDTHH:MM:SSZ` Gregorian seconds; approval_sequence is an integer in `[1, 9007199254740991]`. Reject nulls, booleans in numeric fields, floats, duplicate JSON keys, unknown fields, invalid calendar values and noncanonical payload bytes. The envelope has exactly string fields `payload_b64u` and `signature`; both are unpadded base64url with strict decode/re-encode identity, and signature decodes to exactly 64 Ed25519 bytes. The signature covers the decoded canonical payload bytes. Exactly one signature by `l17728` is sufficient; a second reviewer is neither required nor accepted. Every consumer verifies the signature, reviewer role authorization, key revocation/sequence, exact artifact digests, and outcome before accepting `PASS_GOLDEN`. Candidate report and process record each bind `run_id`, `authorization_payload_sha256`, full signed receipt envelope SHA-256, `receipt_id`, `run_nonce`, sequence and source-snapshot digest. The process record, candidate groups, report and archive must agree on every binding; promotion verification also validates receipt signatures and its `authorization_payload_sha256`. Any cross-run mix, receipt/report swap, duplicate run ID with conflicting fields, or missing binding fails closed. Candidate-run authorization, runner output, an unsigned human note, or a self-signed record never grants promotion.

The promotion service emits a canonical RFC 8785 record with schema `pilot-vfs-golden-promotion-record-v1` and exact payload fields: `schema`, `promotion_id`, `approval_envelope_sha256`, `repository`, `purpose`, `archive_sha256`, `source_snapshot_sha256`, `candidate_report_sha256`, `reviewed_diff_sha256`, `reviewer_subject`, `reviewer_key_id`, `approval_sequence`, `promotion_time`, and `result`. Types are fixed: schema/repository/purpose/result are exact constants (`pilot-vfs-golden-promotion-record-v1`, `l17728/en-words`, `PILOT_VFS_GOLDEN_PROMOTION`, `PASS_GOLDEN`); promotion_id is 43-character unpadded base64url for 32 random bytes; all five digest fields are 64 lowercase hex characters; reviewer_subject is `l17728`; reviewer_key_id follows the approval rule; approval_sequence is the approval integer; promotion_time is a valid UTC `YYYY-MM-DDTHH:MM:SSZ` second. Reject nulls, duplicate keys, unknown fields, and noncanonical payload bytes; payload bytes must equal RFC 8785 reserialization exactly. The envelope is exactly `{payload_b64u, signature}`; both are strict unpadded base64url fields, signature decodes to 64 Ed25519 bytes, and decoded payload bytes are signed by a promotion-service key pinned out of band, distinct from all authorization, receipt and reviewer keys. Promotion and lookup use HTTPS with authenticated mutual TLS; service credentials are never placed in URLs or logs. The service samples promotion_time from its trusted UTC clock immediately before validating the approval; it fails closed if synchronization is unavailable or reported absolute offset exceeds 2 seconds. The service atomically commits the consumed sequence/high-water mark, unique archive binding, and exact signed promotion record to its anti-rollback ledger before returning success. `POST /v1/promotions` accepts exactly the signed approval envelope as its JSON request body and returns HTTP 201 with the signed promotion-record envelope after commit. Authenticated `GET /v1/promotions/{promotion_id}` returns HTTP 200 with that stored envelope without consuming a sequence or mutating state; unknown IDs return 404 and unavailable service returns 503. All requests require the configured mutually authenticated TLS client identity. A consumer MUST query the authoritative service and validate its pinned service signature, approval signature, exact record/approval/artifact bindings, and `approved_at <= promotion_time < expires_at`; it MUST NOT trust a local record alone, consume the sequence again, or require approval to remain current at read time. Missing/mismatched/rolled-back records and unavailable service fail closed. The registered promotion key for subject `l17728` must hold `PILOT_GOLDEN_REVIEWER` under the promotion trust root. Approval validity is exactly `approved_at <= promotion_time < expires_at` and `approved_at < expires_at <= approved_at + 24 hours`; run-authorization's 15-minute lifetime does not apply to this distinct approval schema. This expiry gates the one-time promotion operation only. `approval_sequence` must strictly increase per promotion key ID and exceed its revocation floor. The promotion operation atomically consumes `(reviewer_key_id, approval_sequence, archive_sha256)` and persists the signed promotion record described above in one durable anti-rollback transaction before accepting promotion. Concurrent identical promotion submissions produce one success only; after durable commit, retries (including after timeout, restart, backup restore or failover) refuse and require a newly signed higher sequence. If commit outcome is uncertain, the promotion operation returns no success and operators reconcile the durable ledger before retrying. Subsequent read-only consumers use the authenticated lookup to verify the service-signed promotion record, approval signature, historical validity at `promotion_time`, and exact artifact digests; they MUST NOT consume the sequence again or require the approval to remain unexpired at read time. Local cached records alone, missing/duplicate/mismatched records, ledger rollback, or lookup-service unavailability fail closed. The v2 envelope has one signature string; a signature array, extra `signatures` field, multiple signatures, missing signatures and unknown fields are rejected. Version-1 `pilot-vfs-golden-approval-v1` dual-review approvals are invalid under v2 and must not be migrated or grandfathered. All signed JSON payloads and envelopes reject duplicate object keys before parsing; payload bytes must equal their RFC 8785 reserialization exactly, so key reordering, insignificant whitespace and alternate escapes are invalid signed encodings. This is an explicit project risk decision: exact immutable artifact binding, a distinct promotion trust root, an authorized human review role, and a separately recorded approval remain mandatory.
