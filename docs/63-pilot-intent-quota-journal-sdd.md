# Pilot Intent Quota Journal SDD

## Status and scope

This is a design proposal for the protected quota journal required by [docs/50](50-pilot-runroot-product-orchestration-sdd.md). It specifies durable rolling-hour permits and outstanding-handle accounting only. It does not enable intent minting, implement a business API, or replace the control ledger, launcher journal, keyring nonce counter, or private SQLite VFS. Architecture, backend, security, and test-design review of this exact document its case manifest, and the canonical frame vectors are required before implementation.

## State and record contract

The journal is a separate append-only file owned by the dedicated resident admission service under its protected state directory. A deployment pin provisioned by the trusted installer fixes the expected directory device/inode, owner UID, and service identity; the directory must be owned by that UID, mode `0700`, and not group/world writable. Open it by handle without following symlinks, then verify the pin before opening the journal. The journal must be a regular file owned by the service UID, mode `0600`, on the pinned device, and its inode is pinned for the service lifetime. A changed directory/file identity fails closed. API workers submit typed requests to the one resident coordinator; they never open or write the journal themselves. The component boundary is fixed: the web admission service authenticates the browser session and signs the mint claim; the launcher alone verifies its canonical signature/schema and current authorization, calls the resident principal resolver, and owns the AEAD keyring/nonce counter and encryption. The quota coordinator alone owns this journal and quota indexes. It accepts typed `ReservePermit` and `CommitIssued` requests only from the exact registered launcher over authenticated local IPC; every reservation binds the authenticated launcher peer identity, launcher-generated `operation_id[16]`, server-generated `request_id[16]`, `principal_ref[32]`, `binding_digest[32]`, and the anchored `permit_sequence` as one immutable tuple; it never resolves principals, signs claims, reserves AEAD nonces, or encrypts handles. Requests carry the exact signed-claim bytes, resolver-returned `principal_ref`, server-generated `request_id`, and binding digest. The coordinator recomputes and validates the binding digest and rejects any caller-supplied principal that is not part of the authenticated launcher envelope.

Each frame has a 16-byte header: `magic[8] = "ENWQJNL1"`, `version:u16be=1`, `type:u8`, `flags:u8=0`, `total_length:u32be`. The authenticated common body prefix has fixed offsets: bytes 0..15 `key_id[16]`, 16..31 `operation_id[16]` (all mutating records persist the initiating IPC operation ID), 32..39 strictly increasing `sequence:u64be`, nondecreasing `record_time:u64be` (Unix nanoseconds), `principal_ref[32]`, server-generated `request_id[16]`, `binding_digest[32]`, and `previous_digest[32]`; the first record uses 32 zero bytes. `binding_digest` is `SHA-256(ASCII("en-words-intent-binding-v1") || 0x00 || canonical-CBOR([bstr32(SHA-256(canonical_signed_claim_bytes)), bstr32(resolver_principal_ref)]))`. The signed mint claim bytes are exactly the docs/50 fixed-order claim, including server-generated request nonce (which is also this journal request ID), tenant/user/session/authz revisions, role, fixture, payload digest, issue and expiry. `resolver_principal_ref` comes only from the authenticated server-side principal resolver and is not caller-supplied or retroactively treated as a signed claim field. Type-specific bytes follow, then `mac[32] = HMAC-SHA-256(keyring[key_id], ASCII("en-words-intent-quota-v1") || 0x00 || header || body_without_mac)`. `keyring[key_id]` resolves to secret key bytes from the OS credential store; the public key ID alone cannot produce a valid MAC. `previous_digest` is `SHA-256(ASCII("en-words-intent-quota-frame-v1") || 0x00 || complete_previous_frame)`. Total frame length is exact and at most 4 KiB. Fixed type bodies are: `PERMIT` has an empty type-specific suffix; its operation ID is in the authenticated common prefix and it consumes one rolling-hour admission; `ISSUED` is `[permit_sequence:u64be, handle_hash[32], issued_at_unix_seconds:u64be, expires_at_unix_seconds:u64be, sealed_handle_length:u16be, sealed_handle[1..512]]`; `BOUND` is `[issued_sequence:u64be, handle_hash[32], run_epoch[16], event_time_ns:u64be]`; `EXPIRED` is `[issued_sequence:u64be, handle_hash[32], issued_at_unix_seconds:u64be, expires_at_unix_seconds:u64be, event_time_ns:u64be]`. Thus PERMIT has zero bytes after the fixed common prefix; ISSUED type-specific suffix begins at fixed-prefix offset 160 with `permit_sequence:u64be` and then the fields listed above. The sealed handle is the exact AEAD ciphertext returned by the API, never plaintext; its hash must match the ciphertext and canonical claims. For every record, `record_time_ns` is the trusted journal append time and remains nondecreasing. BOUND/EXPIRED persist the exact signed receipt `event_time_ns` in their suffix. A BOUND is valid when `issued_at_unix_seconds*1e9 <= event_time_ns <= expires_at_unix_seconds*1e9` and `record_time_ns >= event_time_ns`; the frame may therefore be appended after expiry when a valid pre-expiry bind receipt arrives late. An EXPIRED is valid only when its authenticated receipt proves the expiry decision won the bind race and `event_time_ns >= expires_at_unix_seconds*1e9`, with `record_time_ns >= event_time_ns`. At exact expiry, the resident ledger lock determines the sole terminal decision; replay accepts at most one settlement per issued handle. Reject unknown versions/types, noncanonical lengths, invalid sequence/hash links, duplicate events, invalid timestamps, and MAC failures. Old verification keys remain available until every record they authenticate has been retired by a separately reviewed rotation procedure.

All time conversion is checked before arithmetic. `event_time_ns` and `record_time_ns` are nanoseconds and must each be in `[0, MaxInt64]`. `issued_at_unix_seconds` and `expires_at_unix_seconds` are seconds and must each be in `[0, floor(MaxInt64/1e9)]`, whose ceiling is `9,223,372,036`. Reject larger seconds before multiplying, reject any overflow, require `issued_at <= expires_at`, and compare only after checked conversion. This prevents unsigned-second wraparound from turning an invalid expiry into an early or late settlement.

The service issues a random request ID before signing the server-owned mint claim. Browser clients cannot choose or replay this ID. The launcher first authenticates/resolves and calls `ReservePermit` with its unique `operation_id`; the coordinator serializes by principal, expires stale reservations, and atomically checks all limits using `outstanding = anchored unbound ISSUED + live pending reservations` and `in_flight = pending + COMMITTING reservations`, plus capacity escrow. It commits `PERMIT` plus external anchor, then, while still holding the per-principal lock, publishes one volatile `PENDING` reservation occupying exactly one outstanding slot and one in-flight slot, with a fixed 30-second `CLOCK_BOOTTIME` deadline, before returning a cryptographically random 32-byte `permit_ticket` once to that launcher operation. The volatile ticket entry stores only the ticket digest plus the immutable bound tuple (permit sequence, request ID, principal reference, binding digest, operation ID, and authenticated launcher peer identity); it never persists or logs the ticket. A duplicate reserve never reissues it. `CommitIssued` must match every tuple field and peer, present the ticket before its deadline, and transition PENDING -> COMMITTING under the per-principal lock before any ISSUE append; ticket substitution, replay, late commit, or mismatched context is rejected with no ISSUE and no ciphertext response. On anchored ISSUE, transition COMMITTING -> ACKABLE atomically, retain the outstanding slot, and release the in-flight slot. If the deadline elapses first, atomically mark the reservation BURNED, invalidate its ticket, release both volatile slots, and permanently deny that request ID; the anchored PERMIT remains spent and any nonce remains burned. Late encryption/commit cannot return ciphertext. The caller must make a new explicit activation with a new request ID. A lost ReservePermit reply therefore occupies the bounded slots for at most 30 seconds, cannot retrieve or reissue the ticket, and then burns/releases them. A coordinator restart discards all volatile tickets/reservations; every anchored PERMIT without anchored ISSUE is permanently burned and cannot resume. The reservation deadline is checked at CommitIssued admission under the same principal lock; once admitted before deadline, COMMITTING holds its slots through the durable decision. Losing the ticket or restarting the coordinator burns the PERMIT. Only that operation may reserve and sync one AEAD nonce in the launcher keyring and encrypt once. The launcher then sends `CommitIssued` with the same authenticated request context, `permit_ticket`, exact ciphertext, and its hash; the quota service verifies the envelope/binding, appends `ISSUED`, syncs it, advances/syncs the external anchor, and only then acknowledges. The launcher may return the handle to the browser only after this acknowledgement. The global append mutex assigns sequence and performs append+fdatasync+anchor sync+replay-index publication; it is never held across IPC or keyring calls. Startup acquires an OS singleton lock before anchor validation or journal scan and holds it until all requests are drained and shutdown releases it; a second process fails before journal access or writing. Lock order is per-principal coordinator, then global append mutex; all launcher IPC happens with neither journal mutex held. Before admission, reserve byte/frame capacity for maximum-size `PERMIT`, `ISSUED`, and one maximum-size settlement frame (`BOUND` or `EXPIRED`): one frame slot plus 4 KiB. A repeated `ReservePermit` for an anchored `PERMIT` without anchored `ISSUED` is permanently denied and never reauthorizes encryption; the launcher must not reserve another nonce or retry encryption for that request ID. This applies after a timeout, lost IPC reply, process crash, and restart, including when encryption may have completed but `CommitIssued` did not become anchored. The permit remains burned and any nonce already reserved remains burned; no ciphertext is returned. A new explicit browser activation uses a new request ID and consumes a new permit. Same-ID/same-binding replay returns exact stored ciphertext only when `ISSUED` is already anchored; changed binding conflicts. A failure between journal sync and anchor sync trips the global circuit breaker; no in-flight request may return a handle. On startup, settlement escrow is reconstructed from every anchored `ISSUED` without `BOUND`/`EXPIRED`. No handle returns if any durable boundary is uncertain.

The quota service accepts settlement only over authenticated local IPC from the exact registered launcher. The launcher is the only caller of the always-resident `PilotControlReaper` RPCs `FirstBindIfUnbound` and `ExpireIfUnbound` (never the per-run Reaper), after validating the signed intent, current principal, fixture, authorization fence, and exact handle. These RPCs are absent/denied in default A0 and enabled only with reviewed v3 schema and pilot gates; they cannot bypass bootstrap or live-run method allowlists. After commit, the resident PilotControlReaper re-reads and verifies the immutable row and signs the canonical receipt with a dedicated Ed25519 key whose credential-store key-use policy is restricted to intent-binding receipts. The deployment installer pins the matching public-key fingerprint and key ID in the quota service. The exact signed message is `ASCII("en-words-intent-binding-receipt-v1") || 0x00 || canonical-CBOR([uint(1), bstr16(key_id), uint(control_generation), bstr32(handle_hash), bstr32(principal_ref), uint(decision), int(event_time_ns), null-or-bstr16(run_epoch), bstr32(row_digest)])`. The domain suffix is exactly one NUL byte (0x00), not the two printable characters backslash and zero. The CBOR array has exactly nine definite-length elements; unsigned values are canonical CBOR unsigned integers, signed event time is a canonical CBOR integer in `[0, 2^63-1]`, fixed-width values are byte strings of the stated lengths, and EXPIRED encodes run_epoch as CBOR null. Decision 1 is BOUND and 2 is EXPIRED. Reject noncanonical CBOR, unknown key IDs, wrong pinned fingerprint, wrong domain/version, invalid field lengths, and signature mismatch before journal mutation. The launcher only transports the receipt; the quota service independently verifies the signature, key pin, exact receipt encoding, principal, handle, and decision before journaling settlement. The signature proves the resident ledger attested to the committed row; it does not replace IPC peer authentication, and the launcher cannot create a valid receipt. Key rotation requires a separately reviewed overlap/retirement procedure. The receipt uses `control_generation` read from the resident ledger's monotonic startup counter; it is independent of per-run BOOTSTRAP generation and exists before any run starts, including expiry of a never-launched handle. On first start, launcher first commits a `binding_pending` intent-to-run mapping and chosen run epoch in its journal, then asks the resident Reaper to insert immutable `BOUND` in `intent_binding`, then commits local `bound`; spawn is allowed only after both durable records match. A crash after the launcher mapping retries the same epoch. If the exact BOUND row was already committed, recovery reads and finalizes that same epoch. If recovery occurs at/after expiry and no BOUND row exists, `ExpireIfUnbound` may commit EXPIRED at the actual current event time, cancel the pending mapping, and permanently reject start; it must not backdate BOUND. Thus a pre-expiry pending record alone is not a binding. A crash after ledger EXPIRED but before the local expiry marker is recovered by reading EXPIRED. Conflicting epoch/decision quarantines both services. First-bind and expiry serialize on the same ledger handle key, with launcher lock held across the decision RPC. At exact expiry, bind is eligible only if it wins and commits with `event_time_ns == expires_at_unix_seconds*1e9`; if expiry wins at or after the boundary, later bind rejects. A delayed receipt with `event_time_ns <= expires_at_unix_seconds*1e9` still records BOUND. Restart reads that row as terminal authority. Quota service contacts launcher with no journal lock held, verifies the receipt and sender independently, then appends `BOUND` or `EXPIRED`; uncertainty retains the slot and retries/query. Expiry records `(principal_ref, handle_hash, issued_at_unix_seconds, expires_at_unix_seconds)` and never invents a run epoch. User/browser/API assertions are not evidence.

## Local IPC wire contract

Local IPC uses Linux AF_UNIX `SOCK_SEQPACKET`, one frame per packet, authenticated by `SO_PEERCRED` and one matching `SCM_CREDENTIALS`. V1 header is exactly 16 bytes: `magic[8]="ENWQIPC1"`, `version:u16be=1`, `message_type:u8`, `flags:u8=0`, `payload_length:u32be`; payload is at most 16 KiB and one canonical-CBOR definite-length array with no trailing bytes. Types and directions are fixed: 1 ReservePermit request (launcher->coordinator), 2 ReserveResponse (coordinator->launcher), 3 CommitIssued request, 4 CommitResponse, 5 SettlementLookup (coordinator->launcher), 6 SettlementLookupResponse (launcher->coordinator), 7 LauncherTurn (coordinator->launcher). Type 7 payload is exactly `[uint(1)]` and grants the launcher permission to send one type 1 or 3 frame. A new connection starts in coordinator-turn state. The coordinator either sends one type 5 lookup and requires its matching type 6 response, or sends type 7; after type 7 it must receive one type 1/3 and answer with type 2/4 before regaining coordinator-turn state. Type 5 is legal only during coordinator-turn and type 6 only as its immediate response; no simultaneous send, pipelining, or unsolicited frame is legal. Request/response frames 2/4/6 echo the 16-byte operation_id; sender verifies exact equality with the outstanding request. Type 7 is connection-scoped and valid only in coordinator-turn. Any out-of-turn frame closes the session without mutation. This explicit token alternation gives the coordinator exclusive send ownership during its turn and prevents crossed requests.

The coordinator obtains `SO_PEERCRED` once at accept and validates kernel-supplied credentials on every `recvmsg`; it requires exactly one `SCM_CREDENTIALS` equal in PID/UID/GID to the accepted peer and rejects ancillary truncation or extra credential records. Launcher and coordinator UIDs are distinct dedicated accounts. A root-owned verifier checks the peer executable device/inode/hash against an install-time pin and checks `/proc/<pid>/status` plus the root-owned systemd unit MainPID/active state at accept and before each mutation. Install-time executable/unit identity pins are root-owned mode 0400 and covered by signed installation metadata. Restart closes old sockets and burns tickets bound to the old PID; a reused PID requires fresh executable/unit checks. Same-UID helper processes are forbidden; deployments unable to enforce separate UIDs and this verifier keep IPC/minting disabled. Instance identity is proved by a dedicated launcher UID not shared by another service/user, a root-owned mode-0755 launcher executable with pinned device/inode and SHA-256, and a root-owned systemd unit with pinned unit name and `MainPID` equal to peer PID. At accept and before each mutating request, the coordinator verifies `/proc/<pid>/exe` device/inode/hash, `/proc/<pid>/status` UID/GID, and systemd `MainPID`/unit active state via a root-owned verifier helper. Launcher restart produces a new PID and must pass the same checks; existing sockets close and pending tickets remain bound to old peer identity and are burned. If systemd/procfs evidence is unavailable, ambiguous, or differs, fail closed. Same-UID helper processes are forbidden by deployment policy; the unit uses `NoNewPrivileges`, `User=`, `Group=`, `ProtectSystem=strict`, `ProtectProc=invisible`, and no supplementary groups. The socket directory is root-owned `0755`, socket mode `0600`, owned by launcher UID; no alternate group access.

Response field presence is exact. ReserveResponse is `[uint(1), bstr16(operation_id), uint(status), uint(sequence)|null, uint(deadline)|null, bstr32(ticket)|null, bstr(ciphertext)|null]`; status 0 requires sequence+deadline+ticket and null ciphertext; status 1 requires sequence+ciphertext and null deadline/ticket; status 2 requires sequence only; statuses 3-11 require all nullable fields null. CommitResponse is `[uint(1), bstr16(operation_id), uint(status), uint(sequence)|null, bstr32(handle_hash)|null]`; statuses 0-1 require both values; status 2 requires sequence only; statuses 3-8 require both null. Any other combination is malformed and connection-closing. The complete literal header+payload vectors for message types 1-7 are checked in at `review/pilot-intent-quota-ipc-v1-vectors.json`; QJ-22 compares every payload length and frame byte exactly. Unsupported types, truncation, ancillary-credential mismatch, oversized packets, or malformed CBOR close the socket without response and never mutate state. A well-formed request from a kernel-authenticated but unregistered peer receives the fixed `UNAUTHORIZED_PEER` response; a credential mismatch is never assigned a peer status because the claimed identity is untrusted. There is no negotiation or JSON mode.

`ReservePermit` payload is `[uint(1), bstr16(operation_id), bstr1..8192(signed_claim), bstr32(principal_ref), bstr16(request_id), bstr32(binding_digest)]`. `ReserveResponse` payload is `[uint(1), bstr16(operation_id), uint(status), uint(permit_sequence)|null, uint(ticket_deadline_boottime_ns)|null, bstr32(permit_ticket)|null, bstr1..512(sealed_handle)|null]`; ticket and handle are mutually exclusive. Statuses are 0 RESERVED, 1 ISSUED_REPLAY, 2 PENDING_NO_TICKET, 3 RATE_LIMIT, 4 CAPACITY_LIMIT, 5 BURNED, 6 CONFLICT, 7 UNAUTHORIZED_PEER, 8 MALFORMED, 9 IN_PROGRESS, 10 UNAVAILABLE, 11 UNCERTAIN. An identical Reserve retry never returns a prior ticket; an already anchored same-binding ISSUE may return only its exact stored ciphertext as ISSUED_REPLAY. `CommitIssued` payload is `[uint(1), bstr16(operation_id), bstr16(request_id), bstr32(principal_ref), bstr32(binding_digest), uint(permit_sequence), bstr32(permit_ticket), bstr1..512(ciphertext), bstr32(SHA-256(ciphertext))]`. `CommitResponse` payload is `[uint(1), bstr16(operation_id), uint(status), uint(permit_sequence)|null, bstr32(handle_hash)|null]`; it never contains ciphertext. Commit statuses are 0 ACKNOWLEDGED, 1 ALREADY_ACKNOWLEDGED, 2 IN_PROGRESS, 3 BURNED, 4 CONFLICT, 5 UNAUTHORIZED_PEER, 6 MALFORMED, 7 UNAVAILABLE, 8 UNCERTAIN. Repeated Commit with byte-identical context/ticket/ciphertext is idempotent; altered content conflicts. A transport loss after a complete request packet does not undo its operation. After lost Reserve response, exact retry returns PENDING_NO_TICKET until timeout, then BURNED; never retry encryption. After lost Commit response, retry only the exact Commit packet; never reserve another nonce or encrypt again. IN_PROGRESS may be retried with the exact packet; UNAVAILABLE/UNCERTAIN is not retryable in-process and requires restart/reconciliation. The browser sees only the API's bounded status mapping, never these internal credentials, tickets, or frames.

## IPC status decision matrix

The following mapping is exhaustive; status fields must satisfy the presence rules above. Reserve statuses: 0 RESERVED means this request atomically anchored PERMIT and published PENDING with a one-time ticket; 1 ISSUED_REPLAY means an exact same-ID/binding ISSUE is already anchored and returns only its ciphertext; 2 PENDING_NO_TICKET means a matching PERMIT is pending but its ticket is unavailable/previously delivered, and never supplies it; 3 RATE_LIMIT means rolling-hour or token-bucket policy denied before PERMIT; 4 CAPACITY_LIMIT means a business-state cap denied before PERMIT; 5 BURNED means PERMIT-only or expired pending request; 6 CONFLICT means same operation/request ID with changed immutable tuple; 7 UNAUTHORIZED_PEER means authenticated OS peer is not the registered launcher; 8 MALFORMED means a valid frame from an authorized peer has invalid payload schema/value; 9 IN_PROGRESS means same operation is actively committing and caller must retry exact bytes; 10 UNAVAILABLE means service is not ready or breaker is open before an uncertain operation is identified; 11 UNCERTAIN means this operation crossed an ambiguous durable boundary and requires process restart/reconciliation. Reserve duplicate while live PENDING returns 2; while COMMITTING returns 9; after anchored ISSUE returns 1; after PERMIT-only/burn returns 5.

Commit statuses: 0 ACKNOWLEDGED means this packet's ISSUE became anchored and reservation reached ACKABLE; 1 ALREADY_ACKNOWLEDGED means exact persisted operation tuple/hash/sequence/anchor already matches; 2 IN_PROGRESS means the identical operation is currently COMMITTING and exact packet retry is allowed; 3 BURNED means permit/ticket expired or PERMIT-only was recovered; 4 CONFLICT means operation tuple, ticket, ciphertext, or hash differs; 5 UNAUTHORIZED_PEER means peer verification failed; 6 MALFORMED means authorized peer sent a valid frame with invalid payload; 7 UNAVAILABLE means no operation-specific ambiguity exists but service admission is closed; 8 UNCERTAIN means the operation's durability outcome is ambiguous and only restart reconciliation may resolve it. For malformed header, ancillary credentials, truncation, or oversized packet, close without mutation and emit only the fixed protocol error counter; no response payload is required because no trusted operation ID exists. A syntactically valid request with invalid semantic fields gets the corresponding fixed MALFORMED response. These rules plus the fixture vectors uniquely determine every response assertion.

SettlementLookup request payload is `[uint(1), bstr16(operation_id), bstr16(request_id), bstr32(principal_ref), uint(permit_sequence), bstr32(handle_hash), uint(expires_at_unix_seconds)]`. It contains no ticket, sealed handle, or user data. SettlementLookupResponse is `[uint(1), bstr16(operation_id), uint(status), bstr(receipt)|null]`; status 0 FOUND requires exactly one 1..512-byte signed receipt; 1 NOT_DECIDED, 2 IN_PROGRESS, 3 UNAVAILABLE, 4 CONFLICT, and 5 MALFORMED require null. The coordinator originates a lookup only during its explicit coordinator turn for an anchored unbound ISSUE and holds no principal or append lock during IPC. It emits one lookup and waits for its matching type 6 response before sending another lookup or LauncherTurn. The launcher verifies its peer identity, maps request_id to its durable issuance record, then returns the exact resident-ledger BOUND/EXPIRED receipt if present. At/after trusted expiry, it may call `ExpireIfUnbound` as the sole authorized caller, read back the immutable decision and return its signed receipt; before expiry with no BOUND row it returns NOT_DECIDED. Coordinator validates receipt signature/pin/tuple before journaling settlement. If no matching type 6 arrives before the lookup deadline, the coordinator closes that socket, terminates the exchange with no receipt, and retains capacity; it retries with a fresh operation_id only after bounded exponential backoff from 1 to 60 seconds, on a new authenticated socket whose initial coordinator-turn state is clean. A late type 6 on the closed session is discarded and can never satisfy the retry. There is one active lookup per request_id. Exact duplicate lookup is read-only/idempotent. No retry changes expiry time or creates another ledger decision.

## Global resource caps and state transitions

To bound state across principals, V1 fixes 256 striped principal locks, at most 4,096 active principal entries, 8,192 total pending/committing reservations, and 65,536 total outstanding slots (anchored unbound handles plus pending reservations). IPC resources are separately capped at 127 accepted sockets process-wide (the 128-FD total includes the listener), 16 per authenticated launcher PID, 64 queued packets total, and 16 dispatch workers. A fixed 127-entry accept queue closes new sockets without reading payload on saturation and increments only a bounded aggregate rejection counter. Each socket permits one in-flight exchange; a second request before its response closes it with no mutation. Coordinator lookup traffic uses the same worker, queue, socket and aggregate rejection caps; no separate unbounded settlement pool exists. No unbounded goroutine, buffer, or descriptor allocation is permitted. Each request pins its principal entry under the registry mutex, releases that mutex, then acquires the fixed stripe; references prevent eviction until the stripe is released. No operation acquires the registry mutex while holding a stripe. Global pending/outstanding counters use bounded atomic reservations with rollback before PERMIT if any later admission check fails. Lock order for durable operations remains principal stripe then global append mutex. A stripe collision only serializes work and does not merge principal state. Admission that would exceed any cap returns CAPACITY_LIMIT before PERMIT, ticket, nonce, or encryption. Indexes hold fixed-size metadata and journal offsets/lengths, never copies of ciphertext. A principal entry can be evicted only with zero references, zero pending reservations, zero unbound handles, and no permit in the rolling hour; eviction resets its token bucket empty, which is conservative. Startup retains only principals with current rolling permits or unbound handles; if replay would exceed a cap, service remains unavailable and does not truncate/compact.

Every durable operation uses the same arbiter state machine, independent of its business phase: `DURABLE_PENDING` is entered before acquiring the append mutex and owns a unique operation ID/deadline; `DURABLE_ACKABLE` is entered only after record fdatasync and anchor durable CAS both succeed and the completion thread wins the terminal CAS while CLOCK_BOOTTIME is strictly before deadline; `DURABLE_UNCERTAIN` is terminal on timeout, ambiguous I/O, or completion at/after deadline. The watchdog races every PERMIT, ISSUE, BOUND, and EXPIRED transaction, including mutex wait. Before an anchored PERMIT, uncertainty trips the global breaker and admits no ticket; after PERMIT it remains charged and burns on restart. Before anchored ISSUE, uncertainty returns no ciphertext and restart maps PERMIT-only to BURNED; after anchored ISSUE, restart maps ISSUE to ACKABLE and may return its exact ciphertext only after a fresh authorized Reserve with matching request ID/binding and a fresh peer session. A retried old Commit after restart never consults or requires the lost ticket: it returns ALREADY_ACKNOWLEDGED only when replay proves the exact operation ID, request ID, principal, binding, ciphertext hash, ISSUE sequence, and anchor are identical; if only PERMIT exists it returns BURNED, and if replay/anchor is uncertain it returns UNCERTAIN with service unavailable. Operation ID is persisted in PERMIT and ISSUE bodies, and ISSUE links its permit sequence; duplicate operation IDs with changed fields quarantine. For BOUND/EXPIRED, an anchored settlement is terminal; PERMIT/ISSUE transaction ACK state does not substitute for settlement ACK state. A late durable completion after UNCERTAIN cannot change the response or release capacity; process restart and exact replay are required.

The durable-I/O arbiter and reservation lifecycle are orthogonal state dimensions, not competing state machines. `DURABLE_PENDING`, `DURABLE_ACKABLE`, and `DURABLE_UNCERTAIN` describe one append+sync+anchor transaction only; reservation states `PENDING`, `COMMITTING`, `ACKABLE`, `BURNED`, `BOUND`, and `EXPIRED` describe business eligibility/slot ownership. Every durable operation uses the same arbiter state machine, independent of business phase: `DURABLE_PENDING` is entered before acquiring the append mutex and owns a unique operation ID/deadline; `DURABLE_ACKABLE` is entered only after record fdatasync and anchor durable CAS both succeed and the completion thread wins the terminal CAS while CLOCK_BOOTTIME is strictly before deadline; `DURABLE_UNCERTAIN` is terminal on timeout, ambiguous I/O, or completion at/after deadline. The watchdog races PERMIT, ISSUE, BOUND, and EXPIRED transactions, including mutex wait. Before an anchored PERMIT, uncertainty trips the global breaker and admits no ticket; after PERMIT it remains charged and burns on restart. Before anchored ISSUE, uncertainty returns no ciphertext and restart maps PERMIT-only to BURNED; after anchored ISSUE, restart maps ISSUE to ACKABLE. Operation ID is persisted in PERMIT and ISSUE bodies, and ISSUE links its permit sequence; duplicate operation IDs with changed fields quarantine. A lost CommitResponse retried after restart returns ALREADY_ACKNOWLEDGED only when replay proves the exact operation ID, request ID, principal, binding, ciphertext hash, ISSUE sequence, and anchor; PERMIT-only returns BURNED and ambiguous replay returns UNCERTAIN. Exact stored ciphertext can be returned only through a fresh authorized Reserve replay for the same request/binding, never from the commit response. BOUND/EXPIRED anchor completion releases capacity only after its own terminal arbiter wins; later completion after UNCERTAIN cannot ACK or release capacity.

Legal state transitions are fixed: no row -> anchored `PERMIT` -> volatile `PENDING`; `PENDING` -> `COMMITTING` only after exact tuple/ticket validation strictly before its 30-second deadline; expired `PENDING` -> `BURNED` with no new row (PERMIT remains charged); `COMMITTING` -> reservation `ACKABLE` only after ISSUE sync+anchor and the durable-I/O arbiter reaches `DURABLE_ACKABLE` strictly before its deadline; an arbiter `DURABLE_UNCERTAIN` leaves the reservation uncertain, holds all slots, and trips the global breaker until process exit. Reservation `ACKABLE` means ISSUE is anchored, the outstanding slot remains occupied, and the in-flight slot is released. Restart maps anchored ISSUE to ACKABLE, PERMIT-only to BURNED, exact BOUND/EXPIRED settlement to terminal settled, and any journal/anchor mismatch to QUARANTINED. `ACKABLE` -> anchored `BOUND` or `EXPIRED` releases outstanding capacity only after the settlement anchor; an uncertain settlement releases nothing. No other transitions are legal.

## External anchor provider contract

The journal uses a typed `MonotonicAnchor` provider, never a same-filesystem sidecar. `Read()` returns the exact tuple `(sequence,digest,restore_generation,trusted_time_high_water_ns,boot_id,boottime_ns)`. `CompareAndAdvance(expected,next)` is an atomic compare-and-advance: it accepts only exact expected tuple equality, `expected.sequence < 0xffffffffffffffff`, `next.sequence=expected.sequence+1` without wrap, digest matching the newly synced frame, unchanged nonzero restore generation, nondecreasing time high-water, and one boot/time sample; `ADVANCED` is returned only after provider durability sync. `CONFLICT` guarantees no mutation; `UNAVAILABLE` means no operation was accepted; `AMBIGUOUS` means it may have advanced and forces UNCERTAIN/global breaker; malformed/stale generation is QUARANTINED. Restart reads the provider and compares exact tuples; it never guesses whether an ambiguous call succeeded.

The installer-owned `/etc/en-words/pilot-anchor.pin` is a fixed 106-byte v1 record: `magic[8]="ENWAPIN1"`, `version:u16be=1`, `provider_id[16]`, `provider_instance_id[16]`, `object_id[32]`, and `provider_public_key_fingerprint[32]`. It is root-owned mode `0400`; its SHA-256 is fixed in trusted signed installation metadata. The selected compiled provider must match all pin fields and provide a non-snapshot monotonic tuple with atomic durable CAS; no provider, pin mismatch, unsupported provider, or provider outside an independently durable rollback domain keeps mint disabled. Test fakes implement the same CAS interface but cannot be selected by a production build. The hardware/provider adapter and install pin require separate platform review before enabling mint.

## Durability, recovery, and resource limits

Append uses a complete-write loop followed by `fdatasync`. Short write followed by completion and sync succeeds; zero progress, EIO, ENOSPC, or uncertain sync fails closed. Sequence and digest advance only after sync. Then an installer-pinned, non-snapshot OS monotonic anchor advances to `(sequence,digest,restore_generation,trusted_time_high_water_ns,boot_id,boottime_ns)` and syncs before acknowledgement. The trusted clock samples Linux `CLOCK_REALTIME`, `CLOCK_BOOTTIME`, boot ID, and kernel time-synchronization status/offset via `adjtimex`; accept only TIME_OK/TIME_INS/TIME_DEL/TIME_OOP/TIME_WAIT (reject TIME_ERROR, including STA_UNSYNC or STA_CLOCKERR), and normalize `timex.offset` to nanoseconds (`STA_NANO` means ns, otherwise microseconds) before requiring absolute offset at most 2 seconds. The implementation must use checked integer conversion and accept only the Linux UAPI timex.status mask 0x0000ffff in v1; reject any set bit outside that mask as unsupported, as well as overflow. Known STA_PLL/PPS/INS/DEL/FREQHOLD/MODE/CLK bits do not independently establish synchronization; TIME_ERROR, STA_UNSYNC, or STA_CLOCKERR always rejects. On the same boot, `record_time_ns` is advanced from the persisted high-water by `CLOCK_BOOTTIME` elapsed time; if realtime diverges from that prediction by more than 2 seconds in either direction, fail closed and require trusted-time recovery. Across boot IDs, accept realtime only after the kernel reports synchronized time with offset within 2 seconds and it is not below the persisted high-water; otherwise fail closed. The trusted sample is frozen under the per-principal coordinator immediately before starting the PERMIT append and is used for rolling-hour admission and the frame timestamp. Thus forward wall-clock jumps cannot release quota early on the same boot; time is never moved backward. A missing/invalid clock sample causes `pilot_unavailable` before PERMIT/nonce mutation. Journal/anchor disagreement, missing anchor, generation/time-high-water mismatch, or digest mismatch quarantines the journal. Journal and anchor must be outside the same rollback domain, detecting valid-prefix rollback and VM snapshot restore; without such a store, mint remains disabled. An uncertain append/sync makes the service unavailable until recovery. Every quota transaction begins a fixed 10-second `CLOCK_BOOTTIME` durability deadline before waiting for the global append mutex; the budget includes mutex wait, complete write, `fdatasync`, external-anchor write and anchor sync for `PERMIT`, `ISSUED`, `BOUND`, and `EXPIRED`. If it expires, atomically trip the global breaker and mark the in-flight operation `UNCERTAIN`; return no success, do not release its outstanding/in-flight reservation, and reject every new service request. Durable completion and the watchdog arbitrate one terminal transition through the same operation-state CAS: after anchor sync, completion may transition `COMMITTING -> ACKABLE` only while holding that arbiter and observing `CLOCK_BOOTTIME < deadline`; the deadline is exclusive. At or after the deadline, completion itself must transition unresolved `COMMITTING -> UNCERTAIN` and cannot ACK, even if the watchdog thread has not run. The watchdog may transition only unresolved `COMMITTING -> UNCERTAIN`; exactly one terminal state wins. If ACKABLE won before deadline, subsequent response delivery may finish normally. If UNCERTAIN won, any later append/anchor completion cannot ACK or release slots; only process exit and exact restart replay can resolve it. The supervisor sends termination within 2 seconds and the singleton lock remains held until process exit, so no second writer can overlap. On restart, replay accepts only exact journal/anchor equality: an anchored `ISSUED` may return the same ciphertext only for the same request/binding; a `PERMIT` without anchored `ISSUED` is permanently burned; any ambiguous or mismatched durable state quarantines the service for offline recovery. Never cancel the underlying write and resume admission in the same process, release an uncertain slot, retry encryption, or reissue the ticket. A process unable to exit keeps the service unavailable; availability is subordinate to durable-state safety.

Startup validates the external anchor, scans the journal once, validates frames, MACs, indexes and state transitions, then serves quota checks from in-memory indexes rather than rescanning under every request lock. Malformed, missing-key, duplicated, reordered, truncated, missing-anchor, valid-prefix rollback, or replaced journals are quarantined; no automatic repair, truncation or compaction. Offline recovery preserves original bytes and hashes and needs security/backend review. Clock rollback or excessive forward divergence below/above the trusted high-water fails closed. A durable `PERMIT` without `ISSUED` permanently burns that permit and any nonce reserved for it; after restart that request ID is non-mint and cannot resume or re-encrypt. Only a new explicit activation may start another request. A complete authenticated `ISSUED` with matching anchor can be returned only for the same internal request ID and binding. An unanchored append quarantines the service. Token bucket restarts empty; rolling permits and bind/expiry persist.

The journal cap is 64 MiB, maximum frame 4 KiB, and maximum 1,000,000 frames. Both byte and row caps are enforced; because the minimum valid frame is 208 bytes, the effective maximum under the byte cap is 322,638 frames (the explicit 1,000,000-row guard is an additional format ceiling). Each admission reserves maximum-size `PERMIT`, `ISSUED`, plus one 4 KiB settlement frame and one frame slot. Escrow counts against both hard caps; it is per live issued handle and released only after settlement sync+anchor. Mint rejects before permit/nonce if all three records cannot fit. At exact cap no mint is admitted; room for PERMIT alone is insufficient. Every anchored unbound ISSUE retains settlement escrow across restart, reconstructed from replay. No online compaction is defined; retention, segmentation, snapshotting, and key retirement require a separate SDD. Limits from docs/50 remain burst 3/refill 1 per 60 seconds, 20 rolling-hour permits, 16 outstanding unbound handles, and 2 concurrent mint operations per principal. The rolling-hour window is the half-open interval `(trusted_now_ns - 3_600_000_000_000, trusted_now_ns]`: a permit exactly one hour old is excluded; one nanosecond younger is included. Admission tests and then anchors the PERMIT using the same trusted sample frozen before append. The token bucket starts empty after restart; its first token arrives after 60 seconds, and each subsequent token arrives at another 60-second interval up to burst 3. Logs are structured and allowlisted: `trace_id` (random per request, not persisted), module, event, phase, safe failure class, record type, aggregate capacity counters, duration, and coarse errno category only. Never log principal references, request IDs, binding/handle hashes, key IDs or bytes, claims, ciphertext, raw frame/body, filesystem paths, peer credentials, or signing/keyring material. Every injected error path must scan all captured service/API/launcher logs against the forbidden-field and secret fixture set; this is mandatory for sync/anchor, rollback, missing-key, limit, clock, and IPC failures, not only codec failures.

The companion [quota-journal case manifest](../review/pilot-intent-quota-journal-manifest-20261022.json) and [complete frame vectors](../review/pilot-intent-quota-frame-v1-vectors.json) bind this SDD; every case remains design-only until all three artifacts are reviewed at matching hashes. Its mixed-chain replay fixture is a separate legal chain with two handles (PERMIT→ISSUED→BOUND for one, PERMIT→ISSUED→EXPIRED for another), linked by each prior frame digest, so no ISSUED has two terminal settlements. Store the generated fixture and expected relative offsets under `server/internal/pilotquota/testdata/`; tests load the checked-in vector JSON directly and run with `cd server && go test ./internal/pilotquota`. The suite must cover pinned directory/file identity and permissions, frame/MAC/chain parsing, signed-receipt forgery and canonical encoding, isolated limits, concurrent writers, duplicate request IDs, write/sync/anchor/encryption-RPC crash boundaries, lost HTTP responses, bind/expiry races and late delivery, trusted-clock behavior, key rotation, corruption/truncation and valid-prefix/snapshot rollback, and exact capacity boundaries. Before implementation, reviewers must approve this SDD and manifest at matching hashes.
