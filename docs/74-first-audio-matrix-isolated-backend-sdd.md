# First-Audio Matrix Isolated Backend SDD

Date: 2026-10-26  
Status: design reviewed; implementation may proceed behind the test-binary boundary. Matrix execution remains pending implementation acceptance.

## 1. Goal and non-goals

Provide the test-binary controller in `docs/73` with a fresh, private SQLite database and the real `api.App` used by a browser journey. Prove that application writes cannot escape the synthetic first-audio fixture, and that reset cannot advance while old-generation effects remain admitted. This is a test-only path: no production route, startup flag, database reset endpoint, or relaxed production policy is added. A green protocol workflow is not a matrix result.

This SDD does not implement the 30-cold/100-warm run, latency claims, or a real-student pilot. Those remain gated on the dedicated application backend, two-journey Playwright entry point, and acceptance review in `docs/70`.

## 2. Current application facts

`store.Open` uses `glebarez/sqlite` and initializes the GORM startup models, config-revision triggers, and normalized-word index. `api.NewApp` then performs DB work: a no-op `UPDATE users SET id=id WHERE 1=0`, loads users, saves missing teacher/system-agent accounts, restores `notifications` and legacy `feedbacks` runtime records, and migrates any restored legacy feedback. Therefore the guarded application pool cannot be created against an empty fixture and simply deny all user writes: the fixture must seed both agent accounts before pool publication, and startup-only reads/writes must be enumerated and tested. The zero-row `users` update must have an execution-time row trigger that rejects every actual row change.

## 3. Ownership and initialization sequence

1. The Python runner creates the run root with exclusive creation and private permissions, verifies it is not a symlink/reparse point, and rejects an existing `matrix.db` or `-wal`, `-shm`, or `-journal` sidecar. The child independently verifies the capability, root, DB path, and sidecar absence.
2. A setup-only pool creates the full application schema and fixed schema objects, seeds exactly one synthetic student, one book, the frozen word set, both internal agent accounts, and the synthetic lesson. The student username is `first-audio-<lowercase-run-id>` (run ID sanitized to `[a-z0-9-]`, max 32 suffix bytes). Its browser-only password is the unpadded base64url SHA-256 of `capability_bytes || 0x00 || "first_audio_login"`; derive it independently in the parent and child, never return or persist it, and store only the normal salted password hash. It is a per-run synthetic login credential, not an external secret. It installs the reviewed fixed row-guard triggers. Fixture setup is complete before baseline capture. The setup handle and all setup connections are closed and verified unusable before continuing.
3. Register a uniquely named test SQLite driver using the repository's `mattn/go-sqlite3` fork. Its `ConnectHook` installs required deterministic UDFs and the immutable authorizer before the connection is returned to `database/sql`. Start the controller in `DRIVER_PROBE`, allowing only the explicit `sqlite_version` probe needed by GORM's SQLite dialector. Open the GORM application pool using that registered driver name and the exact private DB path; immediately after `gorm.Open` returns, tighten to `STARTUP_PROBE`. Do not call migrations or expose a raw setup handle after this point.
4. Preseed both agent accounts so `NewApp` does not insert users. Construct `api.NewApp` using the guarded pool, with the controller still in `STARTUP_PROBE`. `NewApp` prepares a known zero-row `UPDATE users SET id=id WHERE 1=0`. Because SQLite authorizers run at prepare time and cannot inspect the SQL predicate, the immutable authorizer has one narrow exception: `SQLITE_UPDATE` on `main.users.id` is permitted only in `STARTUP_PROBE`. Fixed user `BEFORE INSERT/UPDATE/DELETE` triggers reject every row effect in every phase; the startup probe succeeds only because it matches no row. Current `NewApp` and first-audio teacher-effect code do not prepare a `config_globals` write reservation; deny all config-global DML and do not grant config-revision trigger write tuples in application phases. Any future reservation wrapper is a new design change, not an implicit exception. After `NewApp` returns, verify all startup reads, both agent accounts, empty `notifications` and legacy `feedbacks`, and no user/config row-guard invocation; then tighten one-way to `PREFLIGHT`. This happens before any listener/browser request. Cached statements cannot bypass row guards after phase tightening. Any row effect, unexpected startup write set, or phase-transition uncertainty fails closed.
5. In `PREFLIGHT`, verify the authorizer/UDF hook on every live physical connection by pinning the configured pool capacity, running per-connection positive and negative probes, and checking a process-owned connection registry. On each pinned connection, issue a test-only no-op `UPDATE lessons SET phase=phase WHERE id=?` under a one-use PREFLIGHT guard context whose canonical OLD and NEW lesson rows are identical; the fixed lesson trigger must invoke `first_audio_row_guard`, accept only this exact probe, and the surrounding transaction must roll back. Then compare the complete snapshot. This proves the row UDF exists and is attached on that physical connection without changing fixture data. Release the pins and recheck the registry. Every later connection is covered by the same `ConnectHook`; connect failure, unregistered connection, missing UDF, hook count mismatch, or unexpected replacement is terminal. Probe UDF statements and the one-use lesson transition cannot be executed once the controller advances to the browser phase.
6. Before opening a listener, assert none has been created and that schema/row baselines, hook coverage, `unexpected_guard_denials`, App startup, and every physical-connection probe have passed. Then bind exactly one `net.Listen("tcp4", "127.0.0.1:0")`, verify the actual bound IP is loopback, and serve `api.App.Router()` behind a test-only admission/counting handler from the dedicated test child. Return that observed `http://127.0.0.1:<port>` origin in the `bind` response. Never bind `0.0.0.0`, hostnames, or non-loopback interfaces. The listener remains owned by the same child and database through both browser journeys and reset; shutdown drains it before the GORM pool. The browser runner owns and launches the dedicated test binary; no production server process is reused.

If the required per-connection hook cannot be guaranteed with the actual GORM driver configuration, do not fall back to `glebarez` or a one-connection assumption. Stop before a browser journey and record `NOT RUN`.

## 4. Immutable database policy

Every physical connection receives the same authorizer. It denies all schema DDL, temporary schema objects, ATTACH/DETACH, every PRAGMA action in SQL issued after `ConnectHook`, and DML on every non-allowlisted table. Config-global and config-revision DML is denied in application phases; there is no no-op reservation exception. If a later reviewed implementation adds a reservation wrapper, capture and review its exact authorizer tuples before changing this policy. The authorizer never transitions from permissive preparation to restrictive execution. Connection-only `foreign_keys=ON`, `recursive_triggers=ON`, `busy_timeout=5000`, and journal-mode configuration are applied by the driver before the hook is installed; the hook verifies resulting settings through driver state or a private probe function, not by allowing runtime PRAGMA SQL. Explicit non-data authorizer actions are limited to `SQLITE_SELECT`; `SQLITE_TRANSACTION` with `BEGIN`, `COMMIT`, or `ROLLBACK`; and built-in `SQLITE_FUNCTION` names `count`, `max`, and `coalesce` in application phases (ASCII case-normalized, matching the checked-in word-count and next-ID queries). `sqlite_version` is additionally permitted only during `DRIVER_PROBE`. The only test UDF is `first_audio_row_guard`; its `SQLITE_FUNCTION` action is permitted only when SQLite supplies one of these exact trigger sources: `fa_users_no_insert`, `fa_users_no_update`, `fa_users_no_delete`, `fa_config_globals_no_insert`, `fa_config_globals_no_update`, `fa_config_globals_no_delete`, `fa_lessons_guard_insert`, `fa_lessons_guard_update`, `fa_lessons_guard_delete`, `fa_runtime_guard_insert`, `fa_runtime_guard_update`, `fa_runtime_guard_delete`, `fa_audit_guard_insert`, `fa_audit_guard_update`, or `fa_audit_guard_delete`. A separate `first_audio_probe` UDF is permitted only with nil trigger source in the `PREFLIGHT` phase; the UDF itself is bound to the expected probe token and fails once phase advances. Direct top-level `first_audio_row_guard`, same-name functions from any other source, and any other UDF/function are denied. The pinned SQLite runtime treats `RAISE()` as trigger syntax and emits no `SQLITE_FUNCTION` authorizer callback for it, so the policy grants no synthetic `raise` function tuple. No `SQLITE_SAVEPOINT` or other function is permitted unless implementation review adds an observed exact tuple and regression test. `DRIVER_PROBE` tightens to `STARTUP_PROBE` immediately after `gorm.Open`; `NewApp` runs entirely in `STARTUP_PROBE`; only after it returns do we tighten to `PREFLIGHT`, then complete per-connection probes before browser operations. Reads use a checked-in, schema-derived table/column manifest for **every table in the approved schema**, not only the App's direct queries, because complete snapshots must read all rows. The manifest includes all columns of all models returned by `store.startupModels`, fixed triggers/indexes, and `sqlite_sequence` when the schema uses AUTOINCREMENT; each table/column pair comes from the checked-in expected schema digest and unknown objects/columns are denied. This means `users` and config `SELECT *` include timestamp/metadata columns; classroom App queries additionally use the exact columns described in the manifest for `word_books`, `word_entries`, `lessons`, `memory_cards`, `runtime_records`, and the config tables. `audit_logs.id` plus the trigger-specific empty-column/empty-database table-existence callback is readable from `fa_audit_no_replace` for its collision check; full audit rows are readable through the same approved schema manifest for snapshots. Read-only `sqlite_master`/`sqlite_schema` metadata columns (`type`, `name`, `tbl_name`, `rootpage`, `sql`) are allowed in every phase; top-level reads have nil authorizer source and this policy does not claim to identify the Go caller. This is acceptable because the database is private and contains only synthetic data; schema DDL and all non-allowlisted writes remain denied. The manifest's digest is checked before app construction and is never derived solely from arbitrary run-DB objects. Any other table, column, database, trigger source, or authorizer action tuple is denied. Any unknown action increments a monotonic process-owned denial counter. No callback may query SQLite, acquire the lifecycle lock, or block on application locks.

Only three row families can change during the first-audio journey:

| Table | Permitted change | Execution-time enforcement |
|---|---|---|
| `lessons` | Exactly one synthetic lesson row. Reset changes its primary key from the current synthetic ID to the next unique ID and replaces the canonical row in one controller-supplied OLD→NEW transition. It does not insert a second lesson or delete an unexpected row. | Fixed `BEFORE INSERT/UPDATE/DELETE` triggers call the test-only UDF with operation and complete relevant OLD/NEW identity/state fields. Only reset may change the ID, and only to the controller-pinned next ID. |
| `runtime_records` | Journey upsert of only the current `snapshot/<lessonID>`. Reset may delete the exact prior synthetic snapshot key and insert the exact next snapshot key in its single transaction. | Triggers require exact key, operation, and phase; report/settled/agent-result and all other keys are rejected. |
| `audit_logs` | INSERT only with exact current `lesson-<lessonID>` trace; no update/delete. Prior synthetic trace rows stay byte-identical across reset. | Trigger/UDF validates full identity fields and rejects an already-existing `NEW.id` before insertion, regardless of conflict algorithm. |

All other GORM models, manually created pilot/duplex objects if present, users, books, word entries, cards, config, feedback, notifications, classroom events, tickets, and non-sample rows remain denied. The complete `sqlite_master` object set is inventoried; unknown objects fail closed. Setup-created guard triggers are included in the approved schema baseline and cannot be altered in the matrix pool.

The UDF reads one immutable `guardContext` snapshot containing run ID, current/prior/next synthetic lesson IDs, generation, phase, canonical expected OLD/NEW row encodings, old/new runtime snapshot keys, probe token (when applicable), and an increasing context version. The controller fully constructs each snapshot, then publishes its pointer through one `atomic.Pointer[guardContext]` store; callback loads it once and uses only that snapshot for the whole decision. Snapshot memory and byte slices are immutable after publication. The callback never reads separate phase/expectation atomics, takes the lifecycle lock, queries SQLite, or blocks on application locks. Attempt counters use independent monotonic atomics. Before a reset transition is published, classroom admission is closed, all old-generation leases/effects are drained, and the controller has verified the exact old lesson/snapshot and computed the next unique ID, canonical lesson row, and snapshot key. It then atomically publishes one `RESET_APPLY` snapshot containing both lesson rows and both snapshot keys. Only the reset writer may run while that snapshot is active. After commit, same-pool readback and complete snapshot verification succeed, publish the corresponding next-generation journey snapshot; on any uncertainty publish a terminal context. The set of permitted tables, columns, and operations is fixed for the run; context replacement only narrows a particular operation to one generation/row tuple and does not widen the policy. Tests race callback reads against legal context publication and assert each decision observes one complete version, never mixed phase/expectation data.

The UDF checks operation, phase, canonical row identity, and controller-held expected transition values from that single immutable context. It returns a SQLite error for any violation and increments a monotonic atomic attempt counter outside the SQL transaction, so rollback cannot erase evidence. Counters distinguish `expected_probe_denials` (only known preflight negative probes), `unexpected_guard_denials` (any denial during app startup, journey, reset, or shutdown), and `row_guard_invocations`; none may be reset or decremented. The preflight suite must prove expected probes are rejected and counted while `unexpected_guard_denials` remains zero. At the start of each journey/reset, capture a monotonic counter baseline; only the phase-local unexpected-denial delta must be zero. Trigger/UDF failures, wrong argument types, missing trigger, or UDF replacement are terminal. `recursive_triggers=ON` is defense in depth only. For audit ID collision, the fixed BEFORE INSERT trigger performs `WHEN EXISTS(SELECT 1 FROM audit_logs WHERE id=NEW.id) BEGIN SELECT RAISE(ABORT,...); END` before SQLite resolves conflict policy; this trigger-side lookup rejects `INSERT OR REPLACE` without UDF re-entry or a Go callback querying SQLite. UDF validates the remaining row parameters and phase. The immutable-context publication order ensures a callback sees either the complete old snapshot before drain or the complete new snapshot after publication.

SQLite has one observed authorizer edge case for `COUNT(*)`: the callback may report `SQLITE_READ` with an empty database name and empty column. The implementation may allow that exact tuple only for a manifested main-schema table's empty-column row-count sentinel. It must still deny an unknown table, unknown column, or `temp` database; the regression suite locks all four outcomes. `count`, `coalesce`, and `max` are allowed only with nil trigger source in application phases; all config-global and config-revision DML remains denied in application phases. `SQLITE_SELECT` is allowed only at top level, from the six fixed user/config row-guard triggers, or from `fa_audit_no_replace`. That audit trigger's additional reads are `SQLITE_READ` on `main.audit_logs.id` and the observed empty-column/empty-database `audit_logs` table-existence tuple with source `fa_audit_no_replace`; every other table, column, database, or trigger source remains denied. Tests prove an unused audit ID insert succeeds, collisions and `INSERT OR REPLACE` abort before changing rows, and wrong source/table/column tuples remain denied. Tests also cover phase/source boundaries and reject unknown-function tuples.

### Schema-to-read manifest consistency

After the fixed schema digest is accepted on the setup pool, derive physical column names for every manifested table using `PRAGMA table_xinfo` and compare exact sets with the authorizer read manifest generated from startup models. Include `sqlite_sequence`; handle `sqlite_master`'s fixed metadata columns explicitly. Reject missing, extra, or duplicate table/column entries before closing the setup pool. The empty-string `SQLITE_READ` entry is a separate SQLite `COUNT(*)` authorization sentinel, not a physical column: compare it separately as present only for manifested tables, and exclude it from physical-column equality. Read metadata only through the setup pool before it closes; never permit runtime PRAGMA actions on the guarded app pool. Add negative tests for missing/extra tables and columns, invalid count sentinels, plus a positive full-schema equality test.

### Trigger-side read exceptions

The config revision AFTER trigger remains in the pinned schema, but config-global/config-revision DML and its trigger-source authorizer tuples are denied in application phases. The audit collision trigger reads `main.audit_logs.id` plus its empty-column/empty-database table-existence tuple from source `fa_audit_no_replace`; permit these exact read tuples in `STARTUP_PROBE`, `PREFLIGHT`, and `JOURNEY`. `DRIVER_PROBE` and every other phase deny them. During `JOURNEY`, the execution-time UDF still validates the exact synthetic audit row and trace. The pinned runtime emits no `SQLITE_FUNCTION` callback for special `RAISE()` syntax, so do not grant one. All other nonempty trigger-source reads are denied, even when their table/column is present in the top-level snapshot read manifest. Tuple tests capture actual callbacks through the mattn hook. Config-global/config-revision DML is rejected; no unimplemented reservation statement is assumed.

## 5. Guard and snapshot verification

Before exposing the app to a browser, test each physical connection with: allowed synthetic reads; denied DML on a denylist table; denied DDL, ATTACH/DETACH, and unsafe PRAGMA; a rolled-back exact OLD==NEW lesson update that positively invokes `first_audio_row_guard` from an approved trigger; rejected top-level or unknown-source calls to that UDF; allowed `first_audio_probe` only in `PREFLIGHT`; and statement preparation. Required adversarial tests include preparing a row write on an authorizer-allowed mixed table (for example, UPDATE of a non-sample `audit_logs` trace) before the journey, then executing it during the journey; the execution-time trigger must reject it and increment the unexpected-denial counter. Attempt config-global/config-revision DML and verify it is denied without changing rows or firing a config-revision side effect. Other required tests cover forbidden-table insert followed by rollback (prepare-time authorizer denial), audit ID collision with `INSERT OR REPLACE` followed by rollback, audit update/delete, non-sample lesson/runtime/trace writes, and execution through every pool connection. Every negative probe must fail and increment the appropriate monotonic counter; expected preflight probes leave data unchanged and do not count as journey violations.

Capture canonical sorted schema-object and full-row snapshots at fixture baseline, before/after each journey, immediately before/after reset, and after the next journey. Hashes are over stable typed serialization with primary-key ordering. The only reset delta is a primary-key transition of the same sole synthetic lesson row from old ID to next ID, deletion of exactly `snapshot/<oldID>`, insertion of exactly `snapshot/<newID>`, and any append-only audit rows whose trace identifies the completed synthetic journey; prior audit rows must remain byte-identical. Compare exact allowed diffs; do not ignore a changed row because the request failed. Persist sanitized table/key/field diffs, hook coverage, phase, counter values, transaction outcome, and source/database hashes beneath the private ignored run root. Do not persist SQL payloads, user secrets, or absolute paths in ordinary logs.

The direct App read list above describes application call sites, not the whole authorizer read manifest. Snapshot completeness requires read access to every table and column in the checked-in expected schema manifest, including empty denylist tables and implicit `sqlite_sequence` rows when present. The schema manifest is an explicit, reviewed artifact generated from the repository's known startup schema and checked against its fixed digest; any new/missing table, column, trigger, index, or view changes the digest and fails before the guarded pool opens. The database contains only this run's synthetic fixture, so schema-manifest-wide reads are allowed while writes remain limited to the three sample row families. Snapshot queries are serialized against browser admission by the test-only HTTP gate. After a Playwright process exits, close HTTP admission to block new handshakes, retire the active classroom generation to cancel/close WebSocket handlers and drain effects, then wait for ordinary handler count zero before recording the boundary snapshot. Both drains have bounded deadlines; any timeout is terminal and prevents snapshot acceptance.

On known rollback, verify the complete prior state. On COMMIT error or uncertain outcome, observe using the same guarded app pool, record present rows and snapshots, and do not retry cleanup or reset. Any failed reset, unexpected data/schema delta, nonzero phase-local `unexpected_guard_denials` delta, close error, uncertain post-commit read, or baseline mismatch moves the controller to terminal `TERMINAL_FAILED`; nonzero expected preflight denials and row-guard invocation counts alone are not failures. No next lesson/generation can be created. A replayed `reset_id` only returns a previously recorded result and never repeats work.

## 6. Startup and reset boundaries

The setup pool is the only schema/fixture writer. The application pool is guarded from its first prepare and remains guarded through `NewApp`, both browser journeys, reset, and shutdown. No network listener exists until `NewApp`, schema/row baselines, every connection hook, and all preflight probes have succeeded. Then the child opens only the observed IPv4 loopback listener described in §3.6. A test-only HTTP admission wrapper counts active handlers. Before snapshot/reset, close HTTP admission first to block new requests and upgrades, retire the active lesson generation to cancel/close WebSocket handlers and drain leases/effects, then wait for ordinary HTTP handler count zero; reopen the gate only after the reset and snapshot are verified. After retirement drain succeeds, remove the old `Room` from `Hub.rooms`, mark it retired, cancel any remaining judgment continuation, close any residual client handles, revoke its tickets, and only then advance the retired generation. A room/ticket/connection cleanup error is terminal. Shutdown follows the same order: close HTTP admission and listener, retire the active lesson generation to cancel/close WebSockets and drain effects, close residual room/client state and revoke tickets, call `http.Server.Shutdown` with a bounded 30-second context to wait for ordinary handlers, verify wrapper in-flight count zero, close App workers, then close the GORM pool. A Shutdown timeout, undrained hijacked connection, nonzero in-flight count, or any close error is terminal and the runner kills/reaps the whole child process tree; the pool is not closed while a handler can still be using it. The implementation must document and assert all `NewApp` startup DB effects listed in §2; if a new startup query appears, the matrix fails until reviewed. The existing generation coordinator closes admission, cancels registered continuations, and drains admitted effects before reset. Reset must use one guarded transaction to update the sole synthetic lesson row to a new primary key and canonical next-journey state, delete its exact prior `snapshot/<oldID>`, and create `snapshot/<newID>`. After COMMIT succeeds, read back the new lesson and snapshot through the same guarded application pool, compare the full boundary snapshot against the only allowed PK/snapshot/audit diff, and only then publish the next-generation guard context and reopen HTTP admission. Any commit, readback, or snapshot uncertainty is terminal. The old audit rows are retained unchanged; the next journey may append only its current lesson trace. It must not construct a new `App`, replace the pool, truncate tables, delete unexpected rows, or reopen setup access.

Reset success is followed by a complete snapshot and application readback before the next journey is admitted. Shutdown closes App-owned workers, GORM/database pools, and test process; close errors are fatal evidence. The Python runner enforces the JSONL deadlines in `docs/73`, process-tree cleanup, stdout protocol purity, and artifact manifests.
