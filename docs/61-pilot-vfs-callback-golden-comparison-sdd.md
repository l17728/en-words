# Pilot VFS Callback Golden Comparison SDD

## Status and scope

This amendment implements only the canonical, repeatable comparison stage already required by docs/55 and docs/56. It characterizes the pinned SQLite 3.45.1 host `unix` VFS callbacks. It does not implement or approve the private Pilot VFS, syscall policy, A0 readiness, product routes, or classroom use. Architecture, backend, security, and test-design reviewers must approve this exact document and fixture schema before code changes.

## Inputs and test entry point

Keep `TestPilotVFSRuntimeCandidateGeneration` as the raw candidate entry point. Factor its body into a shared candidate-generation helper; keep top-level tests as thin wrappers. Add `TestPinnedVFSCallbackGoldens`, which first requires the exact SQLite version, number, and source ID, then invokes the helper in a named Go subtest using the runner-supplied `PILOT_VFS_RUN_ID` and fresh `PILOT_VFS_ARTIFACT_DIR`. Candidate generation remains exclusive-create and refuses a nonempty directory. The Python runner adds explicit `--mode candidate|golden|propose-goldens` (default `candidate`) and selects exactly one top-level Go test: candidate mode runs `TestPilotVFSRuntimeCandidateGeneration`, golden mode runs `TestPinnedVFSCallbackGoldens`, and proposal mode runs `TestProposePinnedVFSCallbackGoldens`. Never run the two writer tests in one Go invocation: each requires a fresh, empty evidence directory. The supported golden command is `python ../review/run_pilot_vfs_candidate.py --mode golden --artifact-dir <new-absolute-directory>` from `server/`; its `strace -f` wrapper records the test process. Proposal mode writes normalized `*.golden.proposal.json` files only beneath that run's fresh artifact directory, using exclusive creation; it never modifies checked-in `testdata`. A human reviews the proposal against raw trace and candidate evidence before manually adding a fixture. Proposal mode reports only `PASS_CANDIDATE`, never `PASS_GOLDEN`. The comparison must never write or update checked-in fixtures. A missing run ID/artifact directory, wrong source ID, incomplete evidence, or unsupported platform is `NOT RUN`/failure, never a passing comparison.

The runner must treat `--artifact-dir` as an untrusted path: walk from `/` by directory FD with `O_NOFOLLOW` for every component and reject `..`, symlinks, and non-directories. Trusted ancestors (all components except the final run directory) must be owned by root or the effective UID and must not be group/world-writable, except a root-owned sticky shared directory such as `/tmp`; the final run directory must be newly created by the effective UID with mode `0700`. Recheck path-to-FD identity after execution. Pin the checkout root and every directory under `server/internal/pilotcontrol/testdata`; reject if any artifact-path component, including all ancestors and the final run directory, matches the checkout-root or any pinned testdata directory `(device,inode)`. This catches paths within the checkout and bind-mounted aliases to fixture directories. Python retains the validated directory FD through execution and rechecks its identity. It passes the FD device/inode tuple to Go; Go independently walks the absolute path from root with openat(O_NOFOLLOW) for every component, compares final directory identity to the runner tuple, and opens artifacts relative to that verified FD. Go and Python writers must use the retained directory FD (or safe `openat` relative to it) with fixed basenames and `O_CREAT|O_EXCL|O_NOFOLLOW`; no child-supplied path may choose an output name. Validate run IDs as exactly 32 lowercase hexadecimal characters before using them in any path or record. Any path-validation or identity failure fails the run before proposal output and leaves checked-in fixtures untouched.

Child callback trace snapshots use one fixed, scenario-specific basename. The child publishes a complete snapshot before each readiness/terminal barrier; the parent reads only after the corresponding barrier, so publication and reading are serialized by the control protocol. The first publication uses `O_CREAT|O_EXCL|O_NOFOLLOW`. A subsequent publication may reopen only that same basename relative to the verified artifact directory with `O_WRONLY|O_NOFOLLOW|O_NONBLOCK` (without `O_TRUNC`), verify by `fstat` that it is a regular file owned by the effective UID with link count one, then `ftruncate` the verified FD, write all bytes, `fdatasync` the file, and `fsync` the directory. Both first and later publications must finish all writes and both syncs before the child sends its barrier. It must not follow a symlink, block on a FIFO, or alter a non-regular target. Any snapshot publication error, including before the first READY, is a harness failure and must fail the entire candidate run; it must never be translated into an eligible missing-barrier `NOT RUN`.

Tests assert that each publication's complete write, file sync, and directory sync happen before its control barrier is sent, and that the parent reads the matching snapshot only after receiving the barrier. Deterministic fault injection covers first-create, first-write, first-file-sync, and first-directory-sync failures before the first READY; after a child has emitted READY it covers reopen, truncate, short/write, file-sync, and directory-sync failures on the repeated publication. Every fault must yield a failed candidate invocation, successful bounded child cleanup/reaping, no normalized `NOT RUN` row for the harness failure, and no proposal artifact. Separate bounded-time tests verify symlink, FIFO, directory, and other non-regular targets are rejected without truncation or blocking; repeated successful publication verifies the second complete snapshot replaces the first safely.

The child control channel is a strict sequenced packet protocol. A timed-out barrier may be represented as `NOT RUN` only where the scenario's eligibility table explicitly permits it; `LOCK-CROSS-PROCESS-CONTEND` treats every missing barrier or incomplete child outcome as fatal. Peer closure, malformed frame length, unexpected payload on a payload-free message, wrong sequence/type, or an invalid structured-error envelope is a harness/protocol failure and must fail the candidate run. Since a zero-length `SOCK_SEQPACKET` record and EOF can both produce a zero-byte read, a closed peer is treated as ambiguous and fails closed. Deterministic protocol mutation tests cover short and oversized/truncated frames, payload on an empty message, wrong type, wrong sequence, malformed/version-invalid structured-error envelopes, peer EOF, a zero-length record followed by peer closure, and a LOCK barrier timeout; each must fail the candidate run, produce no normalized `NOT RUN` row, and produce no proposal.

Pager snapshot candidate evidence retains each raw file's byte count and SHA-256, and the normalizer must re-open and verify those exact bytes before deriving a golden. The database snapshot keeps its raw SHA-256. The rollback journal golden instead records a stable semantic projection SHA-256 because SQLite's checksum nonce is random per run. For this pinned pilot, accept only the observed single-segment 8720-byte journal shape: exact 8-byte SQLite journal magic; four big-endian uint32 header fields with `nRec=2`, initial database page count `2`, sector size `512`, and page size `4096`; a big-endian uint32 nonce at bytes 12–15 (the full uint32 range, including zero, is valid); zero header padding from byte 28 through 511; then exactly two 4104-byte records, with unique page numbers in `[1,2]`. Reject the `nRec=0xffffffff` sentinel, extra headers/segments, any sector padding after the two records, and trailing bytes. This narrow contract deliberately fails closed if the pinned test's journal shape changes. For each page, interpret its stored checksum as big-endian uint32; initialize `sum` to the header nonce, then for `i = pageSize-200; i >= 0; i -= 200`, add the unsigned page byte at `i` modulo 2^32. Reject any checksum mismatch. This is SQLite's [rollback journal format](https://www.sqlite.org/fileformat.html#rollback_journal) checksum rule. Build the projection by preserving all bytes except zeroing nonce bytes 12–15 and the two validated checksum words at offsets 4612–4615 and 8716–8719. Hash the projection; never accept the candidate's raw SHA as this golden value. The original artifact SHA remains in raw candidate evidence and must match before projection. Any malformed header, extent, page number, or checksum fails proposal generation.

Projection tests use two otherwise identical valid journals with distinct nonces (including zero) and corresponding valid checksums: raw hashes must differ while projection hashes match. A changed page byte with a recomputed valid checksum must change the projection hash. Mutation cases reject bad magic, altered record extent/count, `0xffffffff` sentinel, extra segment/header, trailing bytes, invalid/duplicate page number, nonzero header padding, truncated header/padding/record, wrong page/sector size (including non-power-of-two and out-of-range values), bad checksum, and evidence hash/length mismatch. These tests demonstrate repeatability while preserving journal page data and validating the omitted random-dependent checksums.

## Required tests and acceptance

- `PAGER-EMPTY-OBSOLETE-RESERVED` tests inject one setup failure before the first SQLite call and one failure after it; the first yields only the specified NOT RUN evidence with successful cleanup, while the second fails the run.
- `TestPinnedVFSCallbackGoldens` checks pinned SQLite identity, Linux/amd64/unix lane, runner inputs, fresh artifact isolation, all four candidate groups, strict JSON fields, exact scenario order/status/count, byte-for-byte canonical equality, and first-difference diagnostics. `TestProposePinnedVFSCallbackGoldens` uses the same evidence path but writes proposal files only to the isolated artifact directory and cannot report a golden pass.
- Unit tests mutate one field at a time (callback name, event order, flags, rc, handle ID, scenario order/count, new unknown field, NOT RUN reason, source ID) and require comparison failure. Pager evidence tests reject zero-byte files, altered content, byte/hash or snapshot mismatches, symlinked ancestors, and final directory identity that differs from the runner-pinned device/inode tuple, missing/duplicate/extra basenames, symlinks, and non-regular files; a valid pair is stripped from normalized golden output while snapshot `{bytes,sha256}` remains. EEXIST mutations prove that `INTERPOSER_FAILED_CLOSED` is accepted only for the initial sequence-1 unavailable frame before a qualifying request, and rejected after `EXCLUSIVE_CREATE_OBSERVED` or any injected attempt. Include a status-relabel mutation that changes a mandatory `CANDIDATE` row (for example `VFSFLAGS-JOURNAL-CREATE`) into an otherwise well-formed `NOT RUN` row and require rejection. Separate cases prove that volatile fields are removed and that a NOT RUN EEXIST scenario remains present and cannot be relabeled PASS.
- Python runner unit/E2E tests cover all three modes (`candidate`, `golden`, and `propose-goldens`) and verify the selected test name, outer strace process record, immutable outputs, artifact hashes, exclusive writes, cleanup, and exit-code propagation. Proposal-mode E2E proves output is isolated, exclusive, and never changes checked-in fixtures. The default candidate-only mode remains available for reviewed regeneration evidence.
- Run non-writing comparison/normalizer unit tests directly, for example `go test -tags=pilot_e2e -run '^(TestPinnedSQLiteRuntimeIdentity|TestVFSCallbackGoldenNormalizer)$' -count=1 ./internal/pilotcontrol`. Run candidate, proposal, and golden modes as separate Python-runner invocations, each with a distinct new artifact directory, on Linux/ext4; then run the full tagged package, `-race`, coverage, and `go vet`. Windows may compile portable comparison logic but cannot mark Linux fixtures passed.

Passing this slice means only that current pinned host SQLite callback behavior matches reviewed Linux/amd64 goldens. The private VFS implementation, all native filesystem rows, required function-level coverage, A0, product integration, product E2E, and classroom acceptance remain separate gates.
