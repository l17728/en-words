# Pilot VFS Initialization and Restart-Recovery Amendment

## Status and scope

This is a design amendment to docs/54–58. It resolves initialization-transaction ordering and process-restart sidecar adoption before the private pinned VFS is implemented. It does not authorize implementation, canonical-golden promotion, A0 readiness, product wiring, or classroom use. It supersedes docs/55's current `PAGER-EMPTY-OBSOLETE-RESERVED` expected-delete wording: the frozen candidate trace observes no journal `xOpen`, `xClose`, or `xDelete` for that scenario. The implementation gate in docs/54–55 remains in force: reviewed canonical callback goldens and the lock-range oracle must be complete, and architecture, backend, security, and test reviewers must approve the exact amended design and manifest hashes.

## Initialization transaction boundary

`PRAGMA journal_mode=WAL` cannot run inside the schema/seed write transaction. The `NEW_FILE` path exists only in the process that successfully created the main file with `O_CREAT|O_EXCL`; any later process sees an existing database and must use `EXISTING_ADOPTED`, never re-enter initialization. On every physical SQLite connection, set `foreign_keys=ON` and `recursive_triggers=ON` and read both values back before any other SQL or transaction. While holding the singleton service lock and before application dispatch, the creator must: (1) pin and validate the new main database; (2) open it through the private VFS and verify `SQLITE_FCNTL_VFS_POINTER`; (3) perform a read-only schema preflight through that connection, accepting only an empty database with `user_version=0` and no application schema objects; (4) issue `PRAGMA journal_mode=WAL` outside any transaction and read the result back as exactly `wal`; (5) sync the database and root directory as required by the VFS contract; then (6) start one writer transaction containing the complete reviewed DDL, fixed seeds, and final initialization marker, commit atomically, sync, close, and reopen in `mode=rw` through the same VFS. On every reopened/pool connection, set and verify both required PRAGMAs before any schema/invariant query; only then run the validation-only authorizer and verify exact schema, marker, seed rows, and invariants. Existing databases first use read-only schema preflight: accept only exact v3 schema plus complete marker, otherwise quarantine. Before SQLite identity validation succeeds, filesystem preflight rejection must leave files untouched. After it succeeds, a bounded read-only schema query may trigger SQLite hot-journal recovery; this recovery is allowed and must be recorded with before/after identities and value digests. It may not execute application DDL/DML, initialization, reseeding, `user_version` changes, or journal-mode switches. A non-v3 database is quarantined after any required SQLite recovery. Never set WAL or run initialization DDL/seeds on the existing-database path. No application SQL is dispatched before validation succeeds. An uncertain WAL-setup or initialization-COMMIT result quarantines the current process; a later process may accept only the complete exact marker plus full validation, never retry or reseed.

A crash after WAL setup but before the DDL transaction leaves an initialization-incomplete database. It is quarantined and requires explicit offline reset; it is never silently reseeded. A crash during DDL/seeding rolls back that transaction and has the same quarantine outcome. A crash after commit but before readiness may recover only through the restart-adoption protocol below and exact schema/invariant validation. WAL setup is durable configuration outside the DDL transaction and is not claimed to roll back with it.

## Restart adoption of SQLite sidecars

Restart adoption is a startup-only capability, distinct from runtime `xOpen` EEXIST handling. Before SQLite is registered or any SQL is dispatched, the supervisor must hold the singleton lock, prove the previous service generation and all descendants are gone using the retained child/pidfd records and an empty bound cgroup (never PID-name search), pin the configured root and main database, and validate their exact owner, mode, ACL, link count, and mount identity. If prior-process absence or the trusted root boundary cannot be proved, startup is quarantined. Startup phases are monotonic: `LOCKED -> ROOT_PINNED -> NEW_FILE | EXISTING_ADOPTED -> WAL_SETUP (new only) -> INIT_TX (new only) -> SQLITE_RECOVERY_AND_VALIDATE -> POOL_WARM -> READY`; every error transitions to `QUARANTINED`, and no path returns from quarantine to initialization.

Under that exclusive startup boundary and the docs/55 lock order, enumerate only the exact names `operations.sqlite-wal`, `operations.sqlite-shm`, and `operations.sqlite-journal`. For each existing name, first use root-relative `openat2` with `O_PATH|O_NOFOLLOW|O_CLOEXEC` and the pinned resolution flags to inspect type/owner/group/mode/link/mount without opening a device or FIFO for I/O. Only a verified regular file may then be opened through a second root-relative `openat2` with `O_RDWR|O_NOFOLLOW|O_NONBLOCK|O_CLOEXEC`; query access/default ACL xattrs through that usable FD and fail closed on any result other than `ENODATA`. Compare usable-FD `fstat`, the O_PATH anchor identity, and final root-relative no-follow name identity while the namespace mutex is held. After successful comparison and registry publication, close the temporary usable FD exactly once; retain only the O_PATH descriptor as the identity anchor and record `(dev,inode,mount_id)` before any SQLite callback. Unknown names, symlinks, hardlinks, special files, metadata/query errors, or identity races quarantine startup without unlinking the suspect object. The anchor FD is not a SQLite I/O FD and is not `dup`ed for connections; each `xOpen` obtains an independent open description via locked root-relative `openat2`, compares it to the registered anchor, and owns/closes that connection FD exactly once. `open_fd_refs` and `shm_map_refs` count only live SQLite handles/maps. The generation owner closes the anchor and retires the row only after the name is absent and both counts reach zero; a `delete_pending` generation cannot be replaced before then. No registry/lifecycle/namespace mutex is held while SQLite runs recovery SQL or closes a connection; adoption releases internal locks in reverse order before invoking SQLite.

An existing WAL and journal are adopted as generation 1 and left byte-for-byte intact for the pinned SQLite pager to determine whether the journal is hot or obsolete and to perform recovery. Do not infer journal state from file size or infer recovery completion from WAL presence/absence or checkpoint status. For the initial implementation, any simultaneous WAL and journal is quarantined with evidence preserved, including a zero-length journal; supporting a combination requires a separately reviewed recovery vector. A stale SHM file may be removed only after prior-process absence is proven and its pinned identity has passed all checks; acquire the exclusive lifecycle OFD lock on the reserved main-file byte before unlink, then directory `fsync` is required before SQLite registration. If the process crashes after unlink but before/after directory sync, the next process repeats full preflight against the actual namespace: absent SHM is treated as absent (not as proof of a prior successful deletion), while a reappearing SHM must be revalidated and removed again. If unlink succeeded but directory sync failed, record `unlink_done=true,durability=unknown`, close all temporary/anchor FDs, quarantine, and never claim rollback or readiness. When no sidecar exists, the registry starts empty and the normal exclusive create path publishes generation 1. Startup adoption records are process-local; any startup failure closes all temporary/anchor/usable FDs exactly once.

The lifecycle lock is a distinct OFD lock on main-file byte range `[0x40000200,0x40000201)`, acquired through a separate verified main-file open description; it does not overlap SQLite's pinned SHARED/RESERVED/PENDING/EXCLUSIVE ranges. Hold it continuously from before the SHM identity recheck through `unlinkat` and successful root-directory `fsync`, then release it exactly once before SQLite registration. Failure to acquire or release it quarantines startup. The per-process namespace mutex serializes only this service's threads; it is not treated as protection from another process. External replacement is excluded by the owner-only `0700` root and trusted Reaper UID boundary, with the final no-follow name/anchor identity comparison immediately before mutation; any mismatch fails closed. An administrator capable of mutating the protected root is trusted by the host threat model.

After adoption, SQLite opens only through the private VFS. Existing sidecar `xOpen` calls may obtain a new independent FD only by locked root-relative open and exact comparison to the adopted generation anchor; they cannot share/duplicate the anchor as a data FD or infer a generation from EEXIST. Runtime EEXIST rules remain unchanged: only a matching already-registered generation may be reopened, and SQLite `SQLITE_OPEN_EXCLUSIVE` EEXIST always fails. Before application dispatch, a restricted schema read must trigger pager recovery; all callbacks must complete without unresolved identity/durability ambiguity, then exact schema/invariants and no-uncommitted-transaction state are validated. Do not require WAL disappearance or forced checkpoint as a readiness condition. The only expected namespace transitions during recovery are VFS-observed sidecar creation, SQLite-requested `xDelete`, and `xShmUnmap(deleteFlag=1)` unlink/sync while holding lifecycle EXCLUSIVE, followed by the exact generation retirement/refcount rules; each is recorded with callback/case ID and identity. Any unrequested disappearance, replacement, or identity mismatch fences readiness and preserves evidence for offline recovery.

## Required regression evidence

The amended storage contract is bound to docs/55's exact Linux resolution and ownership policy: every `openat2` uses `RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV`; `ENOSYS`, `EINVAL`, or any unsupported required flag fails closed with no path-based fallback. Root must be owned by configured Reaper euid/egid and mode `0700`; main and sidecars must be regular files owned by that euid/egid, mode `0600`, `nlink=1`, on the pinned mount. Query `system.posix_acl_access` and `system.posix_acl_default` from verified usable FDs; only `ENODATA` means absent, while EACCES/EOPNOTSUPP/EIO and all other query errors quarantine startup. These values are normative references to docs/55, not relaxed alternatives.

To distinguish a committed initialization from an incomplete or uncertain transaction, the docs/51–53 reviewed v3 DDL must add exactly one `pilot_initialization_state` row written as the final statement in the same transaction as schema and fixed seed rows. Its closed schema is `singleton_id INTEGER PRIMARY KEY CHECK(singleton_id=1)`, `format_version INTEGER CHECK(format_version=1)`, `schema_manifest_sha256 BLOB CHECK(typeof(schema_manifest_sha256)='blob' AND length(schema_manifest_sha256)=32)`, `seed_manifest_sha256 BLOB CHECK(typeof(seed_manifest_sha256)='blob' AND length(seed_manifest_sha256)=32)`, and `complete INTEGER CHECK(complete=1)`; all columns are `NOT NULL`, and abort triggers reject every UPDATE/DELETE. The table and its DDL are part of `schema_inventory_v3.json`; no marker value/hash is embedded in either digest input. `schema_manifest_sha256` is SHA-256 over the exact bytes of the production-embedded `server/internal/pilotcontrol/schema_inventory_v3.json` (UTF-8, no BOM, LF line endings, one final LF). The fixed seed manifest is `server/internal/pilotcontrol/initialization_seeds_v1.json`, embedded into the production binary; it is a closed ordered list of table/key/value tuples serialized as canonical JSON (RFC 8785/JCS), UTF-8 without BOM and one final LF, and does not contain its own digest or the initialization marker row. Runtime obtains the approved schema and seed digests only from reviewed build-time source constants (`approvedSchemaInventorySHA256` and `approvedSeedManifestSHA256`) bound into the application artifact; it must never load an expected digest from the writable database root, environment, external config, or the manifest being checked. Tests independently pin the same constants and reject a modified embedded payload. Both expected digests are frozen as 32-byte values in the separate schema-fault manifest/test vectors, which are not included in either digest input. Startup validates the marker against those exact approved manifest hashes and verifies every listed fixed row before readiness. The seed manifest contains immutable reference/content rows only; mutable operational bootstrap rows (including the lease, capacity counters, random launcher-journal ID, restore generation, and runtime metadata) are initialized in the same transaction but are excluded from the fixed-seed digest. On reopen, validate those rows against current legal state, the protected external restore-generation/journal-ID anchor, and cross-table invariants; never compare them to their original NULL/zero values. Random IDs and deployment profile values are supplied by the separately authenticated bootstrap contract and are not digest inputs. Missing, duplicate, mismatched, or incomplete marker means `QUARANTINED`; the service never retries initialization or reseeds. A marker with exact hashes plus full schema/invariant validation is the only route by which a new process may accept an initialization commit whose caller observed an uncertain result. The DDL artifacts, embedded seed manifest, statement inventory, schema-fault manifest, and hashes must be updated and reviewed together before implementation.

The machine-readable recovery case source is `server/internal/pilotcontrol/testdata/pilot-vfs-recovery-cases.json`; it expands every stable ID below and remains `DESIGN_CASES_NOT_EXECUTED` until each case has an executable private-VFS test and artifact. The loader must bind this file and this SDD by exact SHA-256. Extend that manifest with these stable case families and barriers:

Every barrier is observable and deterministic; sleeps cannot prove arrival. The marker oracle includes pre/post value, database/main/WAL/journal identities, SQLite extended result, readiness state/generation, application-dispatch count, and an exactly-once durable marker count. Each DDL barrier names the statement ID and hash from `schema_inventory_v3.json`. Traces carry `run_id`, case/barrier ID, phase, event sequence, `connection_id`, `file_handle_id`, sanitized object role, `(dev,inode,mount_id)`, OS/SQLite result, readiness generation and dispatch count. Artifacts are hash-bound and contain no secrets or absolute user paths. A stable WAL digest and durable marker value are compared in `VFS-ADOPT-WAL-SHM-01`; volatile inode values are checked within-run and are not canonicalized into cross-run goldens.

## Golden and implementation gate

The four current runtime proposals characterize host `unix` callback facts only. They do not provide the per-handle lock-range oracle required by docs/55. The reviewed test-only bridge must be built from the pinned SQLite 3.45.1 source with an isolated compile-time trace hook at `unixOpen`, `unixLock`, `unixUnlock`, `unixCheckReservedLock`, `unixShmMap`, `unixShmLock`, `unixShmUnmap`, and `unixClose`. The VFS wrapper assigns a stable `file_handle_id`; the hook receives that token and records the actual FD, per-FD open generation, `fstat` `(dev,inode)` and `statx` mount ID at open, then emits every actual kernel lock command/range/result against the same token before close. SHM has a separate shared-node identity and FD-generation: trace node creation/attachment, each connection's mapping token to that node, actual SHM lock syscalls on the node's FD, and final node FD close; never use the main database FD identity as the SHM lock identity. Distinguish callback-request events from kernel-operation events. The join is valid only if each callback handle maps to exactly one live main FD, each SHM mapping maps to exactly one live node, identities remain stable, close/unmap occurs exactly once, and no FD-generation is reused ambiguously. Per-run evidence includes volatile `(run_id,dev,inode,mount_id,fd_generation)` values and is checked only for within-run identity consistency. Canonical goldens omit those volatile values and contain only deterministic scenario/object labels, operation order, lock ranges/kinds/flags, and results; normalization occurs only after the per-run identity audit succeeds, so it cannot hide identity drift. Raw traces remain private artifacts and do not include PID/path. Missing, duplicate, reordered, or identity-changing events fail the scenario.

Lock golden scenarios have stable IDs `VFS-LOCKRANGE-UNIX-01..05` (two local connections; cross-process shared contention; reserved promotion; failed exclusive promotion and rollback; downgrade/unlock) and `VFS-LOCKRANGE-SHM-01..04` (two local mappings; cross-process slot contention; release/reacquire; final-unmap racing a new map). Freeze exact byte offset, length, lock kind, transition order and result from the source-pinned instrumented run; compare each run exactly. Human review checks trace-to-hook-to-FD identity join and the matching pinned SQLite source implementation before fixture promotion. A process-level `strace` record without that join is supplemental and cannot satisfy the gate. Human approval of the four callback proposals permits only promotion of those exact callback facts; it does not waive lock-range, private-adapter, native matrix, or later A0 gates.

The updated docs/51–58 (including docs/57), callback/recovery manifests, loader, and test-only evidence bridge must receive exact-hash architecture, backend, security, and test-design review before implementation begins. All 81 existing callback rows and every added startup/recovery row remain `DESIGN_CASES_NOT_EXECUTED` until private VFS tests execute them; design-loader tests are not runtime acceptance.
