# Pilot Promotion Ambiguous-Outcome Recovery SDD

Status: Approved for local client implementation after architecture, backend/security, and test-design review on 2026-10-23. The external service and witness remain unimplemented and require separate implementation review and deployment acceptance.

This SDD is an explicit amendment to the golden-promotion contract in `docs/56-pinned-sqlite-golden-harness-delta.md`. Its recovery/fence semantics supersede the prior manual-only reconciliation behavior for approvals handled by a service that advertises this reviewed protocol. `docs/56` must link this amendment after review; no service implementation may treat this proposal as approved before that gate.

## 1. Purpose and Scope

When `POST /v1/promotions` commits an approval but the HTTP response is lost, the client may not know the returned `promotion_id`. A lookup that merely observes no record is insufficient: a delayed original POST could still arrive and commit later. This amendment adds an explicit reconcile-and-fence operation. It preserves the existing approval payload, single `l17728` signature, promotion record, ledger sequence rules, and candidate gate. Existing `GET /v1/promotions/{promotion_id}` remains read-only.

## 2. Reconcile Endpoint

Add mTLS-authenticated `POST /v1/promotions/reconcile/{approval_envelope_sha256}` with the exact original canonical approval envelope as its JSON body. The path digest is 64 lowercase hexadecimal characters and equals SHA-256 of the raw request body. The service verifies the envelope signature, reviewer authorization and digest binding; recovery remains allowed after expiry because it resolves historical commit state.

The operation requires mTLS identity authorization scope `PILOT_GOLDEN_RECOVERY_OPERATOR`, mapped only to the approved operator subject `l17728`. The service also verifies that the signed approval subject is `l17728`; a different or unbound client identity cannot create a fence. This scope is distinct from read-only promotion lookup. Recovery verifies the reviewer key against an append-only historical key/role registry: the key must be known, bound to `l17728`, and have held `PILOT_GOLDEN_REVIEWER` when the approval was signed. Later key revocation does not prevent recovering a committed historical record or fencing an uncommitted approval; a key that was never authorized cannot create a fence.

The operation acquires the same cross-instance, transaction-scoped lock keyed by the approval-envelope digest as promotion. It reads the authoritative anti-rollback ledger and returns `200 application/json` with one service-signed envelope:

- The existing `pilot-vfs-golden-promotion-record-v1` record if promotion committed.
- A new `pilot-vfs-promotion-recovery-fence-v1` record if no promotion committed. Its exact payload fields are `schema`, `approval_envelope_sha256`, `repository`, `purpose`, `reviewer_subject`, `reviewer_key_id`, `approval_sequence`, `reconciled_at`, `result`, and `fence_id`. Constants are fixed to the schema, `l17728/en-words`, `PILOT_VFS_GOLDEN_PROMOTION`, `l17728`, and `FENCED_NOT_COMMITTED`; the digest is lowercase SHA-256, the sequence is a positive exact integer, `reconciled_at` is UTC second precision, and `fence_id` is 32 random bytes in strict unpadded base64url. The service signs canonical payload bytes with its separately pinned Ed25519 service key.

The service durably records the fence before returning it. A fence does not create a promotion record, but permanently prevents any later POST carrying that exact approval-envelope digest from committing. It advances the per-key anti-replay high-water mark to `max(current_high_water, approval_sequence)` exactly once. Sequence gaps are allowed; reuse of any sequence at or below the high-water mark is forbidden. A new approval after a fence must use a sequence strictly greater than the resulting high-water mark. Reconcile retries return the exact same signed fence or promotion record and never advance sequence state again. If the service cannot establish or durably fence the outcome, it returns `503` and the client remains `outcome_unknown`.

Malformed digest/body/signature returns `400`; missing or unauthorized mTLS identity returns `401`/`403`; `503`, timeout, ordinary unsigned proxy/route errors, malformed records and invalid signatures never prove either outcome. The client treats all responses other than a locally verified promotion record or a locally verified fence envelope as unknown. In particular, a generic HTTP `404` is never interpreted as not committed.

## 3. Atomicity, Races and Crash Recovery

Promotion POST and reconcile POST use the same serializable digest-keyed lock across every service instance, backed by the durable ledger rather than an in-process mutex. They also acquire a durable per-reviewer-key sequence lock, since different approval digests can race the same high-water mark. Lock order is fixed: global checkpoint sequencer, reviewer-key sequence lock, then approval-digest lock. Every path, including retries and recovery, follows this order. Lock acquisition is bounded to 10 seconds; timeout returns `503` with `outcome_unknown` and performs no fence or promotion write. The operation holds the state locks through its durable transaction and decides the exact response payload before releasing the digest/key locks. The durable commit is the operation linearization point. After commit and lock release, the service sends that already-decided response; if sending fails, a repeated reconcile returns the persisted record/fence. A lock holder must never send success before commit.

1. If promotion obtains the locks first and commits, reconcile waits, then returns the exact signed promotion record.
2. If reconcile obtains the locks first and finds no committed record, it commits the fence and advances the high-water mark once. A delayed or concurrent promotion POST then obtains the locks, observes the fence and returns `409 FENCED`; it creates no promotion record and does not advance sequence state again.
3. If promotion aborts before commit, reconcile commits the fence and returns the signed fence record.
4. After a service crash, a committed transaction is returned as the promotion record; an uncommitted transaction is rolled back before reconcile can fence. If durable state or lock ownership cannot be proven, return `503`, never a fence.

All promotion/fence changes also pass through a singleton durable checkpoint sequencer. It assigns one global generation inside the ledger transaction and stores an immutable pending checkpoint over the exact post-transaction ledger root. No later state-changing operation may receive a generation or return a terminal success while an earlier checkpoint is pending. The sequencer advances only after the external witness has durably acknowledged that exact checkpoint. A single global generation chain therefore orders writes from different approval digests and reviewer keys.

A timeout during reconciliation is itself ambiguous, but repeating the same reconcile operation is safe: the durable digest key returns the existing record/fence. Promotion POST itself remains non-idempotent from the caller's perspective: an already consumed or fenced approval returns refusal, and clients never automatically repeat `POST /v1/promotions`. A verified fence is conclusive and requires a fresh higher-sequence approval.

A `409` promotion response is not itself proof of either terminal state because it may be an unsigned transport/service error and an earlier attempt may have committed. After any ambiguous or replay refusal, the caller must invoke reconcile and accept only a locally verified promotion record or fence envelope as conclusive evidence.

## 4. Client Contract

Add `recover(approval_envelope, expected_bindings=None)`. The reviewer trust store is pinned out of band and retains an append-only key history with each key's subject, roles, validity interval, and revocation time. Recovery locally verifies the exact approval signature and requires that its key belonged to `l17728` and held `PILOT_GOLDEN_REVIEWER` at `approved_at`; it does not require the key to remain active now. The service applies the same historical rule. The client then computes the raw envelope digest and sends the reconcile POST. A verified promotion record returns a `PROMOTED` result; a verified fence returns `FENCED_NOT_COMMITTED`; timeout, `503`, unsigned/legacy route errors, malformed response, bad service signature, or any binding mismatch raises an error with `outcome_unknown=True`. Recovery never calls `promote()` and never automatically resubmits the old approval. It works after approval expiry because both signed outcomes attest historical state.

## 5. Security, Storage and Observability

The digest is an identifier, not an authorization token; the body signature, reviewer subject and scoped mTLS identity are all checked. A digest unique constraint/fence index and per-key high-water mark are durable and anti-rollback. Every promotion or fence commit creates an immutable pending checkpoint containing its unique global generation, prior checkpoint hash, exact ledger-root hash after that transaction, and commit ID. The checkpoint is signed by the ledger service and appended to an independently operated witness using compare-and-swap on the prior generation. The witness verification key is pinned out of band and distinct from reviewer, promotion-service, and run-authorization keys. Its signed canonical acknowledgment has a closed schema binding generation, prior checkpoint hash, ledger-root hash, and commit ID. An acknowledgment lost after append is resolved by authenticated lookup of that generation: identical checkpoint returns the original acknowledgment; no entry with the expected prior head allows retrying the identical append; a conflicting entry or unavailable witness remains pending/503. A ledger commit without a verified witness acknowledgment is pending and cannot be exposed as terminal; after restart the service reconciles it before serving terminal results. No later checkpoint can skip a pending generation. A local ledger behind or divergent from the witness fails closed and cannot be repaired by restoring an older backup. Fences are permanent compact ledger entries so a delayed request can never resurrect an approval. The service applies authenticated-client rate limits and storage quotas; it never evicts a fence to free space. If quota, ledger storage, lock ownership, or witness is unavailable, it returns `503` without claiming a fence, and the client preserves `outcome_unknown`. Reconcile logs include trace ID, module, event, result, digest prefix and latency, but exclude private keys, certificates, credentials and full approval bodies. URL access logging must redact or hash the digest where deployment policy requires it.

## 6. Required Acceptance Cases

1. Commit succeeds but POST response is dropped; reconcile returns the exact promotion record and leaves ledger sequence/record count unchanged.
2. Reconcile wins before a delayed POST; it returns a signed fence, creates no promotion record, and advances the per-key high-water mark once. The late POST is refused without another sequence advancement.
3. Force both lock orders across two service instances: promotion-first must yield one promotion record; reconcile-first must yield one fence and late POST `409`. Assert record XOR fence and exactly one advancement to `max(previous_high_water, approval_sequence)`. A follow-up reconcile must verify the signed terminal envelope; the unsigned `409` alone never confirms state. Verify a new approval with the same or lower sequence is refused and a higher sequence is accepted.
4. Inject crashes before promotion commit, after promotion commit but before response, after fence commit but before response, and with unrecoverable lock/ledger state. After restart, pre-commit resolves to a durable fence; committed promotion/fence returns the exact same signed terminal bytes and ID; unresolved state returns `503`. No old request may commit after restart once fenced.
5. Drop a reconcile response and retry serially and concurrently across two instances; both callers receive the same signed terminal record, with one durable fence at most and no additional high-water advancement.
6. Ordinary unsigned 404 from an old server or proxy, malformed/unsupported responses, wrong service key, altered digest, bad Content-Type, oversized/truncated body, timeout and `503` all preserve `outcome_unknown` and never trigger `POST /v1/promotions`.
7. Wrong-body digest, invalid approval, absent identity, wrong subject, missing recovery scope or unauthorized mTLS identity cannot create a fence. Replay of the old approval against an existing fence is refused; repeated reconcile returns the same fence.
8. After fence commit, restart, backup restore and failover preserve the fence and witnessed ledger root; restoring a snapshot older than the external witness is rejected. Crash between ledger commit and witness acknowledgement remains pending/unknown until reconciled. Quota exhaustion does not evict a fence and returns unknown/503 without making the old approval promotable.
9. Existing promotion-record GET stays read-only; a fence is distinguishable from `PASS_GOLDEN` and can never authorize candidate execution.
10. Run new approvals/promotions/fences for distinct digests and sequences concurrently on two instances. Assert per-key high-water never decreases, no new approval at/below it is accepted, equal-sequence approvals cannot both succeed, and digest locking does not replace the per-key sequence lock. Force sequence N+1 to win before N; N must then be rejected and the high-water remains N+1.
11. Delay witness append for generation N while another digest attempts generation N+1; N+1 cannot become terminal or skip N, and a concurrent reconcile cannot return a terminal result while N is pending. Test both witness fault points: (a) append fails before persistence; after restart, authenticated lookup confirms the prior head, and retry appends the byte-identical checkpoint; (b) append persists but its ACK is lost; lookup returns the identical signed ACK. A conflicting checkpoint at the same generation fails closed; neither path may change generation, prior hash, root, or commit ID during retry.
12. For historical key recovery, verify a key valid for `l17728`/reviewer role at `approved_at` still recovers after later revocation and approval expiry. Reject a key never authorized, a key whose validity starts after `approved_at`, and one whose reviewer role ended before `approved_at`; none may write a fence.

## 7. Rollout Gate

The reviewed protocol authorizes implementation of the local Python client and its test fixtures. It does not authorize claiming the independently operated service or witness is implemented. Until those components pass separate code review and deployment acceptance, the client remains fail-closed and operators must continue manual authoritative-ledger reconciliation. Production service, registered keys, mTLS credentials, durable anti-rollback storage, and a valid candidate authorization remain external prerequisites to promotion or candidate acceptance.
