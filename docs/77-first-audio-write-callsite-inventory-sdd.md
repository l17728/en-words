# First-Audio Matrix Write Inventory SDD

Date: 2026-10-27  
Status: review draft; this documents the first-audio-only matrix boundary and does not authorize SQL integration.

## 1. Scope decision

The target matrix is designed to prove two sequential first-entry journeys, interruption, stale-work containment, and reset against one private `api.App`/database. Each browser journey stops after first audio and its interruption. It does **not** finish the lesson or exercise settlement, reports, feedback, or adaptive planning. This is the scope specified in `docs/70` §7g and `docs/74`; synthetic performance does not establish full-classroom or real-student acceptance. Persisted browser evidence is restricted to fixture IDs, generation, timing, cancellation counts, and pass/fail counts; test reports must not serialize utterance/caption text, screenshots, or traces. Browser output directories are deleted only after process-tree exit is confirmed. If cleanup cannot confirm every writer has stopped, the runner returns `cleanup_incomplete`, keeps the directory under the private run root, and forbids archiving or reporting acceptance. The Playwright spec now contains the cancel/delayed-callback, no-advance, and generation-binding assertions described below. The isolated guarded App/browser acceptance has not been run, so these assertions are implementation evidence only, not a passing matrix result.

For the target interruption assertion, the browser cancels the currently playing utterance after its start event, then the E2E injects that utterance's retained delayed `onend` callback before closing the page/socket and verifies it does not start queued audio or advance classroom state. The runner starts each browser journey in a separate process, so a browser callback cannot be retained across the controller's reset. Cross-reset stale-work fencing is instead exercised by Go integration races; the second browser process binds its observed lesson/generation and first audio/caption to the controller's new generation. These assertions are implemented in the spec but remain unexecuted in the isolated guarded matrix. This matrix does not claim microphone barge-in or speech recognition while TTS is playing; that requires a separate real-classroom acceptance path.

The mandatory `plan_next`/`report_push` completion plan in `lessonplan.go` is outside this scenario. Do not substitute an invalid empty plan or claim end-to-end lesson completion. If the test reaches completion, that child run fails its boundary and becomes terminal. A full-lesson matrix requires a separate SDD and expanded row/field allowlist.

## 2. Observed write inventory

Replace the generic GORM transaction path with an observed wrapper that reports exactly `committed`, `rollback_confirmed`, or `outcome_uncertain`; `rollback_confirmed` requires an explicit rollback/cleanup returning nil. For `rollback_confirmed`, release the original SQL permit and insert the one failure audit under a fresh context-bound audit permit; its contract is predeclared as the alternate terminal result for that same tool attempt. If the wrapper says `outcome_uncertain`, perform no further SQL writes (including failure audit or effect-failure snapshot), terminalize the child, and preserve observed state. If the follow-up audit itself fails, terminalize; do not retry it. Failed children cannot reset or continue. IDs are append-only; UPDATE/DELETE/REPLACE are denied. |

For each fresh `Hub.Enter`, `teacherPending=lesson_started` causes `TeacherAgent.Decide` to return the deterministic open utterance, producing exactly one `classroom.say` audit outside `PlanEffects`. The normal first-audio sequence is exactly one `classroom.say` (fresh-entry lifecycle), one `classroom.show_word` (Join action), and one `classroom.play_tts` (first word click): three successful audit appends per journey in that order. The E2E and DB snapshot must reject any extra allowlisted call as well as any unallowlisted tool. Reconnect/restored-room paths do not count as fresh-entry utterances. Preserve prior lesson traces byte-for-byte across reset. A failure audit belongs only to a failed terminal child run and is not passing journey evidence.

## 3. Trusted operations and lease boundary

The snapshot writer accepts a typed, controller-bound lesson operation, reads OLD in the same transaction, and derives NEW from the trusted `Room` transition; arbitrary caller-provided rows or JSON are invalid. Compare full canonical rows for the only allowed runtime key. The browser cannot choose lesson IDs, generation, runtime keys, or context version.

There are two distinct lease layers. The outer REST/WS/timer operation acquires a **generation operation lease** before its first lesson, ticket, or Room read and holds it through side effects, state publication, and response/frame completion; it prevents reset from completing and is not exposed to SQLite callbacks. Every top-level GORM query/operation acquires one **context-bound SQL permit** before loading the active context and holds it through prepare, callbacks, execution, and result close. An explicit transaction acquires one permit for its full lifetime; all statements, nested repository calls, triggers, commit/rollback, and result sets inside that transaction reuse that same permit rather than reacquiring it. If an OLD/NEW contract must change, the request first releases its ordinary SQL permit, then closes SQL admission and drains all prior SQL permits (not generation operation leases); only then it takes one exclusive transition permit, reads OLD in the transaction, validates the typed command, publishes the complete next context, performs DML, commits/readbacks, releases the permit, and reopens SQL admission. A request must never hold a context-bound SQL permit while waiting for that drain. This refines `docs/76`'s use of “ordinary lease”: the per-generation operation lease is intentionally not part of the SQL-context drain. Reset, initiated by the parent/controller and never by a request, first closes operation admission, drains all generation operation leases/effects, then performs the exclusive reset transaction. `callAgentTool`/snapshot writes must enter this sequence without recursively acquiring or draining their own permit.

Reset closes operation admission, drains the old generation, and in one controller-only transaction changes the one synthetic `lessons` row to its next canonical ID/state and replaces only `snapshot/<oldID>` with `snapshot/<newID>`. Prior successful synthetic audit rows remain byte-identical. Verify commit, same-pool readback, and the complete table/object snapshot before reopening. No completion marker, card mutation, extra lesson, or unrelated audit append is allowed. Any uncertain outcome is terminal and cannot create the next journey.

## 4. Required evidence and review

CGO integration tests must prove snapshot transitions and exact tool-audit appends on every physical connection; deny every other table/key/tool/operation; preserve denylisted rows; and exercise interruption, late-result, and reset races. Inject failures before/after DML, audit insert, COMMIT, explicit rollback, and connection cleanup; verify the transaction outcome enum, the second-write permit requirement, `rolled_back_ok`, and that uncertain commit forbids every follow-up write (including `effectFailureLocked` snapshot persistence). The Playwright acceptance must run two start→first-audio→interrupt journeys in separate browser processes against one child process/database, with one reset between them. In each browser process it must cancel the active utterance, invoke the retained delayed completion callback, and assert there is no extra audio/caption or client-side advance before closing the page/socket. After reset, the second journey must assert that its observed lesson/generation and first audio/caption match the controller's new generation. Go races must separately prove stale server callbacks, tickets, and late results cannot affect the next lesson. The spec implements its browser assertions, but the isolated full matrix and cross-reset Go races remain NOT RUN/incomplete. Explicit completion/forbidden-tool probes run in a separate child process because any violation terminalizes the controller; they must leave non-audit rows unchanged and cannot be followed by reset or a passing journey.

## 5. Uncertain transaction terminal behavior

For `callAgentTool`, only a successful COMMIT is `committed`; a callback error plus successful explicit ROLLBACK is `rollback_confirmed`; begin/commit/rollback ambiguity and panic are `outcome_uncertain`. A failure audit may follow only `rollback_confirmed`, under a fresh guarded write permit. `outcome_uncertain` must not write a failure audit or classroom snapshot: retire the Room, cancel pending judgment work, emit `classroom_error` with `code=transaction_outcome_uncertain` and `retryable=false`, and reject further work. The browser must show a stop-and-return-to-course-list message and hide reconnect. For uncertainty during the initial Enter lifecycle, return a structured nonretryable API error that the WS client treats as terminal. Teacher/effect loops, Resume, event and timeout entrypoints, and post-settlement snapshot paths must all stop after retirement. The Playwright test simulates a terminal `/enter` response during WS reauthorization and verifies no retry beyond the first backoff; this does not replace a real commit-ambiguity injection through the guarded pool. Current code implements these terminal fences; deterministic outcome and retired-entrypoint tests are present, while guarded-pool fault injection, per-connection permit enforcement, and the isolated browser matrix remain NOT RUN.

Architecture, backend, security, and test reviewers must approve this exact scope and reconcile conflicting wording in `docs/70`, `docs/74`, and `docs/76` before SQLite wiring. Test-binary/controller protocol, performance, and human classroom acceptance remain separate gates; this draft claims none of them passed.
