# First-Audio Matrix Write Inventory SDD

Date: 2026-10-27  
Status: reviewed design baseline (2026-10-27); implementation and acceptance remain open. This is not evidence that guarded SQL integration or the classroom matrix has passed.

## 1. Scope decision

The target matrix is designed to prove two sequential first-entry journeys, interruption, stale-work containment, and reset against one private `api.App`/database. Each browser journey stops after first audio and its interruption. It does **not** finish the lesson or exercise settlement, reports, feedback, or adaptive planning. This is the scope specified in `docs/70` §7g and `docs/74`; synthetic performance does not establish full-classroom or real-student acceptance. Persisted browser evidence is restricted to fixture IDs, generation, timing, cancellation counts, and pass/fail counts; test reports must not serialize utterance/caption text, screenshots, or traces. Browser output directories are deleted only after process-tree exit is confirmed. If cleanup cannot confirm every writer has stopped, the runner returns `cleanup_incomplete`, keeps the directory under the private run root, and forbids archiving or reporting acceptance. The Playwright spec now contains the cancel/delayed-callback, no-advance, and generation-binding assertions described below. The isolated guarded App/browser acceptance has not been run, so these assertions are implementation evidence only, not a passing matrix result.

For the target interruption assertion, the browser cancels the currently playing utterance after its start event, then the E2E injects that utterance's retained delayed `onend` callback before closing the page/socket and verifies it does not start queued audio or advance classroom state. The runner starts each browser journey in a separate process, so a browser callback cannot be retained across the controller's reset. Cross-reset stale-work fencing is instead exercised by Go integration races; the second browser process binds its observed lesson/generation and first audio/caption to the controller's new generation. These assertions are implemented in the spec but remain unexecuted in the isolated guarded matrix. This matrix does not claim microphone barge-in or speech recognition while TTS is playing; that requires a separate real-classroom acceptance path.

The mandatory `plan_next`/`report_push` completion plan in `lessonplan.go` is outside this scenario. Do not substitute an invalid empty plan or claim end-to-end lesson completion. If the test reaches completion, that child run fails its boundary and becomes terminal. A full-lesson matrix requires a separate SDD and expanded row/field allowlist.

## 2. Observed write inventory

| Journey operation | Source path | Matrix disposition |
|---|---|---|
| Save live classroom state | `Room` → `saveLessonStateContext` → `App.saveRuntimeContextLocked` in `roomcontext.go`, `hub.go`, and `app.go` | Allow only upsert of `runtime_records[snapshot/<syntheticLessonID>]`. Initial state is `show_word`, index 0. The first word-click may change only `phase=tts_seg` and `tts_seg_idx=1`; lesson/book/student IDs, config digest, `started_at`, other scalar fields, maps, and slices remain identical. Client interruption cancels playback locally and must not advance server state. Any other key/state delta is denied. |
| Execute frozen teacher effects | `Room.broadcastEffectsLocked` → `TeacherAgent.PlanEffects` → `App.callAgentTool`; utterance via `teacherUtteranceLocked` → `classroom.say` | Allow only effects emitted by the frozen first-audio script: `classroom.show_word`, `classroom.play_tts`, and `classroom.say` when the deterministic teacher policy emits it. These handlers validate frozen facts and do not mutate domain rows. Quiz, judge, report, config, memory, scheduler, and all other tools are denied. |
| Persist effect audit | `callAgentTool` → `persistToolAudits` in `agenttransaction.go` | Permit append-only `audit_logs` in the same transaction as an allowed effect, with exact `trace_id=lesson-<id>`, `actor_id=teacher_agent`, `actor_role=teacher_agent`, `actor_type=""` (the current struct literal leaves it empty), low risk, and only the effect-tool allowlist above. `Args` must match the registry's canonical `{"bytes":N}` summary with `0<N<=512`; never store speech text, student answers, transcripts, or audio. Success rows require `OK=true`, `Result=ok`, duration `1..60000 ms`, and a timestamp within the run. A failure audit is allowed only when the transaction wrapper returns `rollback_confirmed`: `OK=false` and `Result` is one of `rolled_back_ok`, `rolled_back_canceled`, `rolled_back_deadline_exceeded`, or `rolled_back_handler_failed`. Replace the generic GORM transaction path with an observed wrapper that reports exactly `committed`, `rollback_confirmed`, or `outcome_uncertain`; `rollback_confirmed` requires an explicit rollback/cleanup returning nil. A COMMIT error, rollback/cleanup error, panic, or lost connection is `outcome_uncertain`, never `rolled_back_ok`. For `rollback_confirmed`, release the original SQL permit and insert the one failure audit under a fresh context-bound audit permit; its contract is predeclared as the alternate terminal result for that same tool attempt. If the wrapper says `outcome_uncertain`, perform no further SQL writes (including failure audit or effect-failure snapshot), terminalize the child, and preserve observed state. If the follow-up audit itself fails, terminalize; do not retry it. Failed children cannot reset or continue. IDs are append-only; UPDATE/DELETE/REPLACE are denied. |
| Persist report/completion | `App.saveReport`, `commitLessonWithAgents`, `writeLessonRuntime` | Forbidden. `report/<id>`, `settled/<id>`, `agent_result/<id>`, `notifications`, settlement card writes, lesson completion, and system-agent plan/audits remain unchanged/absent. |
| Lesson lifecycle writes | `SchedulerRepo.SaveLesson` (`gorm.Save`) and scheduler create/delete paths | Forbidden during browser journeys. The controller's separate reset transaction is the only lesson-row writer: change only the synthetic scheduled lesson primary key to the next canonical ID after draining old-generation effects; every other persisted field stays identical. Never call generic `SaveLesson`; it writes whole structs and may insert when no row matches. |
| Other persistent models | Store repositories, feedback, settings, placement, overdue, and import routes | Denied and included in complete boundary snapshots: all `memory_cards`, config/revisions, memories, notifications, classroom events, tickets, feedback records, and non-sample audit rows. |

For each fresh `Hub.Enter`, `teacherPending=lesson_started` causes `TeacherAgent.Decide` to return the deterministic open utterance, producing exactly one `classroom.say` audit outside `PlanEffects`. The normal first-audio sequence is exactly one `classroom.say` (fresh-entry lifecycle), one `classroom.show_word` (Join action), and one `classroom.play_tts` (first word click): three successful audit appends per journey in that order. The E2E and DB snapshot must reject any extra allowlisted call as well as any unallowlisted tool. Reconnect/restored-room paths do not count as fresh-entry utterances. Preserve prior lesson traces byte-for-byte across reset. A failure audit belongs only to a failed terminal child run and is not passing journey evidence.

The complete cross-table commit order for each journey is fixed: `classroom.say` audit commit during `Hub.Enter` → `classroom.show_word` audit commit during first `Join` → initial snapshot INSERT commit after Join effects finish → `classroom.play_tts` audit commit after the first word click → snapshot conflict-UPDATE commit. The second journey repeats this same order under its new lesson ID. Capture this with a test-only monotonic event ledger only after successful transaction boundaries. Its closed record schema is `sequence`, `lesson_id`, `event_kind`, `tool_or_key_class`, `context_version`, and `outcome`; `event_kind` is exactly `tool_audit_committed`, `snapshot_insert_committed`, or `snapshot_update_committed`; `tool_or_key_class` is exactly one of the three tool names or `snapshot_insert`/`snapshot_update`; `outcome` is always the literal `committed`. Failed or uncertain transactions do not create ledger records. The ledger is private to the child process, is not persisted or exposed to browser reports, and includes no word, speech, caption, student answer, error text, or audio payload. Assert this exact event order; audit row IDs and final table snapshots alone do not prove cross-table chronology.

## 3. Trusted operations and lease boundary

### 3.1 Field-level OLD → NEW contracts (candidate for review)

The guard compares typed canonical rows inside the transaction; it must not authorize a table/key/action tuple alone.

| Write | OLD contract | NEW contract | Denied differences |
|---|---|---|---|
| Initial `runtime_records` lesson snapshot | No row at `snapshot/<lessonID>` for a fresh synthetic lesson, confirmed by a transaction-local read before the production upsert. | The existing `INSERT ... ON CONFLICT(key) DO UPDATE SET value` callsite takes the INSERT-only path: exactly one runtime UDF event `INSERT(expected NEW)`; no UPDATE/DELETE UDF event. `key` is the controller-issued canonical key. `value` is the complete JSON serialization of the trusted initial `classroom.State`: `LessonID`, `BookID`, `StudentID`, `Config`, `Phase`, `GroupIdx`, `WordIdx`, `TtsSegIdx`, `RepeatCount`, `RepeatNudged`, `QuizQueue`, `QuizIdx`, `QuizSeq`, `AnswerStage`, `PendingText`, `InReteach`, `ReteachSeg`, `InReview`, `ReviewList`, `ReviewIdx`, `ReviewSeg`, `Consec`, `Judged`, `Mastered`, `ReteachN`, `FirstWrong`, `FinalWrong`, `Streak`, `StreakBest`, `AnswerMs`, `StartedAt`, `Paused`, and `Finished`. | Any caller-supplied state, noncanonical key, extra row, missing/changed JSON field, or conflict/update callback. The controller captures the exact typed baseline and canonical serialized value; no SQL input chooses IDs or state. |
| First-word teaching transition snapshot | The exact inserted row above, read and byte-compared in the same transaction before the upsert. A missing OLD row aborts before DML. | The production upsert takes the conflict-update path with the exact callback sequence: `INSERT(expected NEW)` followed by `UPDATE(expected OLD, expected NEW)`. `key` is unchanged; complete state changes only `Phase: show_word → tts_seg` and `TtsSegIdx: 0 → 1`. Expected OLD/NEW values are frozen canonical `json.Marshal` byte strings. | Missing OLD row, INSERT without following UPDATE, wrong/extra/reordered callbacks, or any other path/value change including progress, answer, identity, config, start time, map/slice contents, or another key. Client interruption causes no additional snapshot write. |
| Teacher-effect audit append | No OLD row; take the next database-assigned audit ID. | Insert one `audit_logs` row for only `classroom.say`, `classroom.show_word`, or `classroom.play_tts`: `TS` within the frozen run interval; `ActorType=""`; `ActorID="teacher_agent"`; `ActorRole="teacher_agent"`; `Tool` is the exact invoked allowlisted name; `Risk="low"`; `OK=true`; `Result="ok"`; `Args` is that tool's canonical JSON `{"bytes":N}` (`0<N<=512`); `DurationMs` in `1..60000`; `TraceID="lesson-<currentLessonID>"`. | Any audit update/delete/replace, extra append, student/user payload, speech/transcript/audio content, noncanonical actor/tool/trace, or out-of-range timestamp/summary/duration. Prior committed audit rows remain byte-identical forever. |
| Controller reset lesson row | One exact synthetic `lessons` OLD row, loaded under the exclusive transition permit. | Update only `ID: oldLessonID → nextCanonicalLessonID`. Every other persisted column is byte/value identical: `StudentID`, `BookID`, `Seq`, `Status`, `OpenAt`, `StartedAt`, `FinishedAt`, `BatchWordIDs`, `Phase`, `GroupIdx`, `WordIdx`, `RepeatCount`, `TtsSegIdx`, `QuizState`, `CumulativeIDs`, `Result`, and `StateUpdAt`. The new ID must be absent before the update. | Generic `Save`, insert/upsert, any non-ID column change, multiple/no matched rows, or a conflicting next ID. The lesson row is read back through the same guarded pool before admission reopens. |
| Controller reset snapshot key | Exact `snapshot/<oldLessonID>` row and its complete JSON value. `snapshot/<newLessonID>` must be absent. | In the same transaction, delete only the old key. Leave the new key absent. The next ordinary `Hub.Enter` must therefore create a fresh Room, call `Machine.Start`, emit `lesson_started`, and insert the new initial snapshot under the initial-snapshot contract above. This is how the second browser tests a second first entry rather than restoring the interrupted `tts_seg` state. | Any snapshot insert/upsert during reset, missing source row, preexisting destination row, any other snapshot key change, or a new-lesson snapshot before second `Hub.Enter`. Verify both keys absent after reset commit and before the second journey. |

The first snapshot's dynamic values (effective config and `StartedAt`) are not guessed or supplied by SQL callers: the controller obtains the trusted initial state from the bound `Room`, freezes a deep copy and its `json.Marshal` bytes, and authorizes exact byte equality. The transition command similarly carries the typed expected state generated by the single allowed Room transition. Reset does not synthesize a replacement state; it deletes the prior snapshot and the next ordinary `Hub.Enter` constructs the new Room's initial state and timestamp through production logic. No parse-and-normalize comparison is used: whitespace/order changes, duplicate keys, changed numeric representation, omitted/null fields, or serializer drift all fail closed and require a new reviewed contract. The same pinned Go serializer and struct version must produce the bytes being written.

`saveRuntimeContextLocked` currently compiles the upsert for both initial insert and state update. For the initial-insert mode, the controller verifies absence in the same explicit transaction before executing it; the row guard accepts only the exact INSERT event and the post-statement event ledger must be exactly `[INSERT]`. For update mode, the controller reads and byte-compares OLD in that transaction before executing the same upsert; SQLite's conflict path must produce exactly `[INSERT(expected NEW), UPDATE(expected OLD, expected NEW)]`. The INSERT callback on the conflict path is only an expected-new-value check; it is not proof that OLD existed or that the UPDATE happened. The guarded statement wrapper verifies the exact event sequence before COMMIT. A missing OLD row, an unexpected pure INSERT, missing UPDATE, duplicate/reordered event, or any other callback rolls back; no rowcount-only success decision is permitted. Each event is scoped to one connection, statement, context version, and permit so unrelated callbacks cannot satisfy the sequence.

Tool audit `ID` assignment is database-managed and is the only generated audit field. `TS` and `DurationMs` are bound to the invocation record captured before SQL; they are not free-form SQL arguments. For a confirmed rollback, only the documented alternate failure-audit contract in §2 may append a row under a fresh permit. No reset audit is generated.

The snapshot writer accepts a typed, controller-bound lesson operation, reads OLD in the same transaction, and derives NEW from the trusted `Room` transition; arbitrary caller-provided rows or JSON are invalid. Compare full canonical rows for the only allowed runtime key. The browser cannot choose lesson IDs, generation, runtime keys, or context version.

There are two distinct lease layers. The outer REST/WS/timer operation acquires a **generation operation lease** before its first lesson, ticket, or Room read and holds it through side effects, state publication, and response/frame completion; it prevents reset from completing and is not exposed to SQLite callbacks. Every top-level GORM query/operation acquires one **context-bound SQL permit** before loading the active context and holds it through prepare, callbacks, execution, and result close. An explicit transaction acquires one permit for its full lifetime; all statements, nested repository calls, triggers, commit/rollback, and result sets inside that transaction reuse that same permit rather than reacquiring it. If an OLD/NEW contract must change, the request first releases its ordinary SQL permit, then closes SQL admission and drains all prior SQL permits (not generation operation leases); only then it takes one exclusive transition permit, reads OLD in the transaction, validates the typed command, publishes the complete next context, performs DML, commits/readbacks, releases the permit, and reopens SQL admission. A request must never hold a context-bound SQL permit while waiting for that drain. This refines `docs/76`'s use of “ordinary lease”: the per-generation operation lease is intentionally not part of the SQL-context drain. Reset, initiated by the parent/controller and never by a request, first closes operation admission, drains all generation operation leases/effects, then performs the exclusive reset transaction. `callAgentTool`/snapshot writes must enter this sequence without recursively acquiring or draining their own permit.

Reset closes operation admission, drains the old generation, and in one controller-only transaction changes only the ID of the one synthetic `lessons` row and deletes only `snapshot/<oldID>`. It does not insert `snapshot/<newID>`. Verify commit, same-pool readback, both snapshot keys absent, and the complete table/object snapshot before reopening. The second journey then uses ordinary `Hub.Enter`; the absent new key selects the fresh-machine path (`Machine.Start` and `lesson_started`), which writes the new initial snapshot and enables the second three-audit first-entry oracle. Prior audit rows remain byte-identical; the second journey appends its own three rows under the new lesson trace. No completion marker, card mutation, extra lesson, or unrelated audit append is allowed. Any uncertain outcome is terminal and cannot create the next journey.

The controller binds an ordered, immutable `word_ids` vector together with student and book identity. Bind response and startup metadata must match all three values exactly. Reset metadata and the reset result must repeat the same ordered vector; a missing, reordered, added, removed, or substituted word is a terminal reset failure. The second browser journey must therefore use the same frozen lesson content under a new lesson ID and generation. This is a protocol consistency assertion; it does not make client- or response-supplied IDs authoritative for SQL writes.

## 4. Required evidence and review

The bind result, initial metadata, reset result, reset metadata, and second-journey binding must agree on the exact ordered fixture `word_ids`, student ID, and book ID. A reset may change only lesson ID and generation; any word-set drift is terminal and cannot be accepted as a successful reset.

CGO integration tests must prove snapshot transitions and exact tool-audit appends on every physical connection; deny every other table/key/tool/operation; preserve denylisted rows; and exercise interruption, late-result, and reset races. Inject failures before/after DML, audit insert, COMMIT, explicit rollback, and connection cleanup; verify the transaction outcome enum, the second-write permit requirement, `rolled_back_ok`, and that uncertain commit forbids every follow-up write (including `effectFailureLocked` snapshot persistence). The Playwright acceptance must run two start→first-audio→interrupt journeys in separate browser processes against one child process/database, with one reset between them. In each browser process it must cancel the active utterance, invoke the retained delayed completion callback, and assert there is no extra audio/caption or client-side advance before closing the page/socket. After reset, the second journey must assert that its observed lesson/generation and first audio/caption match the controller's new generation. Go races must separately prove stale server callbacks, tickets, and late results cannot affect the next lesson. The spec implements its browser assertions, but the isolated full matrix and cross-reset Go races remain NOT RUN/incomplete. Explicit completion/forbidden-tool probes run in a separate child process because any violation terminalizes the controller; they must leave non-audit rows unchanged and cannot be followed by reset or a passing journey.

The reset test must also take full snapshots immediately before and after reset: allow exactly the lesson primary-key change and deletion of `snapshot/<oldLessonID>`; assert `snapshot/<newLessonID>` remains absent until the second ordinary `Hub.Enter`. Then assert that Enter emits the fresh-entry `lesson_started` lifecycle, creates exactly the new initial snapshot from a fresh `Machine.Start` state (with a new `StartedAt`), and appends the three expected new-lesson audit rows in order. The second first-word click may alter only the two state paths listed in §3.1. Preserve all first-journey audit rows byte-for-byte and compare every non-ID persisted lesson field exactly across reset.

The snapshot-upsert regression must record actual UDF callback tuples per statement and prove the initial `[INSERT]` path, the transition `[INSERT, UPDATE]` path, and failure/rollback for update mode when OLD is absent, when only INSERT occurs, or when callbacks are missing, extra, duplicated, or reordered. Assert the row remains absent/unchanged after each rejected transaction; `RowsAffected` is insufficient evidence. A successful transition requires exact frozen OLD and NEW JSON bytes at the corresponding callback.

An integration assertion must independently verify the full five-event commit order in §2 for both journeys, and prove the new snapshot key remains absent after reset and before second Enter. The observation must come from the child-local commit ledger, not inferred from audit IDs or a final database diff.

## 5. Uncertain transaction terminal behavior

For `callAgentTool`, only a successful COMMIT is `committed`; a callback error plus successful explicit ROLLBACK is `rollback_confirmed`; begin/commit/rollback ambiguity and panic are `outcome_uncertain`. A failure audit may follow only `rollback_confirmed`, under a fresh guarded write permit. `outcome_uncertain` must not write a failure audit or classroom snapshot: retire the Room, cancel pending judgment work, emit `classroom_error` with `code=transaction_outcome_uncertain` and `retryable=false`, and reject further work. The browser must show a stop-and-return-to-course-list message and hide reconnect. For uncertainty during the initial Enter lifecycle, return a structured nonretryable API error that the WS client treats as terminal. Teacher/effect loops, Resume, event and timeout entrypoints, and post-settlement snapshot paths must all stop after retirement. The application uses a local `github.com/glebarez/go-sqlite` v1.21.2 fork that checks autocommit and rolls back any active SQLite transaction after a failed COMMIT. The regression verifies a deferred-FK failure leaves no audit or snapshot row on reuse of the single-connection pool. The Playwright test simulates a terminal `/enter` response during WS reauthorization and verifies no retry beyond the first backoff; this does not replace a real commit-ambiguity injection through the guarded pool. Current code implements these terminal fences; guarded-pool fault injection, per-connection permit enforcement, and the isolated browser matrix remain NOT RUN.

Architecture, backend, security, and test reviewers must approve this exact scope and reconcile conflicting wording in `docs/70`, `docs/74`, and `docs/76` before SQLite wiring. Test-binary/controller protocol, performance, and human classroom acceptance remain separate gates; this draft claims none of them passed.
