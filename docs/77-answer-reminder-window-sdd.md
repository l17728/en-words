# 答题提醒后的第二次时限：修复规格

## 场景与原因

最终测试等待答题时，第一次超时只提示学生继续尝试，仍保留同一题与文字草稿。`AnswerStage` 改变会在 `contextLocked` 更新回合并刷新 `phaseSince`；但提醒帧发出后，教师工具和话术处理仍可能占用 Room 锁。若处理耗尽完整答题时限，下一个计时 Tick 会立即判错，学生看到提醒后几乎没有第二次机会。完整首用浏览器旅程曾观察到提醒与重教相隔约 0.6 秒；同配置复跑通过，属于时序相关问题。

## 修复合同

`Room.Tick` 在 `wait_answer` 的第一次超时后先完成现有提醒广播与课堂状态保存；若仍为同题、`wait_answer`、`AnswerStage=1` 且 Room 未退休、交付仍可用，则在广播返回后将 `phaseSince` 设为当前时钟。保留 `contextLocked` 的回合身份变化，不重复发提醒，也不改变答题总次数。失败导致交付停用时不得悄悄判分；提交中的答案仍沿现有门处理。日志记录固定事件 `answer_reminder_window_started`，带 lesson_id、时限毫秒数，不写答案正文。

## 验收

Go 用 FakeClock 和可控 Client 在提醒发送后推进一个完整时限，先确认下一 Tick 不会提前判错、提醒帧仅一次；再推进至新时限边界，确认按既有规则推进。Playwright 专项用例覆盖提醒后草稿保留、输入可用与提交；完整首用旅程及时答题，不再承担等待提醒的专项职责。全量 Go 与两组浏览器旅程复验。架构、测试按这一行为和日志边界复核。

实施后记录：延迟客户端 Go 用例在修复前失败、修复后通过，且提醒帧仅一次；`go test -p 1 ./...` 全绿。核心模块覆盖率：`api` 82.3%、`classroom` 90.6%。隔离真实浏览器：提醒专项 1/1、首用完整旅程 1/1、教学中服务重启恢复 2/2。架构/后端复核确认同题、未退休、交付可用的门；日志事件仅含课次与时限。浏览器收到帧的物理确认不在此合同内。
