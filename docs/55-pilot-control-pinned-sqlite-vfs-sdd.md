# Pilot Control Pinned SQLite VFS SDD
## Status and scope
This is a required A0 design delta for the protected `operations.sqlite` store. It resolves the gap between the path-based CGO driver prototype in `server/internal/pilotcontrol` and the handle-relative filesystem contract in docs/43 §2.1. It is not implementation approval. Until the VFS and native Linux acceptance gates below pass, Pilot Control must not open the authoritative ledger or publish readiness.

### Implementation and execution status (2026-10-21)

The private pinned VFS is not implemented; `server/internal/pilotcontrol/sqlite.go` remains a path-based prototype. The only runtime tracer currently present is `TestPilotVFSRuntimeCandidateGeneration`, which emits noncanonical host candidates. The planned fixtures `sqlite3451-vfs-flags.golden.json`, `sqlite3451-unix-lock-trace.golden.json`, `sqlite3451-shm-lock-trace.golden.json`, and `sqlite3451-pager-delete-trace.golden.json` are absent. Planned tests named below—including `TestPinnedVFSFlagGolden`, `TestPinnedVFSUnixLockTrace`, `TestPinnedVFSShmLockTrace`, `TestPinnedVFSJournalDeletePagerTrace`, `TestVFSCallbackCases`, and the synthetic `TestVFSDelete*`/`TestVFSGenerationDeletePendingSynthetic` cases—are not implemented. Their commands and fixture contracts are future acceptance requirements, all currently **NOT RUN**. Manifest loading proves only the design inventory/hash, not callback execution. No production Pilot ledger/readiness or product route may be enabled until the golden fixtures, private VFS, all 80 behaviors, and native Linux filesystem matrix pass.
## Problem and decision
The current `mattn/go-sqlite3` `ConnectHook` installs a SQL authorizer, but SQLite still opens the database and sidecars from a pathname. `Lstat` plus a later SQLite open cannot prove that the actual main database, WAL, shared-memory, rollback-journal, lock, sync, rename, or delete operations use the previously validated filesystem object. A changed pathname or sidecar can therefore violate the protected-root identity contract even when the schema inventory is exact.
The production store will use a private SQLite VFS registered only by the Pilot Control binary. The VFS receives a pinned trusted-directory handle and opens every SQLite file relative to that handle with no-follow semantics. It reports the identity of the actual open handle (device, inode, mount ID, owner, group, mode, and link count); startup compares those values with the pinned identity and rejects any drift before SQL dispatch. WAL/SHM and rollback-journal files must remain on the same approved filesystem and under the same directory authority. All lock, shared-memory, sync, truncate, and delete operations use those retained handles. No path-based fallback is permitted.
The `database/sql` connection pool and per-connection authorizer remain above the VFS. VFS identity validation is a separate mandatory gate; schema validation and trigger authorization cannot substitute for it. VFS registration failure, unsupported file control, unrecognized SQLite open flags, identity mismatch, or sidecar escape fences the store and prevents readiness. The current path-based implementation remains an isolated driver experiment and must not be wired to A0 or product routes.
## Filesystem and SQLite callback contract
The SQLite ABI is pinned to the amalgamation embedded by `github.com/mattn/go-sqlite3 v1.14.22`: SQLite 3.45.1, source ID `2024-01-30 16:01:20 e876e51a0ed5c5b3126f52e532044363a014bc594cfefa87ffb5b82257cc467a`. Build and startup assert both `sqlite3_libversion()` and `sqlite3_sourceid()` against those values. A driver upgrade or system-SQLite build changes the ABI gate and requires a reviewed SDD delta plus a regenerated callback and crash matrix.
The launcher passes a pinned operations-root directory FD to the resident Reaper. The Reaper records its startup euid/egid, root directory identity `(dev,inode,mount_id)`, configured directory name and database basename from trusted read-only configuration. It opens the root with `openat2(RESOLVE_BENEATH|RESOLVE_NO_SYMLINKS|RESOLVE_NO_MAGICLINKS|RESOLVE_NO_XDEV)` from a separately pinned trusted anchor; root must be owned by that euid/egid, mode `0700`, same approved mount, and not a symlink. Every ancestor is opened and pinned without crossing a mount. Existing `operations.sqlite` must be regular, owned by the same euid/egid, mode `0600`, `nlink=1`, and on the root mount. The Reaper is the sole creator: it creates a missing main file with `openat2` beneath the retained root using `O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC`, mode `0600`, then `fstat`s it and syncs the parent. An existing file is opened without create and checked from the returned FD. SQLite never creates the main DB. Before the race barrier, Reaper opens (or exclusively creates) the main file once, verifies with `fstat`, and retains the identity; VFS never repeats creation. The VFS main `xOpen` must match that pinned identity. The DB file's initial verified identity is pinned for the service lifetime; pathname identity is rechecked against the FD before every namespace mutation and on every new connection. The trust boundary assumes the Reaper service UID and privileged host administrator are trusted; an adversary with the same euid can bypass DAC and is outside this VFS threat model. The run root is private to that dedicated UID, only Reaper code may mutate its namespace, and all VFS namespace mutations share one process-wide mutex. No untrusted Gateway/worker shares the Reaper euid.
Every control-root directory and regular file must be checked for `system.posix_acl_access` and `system.posix_acl_default` xattrs, in addition to owner/group/mode/link/mount identity, before SQLite registration, after every root/ancestor/main/sidecar open, and before namespace mutation. Read xattrs from pinned FDs; for a not-yet-opened name, use root-relative `fstatat(..., AT_SYMLINK_NOFOLLOW)`, open without following links, then inspect the returned FD. `ENODATA` means absent. A present ACL, any xattr query error (including EACCES, EOPNOTSUPP, or EIO), or identity race fails closed as `ipc_registry_corrupt` before application SQL dispatch; only ENODATA means absent. SQLite/VFS entry is prevented for root/ancestor preflight failures, while main/sidecar xOpen failures return `SQLITE_CANTOPEN`. Newly created sidecars are checked after creation because inherited ACLs can change effective access under umask 077. Synthetic injection covers file cases that the host filesystem cannot represent; native Linux cases use real access/default ACLs on directories and access ACLs on files. This carries docs/43 ?2.8 into the VFS root, database, WAL, SHM, and journal trust checks.

URI parsing is enabled only for the byte-exact URI `file:operations.sqlite?mode=rw&vfs=en_words_pilot_v1`; reject every other URI before `xFullPathname`. The negative vectors separately reject query reordering, percent-encoded path bytes, an authority, a fragment, extra query parameters, `mode=ro`, and a different VFS name before any filesystem callback. xOpen validates one object-role bit and a pinned caller-flag mask. The main DB must already exist because Reaper is the sole creator; `xOpen` opens it without CREATE or EXCLUSIVE. SQLite may request CREATE for a missing sidecar, and EXCLUSIVE only paired with CREATE, meaning create-if-absent. The caller-flag mask (READWRITE, URI, and explicitly selected mutex/result/cache bits) is recorded as numeric and symbolic values by a trace test compiled against the pinned SQLite source ID. The host `unix` VFS golden records only observed SQLite callback facts: URI, source ID, caller/request flags, role/name, `xOpen` flags, `pOutFlags`, and SQLite result. It does not assert filesystem syscalls or private-adapter behavior. An optional host collision trace may be `NOT RUN` if SQLite does not naturally issue the exact target `O_CREAT|O_EXCL`; this does not block callback-golden generation. The private VFS's EEXIST/reopen path is a separate required adapter acceptance case specified by docs/58 and mapped to `VFS-OPEN-SIDECAR-01`, `-02`, and `-07`. The fixture path is `server/internal/pilotcontrol/testdata/sqlite3451-vfs-flags.golden.json`; At present, `TestPinnedVFSFlagGolden` and `sqlite3451-vfs-flags.golden.json` are planned but not implemented/present; `TestPilotVFSRuntimeCandidateGeneration` produces noncanonical host candidates only. Add an exact-hash golden comparison test and reviewed fixture after the evidence-layer SDD/manifest synchronization; until then callback-golden acceptance is `NOT RUN` and private-VFS implementation approval is blocked. In that future gate, `-update` is permitted only during an explicitly reviewed SQLite ABI upgrade. A missing fixture or source-ID mismatch remains `NOT RUN`, never PASS. Reject all unlisted bits, role combinations, READONLY, DELETEONCLOSE, temp/transient DBs, subjournal and super-journal. SHM is not an xOpen object; `xShmMap` derives its name only from the validated main-file token. `PRAGMA temp_store=MEMORY` is set and read back before application statements. A NULL temporary filename returns SQLITE_CANTOPEN and leaves readiness zero or fences an already-ready store; no default VFS fallback is allowed. WAL/journal/SHM sidecars are created under the pinned root with O_CREAT|O_EXCL|O_NOFOLLOW|O_CLOEXEC, mode 0600, then checked for regular type, owner, nlink=1 and mount. Retain each actual (dev,inode) until close. Each registry row is `{name,generation,dev,inode,open_fd_refs,shm_map_refs,state}`. xDelete removes the row in its critical section only if both reference counts are zero; otherwise it unlinks the verified name, records `delete_pending`, and rejects same-name open/create with SQLITE_BUSY until the final xClose/xShmUnmap drains both counts and reaps the tombstone. Only then may the next generation be published. All sidecar `xDelete` operations hold the process-wide namespace mutex continuously from the `fstatat(rootFD,name,AT_SYMLINK_NOFOLLOW)` identity comparison through `unlinkat` and directory `fsync`; VFS creates, reopens and deletes use that same mutex and consult the sidecar-generation registry. Registry reference counts include every per-connection xOpen handle and every active SHM mapping, including the callback caller own handle. The root is writable only by the trusted Reaper UID, and no untrusted same-euid process is in scope, so no external namespace writer can replace a name inside this critical section. The deterministic fault test pauses after `fstatat` and before `unlinkat`, attempts replacement through a second process running under an untrusted UID, and proves it cannot mutate the `0700` root; an in-process test actor must block on the namespace mutex. If a replacement or identity mismatch is observed, do not unlink and fence. No xRename callback is implemented; reject rename requests unless a separately reviewed SQLite contract proves one is required.
The VFS callback ABI is pinned to SQLite 3.45.1. `sqlite3_vfs` iVersion=2: implement `xOpen/xDelete/xAccess/xFullPathname/xRandomness/xSleep/xCurrentTime/xGetLastError/xCurrentTimeInt64`; `xDlOpen/xDlSym/xDlClose/xDlError` are NULL and extension loading is disabled; v3 `xSetSystemCall/xGetSystemCall/xNextSystemCall` are absent. `sqlite3_io_methods` iVersion=2: implement `xClose/xRead/xWrite/xTruncate/xSync/xFileSize/xLock/xUnlock/xCheckReservedLock/xFileControl/xSectorSize/xDeviceCharacteristics/xShmMap/xShmLock/xShmBarrier/xShmUnmap`; v3 `xFetch/xUnfetch` are NULL. The exact byte-string returned by `xFullPathname` for the allowlisted URI is `operations.sqlite`; SQLite treats it only as the VFS name token, and the VFS must never pass it to a cwd/path-based OS open. `xSectorSize` returns 4096 and `xDeviceCharacteristics` returns 0; both return values have exact callback inventory assertions. `xFileControl` supports only `SQLITE_FCNTL_VFS_POINTER` and `SQLITE_FCNTL_LOCKSTATE`; unknown controls return `SQLITE_NOTFOUND`. Extension loading is disabled and no callback delegates filesystem operations to the default file VFS. `xRead` zero-fills unread bytes and returns `SQLITE_IOERR_SHORT_READ` on EOF. `xSync` maps `SQLITE_SYNC_DATAONLY` to `fdatasync`, other sync flags to `fsync`. `xShmUnmap(deleteFlag=1)` first unmaps this connection and returns SQLITE_OK when another process still holds the lifecycle lock; it releases this connection shared lifecycle lock and retains the SHM file. The lifecycle lock protocol below gates deletion.

All paths acquire locks in this order: per-inode generation-registry mutex, then lifecycle OFD lock, then process-wide namespace mutex. Release in reverse order; no code may acquire an earlier lock while holding a later one. `xClose` may take the registry mutex only after releasing its SQLite byte locks; the callback race tests assert this order under `-race` and across processes.

The VFS object is registered once and immutable after registration. `xDlOpen` is disabled for the private VFS. `xRandomness`, clock and sleep operations may delegate only to OS primitives and never to the default file VFS. Any SQLite callback not listed or not covered by the exact SQLite version's ABI is rejected at build/test time rather than delegated to a default VFS.
## Initialization, readiness, and test oracles
The launcher pin and ownership check precede SQLite registration. Register a uniquely named private VFS; open only with the exact single URI allowlist above, then use `SQLITE_FCNTL_VFS_POINTER` on every physical connection to prove the selected VFS pointer is the expected registered object; failure cannot fall back to the platform VFS. For a new database, Reaper creates and pins the main file before SQLite starts; the VFS then opens that existing inode. Initialize WAL and the exact reviewed DDL/seeds in one protected transaction, sync the DB and directory, close, then reopen in `mode=rw` through the same VFS under a validation-only authorizer that permits schema/invariant reads and denies writes; verify the pinned schema/invariants before ready. This avoids relying on read-only WAL startup, which requires extant or creatable WAL/SHM sidecars or immutable mode. A crash before initialization COMMIT leaves no partial schema/seed rows; the next open marks an empty/incomplete database `initialization_incomplete`, quarantines it, and does not silently reseed. A crash after COMMIT but before readiness may reopen only if exact schema and invariants validate. Existing DB startup follows the same VFS open and validation-only authorizer in read/write mode. Every pool connection repeats actual-handle checks before authorizer installation; readiness publishes only after the complete fixed pool is warm. `xShmMap` derives `operations.sqlite-shm` only from the already validated main-file token and retained main-file object; callers cannot supply a separate SHM path. The production connection mode is read/write only, so SHM is opened/created read-write and sized only after the root/identity check. The exact DDL remains subject to the independent manifest/review gate.
Tests distinguish three failure classes. (1) Root/VFS/identity rejection before database initialization: a synchronized observer stays `generation=0, ready=false`; the application-dispatch wrapper count stays zero. The positive control initializes, becomes ready, then executes one marked public API probe; the wrapper count becomes exactly one. (2) DDL/seed initialization failure: raw SQLite startup statements may run, but application-dispatch count remains zero, readiness stays at generation zero, the init transaction rolls back, and reopen classifies the database as incomplete/quarantined with no partial schema or seed rows. (3) Failure after readiness: the current call returns an error and never reports success; the injected errno and SQLite extended code are observed; the store transitions once from ready generation 1 to fenced generation 2; later admissions reject; reopen checks invariants when recovery permits. The application counter increments only in the public store-operation wrapper immediately before application transaction dispatch. Separate raw SQLite trace telemetry counts all statements and tags them `startup`, `preflight`, `init`, or `app`; it is diagnostic, not the zero-dispatch oracle.
Crash/reopen tests kill a child process at named barriers: after exclusive main-file creation but before WAL setup; after WAL setup but before initialization; after each DDL statement; after seeds but before COMMIT; immediately after COMMIT but before ready publication; after a runtime transaction COMMIT succeeds but before its response/ACK is sent; and after an acknowledged runtime transaction. Before COMMIT, reopen must classify the database as incomplete/quarantined without partial schema or seed rows. After COMMIT, it may become ready only after exact schema/invariant validation. An acknowledged runtime effect appears exactly once. A barrier not proven reached is `NOT RUN`, never PASS. The test observer exposes only the readiness generation/state, application-dispatch count, and raw trace categories. Each DDL barrier is keyed to the stable statement ID and hash in `schema_inventory_v3.json`; tests are generated from that manifest and fail if an ID is missing or duplicated. For both crash cases (after COMMIT/before response and after acknowledged response), reopen replays the same operation/receipt key and asserts exactly one durable receipt and one effect. Barriers synchronize every race; sleeps are not accepted as evidence.

| Runtime open/read/write/access/truncate/lock/sync/delete/close/SHM/file-control error | Callback adapter after ready during a named protected operation | Each callback returns its specified SQLite error; any ambiguous durability/identity failure fences exactly once (ready generation 1-to-fenced generation 2); admissions fail and reopen invariants are checked. Ordinary BUSY and deferred SHM deletion do not fence |
| Concurrent open, WAL, pool churn, close | Named barriers, no sleeps | No duplicate writer/identity state; every handle stays pinned; close is single-owner and race-clean |
Mount-crossing acceptance is PASS only when the provisioned runner successfully creates and verifies distinct mounts; EPERM, absent user namespaces, or missing privileges are `NOT RUN`, never a passing fail-closed case.
## Native acceptance
Implement the first production adapter for Linux amd64 and arm64. Tests compare VFS-reported identities with independently pinned `openat2`/`statx` handles. Each self-hosted runner must record kernel, architecture, SQLite source/version, Go version, filesystem, mount identity, cgroup/privilege preflight, and exact source hashes. Required matrix: amd64/ext4, amd64/XFS, arm64/ext4, arm64/XFS, each with normal, race and coverage runs. Commands: `go test -tags=pilot_e2e ./internal/pilotcontrol -count=1`; `go test -race -tags=pilot_e2e ./internal/pilotcontrol -count=1`; `go test -coverprofile=pilotcontrol.cover -tags=pilot_e2e ./internal/pilotcontrol -count=1`; and `go vet -tags=pilot_e2e ./internal/pilotcontrol`. Add tagged-package and full `go test ./...` runs after the focused matrix. `pilotcontrol` unfiltered statement coverage must reach 80%; path trust, VFS open/delete, WAL SHM, lock, and store fence functions must each reach 90%. Every unavailable host/filesystem/privilege row is recorded `NOT RUN` with preflight output, not skipped as PASS. Windows remains unsupported until a separately reviewed VFS implements and tests volume/file-index and DACL identity semantics.
## Exit criteria
Architecture, backend, security, and test reviewers approve this exact SDD hash before the VFS implementation begins. A Go VFS bridge may be evaluated, but its API, licensing, callback completeness, exact VFS-pointer assertion, and ability to retain real Linux handles must be audited and pinned before adoption; the existence of a Go VFS interface is not itself a security approval. SQLite VFS callbacks are defined by the upstream [SQLite VFS API](https://www.sqlite.org/c3ref/vfs.html) and [file I/O methods](https://www.sqlite.org/c3ref/io_methods.html); implementation must map those callbacks to the contract above without undocumented rename semantics. Product wiring remains blocked until both native Linux architectures pass the full matrix, package/function coverage gates in docs/54 pass, and review findings converge to zero. The logger and RunRoot acceptance gates remain independent and are not waived by a passing VFS.
