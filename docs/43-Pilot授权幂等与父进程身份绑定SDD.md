# Pilot 授权幂等与父进程身份绑定 SDD

**状态：** Draft，2026-10-19。此阶段只设计，不接入产品路由或课堂副作用。实现前须完成架构、安全、后端和测试评审并收敛阻断项。

## 1. 背景与目标

`docs/42-Pilot隔离运行监督器SDD.md` 的 peer 层证明 grant 只在单连接消费；它不能防止相同签名请求从新连接重放。Linux worker 也只检查继承 pidfd 是否存活，尚未验证 pidfd 指向 bootstrap 声明的 Gateway。此设计定义两个独立授权门：跨连接/并发请求幂等，以及 Linux 父进程句柄身份绑定。

目标是保证一个 run 内只有一个请求 owner 可以进入操作入口；完全相同的重试等待或返回原结果，冲突请求失败关闭；所有可产生持久副作用的操作在持久化边界也使用同一个幂等键。Linux worker 必须证明继承的 pidfd 指向其真实直接父进程。任何身份、缓存或持久化状态不确定都拒绝操作，隔离课堂保持关闭。

本SDD中的`ipc_registry_*`、`ipc_request_conflict`、`ipc_operation_abandoned`、`ipc_result_indeterminate`、`ipc_launcher_failed`和`ipc_operation_target_invalid`属于Gateway/HostReaper控制面错误；它们与docs/42 §3列出的六种OS-authenticated IPC peer/wire错误分层，不在worker IPC wire上互换或伪造。

## 2. 请求注册表契约

### 2.1 持久对象归属与身份

`docs/42` 的 run root、catalog 和 case SQLite DB 都是 run-local；abandoned root 永不重开。跨run的协调账本必须位于经OS验证的固定私有 `pilot-control/operations.sqlite`，与 `pilot-runs/<run_epoch>/` 平级但不在其下，由独立常驻 PilotHostReaper 创建并持有生命周期；Gateway经本机受保护IPC读写。账本保存幂等键、规范digest、状态、run/generation、结果引用和短期规范响应，不保存case内容、音频、密钥或selector明文。采用SQLite WAL+FULL同步、单写者文件锁、父目录同步和严格schema验证；文件身份/事务不确定或损坏→`ipc_registry_corrupt`并停止pilot。清理run root不删除ledger；业务对象删除后只保留不可复用的key/digest/status tombstone。

`pilot-control`必须复用docs/42 §2的OS路径保护强度：从配置的trusted anchor handle逐级pin所有祖先，拒绝symlink/reparse、hardlink、跨设备/挂载点及identity drift。POSIX owner必须等于Reaper启动时的`geteuid()`且该UID不得变化，group必须等于配置的Reaper service GID；目录`0700`、文件`0600`、umask `077`，逐项核验owner/group/mode/nlink/dev/inode/mount ID。Windows目录/文件owner必须是Reaper service account SID或SYSTEM；关闭DACL继承，DACL精确为Reaper service SID最小必要访问和SYSTEM full-control两条allow ACE，不得有其他allow/deny ACE；目录权限只含list/add child/read attributes/synchronize及维护ACL所需权，文件权限只含read/write/delete/read-control/synchronize，owner/DACL/volume/file index须读回核验。Gateway/worker仅经Reaper IPC访问账本，不得打开control root。`operations.sqlite`、alias文件、keyring均以handle相对操作；替换/链接/权限放宽→`ipc_registry_corrupt`，不得创建新Gateway。

`operations.sqlite`必须使用经专项实现和评审的PilotControl SQLite VFS/driver：VFS的`xOpen`必须相对已pin目录handle打开主库及WAL/SHM/journal，并能从SQLite正在使用的真实OS file handle返回、核对device/inode/mount ID或Windows volume/file index；主库与副文件所有读写、锁、Sync、rename/delete均走同一VFS handle合同。禁止使用docs/42注明无法证明实际SQLite handle身份的`glebarez/sqlite`路径实现该ledger，也不得以“打开前stat + SQLite canonical path”代替。若VFS不能在目标OS上证明实际handle身份，control ledger不能打开，唯一映射`ipc_registry_corrupt`，Pilot功能不启动。原生Linux/Windows测试必须比较VFS报告的真实handle identity与pin identity，并注入替换/硬链接/reparse竞态断言零SQL dispatch。

HMAC key以Reaper身份保护的OS credential store/DPAPI或等价机制包装；磁盘keyring仅存加密材料，不存明文principal key。包装key轮换采用`write new version→fsync→atomic rename→fsync parent→readback verify→commit active key version`；任一步失败不切换active version并返回`ipc_registry_corrupt`。旧包装key只有在所有对应HMAC key均成功重包且readback验证后才可退役；HMAC key及principal alias仍依tombstone寿命保留。

归属固定如下：HTTP session/idempotency映射由Gateway持有并按`docs/42`的`session_key_hash`作用域；跨连接request registry也由Gateway持有，故worker同run重启时缓存仍在；跨run business ledger位于上述control root；lesson、receipt、case members与case DB位于各自run-local case root，case abandon后不导入新root；catalog只描述同一run的case/worker状态，不成为跨run业务数据仓库。ledger与case DB/catalog不是单一事务，必须按本节逐操作intent/saga协调，不得声称跨存储原子提交。

`principal_ref`是稳定账户身份的HMAC pseudonym。输入必须按版本化、域分离、长度前缀的规范二进制编码：`ASCII("en-words-principal-v1\0") || U32BE(len(tenant_id)) || tenant_id || U32BE(len(immutable_user_id)) || immutable_user_id`；两字段是认证服务提供的opaque canonical bytes，限长且不得由HTTP/body传入。认证服务必须保证immutable account ID不可回收复用；账号恢复沿用原ID，真正新账号必须分配新ID，否则禁止跨run幂等。再计算`HMAC-SHA256(K_principal_vN, encoded_identity)`。control root保存带版本的key ring和principal alias表；每次认证用所有仍保留的版本查找既有alias，已存在账户继续使用其首次创建的canonical principal_ref，新账户只用当前写版本创建alias。HMAC key不能因常规轮换而退役；只有其覆盖的全部business-key tombstone依保留策略永久删除后才能销毁。常规轮换只轮换包装/加密key，不改HMAC key字节；旧HMAC key或alias丢失时拒绝新建principal与跨run操作，返回`ipc_registry_corrupt`，不得形成新身份空间。身份撤权/角色变更仍在每次HTTP请求前实时验证，未授权者不得因命中缓存读取旧结果。session撤销不改变账户pseudonym，但撤销后不允许恢复响应。匿名主体只得到session作用域pseudonym，不获得跨session/run业务幂等。日志不写原始账号或完整pseudonym。

### Pilot product admission identity-resolution amendment (2026-10-21)

This amendment supersedes only the storage and invocation wording for principal aliases in §2.1 as used by the docs/50–52 pilot product flow. The protected canonical alias registry is the immutable `pilot_principal_aliases` table inside `operations.sqlite`; there is no separate alias sidecar file. It inherits the same pinned SQLite VFS, handle identity checks, access policy, schema allowlist, and per-connection `foreign_keys=ON` / `recursive_triggers=ON` checks as the ledger. The wrapped HMAC keyring remains a separate protected file/OS credential-store object as specified above.

A resident `PilotIdentityResolver` runs under the Reaper service identity before the product launcher/API accepts pilot requests. It validates the web service's short-lived signed admission containing canonical opaque `(tenant_id, immutable_user_id)` from authenticated server context, then resolves the stable principal using the Reaper-only HMAC keyring and alias table. It exposes no HMAC key and accepts no caller-supplied `principal_ref`. Alias creation is an independent `BEGIN IMMEDIATE` transaction in `operations.sqlite`, committed before launcher journal lookup or any business operation. A crash after alias commit may leave an unused alias; this is safe and the next request reuses it. Concurrent first-use requests serialize to one canonical alias. An existing alias always wins across wrapping-key rotation. A missing key version or alias integrity failure is `ipc_registry_corrupt`; before creating an alias where no mapping is found, the resolver checks all candidate principal refs against permanent business-operation tombstones and treats any matching tombstone as a missing-alias corruption, never as a new account. It discards `immutable_user_id` after resolution and never logs it.

The resident process is `PilotControlReaper`, the sole process allowed to open `operations.sqlite`, hold its OS single-writer lock, or perform SQLite transactions. `PilotIdentityResolver` is a command/module inside that resident service, not a competing process or database writer. Per-run Reaper processes never open the ledger or take its OS lock; they send typed authenticated requests to the resident control service, which owns and commits each complete ledger transaction. Launcher calls `ResolvePrincipal` before taking its own journal lock or looking up any key. All identity resolution/verification IPC occurs outside a business-ledger transaction; no caller may hold the ledger writer or journal mutex while waiting for resolver RPC. The resident writer serializes alias and business transactions on its one controlled connection; SQLite transactions, rather than multiple process locks, provide transaction serialization.

The resolver request is one canonical-CBOR `SOCK_SEQPACKET` frame `[version=1, request_nonce_16, admission_sha256_32, signed_admission_bytes]`; this admission-resolution endpoint accepts only the configured launcher service identity, validated by pinned socket ownership, `SO_PEERCRED`, and per-packet `SCM_CREDENTIALS`. The reply is `[version=1, request_nonce_16, admission_sha256_32, tenant_id, principal_ref_32, session_key_hash_32, role, expires_at_unix_seconds, signature_64]`, signed Ed25519 by a resolver-only key. The launcher pins the resolver public key and accepts only the exact outstanding nonce and admission digest, with expiry no later than five seconds or the admission expiry, whichever is earlier. Each request has a 500 ms deadline; timeout, channel ambiguity, or invalid reply closes/fences the resolver channel and yields `pilot_unavailable` before journal lookup/spawn. This endpoint is never used by per-run Reapers. Per-run Reapers use a separate typed ledger-RPC endpoint; the resident service admits only the exact registered child process identity (PID plus start-time, PID-namespace, UID, and cgroup tuple) bound to that generation and run epoch, and checks it on every packet. Reused UID alone is insufficient; stale generations, replaced processes, and mismatched tuples are rejected before dispatch. No nested resolver call is permitted inside an open ledger transaction.

The resident resolver is control-plane infrastructure, not a per-run child and not a business run. The launcher resolves and validates each fresh admission before its journal mutex, journal/key lookup, queueing, spawn, status projection, or close. Alias/key corruption fails as `ipc_registry_corrupt`; timeout/unavailable service fails as `pilot_unavailable`, both with no journal lookup or spawn. A public client cannot set or obtain another subject's resolution. New identities under an active HMAC version, same-account login after rotation, concurrent alias creation, missing old-key version, missing alias with an existing tombstone, and resolver-unavailable cases are locked by named tests.

### 2.2 Request registry 与业务账本

Gateway常驻request registry以`(run_epoch, request_id)`为键，绑定`principal_ref/scope/digest`。Gateway在worker重启时仍保留该registry；启动新worker前从control ledger与run catalog重建同run已完成条目。completed响应在返回HTTP前先持久化；pending在worker死亡后通过操作journal/case DB/catalog裁决，无法证明成功/未执行时变为`indeterminate`；owner panic同样变indeterminate。只读receipt也缓存原规范响应，避免重试返回不同快照。worker不持有HTTP幂等owner状态。

跨session/跨run的操作另用客户端在首次发送前生成并持久保存的随机`business_operation_id`（至少128 bit）；所有网络重试和Gateway重启都复用。每个操作先按固定versioned typed schema验证；拒绝未知/重复字段、非法UTF-8、非有限数值和超长payload，再以RFC 8785 canonical JSON编码。`canonical_payload_digest=SHA256(ASCII("en-words-business-operation-v1\0") || U32BE(schema_version) || U32BE(len(operation_kind)) || operation_kind || canonical_json_bytes)`；同一schema版本内字段含义/默认值不得漂移，升级必须新增schema version并纳入digest。持久账本唯一键为`(principal_ref,business_operation_id)`，首条记录不可变绑定`operation_kind/schema_version/canonical_payload_digest/first_run_epoch/request_id/state/result_ref`。相同key但kind/schema/digest不同→`ipc_request_conflict`；相同key/kind/schema/digest按操作表裁决。Run-local结果在新epoch一律不返回；同key用于防止暗中重复创建，并返回`ipc_operation_abandoned`。账本的`principal_ref`先由Gateway认证身份产生，不能由HTTP/body覆盖。

| 状态 | 输入 | 行为 |
|---|---|---|
| 不存在 | 已验证且未过期 grant | 原子创建 `pending` 记录并返回唯一 owner token；仅该 owner 可进入 dispatch |
| `pending` | 指纹完全相同的重试 | 不 dispatch；等待 owner 结果，受调用 deadline/context 限制 |
| `completed` | 指纹完全相同的重试 | 返回缓存的规范响应；不重新调用 Supervisor/store |
| 任意已有状态 | principal、scope 或 digest 不匹配 | 返回稳定 `ipc_request_conflict`；不泄露原请求数据、不执行副作用 |
| `indeterminate` | 任意重试 | 返回稳定 `ipc_result_indeterminate`，要求业务层对账；绝不再次 dispatch |
| 容量已满/状态损坏 | 新请求或重试 | 失败关闭；禁止通过淘汰 live-run 记录腾出容量 |

owner 必须在任何 handler 或 Supervisor 调用前取得；owner 完成只能提交一次。响应缓存保存有界、规范编码的业务结果，不保存 grant、私钥、音频或原始凭据。实现初始上限固定为每run 4,096 entries、每request最多16个waiters、单结果64 KiB、每run结果缓存总计16 MiB；跨run业务tombstone最多全局1,000,000条且每principal最多100,000条。每个上限的N+1请求返回`ipc_registry_full`，不得淘汰live-run记录或business-key tombstone；业务对象结果可按保留策略擦除，只保留唯一键、kind/schema/digest和terminal status。tombstone达到容量后现有键仍可查询，但不接受任何新增业务key，直至人工批准的迁移提高容量并完成审计；不得TTL过期或哈希压缩为可碰撞键。completed/indeterminate entry保留到run结束，避免TTL到期后旧请求在同一run被再次执行。评审后若调小上限，必须同步修改契约与N/N+1测试。

Ledger和case catalog/DB跨文件时不构成SQLite单事务；所有操作采用先写ledger intent、再写case-local operation marker和effect、最后回写ledger result的saga。任何边界不确定均indeterminate，不能盲目重复。

| 操作 | durable intent 与提交 | 崩溃恢复规则 |
|---|---|---|
| 所有业务操作的共同前置条件 | 首个ledger事务创建`prepared`记录；唯一owner必须在任何handler、catalog intent、spawn、case DB写入或其他effect前，以CAS提交`prepared→executing`并固定`owner_generation`。未提交executing不得触碰副作用 | `prepared`说明尚未授权dispatch；owner crash在CAS前可安全按无effect证据abandon，CAS后按operation marker/cleanup证据裁决；不能证明时indeterminate |
| Create case root/member (run-local object) | Reaper durably records `prepared -> executing`, owner generation, and a single-use token, then dispatches a typed request; worker Supervisor alone generates the selector and creates catalog/root/members under docs42 locks. Reaper only verifies returned evidence and commits the durable receipt/terminal state. | A crash is completed only from durable Supervisor evidence; proven no-effect may be abandoned; otherwise indeterminate. Cross-epoch responses never expose the prior selector. |
| Create lesson（case-local DB对象） | lesson row只存在于case DB；ledger先写`prepared`并CAS到`executing`，再在case DB事务中写lesson、business_operation_id marker及结果，随后ledger置completed | Same-run marker restores the result. After run abandonment preserve its proven ledger terminal state; cross-epoch business-key lookup returns ipc_operation_abandoned without exposing lesson data.|
| Start lesson（case-local状态） | 权威记录分层：control ledger记录业务operation状态，run catalog记录worker generation/identity/READY，case DB记录lesson业务状态。按`not_started→start_pending→worker_ready→active`推进：ledger先CAS至`executing`再spawn；worker READY并完成peer校验后，先durable写catalog，再由case DB事务写`active`及operation marker，最后ledger记录规范结果并应答 | READY前lesson不得显示active或接受答题。Gateway仍存活时若case marker存在而ledger未完成，按marker恢复ledger结果；marker不存在且执行状态可证未发生时可重试；无法证明时indeterminate并关闭worker。Gateway死亡后该run只能abandon，不能跨epoch把lesson恢复为active |
| Start worker（物理进程） | 独立operation kind；先ledger CAS至`executing`，再写worker generation/endpoint/intent；平台process containment在worker执行任何代码前生效 | Gateway存活时以PID/start identity及catalog恢复。Gateway死亡时独立HostReaper终止并清空整个run containment，确认旧generation退出后才可启动新run；spawn到identity写入间若不能由containment确认退出，则operation永久indeterminate、pilot停用，不自动spawn |
| Case-local cleanup | Reaper durably claims the operation and dispatches a typed request to the owning worker; worker Supervisor alone takes the stable case lock and performs quarantine, fixed-member deletion, catalog tombstone, and operation evidence. Reaper may only read-verify evidence and commit the receipt/terminal state. | Supervisor tombstone plus matching identity evidence permits completed; exact intact inventory with no marker permits no-effect abandoned; partial, conflicting, or unknown state is indeterminate. Reaper never unlinks case members. |
| Receipt read | ledger先写`prepared`并CAS至`executing`，再在授权case DB内固定读取并缓存规范响应 | 同一run由Gateway registry恢复原响应；run abandoned后不得把旧case结果返回到新root，返回`ipc_operation_abandoned` |

control ledger、case DB与catalog之间以durable intent和operation marker构成saga，不存在跨DB原子事务。Gateway活着时崩溃恢复按operation marker reconciliation；Gateway死亡则Reaper按§3顺序持久化`terminating`、fence旧Gateway generation、杀停containment并取得empty证据，再按§2.3逐operation生成/持久化receipt并CAS终结；最后独立run-terminal事务核验无pending operation及receipt齐备后提交run状态和lease。任何operation不可判定时保留terminating与lease，不做原子批量abandon。run清理另有`cleanup_state=not_required|pending|complete|retained|indeterminate`：只有containment已empty且run-local对象按文件身份清理完成，或经核验可安全保留在隔离旧root，才允许新run。`retained`必须满足：所有旧child已empty、旧root所有handles已关闭、Reaper撤销Gateway/worker对该root的读写ACL并验证DACL/mode、root路径及文件identity被control ledger永久登记为不可重开；新run使用新随机epoch及CREATE_NEW路径。任何ACL撤销/identity核验失败、清理失败且不能安全隔离、或control root不确定时禁止以新key绕过。`ipc_operation_abandoned`只给稳定错误码和不含旧selector/业务数据的“需确认后新建”提示；用户确认不能绕过清理门。跨epoch不返回旧case selector、lesson、receipt或worker响应；旧business key只能返回`ipc_operation_abandoned`，明确要求用户确认新操作后使用新key。completed响应结果可归档，但business key/digest/terminal status tombstone必须与账号身份生命周期同寿命保留，不能过期回收复用。

### 2.3 Ledger 持久状态机与操作终态

本节中的账本状态是唯一持久状态；表格中的 `start_pending`、`worker_ready` 是 lesson/catalog 投影，不是 business ledger 状态。每个业务键只能沿 `prepared → executing → completed`、`prepared → abandoned`、`prepared|executing → indeterminate`、`executing → abandoned` 转移；`completed`、`abandoned`、`indeterminate` 均为不可逆 terminal 状态。创建 `prepared` 时同一事务写入不可变键、digest、首次 run、request、operation kind/schema 及容量计数；owner claim必须在任何handler或副作用前以compare-and-swap提交`prepared→executing`并固定`owner_generation`。因此`prepared→completed`永不合法。只有持久effect marker证明effect已提交才允许`executing→completed`；只有证明effect从未发生且资源已清理才允许`prepared|executing→abandoned`；其余不确定统一为`indeterminate`，绝不因kill/reap把它改成`abandoned`。

跨存储证据使用不可变 `OperationEvidenceReceipt`，不声称case DB、文件系统与control ledger之间有原子事务。receipt固定包含`business_operation_id/principal_ref/operation_kind/schema_version/payload_digest/first_run_epoch/owner_generation/evidence_sources/outcome/evidence_version`，prepared从未claim的operation以`owner_generation=0`表示。`evidence_sources`是typed source数组，按`source_kind`再按`source_identity_digest`字节序排序、拒绝重复项；每项包含`source_kind/source_identity_digest/evidence_payload_digest/evidence_digest`，其中`evidence_digest=SHA256(ASCII("en-words-evidence-item-v1\0") || deterministic_CBOR([source_kind,source_identity_digest,evidence_payload_digest]))`。source identity digest定义为`SHA256(ASCII("en-words-evidence-source-v1\0") || deterministic_CBOR([source_kind, platform_identity_fields]))`；receipt digest定义为`SHA256(ASCII("en-words-operation-evidence-v1\0") || deterministic_CBOR(receipt_fields_without_receipt_id_or_digest))`，`receipt_id`即该digest的小写hex。deterministic CBOR按RFC 8949 §4.2，数组字段顺序按本SDD列出，map key按规范排序，整数用最短编码，拒绝重复key、非整数浮点、非UTF-8 run ledger 另有 `run_state=active|terminating|containment_empty|abandoned` 与 `cleanup_state=not_required|pending|complete|retained|indeterminate`。合法转移为 `active→terminating→containment_empty→abandoned`；cleanup 只能由 `pending` 到 `complete|retained|indeterminate`。run terminal严格分两阶段。旧Gateway generation fence且containment empty后，Reaper逐操作核验source、按(outcome)生成immutable receipt并durable写入，再以对应操作CAS终结；每步可崩溃重试，同receipt幂等。仅当所有operation均为completed/abandoned且cleanup_state为complete|retained时，才可进入最终run-terminal事务。该单个SQLite transaction只核验该run无prepared/executing/indeterminate operation、所需receipts均已持久且匹配、empty evidence及cleanup状态满足条件，然后将run置`abandoned`并保存reaper generation与lease-release marker；它不直接生成receipt或改写operation状态。任一receipt缺失/冲突、旧Gateway未fence、containment未empty或存在未决CAS时禁止lease释放。任何operation或cleanup进入indeterminate时，run保持terminating、cleanup_state=indeterminate且lease永久占用；只有cleanup_state=complete|retained且最终事务durable commit后才释放全局run lease。崩溃在 empty evidence 前保持 `terminating`；崩溃在 evidence 与事务之间重做 containment identity/empty 核验；崩溃在事务后 lease 已释放。新 CreateRun 先以同一个 ledger writer 锁检查前一事务和唯一 lease，再分配 epoch，故没有可观察的“旧run未收敛但新run已打开”窗口。cleanup失败且可安全隔离记 `retained`，ACL或identity不能证明安全则记 `indeterminate` 并永久关闭 pilot。

### 2.4 Gateway–Reaper control IPC 合同

`CreatePinnedCaseRoot` and `ExecutePinnedCleanup` are allowlisted typed IPC actions dispatched by Reaper to the worker Supervisor; they are not Reaper filesystem operations. The Supervisor owns selector generation, case locks, catalog/member mutation, quarantine, deletion, and tombstone evidence; Reaper owns the durable operation ledger and receipt/terminal commit.

调用有单调deadline，传输断开/调用方取消不能撤销已开始的ledger事务。Reaper在同一事务内先写control request与业务状态、commit+FULL sync，再回ACK；Gateway收不到ACK时用相同request ID及字节重试，Reaper返回已提交结果。若事务提交状态无法确定，Reaper poison当前服务并回 `ipc_registry_corrupt`；恢复后先跑ledger integrity/recovery再接受连接。重复/迟到命令由generation、expected state及CAS拒绝；过期Gateway不得续写。IPC peer失败为 `ipc_peer_rejected`，格式错 `ipc_bootstrap_invalid`，缺失/不匹配的Cleanup target anchor为 `ipc_operation_target_invalid`，deadline `ipc_timeout`，ledger不确定 `ipc_registry_corrupt`。必须有真实OS IPC测试覆盖身份错、授权错、同请求重放、同ID异字节、提交后丢ACK、事务前断连、超时、Reaper重启恢复及零重复副作用。

### 2.5 Lesson generation、worker 唯一关联与 active 判定

`StartLesson` 在 ledger 同一事务内分配单调 `lesson_generation`，创建唯一键 `(run_epoch,case_id,lesson_id,lesson_generation)` 的 generation claim，并保存其 `start_business_operation_id`；该claim唯一关联一个 `start_worker_operation_id` 和至多一个 worker generation。StartWorker不得由独立HTTP调用或新business key直接绕过claim。同run `mode=resume` 复用既有 lesson generation/claim，只能接管该generation已有 worker 的恢复流程；新lesson generation只能由新的、明确授权的 StartLesson 创建。spawn前CAS claim `claimed→spawn_pending`，catalog记录同一 claim ID、worker generation及process identity；进程身份未持久化时只能通过containment empty证明未存活/已终止，不能因PID缺失重新spawn。无法证明时claim及operation记 `indeterminate`，该lesson/run停用。

跨存储 active 判定为唯一查询合同：HTTP/read path只有在同一run catalog的当前generation为 `READY`、peer验证成功且PID/start identity匹配，并且case DB lesson行的 `state=active`、`lesson_generation` 与claim一致、case DB operation marker匹配 StartLesson business key，同时control ledger claim为`active_committed`且对应operation为`completed`时才返回active或接受课堂命令；任何一项缺失、矛盾或读失败均不可见为active并拒绝命令。提交顺序固定为ledger claim `spawn_pending`→worker READY→catalog `worker_ready` durable→case DB事务提交 active+marker→ledger事务将claim `active_committed`并operation completed。Gateway存活恢复时可依据同generation marker完成最后ledger事务；若DB已active但worker/claim证据不齐，先将lesson对外隐藏并关闭worker，无法安全补齐则终结indeterminate。Gateway死亡总是abandon整run，不跨epoch恢复active。

### 2.6 Request/result 恢复与保留期

Gateway每次启动业务listener前必须完成registry重建；重建期间只允许健康/control IPC，不允许HTTP业务流量。每条request结果从ledger/case marker重建时校验run epoch、principal、scope、digest、generation及operation marker；receipt读取的精确响应字节必须在ledger result_ref或run-local不可变result blob中可取回并校验digest。短期response blob按run清理策略擦除，但request ID/digest/terminal状态至少保留至run abandoned并完成HTTP会话撤销；跨run business-key tombstone按§2.1身份生命周期保留。worker resume不清除Gateway registry；Gateway进程重启则依上述规则重建，任一completed response无法重建即`ipc_registry_corrupt`，不得以重新执行代替。业务层错误区分：HTTP同run request冲突=`ipc_request_conflict`；跨run业务键冲突/旧结果不可返回=`ipc_operation_abandoned`；账本业务kind/digest冲突=`ipc_request_conflict`。对外HTTP envelope采用docs/42 §3的稳定映射表，`request_conflict`与`ipc_request_conflict`保持不同错误码，不做别名折叠。

### 2.7 冲突优先级、主体绑定与容量运维（规范性补充）

本节优先于§2.2操作表及早期恢复措辞。跨epoch查询先检查first_run_epoch对应run的终态：只要旧run已abandoned，任何run-local结果（包括ledger状态为completed的Create case、lesson、receipt、selector及worker结果）一律不返回缓存或业务内容，统一仅返回ipc_operation_abandoned；存储状态仍保持原completed/abandoned/indeterminate，不得重写terminal。仅明确标记result_scope=control_root且响应schema证明不含run-local引用的操作可跨epoch返回缓存结果。Create case等崩溃恢复只有在证据证明effect未发生且部分资源已清理时才记abandoned；effect已完成且marker可验证则保留completed；其余记indeterminate。返回错误码不改变账本事实。跨Gateway重启测试必须分别覆盖三种持久终态及completed run-local结果，逐项断言账本终态与不泄露响应字节。

每个(run_epoch,case_id,lesson_id)另有唯一活动generation claim，不以business key区分。不同business key并发StartLesson时由case/lesson CAS选出唯一claim；输家返回稳定lesson_start_conflict，不得创建generation、worker或副作用。当前claim只有在lesson被显式结束且DB/catalog/worker均终态后才释放；创建新generation必须使用显式RestartLesson operation及新的授权nonce，不能靠StartLesson重试或新key隐式重启。任何时刻active/nonterminal claim数及可服务worker数均≤1。parallel-fresh-key测试须两个不同business key并发并断言总worker与active generation均≤1，同时核验输家错误码。

身份信任边界固定：Gateway是唯一HTTP认证执行者；成功认证后Gateway通过Reaper BindAuthenticatedSession 建立会话映射，消息包括session_key_hash、principal_ref、role、auth_generation、expiry、revocation_version，由Reaper ledger在唯一Gateway peer身份及active gateway_generation下持久化。HTTP派生的后续control消息只携session_key_hash和operation字段；Reaper从已绑定映射读取principal/role，不接受调用者再次声明或覆盖principal。撤销/到期在每次claim/commit前校验；映射提交ACK丢失使用同control_request_id重试。此合同信任受限Gateway作为认证attestor，不声称Reaper独立验证用户凭证。冒用他人session hash、角色越权、撤销竞态及Gateway generation替换均须断言零副作用。

BindAuthenticatedSession、RevokeAuthenticatedSession及UpdateSessionExpiry必须加入§2.4的Reaper IPC typed method allowlist；三者只能由经OS peer认证的当前Gateway调用，Bind仅能绑定本连接中已由Gateway auth middleware验证的会话，Reaper按session_key_hash唯一键拒绝覆盖不同principal的既有映射。撤销/过期更新采用单调revocation_version和control_request_id CAS；同ID同字节回原结果，异字节ipc_request_conflict；过期/撤销状态不可通过旧版本回退。更新未ACK时Gateway用相同请求ID重试，不能继续提交受影响session的新业务操作。

CreateRunLease is an internal Reaper controller method, outside the Gateway business IPC allowlist. The controller caller is authenticated only by the configured OS service UID/SID plus service generation, as specified in section 2.8; no shared controller secret is used. The controller frame is controller_request_id, controller_generation, requested_profile and deadline, with no run/principal/PID fields. Reaper checks prior run terminal state, containment empty and lease under the ledger writer lock, then atomically allocates the epoch/lease and starts Gateway. Same request ID/digest is idempotent; a different contender while a lease exists receives ipc_launcher_failed with spawn=0. Gateway IPC cannot call CreateRunLease.

Windows worker process object DACL must be explicit at CreateProcessW: Gateway creator ACE exactly PROCESS_QUERY_LIMITED_INFORMATION|SYNCHRONIZE (0x00101000), Reaper service SID ACE exactly PROCESS_QUERY_LIMITED_INFORMATION|PROCESS_TERMINATE|SYNCHRONIZE (0x00101001), SYSTEM exactly PROCESS_ALL_ACCESS; no other allow/deny ACE and no inheritance. The worker primary-thread DACL must also be explicit: Gateway ACE exactly THREAD_QUERY_LIMITED_INFORMATION|THREAD_SUSPEND_RESUME|SYNCHRONIZE (0x00100802), Reaper has no thread access, SYSTEM has THREAD_ALL_ACCESS, with no other ACE or inheritance. Immediately close the full-access handles returned to Gateway by CreateProcessW; Gateway then OpenProcess/OpenThread only with the exact masks above, confirms PID/TID ownership and process creation time, and resumes only the reopened thread after Reaper receipt validation. Reaper OpenProcess requests only 0x00101001. DACL/readback mismatch, reopen failure or identity mismatch fails closed before ResumeThread and routes cleanup through Reaper.

Controller endpoint的OS身份是唯一认证凭证：Linux controller以独立、不可复用的service UID运行，Reaper以SO_PEERCRED取UID/PID并以pidfd及/proc start-time pin该进程身份，listener仅置于该UID可连接的0700目录；Windows使用独立controller service SID的named-pipe DACL（仅controller SID与SYSTEM、拒绝远程客户端），并以GetNamedPipeClientProcessId、TokenUser及process creation time联合核验。Reaper从受保护启动配置读取允许的controller UID/SID与服务generation；不使用可由本机普通进程读取的共享口令。服务身份轮换由OS服务管理器先配置新身份、更新Reaper allowlist并重启controller，再撤销旧身份；轮换中不开放未绑定身份。伪造UID/SID、PID复用、错误generation、远程客户端及重放异字节均拒绝并记录审计，CreateRun spawn=0。

Windows worker launch uses CREATE_SUSPENDED|EXTENDED_STARTUPINFO_PRESENT and PROC_THREAD_ATTRIBUTE_JOB_LIST to enter the precreated Reaper Job at creation. Windows necessarily returns full-access `PROCESS_INFORMATION.hProcess` and `.hThread` handles to the creator even when object DACLs are restricted. Gateway must perform no operation, inheritance, duplication, or IPC transfer using those returned handles and close both immediately while the worker remains suspended; then reopen by returned PID/TID using only process `PROCESS_QUERY_LIMITED_INFORMATION|SYNCHRONIZE` (0x00101000) and thread `THREAD_QUERY_LIMITED_INFORMATION|THREAD_SUSPEND_RESUME|SYNCHRONIZE` (0x00100802). Before any resume, Gateway verifies process creation time, `GetProcessIdOfThread` ownership, run/gateway/worker generations, process token SID and Reaper-authenticated Job placement receipt; any reopen/readback mismatch requests Reaper termination and does not resume. If either immediate CloseHandle fails, Gateway does not continue or resume; it reports the failure and Reaper terminates the entire run Job, including Gateway, so all outstanding full-access handles close with their owner process. Reaper alone holds the Job handle, opens the reported PID with its restricted query/terminate handle, verifies process creation time, run/gateway/worker generations and actual Job membership, then returns an authenticated VerifyWorkerPlacement receipt bound to PID, TID, creation time, generations, Job name and Job identity. On verification failure Gateway sends TerminateVerifiedWorker; Reaper repeats the identity checks, terminates and waits until the process object is signaled, then reports an authenticated, replayable completion receipt bound to request ID, process identity, signaled state and exit status. Reaper termination error or wait deadline expiry leaves the run `terminating`, maps to `ipc_launcher_failed`, and blocks every new generation until recovery proves containment empty. If Gateway successfully reopened its limited process handle, it must also wait on that handle within the operation deadline, collect exit status with GetExitCodeProcess, and close it before retry/terminal-state decisions; timeout, query failure, or `STILL_ACTIVE` makes the operation indeterminate and blocks another generation. If Gateway could not reopen a process handle, the authenticated Reaper completion receipt is the only termination oracle: accept it only when identity matches and signaled/exit-status fields prove completion; otherwise mark indeterminate and block another generation. Windows has no Unix-style parent waitpid zombie collection; the creator's resource-reap condition is completion evidence plus closing every process/thread handle. This custom native launcher does not pass the full-access handle to `os/exec.Cmd` or use `cmd.Wait`. Gateway never calls TerminateProcess, and must not retain, use, duplicate or transfer `PROCESS_DUP_HANDLE` or other extra rights from the full-access returned handle beyond the immediate close. Tests assert the worker entry counter remains zero on every failure and that Reaper receipt logging precedes entry on success.

文中cgroup placement capability只表示Reaper IPC的不可伪造、按run/generation/PID限权请求，不是Gateway持有cgroupfs写handle或可自行迁移权限；cgroup唯一写者仍为Reaper。Gateway/worker直接尝试写控制文件、父兄弟目录和迁移的负向测试为硬门。

永久tombstone容量服务合同：达到全局或principal配额80%先写审计事件并向管理员健康端点告警，90%触发容量预案告警；不自动删改记录。每principal上限防止单账户耗尽全局池。扩容须离线审计迁移：停接新run，备份并校验全库、增加schema容量版本、原子迁移/同步目录、校验唯一索引和记录计数、写迁移审计、再恢复服务；失败保持旧库只读且pilot关闭。100%时只允许读取已有键及清理，不准新业务key。容量测试另断言80/90%告警一次、principal quota隔离和迁移前后旧键digest/终态完全一致。

### 2.8 OS 权限、进程句柄与 controller 身份精确合同

POSIX control root及其所有后代必须核验owner UID=Reaper euid、group GID=配置service GID；目录mode逐位严格为0700，普通文件严格为0600，拒绝setuid/setgid/sticky及任何额外mode位。对每个目录/文件读取并拒绝存在system.posix_acl_access或system.posix_acl_default扩展属性；不允许扩展POSIX ACL，即使其有效权限当前不扩大mode也拒绝。每次打开ledger、alias、keyring和socket前后都检查dev/inode/mount ID、owner/group/mode/nlink和ACL xattr；不满足返回ipc_registry_corrupt且SQL dispatch=0。

Windows control root所有者固定为Reaper专用service SID（不接受SYSTEM作为owner）；DACL设置SE_DACL_PROTECTED，ACE inheritance/object flags均为0且无继承ACE，恰有按规范顺序排列的两条ALLOW ACE：Reaper service SID与SYSTEM。目录Reaper ACE mask严格为0x00160087（FILE_LIST_DIRECTORY 0x1、FILE_ADD_FILE 0x2、FILE_ADD_SUBDIRECTORY 0x4、FILE_READ_ATTRIBUTES 0x80、READ_CONTROL 0x20000、WRITE_DAC 0x40000、SYNCHRONIZE 0x100000）；文件Reaper ACE mask严格为0x00130007（FILE_READ_DATA 0x1、FILE_WRITE_DATA 0x2、FILE_APPEND_DATA 0x4、DELETE 0x10000、READ_CONTROL 0x20000、SYNCHRONIZE 0x100000）；SYSTEM ACE严格为FILE_ALL_ACCESS 0x001F01FF。任何其他ACE、deny ACE、mask差异、SID差异、继承标志、未保护DACL或owner差异均拒绝。原生测试须用GetSecurityInfo读回owner、control flags、ACE顺序/flags/SID/mask和对象身份逐字节比较。

Linux Reaper placement必须接收并持有child pidfd，不以Gateway提交的裸PID作为操作凭据。Gateway经clone3(CLONE_PIDFD)创建exec前阻塞child，通过经过身份验证的control socket SCM_RIGHTS传递pidfd；Reaper核验pidfd确为PIDFD、fdinfo target PID、存活poll状态、proc start-time、直接parent PID及其与已pin Gateway pidfd身份一致，并核对run/gateway generation、lesson claim与bootstrap nonce。pidfd在placement及child exec gate释放前保持打开；内核以该pidfd指向的task身份绑定进程，避免裸PID复用混淆。Reaper仅在child仍阻塞、pidfd未signaled且所有身份吻合时向run cgroup.procs写入其PID、回读membership并返回ACK；任一检查失败均不写cgroup.procs，关闭gate并按pidfd终止目标child。native测试必须包含PID退出/复用屏障、伪造/非child pidfd、跨run pidfd与先exec尝试，断言无错误进程进入cgroup且child exec前收到ACK。

Windows worker的PROCESS_TERMINATE权不交给Gateway。创建时显式设置worker process object DACL，仅Gateway creator和Reaper service SID可取得各自所需权限；Reaper对该process按PID打开PROCESS_QUERY_LIMITED_INFORMATION|PROCESS_TERMINATE|SYNCHRONIZE，核验GetProcessTimes creation time及Job membership后可TerminateProcess并wait。Gateway只持PROCESS_QUERY_LIMITED_INFORMATION|SYNCHRONIZE及thread的THREAD_SUSPEND_RESUME|SYNCHRONIZE；失败时经Reaper TerminateVerifiedWorker(pid,creation_time,run,generation)请求终止，Reaper重复校验pin后操作。禁止将裸PID直接交给TerminateProcess/OpenProcess后不比对creation time；错误身份或pid复用不终止目标。测试锁定Gateway access mask不含PROCESS_TERMINATE、Reaper终止mask精确且身份错时不触碰替代进程。

Controller endpoint只接受受保护OS peer身份与service-generation bootstrap共同认证：Reaper从root-only配置读取唯一controller service UID/SID及generation；Unix端SO_PEERCRED的UID必须一致，并以pidfd pin PID、核验/proc start-time和controller启动generation；Windows端Named Pipe DACL恰为controller SID与SYSTEM、拒绝远程客户端，GetNamedPipeClientProcessId、TokenUser、process creation time及bootstrap generation必须一致。配置以owner-only原子文件轮换并在服务管理器协调下先加入新UID/SID、启动并完成health challenge，再撤销旧UID/SID；切换中不接受未匹配身份。每条controller请求使用128-bit controller_request_id、规范帧digest和run lease CAS；相同ID/digest幂等，异digest冲突；断连重试同ID，过期generation拒绝。增加攻击者同机但不同UID/SID、冒用PID/creation time、远端连接和轮换中旧controller的测试，均应spawn=0。

## 3. Run 生命周期与进程 containment

`PilotHostReaper` 是由 OS 服务管理器监督的独立 test harness 常驻进程；它是 control root/ledger 的唯一写入代理、Gateway launcher及run containment reaper，但不直接spawn worker。Reaper创建control root与ledger、启动Gateway并持有外部containment句柄；Gateway是worker直接父进程，负责创建parent pidfd/句柄、spawn、正常等待及worker进程句柄，Reaper只在Gateway死亡后通过containment回收整组孤儿。Reaper健康未知时不创建新run。run记录有单调`reaper_owner_generation`和`terminating` intent，写入需持有control-root OS单写锁；OS服务管理器重启Reaper后，Reaper先取得单写锁、校验ledger/schema和run generation，再恢复每个非terminal run的containment清理，不启动Gateway或接受业务请求。外部CreateRun contender必须经过Reaper本机control IPC；Reaper处于`recovering`、ledger锁竞争或containment未empty时立即返回`ipc_launcher_failed`且spawn计数为0，不排队缓存创建请求。仅Reaper在持锁写入durable `containment_empty`后才开放新run lease。run状态变化为`active→terminating(intent fsync)→containment_empty(evidence fsync)→abandoned(final ledger transaction)`；在containment_empty之后按§2.3先逐operation持久化证据receipt并终结operation，再由final run transaction只验证全部operation terminal、receipt完整及cleanup_state后提交run终态并按条件释放lease；indeterminate保持terminating并永久持有lease。中间崩溃重启后重复终止及empty检查，禁止先提交abandoned再杀进程。control ledger不可读时不准启动任何Gateway。

Linux cgroup v2 权限合同：delegated subtree 的owner/GID、mode及mount namespace由服务管理器固定；Reaper是唯一具有该subtree目录写权限的主体，Gateway和worker的UID/GID、supplementary groups、capabilities及挂载视图均不能写`cgroup.procs`、`cgroup.threads`、`cgroup.subtree_control`、`cgroup.kill`或父级目录，也不能通过`setns`/可写cgroupfs bind mount取得权限。Gateway不自行写cgroup文件：它启动一个exec前阻塞的worker后，通过Reaper control IPC请求把该PID加入本run cgroup；Reaper核验PID属于该Gateway、run/generation/claim匹配、PID仍阻塞且目标cgroup identity匹配，再由自身写入并回读`cgroup.procs`，之后才向Gateway返回placement ACK以释放child exec。`clone3(CLONE_INTO_CGROUP)`同样只由Reaper执行；不支持时使用上述brokered fork gate，不允许Gateway直接placement。run cgroup内不创建可写子cgroup，Gateway不能将worker迁出或创建兄弟run。原生Linux验收必须分别以Gateway和worker credentials尝试写上述每类文件、打开父/兄弟cgroup、创建delegation及迁移PID，全部得到`EACCES/EPERM`且membership不变；再验证Reaper broker对本run合法PID成功、跨run PID/错误generation拒绝、Reaper故障时child保持阻塞并被杀/reap。只测启动配置项`deny_migrate`不满足此合同。

Windows启动失败与回收职责按创建者区分：Reaper创建Gateway时，Reaper也立即关闭CreateProcessW返回给它的full-access `hProcess/hThread`，按需要重开句柄并持有其Reaper权限；若属性列表创建、JOB_LIST加入、Job membership/token/DACL readback或ResumeThread前任一步失败，由Reaper按已pin的PID+creation time直接终止并等待Gateway process object signaled，再由Reaper收集退出状态、关闭句柄并保持run未开放。Gateway创建worker时，同类失败由Gateway先关闭API返回的两个full-access句柄，再仅以规定mask重开；任一CloseHandle失败均请求Reaper终止整个run Job，不恢复线程；Gateway退出时Windows由OS关闭其仍持有的进程/线程句柄，Reaper只等待containment empty并持久化empty evidence，证据提交前不得释放lease或启动替代generation。重开/核验失败时通过`TerminateVerifiedWorker`请求Reaper复核身份、终止、等待signaled并返回带request ID和process identity的退出状态回执，Gateway无进程句柄时只能凭该受信回执证明已终止。Reaper终止失败或等待超时保持run `terminating`并拒绝新generation。Gateway有受限process handle时必须在期限内wait并成功取到非`STILL_ACTIVE`退出状态；超时、查询失败或仍活动均转`indeterminate`并禁止新generation。有无Gateway进程句柄的两条失败路径均须先有可验证的终止证据，再裁决重试；Windows不以Unix zombie语义等待父进程waitpid，资源回收条件是证据完成且相关句柄全部关闭。两类路径均禁止先恢复线程再AssignProcessToJobObject；Gateway永不调用`TerminateProcess`。

## 4. Linux pidfd 身份绑定

Gateway 启动 worker 时先创建当前 Gateway 的 pidfd，读取并验证它指向当前进程，再通过 launcher 的显式 FD 白名单传给 worker。bootstrap 包含预期 `run_epoch` 和 Gateway PID；worker 校验 `getppid()`、bootstrap PID 与继承 pidfd 的内核目标 PID 三者一致，并再次检查 pidfd 存活。目标不符、pidfd 关闭、procfs fdinfo 不可读/格式未知或进程已退出，一律拒绝启动并返回 `ipc_parent_gone` 或 `ipc_peer_rejected` 的稳定映射。

pidfd 目标 PID 读取使用 `/proc/self/fdinfo/<fd>` 中内核提供的 `Pid:` 字段；部署必须保证 worker 所见 procfs 与其 PID namespace 一致。PID namespace 映射不一致或 procfs 不可用时失败关闭，不回退到单独整数 PID 检查。Linux `pidfd_open` 从 Linux 5.3 提供；内核 pidfs fdinfo 的 Pid 显示受 procfs 所在 PID namespace 影响，需在目标发行版上实测并锁定最低运行环境。[pidfd_open(2)](https://www.man7.org/linux/man-pages/man2/pidfd_open.2.html)；[Linux pidfs 实现说明](https://github.com/torvalds/linux/blob/master/fs/pidfs.c)。

启动合同要求 launcher 在创建 worker 所处 PID namespace 内打开该 namespace 对应的 procfs。只比较 `readlink(/proc/self)` 与 `os.Getpid()` 不足以证明 namespace 相同（不同namespace可有相同数字PID），所以 launcher 与 worker 都必须比较 `/proc/1/ns/pid` 和 `/proc/self/ns/pid` 的 namespace 身份（`stat` 的 device/inode），并验证 `/proc` 确为 procfs；任一读取失败、不相等或 `/proc/1` 不可见即失败关闭。worker 再比较 bootstrap parent PID、`os.Getppid()` 和 `/proc/self/fdinfo/<pidfd>` 的 `Pid:`。Linux kernel 对 pidfd `Pid:` 的定义是相对于 procfs 实例所属 namespace；procfs 支持 `pidns=` 挂载参数，因此该身份比较是必要启动合同。[Linux pidfs 实现](https://github.com/torvalds/linux/blob/master/fs/pidfs.c)；[Linux procfs PID namespace 挂载文档](https://docs.kernel.org/7.0/filesystems/proc.html)。禁止将宿主机procfs挂载到不同PID namespace的worker并仅比较PID数字。

Linux父Gateway对worker使用独立child pidfd和`cmd.Wait`负责正常退出监控与reap；传给worker的parent pidfd与child pidfd不得混用。Host launcher是Reaper和Gateway的直接父进程并负责两者的正常waitid(P_PIDFD)回收；Gateway是worker的直接父进程并负责worker的正常reap。launcher死亡时由systemd KillMode=control-group清理delegated descendants；Reaper死亡由launcher监控并按§3恢复。launcher在spawn前后核对继承FD白名单，只允许bootstrap通道和声明的parent pidfd；失败路径关闭所有副本并kill/wait child。此机制仍需真实helper/launcher fixture验证，单进程syscall seam不算通过。

## 7. 2026-10-20 跨文档契约补充

本节与`docs/42 §16`共同构成后续实现唯一契约，并优先于本文早期冲突描述。Gateway唯一负责HTTP身份、session和Idempotency-Key；PilotHostReaper唯一负责跨run control ledger、lease、owner-generation CAS、进程containment和run级终止回收；worker内Supervisor唯一负责run-local catalog、stable case lock、case root/member创建及case级cleanup。本文出现的`CreatePinnedCaseRoot`、`ExecutePinnedCleanup`均指Reaper校验ledger/claim后向Supervisor派发的typed操作；Reaper不直接创建、修改或删除case目录、catalog或成员文件。Supervisor不写跨run ledger，不自行重派IPC；每项操作仍按本文intent→effect marker/evidence→receipt→terminal saga完成。run级abandoned-root隔离/清理仅由Reaper在旧Gateway/worker均已fence、containment empty且所有handles关闭后执行。

所有由Gateway签发的worker grant canonical schema新增必填`worker_generation`，签名覆盖该字段；Supervisor按当前bootstrap generation拒绝旧代或未来代grant。`owner_generation`仅是ledger并发claim fencing token，不替代worker_generation。Gateway request registry必须在dispatch前持久化`(run_epoch,worker_generation,request_id,principal_ref,scope,digest,dispatch_state)`。同键同digest已完成请求返回规范缓存响应；同键不同字段拒绝；完全证明未dispatch时可安全恢复，dispatch开始后结果未知只能持久进入`indeterminate`/`abandoned`并禁止重派。Gateway仍存活时worker重启不得清空registry，也不得把旧代grant转签为新代grant以重做已dispatch副作用；只能按receipt/operation marker完成原请求的裁决。

Case cleanup只允许case原owner principal请求；管理员role不授予跨principal delegation。无owner关系时统一返回`case_not_found`，不dispatch IPC，不打开任何成员。若未来需要跨主体管理清理，必须另立特性规格、显式delegation scope和审计/撤销/E2E，不得在本协议中隐式放宽。

本文§2中的Gateway request registry是session/key coalescing cache及可重建projection，不是dispatch durability authority；PilotHostReaper control ledger为唯一durable authority。Gateway须先调用Reaper原子`BeginOperation`：durable写入`prepared`、CAS到`executing`、绑定owner_generation并取得单次owner token，之后才可签grant或发送IPC。Reaper ledger明确无dispatch的`prepared`才允许安全发起；`executing`必须经marker/evidence裁决，无法证明则写`indeterminate`并禁止重派。Gateway启动/重启从ledger、catalog、case marker重建缓存，不能据缓存缺失推导可重试。

请求层与业务层状态映射固定为：HTTP `pending`对应ledger `prepared|executing`；HTTP `completed`仅在ledger `completed` durable后可见；ledger `abandoned|indeterminate`映射为不可重试失败，不能重置成HTTP `pending`。Gateway cache只合并并发等待者、保存已durable规范响应，不授权副作用。`worker_generation`绑定签名grant和peer bootstrap；`owner_generation`绑定Reaper claim CAS，二者不可互换。

新增且必须实现的稳定Go用例：`TestGrantWorkerGenerationBinding/{current_generation,stale_generation,future_generation,signature_covers_generation}`。current仅在签名、peer bootstrap及当前generation全匹配时通过；stale/future、篡改generation、generation缺失均在`peer.claimGrant`与业务dispatch前拒绝，副作用计数为0。新增`TestGatewayProjectionAgainstLedger/{prepared_not_dispatched_retryable,executing_requires_evidence,completed_cache_after_restart,indeterminate_never_redispatch,abandoned_never_pending,cache_loss_rebuild}`：所有重试结论以Reaper ledger为准，断言owner token及dispatch次数、HTTP响应和terminal ledger state完全一致。上述用例进入本SDD实现切片的发现清单；现存纯合同manifest不得将其计为已实现或通过。

具体取代§2.4中的case文件操作步骤：Reaper只创建/更新control-ledger intent、做owner-generation CAS、签发一次性owner token并把Gateway的typed请求转发给当前worker；它不生成case selector、不取得case stable lock或catalog lock、不创建case root/member、不写case catalog、不unlink case文件。Supervisor是这些case-local副作用的唯一执行者；它从bootstrap内的case owner/generation上下文生成selector，在case→catalog锁协议下创建/更新catalog和固定成员并执行case cleanup，再通过worker IPC返回受限operation evidence。Reaper可独立pin对象作只读身份/存在性核验，随后提交唯一durable receipt和terminal CAS。Reaper对整个abandoned run root的隔离/清理是另一操作，仅在Gateway/worker已fence、containment empty且handles关闭后执行，不与case级cleanup并行或竞争。

Cleanup在Supervisor执行后崩溃的唯一裁决规则，取代§2.3中所有由Reaper unlink case target、补偿删除case成员或据此构造case-operation receipt的描述：Supervisor durable写入case catalog tombstone及operation evidence后，Reaper只读核验同一root/catalog/file identity并可提交`completed` receipt；若Reaper只读检查证明所有目标成员仍为创建时相同identity、目录inventory完整且没有cleanup marker，才可提交`abandoned` no-effect receipt。任一成员缺失、部分删除、identity变化、marker冲突或读取结果unknown均转`indeterminate`，不得由Reaper补删、不得重派Supervisor cleanup。旧§2.3中的`cleanup-effect-journal-before-compensation`、`cleanup-compensation-crash-replays-journal`、`compensation-delete-separate`、`journal-before-compensation-unlink`等“Reaper补偿unlink”测试预期全部废止；改为`TestPilotCleanupOutcomeClassification/{supervisor_completed_tombstone,supervisor_proves_no_effect,partial_member_deletion_indeterminate,marker_or_identity_conflict_indeterminate,reaper_never_unlinks_case_member,run_root_cleanup_separate}`。run-root cleanup只能写独立run-cleanup evidence，绝不能改变case Cleanup operation的outcome。若case operation仍indeterminate，pilot lease保持占用，即使run root随后被安全隔离/清除也不得把该operation伪装成completed/abandoned。

## 8. Run-root allocation ledger amendment (docs/45)

This amendment makes the Reaper-created empty run-root operation a first-class docs/43 durable operation. It adds `operation_kind=run_root_create`, `schema_version=1`, and typed evidence sources `run-root-created-v1`, `run-root-create-collision-v1`, and `run-root-create-effect-absent-v1` to the existing registry. They use the existing `OperationEvidenceReceipt` fields and deterministic-CBOR digest formulas; they do not create a parallel receipt format. The required `business_operation_id` is the 16 raw bytes represented by canonical `run_epoch` hex. `principal_ref` is resolved from Reaper's authenticated session binding, never request data. The receipt `operation_kind` is `run_root_create`; `first_run_epoch` is that same epoch; `request_id` is bound in the immutable typed payload and source payload. `canonical_payload_digest` uses the docs/43 business-operation-v1 formula over the fixed versioned JSON payload `{ "layout_version": 1, "run_epoch": "<32 lowercase hex>" }`. `owner_generation` follows the existing ledger CAS rule.

A new `run_epoch_allocations` ledger relation has a permanent unique primary key `run_epoch` and binds `principal_ref`, `session_key_hash`, `gateway_generation`, exact gateway process identity, `request_id`, `business_operation_id`, `payload_digest`, `operation_id`, `allocation_state`, and `run_terminal_state`. A different request ID or binding for an existing epoch is `ipc_request_conflict` before any filesystem operation. The tombstone is never deleted, reused, TTL-expired, or compacted into a collision-prone key. Gateway generates a fresh 128-bit epoch for each attempt. This uniqueness is independent of `(run_epoch, request_id)` operation idempotency and business-key indexing.

The three source kinds use the docs/43 source identity and evidence item digest formulas. `run-root-created-v1` platform identity fields are `[anchor_dev,anchor_ino,anchor_mount_id,root_dev,root_ino,root_mount_id]`; its evidence payload is `[run_epoch,request_id,gateway_generation,gateway_process_identity,worker_uid,worker_gid,root_mode=0700,root_access_acl_absent,root_default_acl_absent,anchor_uid,anchor_gid,anchor_mode=0710,anchor_access_acl_absent,anchor_default_acl_absent,root_fsync=true,anchor_fsync=true]`. `run-root-create-collision-v1` identity fields are the pinned anchor tuple; payload is `[run_epoch,request_id,gateway_generation,gateway_process_identity,syscall=mkdirat,errno=EEXIST,target_opened=false]`. `run-root-create-effect-absent-v1` identity fields are the pinned anchor tuple plus tagged absence witness `["absent",anchor_platform_identity,epoch_basename_digest,"ENOENT"]`; payload is `[run_epoch,request_id,gateway_generation,gateway_process_identity,syscall=mkdirat,errno_class,absence_verified=true]`. Each kind has fixed positive, negative, canonical-encoding, and domain-separation vectors; any missing/duplicate/inconsistent source rejects receipt commit.

Epoch lifecycle and lease release are part of the same durable run-terminal protocol. A verified deterministic no-effect receipt transitions the operation and epoch tombstone to `abandoned`; Reaper fences that run epoch in its authenticated IPC registry, proves worker spawn/containment was never started (empty), proves the root absent, and commits run terminal `abandoned` with `cleanup_state=not_required`. Only after that terminal transaction is durable may the run lease be released. The permanent epoch tombstone remains, so a new attempt always uses a fresh epoch. `EEXIST`, executing-state crash/cancellation, side effect with uncertain durability, or ambiguous evidence sets the epoch and cleanup state to `indeterminate`, retains the lease, rejects workers/new epochs for the affected principal/session, and requires a separately reviewed quarantine/inventory resolution. The operation-level EEXIST collision receipt does not constitute root absence or cleanup completion.

This allocation failure is a pre-worker run terminal path, not the ordinary active-run cleanup path: `cleanup_state=not_required` is permitted only with durable proof that no worker/containment spawn was ever dispatched, the old epoch has been fenced at Reaper IPC, no root exists (or, for EEXIST, this condition does not apply), no other operation is pending, and the terminal/tombstone transaction is committed. Otherwise docs/43 §3's ordinary fence → containment-empty → cleanup/retained gate applies and the lease stays held.

### 8.2 Atomic epoch reservation and restart invariants

The initial transaction BEGIN IMMEDIATE atomically inserts the permanent run_epoch_allocations row, the run lease row, the run_root_create operation in prepared state, and the business-operation index/tombstone. These rows commit together under WAL+FULL and the already specified VFS/parent-directory durability contract. Before commit there is no reservation and no filesystem syscall; after commit every relation exists and is mutually bound by run_epoch, operation_id, principal_ref, request_id, and payload_digest. A crash before COMMIT leaves none; a crash after COMMIT recovers all as prepared/held and no filesystem effect. Recovery never synthesizes a missing row or discards an orphan; an inconsistent set marks the control ledger corrupt and stops pilot.

The ledger models three separate state dimensions. `operation.state` is prepared, executing, completed, abandoned, or indeterminate: prepared→executing; prepared→abandoned only when dispatch provably never occurred; executing→completed only after the created receipt is durable; executing→abandoned after either (a) deterministic errno plus durable absence evidence and the complete run-terminal transaction, or (b) an EEXIST collision receipt proving only that this request did not create the target; otherwise executing→indeterminate. `run_epoch_allocations.allocation_state` is prepared, executing, completed, abandoned, or indeterminate: prepared→executing in the dispatch CAS; executing→completed only with a durable created receipt; executing→abandoned only in the same terminal transaction as a deterministic no-effect proof; executing→indeterminate on EEXIST, crash, cancellation after dispatch, or ambiguous evidence. In particular, EEXIST sets operation=abandoned but allocation=indeterminate and run_terminal=indeterminate; it proves no root absence. `run_terminal_state` is none, active, abandoned, or indeterminate: successful creation makes it active; abandoned requires fencing, proof no worker/containment was started, verified root absence, and cleanup_state=not_required; EEXIST and any uncertainty make it indeterminate. These terminal outcomes are immutable. The lease remains held for prepared, executing, active, and indeterminate states. It is released only in the same durable terminal transaction that marks run_terminal_state=abandoned after all required proofs; active runs use the ordinary docs/43 termination protocol. The permanent epoch row survives lease release. On restart, a prepared operation with no dispatch can be CAS-claimed exactly once; executing without terminal receipt becomes indeterminate and fenced; completed is reopenable only after identity receipt verification; abandoned is never reopened; indeterminate remains fenced pending reviewed quarantine. Transitions never return to prepared, and no permanent allocation row is deleted.

For the Linux launcher handoff, `RECOVERY_BOOTSTRAP` is the only automatic restart path for a nonterminal old run and is control-only; its exact authorization and state machine are specified in docs/47 section 4. It cannot accept Gateway work or manufacture missing evidence. A well-formed authenticated recovery attempt consumes its higher control generation even when it returns `recovery_proof_missing`, `recovery_not_ready`, or target `rejected`; stale/equal/lower generations return rejected without consumption. `recovery_not_ready` means the exact target/evidence row exists but run_state is not `containment_empty`, a required operation is not terminal, a required receipt is missing/mismatched, or cleanup is not `complete|retained`; it changes no target run/lease state and requires offline repair before a later higher-generation query. `RunContainmentEvidence` is a distinct immutable control-ledger object, not an `OperationEvidenceReceipt`. Its exact v1 schema, identity tuples, digest domain, unique key `(run_epoch,gateway_generation)`, idempotent insert rule, and two durable boundaries (evidence row, then final terminal transaction) are specified in docs/47 section 4. The evidence-row transaction atomically inserts the immutable row and CAS-transitions `run_state=terminating` to `containment_empty`, while the lease remains held. This is a distinct persisted run lifecycle state, not terminal completion. The final transaction only verifies the pre-existing evidence row plus `run_state=containment_empty` and operation receipts, binds the evidence digest to the run terminal record, and releases the lease atomically. A crash before evidence-row commit leaves the run terminating and lease held; the handoff cannot infer missing waitid evidence. Such a run is quarantined for this pilot until a separately reviewed offline administrator reconciliation procedure is implemented. A crash after evidence-row commit may be resumed by a fresh Reaper by verifying the exact row and retrying only the final transaction. Tests assert both boundaries, duplicate identical evidence idempotency, conflicting evidence rejection, field-by-field identity mismatch (including cgroup mount ID), and the permanent-hold oracle when the row is absent.

## 8.3 Linux launcher parent/reaper topology amendment (2026-10-20)

For Linux pilot host integration, docs/47 §1–§5 supersedes conflicting process-parent and cgroup-placement statements in §3, the Linux row of §4, and Linux expectations in §5 of this document. The trusted host launcher is the direct parent of Reaper and Gateway, obtains each pidfd atomically at spawn, and is the unique normal `waitid(P_PIDFD)` reaper for those children. Gateway remains the direct parent and normal reaper of lesson workers; workers inherit Gateway's protected per-generation cgroup membership. Reaper remains the authoritative control-ledger/operation component but is not Gateway's parent, cgroup placement broker, or process reaper. The launcher alone creates and controls the Reaper and Gateway cgroup leaves; Reaper cannot migrate Gateway or write cgroup control files. Existing Linux text that assigns Gateway creation/reaping or worker placement to Reaper is superseded for this pilot integration and must not be implemented. On launcher death, the required systemd delegated service boundary (`Delegate=yes`, `KillMode=control-group`) terminates all delegated descendants and PID 1 reaps orphaned children; restart recovery verifies both old leaves empty and reconciles the durable journal before admitting a new generation. The restarted launcher is not the parent of those old processes and MUST NOT call `waitid` on them; it relies on service-manager termination plus verified empty leaves. Windows lifecycle contracts are unchanged. For normal Linux termination, Reaper remains the sole control-ledger and run-lease authority. A valid UNREGISTER stops accepts and durably marks `unregistered`, but Reaper keeps its authenticated launcher channel and lease; UNREGISTER_ACK is not terminal completion. The launcher removes the endpoint, kills the Gateway cgroup, proves `populated 0`, and collects Gateway through its pidfd with `waitid(P_PIDFD)`, then sends the bound CONTAINMENT_EMPTY evidence to Reaper. Reaper first persists a distinct immutable RunContainmentEvidence row (not an OperationEvidenceReceipt), then the final run-terminal transaction verifies that row and existing operation receipts and atomically commits terminal state plus lease release; only then does it send CONTAINMENT_EMPTY_ACK and exit. If UNREGISTER_ACK times out or the control channel closes, launcher completes Gateway containment but sends no CONTAINMENT_EMPTY on that invalidated channel; the lease remains held and the generation quarantined. A recovery-only Reaper session, bootstrapped with a fresh higher control generation/nonce and bound to the exact old run tuple, may finalize only an already committed RunContainmentEvidence row or report an already-terminal run; it cannot create Gateway/listener/operations. Without the evidence row the run remains held for a separately reviewed offline administrator reconciliation procedure. If CONTAINMENT_EMPTY_ACK is lost, launcher reaps the old Reaper and starts only this restricted recovery session; it reads the terminal/evidence rows and either reports already terminal, retries only the final transaction for an existing evidence row, or preserves the hold if evidence is absent; launcher journal state alone cannot release the lease. The conformance suite must cover this handoff and crash points before/after terminal commit and ACK, plus stuck-Reaper bounded escalation, launcher-death service-manager recovery, and an assertion that restarted launcher never waitids old nonchild processes, as specified by docs/47.

## 8.4 Linux Pilot prepared RunRoot cancellation amendment (2026-10-21)

The pilot may close after `PrepareWithHandoff` commits but before `Claim` or filesystem dispatch. This is not `FinalizeNoRootAbort`: allocation, business operation, held lease, and dispatch-intent outbox tombstones already exist. `BeginRunTermination` must first win the ledger writer reservation and atomically move host lifecycle to `terminating`, fencing `Claim`. This is a narrow exception to the generic prepared-no-dispatch recovery timing in §2.3: cancellation is authorized before Gateway containment is stopped, but only after the writer-serialized close has made Claim impossible and a typed `PreparedRunRootCancellationReceipt` proves the operation had never been claimed or dispatched. This receipt is a separate immutable Pilot control object, not the generic `OperationEvidenceReceipt` and cannot authorize other operation kinds. Its fixed fields are `[generation,run_epoch,operation_id,operation_payload_digest,close_operation_id,owner_generation,claim_absent,filesystem_dispatch_absent,root_absence_witness,intent_delivery_disposition,intent_event_digest]`; disposition is `acknowledged|never_authorized`, `acknowledged` binds the exact outbox event digest. Its correlation is validated relationally through the unique `(operation_id,event_name)` outbox row, whose immutable ACK columns must contain the same digest and a non-null 16-byte Logger delivery correlation; the correlation is intentionally not a CBOR receipt field. `never_authorized` requires the exact outbox state `ready` and matching event digest; the cancellation writer atomically changes that row to `suppressed` with this receipt digest. Sender authorization and cancellation use the same ledger writer, so no send can occur after suppression. Its digest is `SHA256(ASCII("en-words-prepared-runroot-cancel-v1\0") || deterministic_CBOR(fields_without_receipt_digest))`; its primary key is the 32-byte digest and operation ID is unique. Only the original registered Reaper may create it. In one cancellation transaction, operation and allocation move `prepared→abandoned`; `run_terminal_state` remains `none` and the lease remains held. The root was never created, so `cleanup_state=not_required`; do not create a docs/43 `run_state` row for a nonexistent root.

The existing `run_root_dispatch_intent` outbox row is not falsely acknowledged. Its delivery states are `ready|send_authorized|acknowledged|suppressed`. The original Reaper must first commit `AuthorizeOutboxSend` under the same ledger writer; only after that commit may it send, and it must retain that state across retries/crash. The cancellation transaction and `AuthorizeOutboxSend` serialize on that writer: if authorization wins, cancellation cannot suppress until exact ACK is durable; if cancellation wins, it changes `ready→suppressed`, and a late sender authorization is rejected. Keep it `acknowledged` if already delivered. Suppression is allowed only from `ready`, with the exact outbox event digest bound into the cancellation receipt; this state proves no send was authorized, so no mutable side journal assertion is needed. An authorized but unacknowledged send is ambiguous and blocks cancellation/finalization with the lease held. No other event may use `suppressed`.

After UNREGISTER, authenticated containment-empty evidence, and root-absence verification, `FinalizePreparedCancellation` atomically verifies that cancellation receipt, abandoned operation/allocation, unchanged close binding, held lease, `cleanup_state=not_required`, and all outbox rows are acknowledged or this one intent is proven suppressed. It sets `run_terminal_state=abandoned`, completes the close operation, marks host lifecycle terminal, and releases the exact lease. This narrow outcome means the business RunRoot operation was never dispatched and the separately tracked Gateway containment is now proven empty; it does not weaken the generic abandoned-run rule. Recovery may retry only this final transaction using already committed evidence. Missing proof, uncertain Logger delivery, or any commit/ACK uncertainty retains the lease and forbids another generation.
