# Pilot Host Logger Service Lifecycle SDD

**Status: lifecycle implementation slice complete and statically reviewed; overall feature incomplete.** The current pilot_e2e service code and Linux test package cross-compile for amd64/arm64; Windows tagged tests and default Go tests pass. Linux-native execution is still outstanding. Host UID/systemd preflight, production launcher integration, and privileged Linux acceptance remain outstanding; this phase does not enable classroom traffic.

## 1. Goal and boundary

Run the existing `hostLoggerStore` as a service that accepts only launcher-authorized RunRoot Reaper channels, registers their fixed run contexts before packet admission, and drains them through `serveOnePacket`. The service owns channel lifecycle and context registration; docs/46 remains authoritative for append, Sync, deduplication, rate limits, ACKs, and queue recovery. It has no RunRoot ledger dependency and cannot change a lease or terminal state. RunRoot transactions and product integration remain outside this slice.

## 2. Trust and channel lifecycle

The launcher is the only process-identity authority. The Logger process is its dedicated child with configured service UID/GID; Logger runs under a dedicated non-login UID/GID that no other executable or service may assume, and Reaper has a different UID/GID. A protected, read-only host service configuration provisions the fixed abstract endpoint name and Logger UID/GID to Reaper; these values are not accepted from Gateway IPC or environment. The abstract endpoint address is a routing identifier, not a secret or authentication factor. Reaper authenticates the connected Logger using SO_PEERCRED UID/GID, not a dynamic Logger PID. This exclusivity is a protected host-provisioning invariant: the UID is locked/non-login; exactly one root-owned launcher unit may start the designated Logger executable under it; no other service, login, setuid executable, or delegated process may assume the UID; the launcher holds a singleton lock; Logger holds an exclusive instance lock and abstract-socket bind. Startup preflight audits passwd/shell, every systemd unit source (including transient and delegated launch paths), setuid file ownership, launcher lock, and endpoint/instance lock; unknown unit/config sources or any conflict block before READY. READY is matched to the launcher-retained Logger pidfd/child record. PID is not Reaper auth input, so PID reuse alone cannot authenticate a replacement process. The threat boundary trusts root/host provisioning; a compromised same-UID process is out of scope and would require an instance capability. Logger independently authenticates each Reaper by registered PID/UID/GID and per-packet credentials. The launcher passes a protected pre-opened mode-0600 log FD and a private control `SOCK_SEQPACKET` socketpair before exec. On that pair, `SO_PEERCRED` identifies the launcher that created the pair; Logger separately verifies its own `geteuid/getegid` against protected Logger configuration and log-file ownership. Logger enables `SO_PASSCRED` and validates exactly one matching launcher `SCM_CREDENTIALS` on every control packet. Its listener is a fixed Linux abstract AF_UNIX `SOCK_SEQPACKET` address in the existing host network namespace shared by launcher, Logger, and Reaper; there is no filesystem socket path or new network namespace. The launcher spawns Reaper with its retained pidfd and child record, completes docs/47 `BOOTSTRAP` and receives its ACK, then sends canonical `LOGGER_REGISTER` over the authenticated Logger control channel with exactly one CLOEXEC Reaper pidfd. The exact JSON fields, in order, are `version,type,context_id,run_epoch,control_generation,gateway_generation,launch_nonce,reaper_pid,reaper_uid,reaper_gid,reaper_start_time_ticks,reaper_pidns_device,reaper_pidns_inode,reaper_cgroup_mount_id,reaper_cgroup_device,reaper_cgroup_inode,event_process_id`; numeric values are canonical unsigned decimal, IDs/nonces are 32 lowercase hex, and frames are at most 1024 bytes. `event_process_id` is the lowercase hex of the first 16 bytes of `SHA-256(ASCII("en-words-pilot-log-process-v1") || 0x00 || raw_run_epoch_16_bytes || U64BE(control_generation))`. Launcher binds Reaper identity and event ID to its retained pidfd/clone3 child record; Logger checks pidfd type/liveness and trusts that authenticated attestation for fields it cannot inspect, while accepted-socket `SO_PEERCRED` independently proves connecting PID/UID/GID. Active duplicate PID, event ID, context ID, or `(context_id,control_generation)` is rejected. Reaper connects to the abstract listener and sends no event until it receives `LOGGER_CHANNEL_READY`. Logger authenticates accepted-socket `SO_PEERCRED`, enables `SO_PASSCRED` on that accepted FD, rechecks the registered pidfd, then sends exactly one canonical `LOGGER_CHANNEL_READY(version,type,context_id,control_generation,result)` frame with `result=ok`; any failure closes the socket without readiness. Reaper authenticates Logger `SO_PEERCRED` UID/GID against the protected dedicated Logger identity and requires the matching readiness frame before its first event. Thus an immediate post-connect event cannot race `SO_PASSCRED` installation. Logger polls the registered Reaper pidfd before accept, immediately before readiness, before packet admission, and before ACK. A registered context with no active data channel is reaped by the accept loop when its pidfd becomes readable, entering the EOF-equivalent state required for UNREGISTER. An active-channel pidfd watcher cancels only that context waiter when Reaper exits. queued work is removed if not dequeued; in-flight append/Sync continues without ACK to the dead peer and does not poison the shared store unless its independent deadline or I/O result is uncertain; after Sync, persistence remains known but no ACK is sent to the dead process. A launcher-created socketpair is never treated as proof of Reaper credentials.

Logger emits one `LOGGER_READY(version,type,result)` frame after validating its inherited log FD and schema; `result` is `ok|restart_required`, and failure/EOF prevents Reaper spawn. Launcher enables `SO_PASSCRED` on its control endpoint and matches READY's single `SCM_CREDENTIALS` to its own pinned Logger pidfd/child record; socketpair `SO_PEERCRED` cannot authenticate Logger because it identifies the creator. The full order is `LOGGER_READY(ok) -> spawn Reaper and held Gateway -> BOOTSTRAP/ACK -> LOGGER_REGISTER/ACK -> Reaper connect -> LOGGER_CHANNEL_READY -> bootstrap.start/ACK -> docs/47 Gateway REGISTER/ACK -> business`. Reaper cannot process Gateway `REGISTER` until its `bootstrap.start` event has a durable ACK. A lost `bootstrap.start` ACK is ambiguous: the line may be durable, but this event is not in docs/46's deduplicated replay allowlist, so it MUST NOT be replayed. Launcher closes admission, kills/reaps Reaper and Gateway by pinned pidfds/cgroups, keeps the run lease unchanged, and uses docs/47 recovery-only bootstrap. If required containment evidence is absent, recovery returns `recovery_proof_missing` and the run remains operator-quarantined; no same-generation retry or new run is allowed. Logger registration ACK loss before or after install follows the same kill/reap/held-lease/recovery-only rule. Gateway `REGISTER_ACK` loss follows docs/47 retirement and recovery rules. Logger context remains until Reaper closes the logger channel and launcher completes `LOGGER_UNREGISTER/ACK`.

Generation and nonce freshness are authoritative in the launcher's singleton-locked, fsynced journal from docs/47; Logger accepts registrations only on the current launcher control channel and rejects duplicate `(context_id,generation,nonce)` during its lifetime. Logger retains generation and event-process tombstones through successful UNREGISTER so an old registration cannot be replayed on the same service instance. Tombstone history is capped at 65,536 accepted registrations; reaching the cap rejects further registration with `restart_required` and requires the normal fenced Logger restart/recovery flow. The cap bounds memory and does not reset on UNREGISTER. It never claims to recover launcher journal state. Logger restart invalidates all registrations and fences attached Reapers; no live context is automatically re-registered. Launcher reaps old Reapers/Gateway processes, strictly rebuilds the log index, preserves held run leases, and uses recovery-only bootstrap before creating a later business generation. No stale-generation replay is allowed.

Each context has one packet handler at a time. Data-channel receive is idle-unbounded and ends on a packet, EOF, pidfd cancellation, or service shutdown. A bounded per-packet ACK deadline starts after a packet has been received; a quiet classroom does not retire its channel. Malformed framing, peer mismatch, or channel cancellation retires that channel only; shared-store poison follows docs/46 and occurs only for ambiguous in-flight file I/O/deadline. After successful registration Logger owns the registered pidfd; ownership of the data socket begins only when Logger accepts that Reaper connection. `LOGGER_UNREGISTER` is valid only after `POLLHUP` caused Logger to drain every queued seqpacket and `recvmsg` returned EOF (`n=0`, no ancillary FDs); HUP alone is not EOF. Then the sole handler, jobs, append/Sync and ACK waiters must be drained. It linearizes at atomic context removal. ACK loss is uncertain; launcher reaps Reaper and restarts Logger before recovery. Admission/unregister races are ordered by the store mutex: admission-first drains; unregister-first rejects. Repeated or concurrent lifecycle calls reject without state change. EOF alone never releases a lease or synthesizes an ACK. Queue poison/Close rejects new registrations and follows docs/46 restart-required rules.

Registration identity clarification: `reaper_pid/reaper_uid/reaper_gid` and the Reaper start-time/PID-namespace/cgroup tuple are the Reaper child identity, not the Gateway identity carried by docs/47 BOOTSTRAP. Launcher obtains them from the same clone3-created Reaper pidfd and pidfd-pinned procfs snapshot, and atomically binds them to the child record in its protected journal before sending LOGGER_REGISTER. Logger does not inspect host procfs; its authority is the authenticated launcher attestation plus live pidfd and independently observed accepted-socket credentials. A mismatch between the launcher's pidfd and its own child record is rejected before sending. The opaque `event_process_id` derivation above is reproducible by Reaper from the authenticated `run_epoch` and `control_generation`. Its domain separator is the ASCII bytes `en-words-pilot-log-process-v1` followed by exactly one `0x00` byte. Frozen vector: `run_epoch=00000000000000000000000000000000`, `control_generation=1`, `event_process_id=9b283a5c8362f1e694ae1101e0a022b8`. The 54-byte SHA-256 input is `656e2d776f7264732d70696c6f742d6c6f672d70726f636573732d763100000000000000000000000000000000000000000000000001`, independently verified with Python and .NET Framework PowerShell. The context ID is exactly the run epoch.

Logger service control operations are distinct from docs/47 Reaper operations: `LOGGER_READY`, `LOGGER_REGISTER`, `LOGGER_REGISTER_ACK`, `LOGGER_UNREGISTER`, `LOGGER_UNREGISTER_ACK`, plus data-channel-only `LOGGER_CHANNEL_READY`. READY is exactly `version,type,result`; REGISTER uses the field list above; REGISTER_ACK is exactly `version,type,context_id,control_generation,launch_nonce,result`; UNREGISTER is `version,type,context_id,control_generation,launch_nonce`; UNREGISTER_ACK uses the ACK shape. All frames use `version=1`, canonical UTF-8 JSON in exact field order, at most 1024 bytes, reject duplicate keys, accept canonical unsigned decimal integers and lowercase-hex IDs/nonces only, and allow one initial READY followed by sequential request/ACK transactions with no pipelining. Before sending any lifecycle ACK, Logger checks for an already queued control packet; if present, it closes the control channel without ACK, leaving any committed registration/removal uncertain and requiring the fenced restart/recovery path. Each accepted Reaper data socket has exactly one initial data-channel-only `LOGGER_CHANNEL_READY` with exact ordered fields `version,type,context_id,control_generation,result`; `context_id` and generation must match the active registration and `result` is `ok|restart_required`. It is at most 1024 bytes, canonical UTF-8 JSON, and is correlated to that socket (no nonce is sent to Reaper). Reaper accepts one matching `ok` readiness only; malformed, duplicate, mismatched, or `restart_required` readiness closes the socket and admits no event. Reaper connect+readiness deadline is 2 seconds; timeout closes the socket and emits no event. After Logger observes EOF and retires that sole handler, Reaper may reconnect on the same active registration, with at most 3 attempts and a 6-second total deadline. No event bytes means no delivery ambiguity. Once any event bytes are sent, this connection is never retried; docs/46 delivery and deduplication rules apply. Logger never queues an event before `SO_PASSCRED` is enabled and accepted peer credentials are checked. Byte vector for `context_id=00000000000000000000000000000000`, generation 1: `{"version":1,"type":"LOGGER_CHANNEL_READY","context_id":"00000000000000000000000000000000","control_generation":1,"result":"ok"}`. An unsolicited packet while awaiting an ACK closes the control channel. Malformed or unauthenticated frames are silently closed without ACK; authenticated canonical frames rejected semantically receive exactly one correlated ACK with `result=rejected`; post-commit uncertainty uses `restart_required` when the ACK can still be sent, otherwise closes. `result` is `ok|rejected|restart_required`. For each data packet, `Recvmsg(MSG_CMSG_CLOEXEC)` must observe exactly one `SCM_CREDENTIALS` matching the connected peer and no other ancillary records; missing/repeated credentials, `SCM_RIGHTS`, unknown cmsg, `MSG_TRUNC`, or `MSG_CTRUNC` yields zero queue admission, append, and ACK, with every received FD closed exactly once. `LOGGER_READY` is sent once before registration and is not pipelined. The readiness socket timeout and failure are channel-local and never mutate run/lease state.

## 3. Recovery and observability

Service restart opens the existing protected append-only log, takes its exclusive lock, and requires strict complete-record index rebuild before accepting registrations. It does not truncate torn tails, infer missing events, or change ledger state. The launcher journal is the sole generation/reaping oracle. The launcher reaps the previous Logger and every attached Reaper/Gateway before service restart; all affected run leases stay held and only docs/47 recovery-only bootstrap may follow. The logger cannot infer process reaping from EOF or pidfd death. It accepts registrations only from the current direct parent launcher control channel after a new Logger process starts with an empty in-memory context set. Existing log dedup keys remain intact. Emit payload-free structured lifecycle events with trace ID, stage, result class, duration, bounded context cardinality, and active handler count; never log paths, PID/UID, nonce, payload, or descriptor numbers. On logger start, validate the inherited log FD is a regular file owned by configured service UID/GID, mode 0600, append-only open, CLOEXEC, protected by exclusive flock, and that configured mount/device identity matches trusted launcher configuration.

## 5. Review questions

Reviewers must confirm the registration trust chain and socket credential semantics, descriptor ownership on every failure path, restart/re-registration fencing, no coupling that allows logger outcomes to mutate authoritative ledger state, bounded resource use, and deterministic test oracles. Any unresolved question blocks implementation; no implementation may infer run terminal state from logger records.

## 6. Implementation and review update (2026-10-21)
