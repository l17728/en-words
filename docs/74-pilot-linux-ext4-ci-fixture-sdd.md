# Pilot Linux ext4 CI Fixture SDD

Date: 2026-10-23
Status: Design amendment for docs/70; implementation is not authorized until architecture, backend, and test review approve this exact document hash.

## Problem

GitHub run 39895884012 passed the Linux pilotcontrol package test and manifest-contract job, but the RunRoot supervisor contract step in the package job failed because `PILOT_FS_TEST_ROOT` was unset. The Linux integration tests intentionally reject `/tmp` and other unverified filesystems; they require a dedicated ext4/XFS mount. This is a workflow fixture omission, not a product-code failure.

## Design

In the Linux package job, install `e2fsprogs` alongside `strace`; exclusively create a per-run directory under `RUNNER_TEMP` named with `GITHUB_RUN_ID` and `GITHUB_RUN_ATTEMPT`; and immediately write an owner marker containing both values. Allocate a bounded 256 MiB image inside that directory, format it as ext4, and mount it at a fresh child mountpoint. Before tests, prove `findmnt` reports that exact target and ext4 type, and that its loop device is associated with this exact image. Create one mode-0700 test directory inside the mount owned by the unprivileged Actions runner, and export only that path as `PILOT_FS_TEST_ROOT` through `GITHUB_ENV`. The tests revalidate the mounted filesystem. Do not fall back to `/tmp`, tmpfs, a skip, or a synthesized success if image creation, mounting, or verification fails.

Run the tagged supervisor package and its race suite with that environment. An `if: always()` cleanup step calls `review/pilot_ext4_fixture.py cleanup`; it acts only when the owner marker matches the current run and attempt. The helper verifies the exact mount target and image-associated loop device, unmounts without lazy/forced options, confirms the path is no longer mounted, and detaches that exact loop device if it remains associated before removing the image and empty directories. If no mount exists after partial setup, it may detach only the single loop device proven associated with this image. If the marker is absent/mismatched, association is ambiguous, or unmount/detach cannot be proved successful, retain resources and fail the job; never recursively delete a mountpoint or prior run's files. Cleanup also runs after partial setup when ownership has been established. The package summary continues to state that product RunRoot, candidate VFS, and draft schema acceptance are NOT ACCEPTED/NOT RUN.

## Verification and boundaries

Extend the existing workflow contract test to assert the ordered lifecycle: install ext4 tooling → exclusive image and mount allocation → format/mount/source verification → runner-owned writable test directory → `GITHUB_ENV` export → both supervisor test commands → unconditional cleanup. Require static failure cases for missing each setup/export contract, wrong filesystem/source, forbidden fallback, cleanup without `if: always()`, and swallowed/unconditional cleanup errors. Add executable helper tests for `review/pilot_ext4_fixture.py` using a fake command runner: successful cleanup order; partial setup with no mounted filesystem but one image-associated loop device; marker mismatch; ambiguous loop association that returns nonzero without detaching or deleting; `umount` failure that retains the image/mountpoint and returns nonzero without invoking detach/removal; and loop-detach failure that returns nonzero and retains image/directories without continuing removal. The cleanup contract must run after a failed test; unmount/detach failure must fail the job without `continue-on-error`, `|| true`, lazy/forced unmount, or broad recursive deletion. Retain the independent Linux manifest and runner-preflight jobs and package-only NOT_ACCEPTED summary. The Linux Actions rerun must show both supervisor commands pass using the explicit fixture and the post-job mount/image absent. The test binary receives no added mount capability and never invokes sudo; the hosted runner account itself has ambient sudo, so this fixture does not claim to contain hostile test code. Playwright is inapplicable because this is an OS-level CI fixture with no user-facing route. Candidate generation remains blocked and must not run.

Any failure to install tooling, format, mount, verify the filesystem, execute tests, or unmount is a failed CI acceptance. This amendment does not authorize product behavior, privileged launcher integration, VFS promotion, or classroom use.
