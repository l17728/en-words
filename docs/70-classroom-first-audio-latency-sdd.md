# Classroom First-Audio Latency Investigation SDD

## Status and intent

This is a measurement-first design for the long tail found while validating the existing classroom flow. It authorizes instrumentation and repeatable evaluation; it does not authorize changing SQLite durability, introducing asynchronous classroom decisions, or changing the speech provider. The user-facing decision remains synchronous and durable before a classroom action is emitted.

## Evidence and boundary

In synthetic SUB03 browser acceptance, one initial `classroom.play_tts` transaction took 31,050 ms (`finalize_ms=31,049`, `begin_wait_ms=0`, `lock_wait_ms=0`, `audit_write_ms=0`). The same classroom's next playback transaction took 353 ms. Earlier runs measured 136–911 ms for A and 236–1,339 ms for B. The delayed first playback was eventually emitted; the browser's 15-second observation expired first.

In the original 31.05-second observation, `finalize_ms` spanned callback completion to `WithAtomicWrite` return. It included `tx.Commit()` and pinned connection return, so that historical event could not identify which one stalled. SQLite WAL, file flush, OS storage, and endpoint scanning remain hypotheses, not findings. The new instrumentation now records separate commit, rollback/cleanup, and connection-release spans; the historical outlier has not been reproduced with those spans yet.

## Requirements

1. Record monotonic operation callback, commit, rollback, raw cleanup/discard, connection release, and total transaction spans for agent-tool writes. Boundaries are non-overlapping: the passed operation closure starts after `Begin` and ends when that closure returns (including the no-op writer reservation); commit covers only `tx.Commit`; rollback covers `tx.Rollback`; raw cleanup covers fallback `ROLLBACK` and connection discard; connection release covers `conn.Close`; total spans entry through connection release and is captured before the timing observer runs. Each phase has an explicit state (`not_started`, `running`, `completed`, `failed`, or `unknown`); an unentered phase is not reported as a measured zero.
2. Preserve existing transaction atomicity, rollback cleanup, WAL, and synchronous durability while measuring. Timing failures must not alter commit results.
3. Classify outcomes as `committed`, `failed_cleaned`, or `outcome_uncertain`. In particular, a COMMIT error is not automatically described as rollback unless cleanup proves it.
4. Use synthetic-only task, student, lesson, and trace identifiers in benchmark artifacts. Never include real-user identifiers, answer content, secrets, audio, full command lines, environment variables, or arbitrary file paths. This GitHub repository is public: do not commit benchmark artifacts that require access controls; store them in a separate access-controlled private artifact store for at most 90 days, then remove them. OS diagnostics may sample only the owned server PID and a fixed whitelist of aggregate counters at a bounded frequency; unavailable values are `unknown` and collection never blocks the product path. Real-user observability requires a separate privacy review and pseudonymization design.
5. Capture database/WAL sizes and effective `journal_mode`, `synchronous`, and `busy_timeout` before and after each controlled run, outside the timed interval and without triggering a checkpoint. Record process startup separately from classroom response latency.
6. Measure these endpoints separately: (a) request/lesson-entry start to first `show_word` and first `play_tts` frame at the browser; (b) browser receipt to audio player's `playing`/`onstart`; and (c) actual audible onset, which requires human or loopback audio acceptance. Use a monotonic clock within each process; never subtract browser and server wall-clock timestamps.
7. Freeze the workload: fresh owned server and database for each cold sample; for warm samples retain one server/database and reset to the same lesson fixture; same mock provider, one student, same wordbook, same entry sequence. Include at least 30 cold and 100 warm attempts. Preserve timeout, failed, and incomplete attempts in the denominator; report all-attempt counts and failure rate beside p50/p95/p99/max of successful observations. The gate is zero failed, timed-out, or incomplete attempts. With 30 cold samples, label p99 as a low-confidence order statistic; with 100 warm samples, label p99 as near-maximum/low-confidence and do not present it as a stable tail estimate.
7a. Warm reset is an in-process hook compiled only into a dedicated Go test/acceptance binary; production `server/cmd/server` must contain no reset route or hook. If the browser controller needs a control channel, it may use only a dedicated ephemeral loopback listener from that test binary, with a cryptographically random run-scoped capability, exact Host/Origin checks, no CORS, and negative tests proving the production binary has no route and unauthorized/non-loopback requests cannot reset.
7b. Reset must keep the same server, database, student, book, provider, and lesson contents while recreating an equivalent initial scheduled lesson outside the timed interval. It atomically retires the old Room generation and closes admission to new durable side effects under the same lifecycle barrier used by callbacks to validate their generation and enter a durable mutation. Thus a callback cannot validate, race with retirement, and then start a write. Reset revokes the old ticket, closes the prior browser/WS lease, cancels provider/judge work, invalidates timers/callbacks, and waits for every already-admitted durable mutation/settlement to finish before removing that sample's ephemeral lesson/runtime state through application-owned operations. Async completions must recheck generation before changing state or emitting a frame; provider cancellation alone is not a fence. After reset returns, no old-generation callback may affect the old or new lesson. If any durable mutation returns `outcome_uncertain`, reset aborts and reconciles the database/runtime state before another sample; it must not retry or continue the matrix. On timeout or cleanup error, fail closed and do not create/measure the next sample. Never call a production book-delete endpoint, edit SQLite files behind an open pool, checkpoint WAL, or reuse an in-progress lesson as a fresh first-entry sample. If these conditions cannot be proven, mark the warm matrix `NOT RUN` rather than substituting a reconnect measurement.
7c. Before each reset and after it returns, compare an explicit synthetic baseline for scheduler configuration, learning/memory state, and report/settlement rows. The only permitted delta is the retired sample's lesson/runtime/ticket lifecycle and test-harness audit data. After reset verify unchanged student/book/provider/config IDs, a new lesson and epoch, no old ticket or active Room, no pending task, and no stale callback able to emit or advance the new lesson. Test no prior Room, active WS, a provider that ignores cancellation, an in-flight transaction/settlement, duplicate reset, and reset cleanup failure. Capture reset phases and baseline diff outside latency samples; a failed reset or unexpected persistent delta is incomplete and fails the zero-failure gate.
8. Treat any frame-receipt sample over 10 seconds as a failed reliability sample. Provisional target: p95 ≤2 seconds and p99 ≤5 seconds under the frozen single-user synthetic load, with zero failures as stated above; audio-start and audible-onset results are reported separately. Report these independently from concurrent multi-student pilot results.
9. Do not claim real-classroom performance from synthetic results. The isolated pilot must separately measure concurrent students, first audio, interruption, transcript errors, and network/model degradation.

## Evaluation and decision gates

Best-effort timing now wraps the existing operation callback, commit, rollback/cleanup/discard, and connection-release boundaries without changing durability policy. The `WithAtomicWriteObserved` observer only copies timing data and is panic-isolated; a separate caller-side emitter writes the event after `WithAtomicWriteObserved` returns and the agent write lock is released. Its synchronous logging time is excluded from storage phase measurements and from `finalize_ms`, which is sampled immediately after `WithAtomicWriteObserved` returns. Tests cover callback errors, canceled acquisition, deferred-constraint COMMIT failure, callback panic, connection reuse, and observer/emitter panic. The safe warm-reset operation and workload matrix are not implemented; code must not begin until this reset contract and its unit/integration/E2E cases pass architecture, backend, and security review. The test binary boundary, generation fence, drain barrier, and persistent-row baseline are mandatory acceptance checks. If reset safety cannot be established within the test harness, retain the matrix as `NOT RUN`. If `commit_ms` dominates after the matrix, inspect SQLite sync and filesystem flush evidence before proposing any durability trade-off. If connection release dominates, trace driver/pool behavior. If neither dominates, add spans around the remaining return path.

Any behavior-changing optimization requires a follow-up SDD and architecture/backend/security review. A durable-write change must explicitly describe power-loss semantics and include crash/reopen tests. A scheduling or fast-path change must define what happens when tentative and confirmed results disagree before implementation.

## Test and logging coverage

- Unit/integration: callback error, Begin failure, commit failure, cancellation, panic, cleanup failure/discard, and connection reuse retain their existing outcomes. Timing output records entered/unentered phases accurately; observer failures preserve operation results and cleanup.
- E2E: preserve SUB03 classroom isolation and assert first-frame receipt within the frame budget, then separately assert player start. Attach server timing phases and browser-local event offsets on failure; do not claim acoustic audibility from a synthetic media stub.
- Regression: rerun Go tests and the complete Playwright recovery suite after the measured fix. Keep the frozen workload definition, environment, source hash, DB PRAGMAs, all attempted/failed/incomplete samples, counts, percentiles, and raw trace IDs in the acceptance artifact.

## Acceptance status

Architecture and backend reviews passed. The transaction timing instrumentation and outcome classification are implemented; targeted store and API tests passed, including deferred-constraint COMMIT failure, callback panic, connection reuse, and diagnostic panic isolation. One current-code synthetic SUB03 observation measured A's first `classroom.play_tts` storage transaction at 297 ms total (2 ms operation, 295 ms COMMIT, 0 ms connection release/cleanup). This is not request-to-frame or audible-onset latency. The single transaction sample did not reproduce the earlier 31.05-second tail and cannot establish a percentile or close the performance gate.

The current clock-order SUB03 run reached the browser but the test WebSocket barrier sent `phase_changed` sequence 7 before its held `play_tts` sequence 6. The client correctly dropped the stale sequence. The fixture now buffers all business frames while the first playback frame is held and asserts ordered delivery. The ordered-barrier rerun passed 1/1 (55.6 seconds); the browser received business sequences `[4,5,6,7,8,9]` in order, the B playback queue produced two scheduled mock utterances, and the fake clock remained frozen until the test resumed it. The complete recovery suite passed 43/43 after two evidence-backed test synchronization corrections: JD28 now waits for all 12 observed mock audio segments before asserting completion, and REC04 allows one full reconnect-backoff window. The earlier failures were test timing failures, not evidence of a production classroom regression. No durability or scheduling optimization is accepted yet. The 30-cold/100-warm matrix, real classroom pilot, and production audio-start measurements remain open.
