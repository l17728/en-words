# Classroom First-Audio Latency Investigation SDD

## Status and intent

This is a measurement-first design for the long tail found while validating the existing classroom flow. It authorizes instrumentation and repeatable evaluation; it does not authorize changing SQLite durability, introducing asynchronous classroom decisions, or changing the speech provider. The user-facing decision remains synchronous and durable before a classroom action is emitted.

## Evidence and boundary

In synthetic SUB03 browser acceptance, one initial `classroom.play_tts` transaction took 31,050 ms (`finalize_ms=31,049`, `begin_wait_ms=0`, `lock_wait_ms=0`, `audit_write_ms=0`). The same classroom's next playback transaction took 353 ms. Earlier runs measured 136–911 ms for A and 236–1,339 ms for B. The delayed first playback was eventually emitted; the browser's 15-second observation expired first.

In the original 31.05-second observation, `finalize_ms` spanned callback completion to `WithAtomicWrite` return. It included `tx.Commit()` and pinned connection return, so that historical event could not identify which one stalled. SQLite WAL, file flush, OS storage, and endpoint scanning remain hypotheses, not findings. The new instrumentation now records separate commit, rollback/cleanup, and connection-release spans; the historical outlier has not been reproduced with those spans yet.

## Requirements

1. Record monotonic operation callback, commit, rollback, raw cleanup/discard, connection release, and total transaction spans for agent-tool writes. Boundaries are non-overlapping: the passed operation closure starts after `Begin` and ends when that closure returns (including the no-op writer reservation); commit covers only `tx.Commit`; rollback covers `tx.Rollback`; raw cleanup covers fallback `ROLLBACK` and connection discard; connection release covers `conn.Close`; total spans entry through connection release and is captured before the timing observer runs. Each phase has an explicit state (`not_started`, `running`, `completed`, `failed`, or `unknown`); an unentered phase is not reported as a measured zero.
2. Preserve existing transaction atomicity, rollback cleanup, WAL, and synchronous durability while measuring. Timing failures must not alter commit results.
3. Classify outcomes as `committed`, `failed_cleaned`, or `outcome_uncertain`. In particular, a COMMIT error is not automatically described as rollback unless cleanup proves it.
4. Use synthetic-only task, student, lesson, and trace identifiers in benchmark artifacts. Never include real-user identifiers, answer content, secrets, audio, full command lines, environment variables, or arbitrary file paths. This GitHub repository is public: do not commit benchmark artifacts that require access controls; store them in a separate access-controlled private artifact store for at most 90 days, then remove them. OS diagnostics may sample only the owned server PID and a fixed whitelist of aggregate counters at a bounded frequency; unavailable values are `unknown` and collection never blocks the product path. Real-user observability requires a separate privacy review and pseudonymization design.
5. Capture database/WAL sizes and effective `journal_mode`, `synchronous`, and `busy_timeout` before and after each controlled run, outside the timed interval and without triggering a checkpoint. Record process startup separately from classroom response latency.
6. Measure these endpoints separately: (a) request/lesson-entry start to first `show_word` and first `play_tts` frame at the browser; (b) browser receipt to audio player's `playing`/`onstart`; and (c) actual audible onset, which requires human or loopback audio acceptance. Use a monotonic clock within each process; never subtract browser and server wall-clock timestamps.
7. Freeze the workload: fresh owned server and database for each cold sample; for warm samples retain one server/database and reset to the same lesson fixture; same mock provider, one student, same wordbook, same entry sequence. Include at least 30 cold and 100 warm attempts. Preserve timeout, failed, and incomplete attempts in the denominator; report all-attempt counts and failure rate beside p50/p95/p99/max of successful observations. The gate is zero failed, timed-out, or incomplete attempts. With 30 cold samples, label p99 as a low-confidence order statistic; with 100 warm samples, label p99 as near-maximum/low-confidence and do not present it as a stable tail estimate.
7a. Warm reset is an in-process hook compiled only into a dedicated Go test/acceptance binary; production `server/cmd/server` must contain no reset route or hook. The controller is exclusively the parent runner's child-process stdin/stdout JSONL channel; loopback reset listeners/endpoints are prohibited. Prove the production binary has no reset hook/route and malformed or unauthorized stdin commands cannot mutate state.
7b. Reset must keep the same server process, database, student, book, provider, and lesson contents while recreating an equivalent scheduled lesson outside the timed interval. It requires a per-lesson lifecycle coordinator with non-reusable generations, operation leases, and effect permits. Every classroom request acquires a generation-bound operation lease before its first lesson read, ticket check, or Room lookup; `/enter` holds it through ticket issuance and response, WS holds it through ticket validation, the HTTP 101 Upgrade, Room binding and Join, and REST voice holds it through any feedback write. An operation lease exists only to keep reset from completing while work is active; it grants no publication authority after retirement. Each durable mutation, ticket issuance, WS handshake/101 Upgrade, connection registration/Join, and frame/state publication must acquire a permit atomically with `OPEN && generation matches`; this permit is the side effect's linearization point. A permit admitted before retirement may finish and must drain before cleanup; an operation lease alone cannot start a permit after retirement. Async provider/judge results must revalidate before state changes, output, or starting another write. Reset first performs only a short coordinator critical section: mark the generation retiring, atomically reject new operation/effect/write permits, invalidate its generation token, and collect cancellation/connection/timer handles. Only after releasing the coordinator lock may it cancel providers, close WS connections, and invalidate timer registrations. Then it drains admitted leases/permits without holding `Hub.mu`, `Room.mu`, `agentWriteMu`, `completionMu`, or `App.mu`. After drain, perform a final sweep that revokes all old-generation tickets and closes any connection registered by a pre-retirement permit after the first handle snapshot. The admission fence must reject stale work before cancellation or cleanup begins, and the final sweep must finish before cleanup or opening another generation. Preserve the existing `Room.mu → completionMu/agentWriteMu → App.mu` order; the coordinator lock is short-lived and never spans I/O, callbacks, other locks, or drain waits. The reset drain deadline is 30 seconds by default (longer than the 8-second judge and 10-second WS cleanup budgets); unit tests inject a shorter deadline, and any timeout marks the run failed with no retry or next sample. Provider cancellation alone is not a fence. Cleanup failure or `outcome_uncertain` also stops the matrix permanently for that run. Never edit SQLite files behind an open pool, checkpoint WAL, reuse an in-progress lesson, or call a production delete endpoint. If this shared fence cannot be proven, mark the warm matrix `NOT RUN` rather than substituting a reconnect measurement.
7c. The fence must also reject stale work that already holds a `*Room` or passed one phase of a handshake: delayed `/enter` cannot sign a ticket after reset; WS cannot Join after a stale ticket check; REST, timer, overdue, settlement, and old queued WS work cannot affect the new generation. Rejection paths must not mutate old Room state or emit frames. Provider cancellation is not a fence: a late result must fail its generation check, and an uncooperative provider must cause bounded reset failure. Reset phases use stable reset IDs so duplicate commands return the same outcome without making another lesson. A failed or timed-out reset never opens the next generation.
7d. Unit/integration barriers must cover: Enter before and after its initial lesson read and before ticket issuance; WS after ticket check but before the 101 permit, after permit but before Upgrade, after Upgrade but before Join; REST after Room lookup; timer after snapshotting Room pointers; write permit before/after `agentWriteMu`; settlement during write-lock waits; late and non-cooperative providers; COMMIT committed/failed/uncertain; duplicate reset; cleanup failure; and persistent baseline drift. Explicitly pause an old-generation `/enter` after lease acquisition until after retirement/first ticket sweep, and a WS handshake after ticket check and after permit/handle registration until after the first connection sweep; on resume the former must leave no valid ticket and the latter must have received no 101 when its permit was denied, and leave no bound Room or open connection if its permit predated retirement. Playwright must drive two sequential first-entry journeys in one server process/database, close the old page/WS before reset, race stale enter/WS/REST work against reset, verify old ticket/epoch/audio cannot affect the new lesson, and prove reset failure prevents the next sample.
7e. Every asynchronous continuation must own or inherit a lease before it is queued and keep that lease until its last state publication and write permit are released. A continuation may not release then reacquire against the new current generation. This explicitly covers timer and overdue work, settlement, provider/judge callbacks, queued WS frames, and feedback work that follows a Room action. Cancellation without drain does not release a lease. If an uncooperative callback does not return by the deadline, reset fails closed.
7f. Before implementation, produce a reviewed write-path inventory from production code: each classroom-related Store/Repo/API/Agent tool write, its caller, transaction boundary, generation check, and permit acquisition. A centralized write wrapper must fail closed when a classroom mutation lacks a valid permit. The inventory must include room snapshots/events, settlement and scheduler changes, memory/config/feedback/notification writes, tool audits, and any callback publication after commit. Reviewers must reconcile the inventory against repository searches; an omitted or unclassified write blocks implementation acceptance.
7g. Baseline audit snapshots canonical rows by stable primary key at four boundaries outside timing: before each first-entry journey, immediately before reset, after reset cleanup, and after the next journey. Compare every adjacent pair over the complete DB object set and all rows; this catches forbidden changes during a journey that reset-before/after alone would miss. Immutable/denylist scope includes users/books/words; global/student config and config revisions; every `memory_cards` row; `agent_memories` and `durable_memories`; overdue records; feedback tasks/intents/todos/notices; notifications; all `classroom_events`; `runtime_records` keys `report/<id>`, `settled/<id>`, and `agent_result/<id>`; and all non-sample audit rows. The only allowlist is the current synthetic sample's `lessons` row replacement and `runtime_records` key `snapshot/<sampleLessonID>`; plus append-only `audit_logs` whose `trace_id` exactly equals `lesson-<sampleLessonID>` for first-audio classroom effects. This is a first-audio-only matrix: no lesson settlement/result, feedback submission, overdue replan, or card mutation may occur. Tests must assert the three completion keys are absent at every boundary and that no `memory_cards` row changes.

To catch transient forbidden writes that later roll back or are deleted, enforce the policy at SQL execution as well as at prepare time. Build the isolated test DB and fixture first, close that setup pool, then open a fresh matrix pool whose every physical connection installs a `mattn/go-sqlite3` `SQLiteDriver.ConnectHook` authorizer before the first application SQL prepare. Keep this authorizer policy immutable for the lifetime of the matrix process: deny DML on every denylist table and all schema DDL/ATTACH/DETACH/unsafe PRAGMA; never switch from a permissive prepare policy to a restrictive one. `api.NewApp` prepares `UPDATE users SET id=id WHERE 1=0`; the only prepare-time exception is `SQLITE_UPDATE` of `main.users.id` during a one-way `STARTUP_PROBE` phase. Fixed user row triggers reject every actual row effect in all phases, and both agent accounts are preseeded so startup cannot insert users. The phase ends before any listener or browser request. Since authorizer callbacks are prepare-time only, the fresh pool must contain no statements prepared before hook installation, and DDL remains denied for the entire run.

For the three mixed allowlist tables (`lessons`, `runtime_records`, `audit_logs`), authorizer table-level decisions are insufficient. Install fixed BEFORE triggers on the setup pool before closing it; each trigger calls a test-only UDF registered by the same per-connection hook. At statement execution, the UDF sees operation, OLD/NEW key and row identity, checks the current test phase and exact row allowlist (`lessons`: only the synthetic sample ID and a reset-controlled transition whose canonical OLD/NEW rows match controller-held expected states; `runtime_records`: only `snapshot/<sampleLessonID>`; `audit_logs`: INSERT only and exact `trace_id=lesson-<sampleLessonID>`). Publish phase plus canonical expected OLD/NEW rows as one immutable guard-context value through `atomic.Pointer`; each UDF callback loads once and never acquires the lifecycle lock or reads independently updated phase/row fields. Close admission and drain the prior generation before publishing a reset context; only the reset writer runs until verified commit/readback publishes the next generation context. For audit insertion, the trigger SQL checks `EXISTS(id=NEW.id)` and raises before SQLite's conflict policy; no existing row may be replaced. Set `recursive_triggers=ON` on every pool connection as defense in depth, but do not rely on it as the sole REPLACE defense. The UDF increments monotonic process-memory counters outside SQLite transactions: expected preflight probe denials, unexpected guard denials, and row-guard invocations are separate and never reset/decremented. Expected negative probes must be distinguished from journey/reset violations. Tests must prepare a write on an authorizer-allowed mixed table before the sample (for example, a non-sample audit trace) and execute it during the sample, proving the execution-time trigger still rejects/counts it; also test denylisted-row insert then rollback, `INSERT OR REPLACE` with a sample trace colliding with an existing non-sample audit primary key followed by rollback (must reject and preserve the original row), update/delete of audit rows, non-sample lesson/runtime keys, exact sample audit trace, all pool connections, raw SQL, and schema/attachment bypass attempts. Any guard/UDF installation or per-connection coverage uncertainty fails closed.

The shared write wrapper also prepares `UPDATE config_globals SET key=key WHERE 1=0` before each `WithAtomicWriteObserved` callback. Since SQLite's authorizer cannot inspect the WHERE clause, allow only `SQLITE_UPDATE(main.config_globals.key)` in application phases and install fixed `BEFORE INSERT/UPDATE/DELETE` row guards so any matching row operation aborts. Because SQLite authorizes existing AFTER triggers during prepare, allow their `config_revisions` INSERT/UPDATE actions only with source `rev_config_globals_UPDATE`; the BEFORE guard must abort matched updates before revision effects. Regression tests must execute the no-row reservation successfully and prove matched writes never alter config or revision rows.

Establish the canonical schema-object baseline after setup and require zero unclassified object delta through both journeys. Compare complete canonical row/object snapshots before and after each journey, before and after reset, and reject all completion keys and forbidden table changes. Store hashes, per-journey guard counter baselines/deltas, and sanitized table/key/field diffs under ignored `.test-artifacts`; never clean up unexpected rows. Expected preflight negative probes may increment only their dedicated expected-denial counter. The unexpected guard-denial counter must have zero delta throughout application startup, journeys, reset, and shutdown. On known rollback, verify the previous state; on COMMIT error/`outcome_uncertain`, reopen/read through the application pool and record which rows are present without retrying cleanup. A reset transaction error, baseline drift, unexpected guard-denial delta, or post-commit verification failure records the observed state, sets the controller to terminal `FAILED`, and creates no next lesson/generation. Reset IDs are idempotency keys only for returning a recorded outcome; a failed outcome is never replayed.
7h. The browser runner owns the dedicated test binary process. Build it with `go test -c`, launch the test binary directly, and exchange JSON-lines commands/responses over that child process's stdin/stdout with request IDs; stdout is protocol-only and app/test-framework diagnostics go to stderr. Allowed commands are exactly `bind`, `metadata`, `reset`, and `shutdown`, with a 64 KiB maximum UTF-8 line, strict per-command schemas, unknown fields rejected, and duplicate request IDs rejected except a matching idempotent reset result. `bind` and `metadata` responses have a 5-second deadline, `reset` 35 seconds (30-second drain plus cleanup allowance), and `shutdown` 5 seconds. The runner records the exact test binary/source manifest, rejects malformed/oversized commands, and stops the run on child exit, non-JSON stdout before the terminal response, missing/late response, or reset failure. Terminal Go test status is read from process exit code and routed to stderr, not parsed as a control response. Protocol tests cover stdout contamination, limits, duplicate IDs, response timeout, and child exit. The reset hook and command parser exist only in `_test.go` and are absent from `server/cmd/server`.
8. Treat any frame-receipt sample over 10 seconds as a failed reliability sample. Provisional target: p95 ≤2 seconds and p99 ≤5 seconds under the frozen single-user synthetic load, with zero failures as stated above; audio-start and audible-onset results are reported separately. Report these independently from concurrent multi-student pilot results.
9. Do not claim real-classroom performance from synthetic results. The isolated pilot must separately measure concurrent students, first audio, interruption, transcript errors, and network/model degradation.

## Evaluation and decision gates

Best-effort timing now wraps the existing operation callback, commit, rollback/cleanup/discard, and connection-release boundaries without changing durability policy. The `WithAtomicWriteObserved` observer only copies timing data and is panic-isolated; a separate caller-side emitter writes the event after `WithAtomicWriteObserved` returns and the agent write lock is released. Its synchronous logging time is excluded from storage phase measurements and from `finalize_ms`, which is sampled immediately after `WithAtomicWriteObserved` returns. Tests cover callback errors, canceled acquisition, deferred-constraint COMMIT failure, callback panic, connection reuse, and observer/emitter panic. The reset contract passed architecture, backend, and security design review, but the first test-binary implementation failed backend/security review and did not compile. That unsafe prototype was removed; findings and disposition are recorded in `review/first-audio-matrix-warm-reset-review-20261023.md`. The 30-cold/100-warm matrix remains `NOT RUN`. A future implementation must establish the shared lifecycle/admission fence, bounded drain, synthetic DB/path isolation, cleanup error handling, and regression cases before E2E or timing runs. If reset safety cannot be established within the test harness, retain the matrix as `NOT RUN`. If `commit_ms` dominates after the matrix, inspect SQLite sync and filesystem flush evidence before proposing any durability trade-off. If connection release dominates, trace driver/pool behavior. If neither dominates, add spans around the remaining return path.

Any behavior-changing optimization requires a follow-up SDD and architecture/backend/security review. A durable-write change must explicitly describe power-loss semantics and include crash/reopen tests. A scheduling or fast-path change must define what happens when tentative and confirmed results disagree before implementation.

## Test and logging coverage

- Unit/integration: callback error, Begin failure, commit failure, cancellation, panic, cleanup failure/discard, and connection reuse retain their existing outcomes. Timing output records entered/unentered phases accurately; observer failures preserve operation results and cleanup.
- E2E: preserve SUB03 classroom isolation and assert first-frame receipt within the frame budget, then separately assert player start. Attach server timing phases and browser-local event offsets on failure; do not claim acoustic audibility from a synthetic media stub.
- Regression: rerun Go tests and the complete Playwright recovery suite after the measured fix. Keep the frozen workload definition, environment, source hash, DB PRAGMAs, all attempted/failed/incomplete samples, counts, percentiles, and raw trace IDs in the acceptance artifact.

## Acceptance status

Architecture and backend reviews passed. The transaction timing instrumentation and outcome classification are implemented; targeted store and API tests passed, including deferred-constraint COMMIT failure, callback panic, connection reuse, and diagnostic panic isolation. One current-code synthetic SUB03 observation measured A's first `classroom.play_tts` storage transaction at 297 ms total (2 ms operation, 295 ms COMMIT, 0 ms connection release/cleanup). This is not request-to-frame or audible-onset latency. The single transaction sample did not reproduce the earlier 31.05-second tail and cannot establish a percentile or close the performance gate.

The current clock-order SUB03 run reached the browser but the test WebSocket barrier sent `phase_changed` sequence 7 before its held `play_tts` sequence 6. The client correctly dropped the stale sequence. The fixture now buffers all business frames while the first playback frame is held and asserts ordered delivery. The ordered-barrier rerun passed 1/1 (55.6 seconds); the browser received business sequences `[4,5,6,7,8,9]` in order, the B playback queue produced two scheduled mock utterances, and the fake clock remained frozen until the test resumed it. The complete recovery suite passed 43/43 after two evidence-backed test synchronization corrections: JD28 now waits for all 12 observed mock audio segments before asserting completion, and REC04 allows one full reconnect-backoff window. The complete Go API package regression passed after removing the rejected warm-reset prototype: 396 pass events, 0 failures, 2 skips, 68.571 seconds; the 90-second diagnostic timeout was insufficient for the full suite and expired during an intentional 10.1-second cleanup wait. The earlier failures were test timing limits, not evidence of a production classroom regression. No durability or scheduling optimization is accepted yet. The 30-cold/100-warm matrix, real classroom pilot, and production audio-start measurements remain open.
